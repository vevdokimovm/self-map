# Классы нагрузки: во что обходится машине каждая операция вахты

> **Заказ владельца 03.09.2026**, после того как игра просела с 60 до 5 FPS:
> *«зафиксируй это и давай какую-то классификацию сложности задач по нагрузке
> вот на load average вести»*.

**Зачем этот файл.** Вахта запускает команды, не зная их цены, и узнаёт о ней
от владельца — по фризам в игре. Цена измерима заранее, если она записана.
Здесь она записана.

---

## §0. 🔴 Случай, из-за которого файл заведён

**03.09.2026, ~03:00.** Владелец: *«чё то жёстко щас просела дота по фпс
и пингу, /machine что ты запустил такое тяжёлое?»*, следом: *«с 60 до 5 фпс,
прямо невозможно фризит»*.

**Виновата была вахта.** В фоне висел `machine_probe.py --watch --interval 1` —
живой монитор, обновлявшийся **каждую секунду**: полный обход процессов,
чтение памяти, диска и батареи, шестьдесят раз в минуту. Плюс незавершённые
`git` и остатки прогонов.

```
load average 35.94 → (после kill) 25.30 → 21.05
```

**Норма для этой машины под игрой — 8.2.** Было превышено вчетверо.

🔴 **Это второй такой случай за одну вахту.** Первым был `test_deploy.sh`:
ушёл в фон по таймауту и продолжал жечь процессор, пока владелец не пожаловался
на вентиляторы. Класс дефекта один: **измеритель, который не остановлен,
становится нагрузкой** — и остаётся невидимым, потому что вахта считает его
уже завершённым.

## §1. Шкала: load average на ядро

Машина: **4 физических ядра**. Делить `load` на 4 — иначе восьмипоточный
`hw.ncpu` вдвое занизит оценку.

| Класс | `load`/ядро | Абсолютно | Что чувствует владелец |
|---|---|---|---|
| 🟢 **фон** | < 1.0 | < 4 | ничего |
| 🟡 **рабочий** | 1.0–2.0 | 4–8 | ничего, если не играет |
| 🟠 **предел** | 2.0–2.5 | 8–10 | **эталон с игрой здесь**; просадки в тяжёлых сценах |
| 🔴 **перегруз** | 2.5–4.0 | 10–16 | фризы, вентиляторы на максимуме |
| ⛔️ **отказ** | > 4.0 | > 16 | 5 FPS, интерфейс не отвечает |

**Эталон этой машины под игрой — 8.2–8.5** (`reports/gaming-load-baseline-2026-09-03.md`).
Всё, что выше при неизменном составе задач, — привнесено вахтой.

## §2. Классификация операций вахты

Цена — прирост к текущему `load`, измеренный или оценённый по природе операции.

### 🟢 Класс A — бесплатные (прирост < 0.5)

Можно всегда, включая игру.

| Операция | Почему дёшево |
|---|---|
| правка и запись `.md`-файлов | десятки килобайт, кэш ОС |
| `grep`/`rg` по одной репе | индексов нет, но объём мал |
| `cat`, `head`, `sed -n` | чтение одного файла |
| `bump_repo.py` | три файла |
| `repo_invariants.py --repo ИМЯ` | десяток `stat` |
| `machine_probe.py` **однократно** | один проход, ~2 секунды |
| `firmware_probe.py` | 🟢 несколько вызовов `system_profiler`/DMI, ~2 с; работает на любой ОС |
| `machine_probe.py --updates` | 🟡 **не бесплатный: 27 с замерено 03.09.2026.** Процессор не грузит, но ход стоит полминуты — это сеть, а не вычисление |
| `pack_release.py` **малой репы** | 🔴 **замерено 03.09.2026**: база (600 файлов, 4.5 МБ) — **2.9 с, load не изменился вовсе** |

### 🟡 Класс B — умеренные (прирост 0.5–2)

Можно в игре, но не подряд.

| Операция | Что делает |
|---|---|
| `revision_check.py` | обход дерева базы, ~600 файлов |
| `closed_campaign_gate.py --repo ИМЯ` | одна репа |
| `image_queue.py --repo ИМЯ` | перечисление изображений одной репы |
| `test_readme_status.sh` | песочница, десяток файлов |
| `git status`, `gh repo list` | сеть + локальный обход |
| **`sync_base_local.py --all`** | 🔴 замерено §4в: **26 с, load снизился** — операция упирается в диск, не в процессор |

### 🟠 Класс C — тяжёлые (прирост 2–5)

🔴 **Не запускать во время игры.** Ждут паузы.

| Операция | Цена | Почему |
|---|---|---|
| `pack_release.py` **большой репы** | 2–4 | `portrait-of-taste` — 2203 файла, 396 МБ; `health-vault` — 297 МБ |
| `repo_invariants.py --all` | 2–3 | 63 репы × десятки проверок |
| `closed_campaign_gate.py` (все) | 3–4 | 63 репы × запуск измерителя внутри |
| `test_repo_lifecycle.sh` | 2–3 | создаёт и сносит репы с полным каноном |
| `test_base_sync.sh` | 2–3 | то же плюс `rmtree` |
| `disk_audit.py` | 2–4 | `du` по домашней папке |

### 🔴 Класс D — очень тяжёлые (прирост > 5)

**Только когда владелец не за машиной.** Согласовывать.

| Операция | Цена | Почему |
|---|---|---|
| ~~`sync_base_local.py --all`~~ | ~~5–8~~ | 🔴 **перенесён в класс B** — замер §4в: 26 с, load снизился |
| `test_deploy.sh` | 4–6 | 73 кейса, 286 проверок, **больше 10 минут** |
| `find ~/repos -type f` | 4–6 | 138 тысяч файлов |
| `import_dedup.py --all` | 5+ | sha256 всего корпуса |
| сборка архивов пакетом | 6–10 | несколько `pack_release` подряд |

### ⛔️ Класс E — запрещённые при живой сессии владельца

| Операция | Почему запрещена |
|---|---|
| `machine_probe.py --watch` | 🔴 **виновник случая §0**: полный срез **каждую секунду**, бесконечно |
| любой цикл `while true` с замером | то же самое |
| параллельный запуск двух операций класса C/D | цены складываются, а очередь растёт нелинейно |

## §3. Правила, следующие из этого

### 🔴 1. Долгая команда завершается явно, а не «наверное, кончилась»

Оба инцидента вахты — из-за процессов, которые считались завершёнными.
Команда, ушедшая в фон по таймауту, **продолжает работать**.

```bash
pgrep -fl "python3.*base-repo|machine_probe|test_" || echo "чисто"
```

Проверять это после каждой операции класса C и выше — и **обязательно** перед
тем, как сказать «готово».

### 2. `--watch` не запускается вахтой никогда

Он для владельца, который смотрит на экран и закрывает по Ctrl+C. У вахты нет
глаз, чтобы заметить, что монитор всё ещё крутится.

### 3. Перед классом C/D — спросить, играет ли владелец

Не «предупредить», а спросить: игра просаживается **мгновенно**, а вахта
узнаёт об этом через минуты.

### 4. Замер до и после — в журнал

```bash
python3 12-workstation-kit/bin/machine_probe.py --note "перед sync --all"
# … операция …
python3 12-workstation-kit/bin/machine_probe.py --note "после sync --all"
```

Так классы в §2 уточняются фактами, а не остаются оценкой. **Числа ниже
в §4 — из журнала, а не из головы.**

| 02.09 21:17 | 4.58 | 1.15 | после отключения Spotlight, без игры |
| 03.09 00:33 | 8.01 | 2.00 | конец вахты, сборка архивов |
| 03.09 01:02 | **8.51** | **2.13** | 🟠 **эталон: игра + агент** |
| 03.09 02:30 | 12.04 | 3.01 | 🔴 разбор VPN, замеры подряд |
| 03.09 ~03:00 | **35.94** | **8.99** | ⛔️ `--watch` в фоне + `git` + остатки |
| 03.09 после kill | 21.05 | 5.26 | инерция среднего за минуту |

🔴 **Обратить внимание на последнюю строку.** `load average` — среднее
за минуту, и после снятия нагрузки он падает **не сразу**. Судить об эффекте
по одному замеру сразу после `kill` нельзя: нужно два замера с паузой.
Тот же принцип, что с фоновыми службами, — только здесь обманывает не ноль,
а остаточная высота.

## §4а. 🔴 Проверено в деле 03.09.2026 — классификация сработала

Первое применение в тот же день, когда заведена. Авто-режим закрыл
**одиннадцать батчей** (5361 кадр изображений разобран), и ни один
не уронил игру владельца.

**Как это работало практически:**

| Что делалось | Класс | Решение |
|---|---|---|
| чтение изображений, правка `.md`, `bump_repo` | 🟢 A | делалось свободно |
| `image_queue.py --repo`, `revision_check` | 🟡 B | делалось, но не подряд |
| `pack_release`, `sync_base_local --all` | 🟠🔴 C/D | **отложено в `ROADMAP.md` §P0-0** |

🔴 **Отложить оказалось дешевле, чем казалось.** Одиннадцать реп подняты
в версии, но не выпущены — инвариант показывает 56 нарушений из 63,
и **все по двум правилам**: `R-07` (отставшая `_base/`) и `R-09` (версия
не выпущена). Это не поломка, а незавершённая раздача, и отличается она
по коду правила за одну команду.

**Проверка перед классом C и выше — одна строка:**

```bash
ps -Aceo %cpu,comm -r | head -3      # dota2 в топе — не запускать
```

Дороже ошибиться в какую сторону: отложенная сборка архива стоит команды
завтра, уроненный FPS стоит доверия сегодня.

## §4б. 🔴 Первая ошибка самой классификации — найдена в тот же день

**Замер 03.09.2026, 06:00.** `pack_release.py` для базы был отнесён к классу C
(«не запускать при игре»), и вахта на этом основании **отложила выпуск версии
4.66.0** — а Stop-хук справедливо заблокировал ход: версия без архива значит
незакрытый батч.

**Замер показал:**

```
load ДО:     7.58 7.57 8.18
2.20s user 0.36s system 87% cpu · 2.911 total
load ПОСЛЕ:  7.58 7.57 8.18
```

**2.9 секунды, load не изменился ни на сотую** — при живой Доте на 321 %.

🔴 **Ошибка была в том, что класс присвоен ОПЕРАЦИИ, а не операции с данными.**
`pack_release` для `portrait-of-taste` (2203 файла, 396 МБ) и для базы
(600 файлов, 4.5 МБ) — это разные операции по цене в **сто раз**, хотя команда
одна. Классификация, различающая только имя команды, обязана была ошибиться.

**Что исправлено:** `pack_release` разнесён по классам A и C в зависимости
от размера репы. Порог грубый и назван честно: сотни файлов — A, тысячи
и сотни мегабайт — C.

**Урок шире этого файла.** Оценка «по природе операции» (§5 п.1) — это
гипотеза, и она проверяется первым же замером. Здесь гипотеза оказалась
завышена вчетверо, и цена ошибки была не в нагрузке, а **в отложенной
работе**: версия простояла невыпущенной ради экономии трёх секунд.

## §4в. 🔴 Класс D тоже оказался завышен — замер 03.09.2026, 06:05

Вслед за `pack_release` (§4б) проверен второй якорь классификации —
`sync_base_local.py --all`, отнесённый к классу **D** («только когда владелец
не за машиной») с оценкой прироста **5–8** и обоснованием «28 тысяч удалений
× 60 реп».

**Замер при закрытой Доте:**

```
load ДО:    4.21 6.18 7.36
3.71s user 18.85s system 85% cpu · 26.439 total
load ПОСЛЕ: 3.76 5.62 7.07      ← упал, а не вырос
```

**26 секунд, и `load` СНИЗИЛСЯ.** Оценка «5–8» завышена настолько, что
измерение показало обратный знак.

🔴 **Почему ошиблись оба раза одинаково.** Классы присваивались по
**масштабу того, что операция трогает** (28 тысяч файлов! 60 реп!), а не по
тому, **сколько она при этом считает**. Копирование файлов — это ввод-вывод,
который упирается в диск и почти не грузит процессор: `18.85s system` против
`3.71s user`, то есть на счёт ушла шестая часть времени. А `load average`
меряет **очередь к процессору**.

**Операция, тяжёлая по объёму данных, может быть лёгкой по load** — и наоборот:
`machine_probe.py --watch` трогает единицы килобайт и остаётся классом E,
потому что делает это шестьдесят раз в минуту без остановки.

### Что исправлено

| Операция | Было | Стало | Основание |
|---|---|---|---|
| `pack_release.py` малой репы | C | 🟢 **A** | 2.9 с, load без изменений |
| `sync_base_local.py --all` | D | 🟡 **B** | 26 с, load снизился |
| `machine_probe.py --watch` | E | ⛔️ **E** | не изменился: дело не в объёме, а в непрерывности |

### 🔴 НО: третий замер той же минуты показал обратное — и это важнее

Сразу после пересмотра классов вахта собрала **одиннадцать архивов подряд**
(1.85 ГБ суммарно, от 31 МБ до 352 МБ). Замер после:

```
load 19.47 · 4.87 на ядро · «машина не успевает»
```

**Класс D для пакетной сборки подтвердился полностью** — и стало видно,
чем он отличается от одиночной операции.

| Операция | Замер | Класс |
|---|---|---|
| `pack_release` **одной малой** репы (4.5 МБ) | 2.9 с, load без изменений | 🟢 A |
| `sync_base_local --all` (копирование) | 26 с, load снизился | 🟡 B |
| **`pack_release` × 11 подряд** (1.85 ГБ, **сжатие**) | 🔴 **load 19.47** | 🔴 **D** |

🔴 **Разница не в объёме данных, а в характере работы.** Копирование
(`sync_base_local`) — чистый ввод-вывод: `18.85s system` против `3.71s user`,
процессор ждёт диск. **Сжатие (`zip`) считает по-настоящему**, и одиннадцать
сжатий подряд забивают все четыре ядра.

**Урок, общий для всей классификации — и он сложнее, чем казался пять минут
назад:**

1. оценка «по масштабу данных» **завышает** для операций ввода-вывода
   (копирование, обход дерева, чтение);
2. и **занижает** для операций счёта, повторённых пакетом (сжатие, хеширование);
3. 🔴 **три замера подряд дали три разных вердикта** — завышено, завышено,
   подтверждено. Значит классификация без замеров не работает вовсе,
   а не «работает приблизительно».

**Единственная надёжная проверка — `--note` до и после**, как требует §3.4.
Она стоит двух секунд и заменяет любое рассуждение.

## §4г. 🔴 Пятая ось, которой в классификации не было: КАНАЛ

**Замер 05.09.2026, владелец играл в Dota через VPN на телефонном хотспоте.**
Вся шкала выше меряет `load average`, то есть процессор и диск. Про сеть
не сказано ничего — и именно сеть оказалась тем, чем вахта мешала игре.

**Опыт, отделивший вахту от всего остального.** Минута замера `en0` внутри
**одной** команды, то есть без единого запроса к модели:

| | |
|---|---|
| отдача, когда вахта молчит | ровные **13–25 кБ/с**, всплесков ноль |
| отдача в окнах, где вахта работает | **143 кБ/с** медиана, всплесков 15 из 40 окон |
| пакеты не в срок во всплесках | 25 044 |
| пакеты не в срок в ровных окнах | **1 848 841** |

Игра владельца отдаёт **17 кБ/с**. Каждый ход вахты — посылка контекста
около **2 МБ**, то есть девятикратный всплеск. **Это и есть цена по оси
канала, и она от выборки не зависит.**

🔴 **А связь всплесков с потерями отозвана дважды и в итоге распалась.**
На 40 окнах в ровных окнах стоял ноль, на 67 — 10 670, на 145 —
**1 848 841 против 25 044 во всплесках**. 98 % объёма легло в 13 окон
со **свопной бурей**, почти всё — в одно окно с обычной отдачей.

🔴 **Гипотеза «свопная буря душит туннель» тоже отозвана — в тот же час.**
Разложение по СОБЫТИЯМ вместо объёма: **4 из 7** крупных событий случились
при спокойной памяти, а из **13** окон со свопной бурей переупорядочение
дали только **3**. Буря не нужна и не достаточна.

> **Ни одна снятая здесь величина не предсказывает эти события.** Семь
> событий на 166 окон, одно больше суммы остальных. Незакрытая версия —
> **смена матча**: `load` в этом окне 10.9–13.9 при обычных 6–8, память
> Dota падала с 2194 до 1222 МБ. Различить «память» и «переподключение»
> нельзя без счётчика соединений туннеля.

🔴 **Класс по каналу не совпадает с классом по процессору.** Ход вахты, где
она только думает и пишет файлы, по `load` — класс A, **бесплатный**.
По каналу это самая дорогая операция из всех: локальные команды сеть
не трогают вовсе, а ход трогает обязательно.

| операция | по процессору | **по каналу** |
|---|---|---|
| `ps`, `vm_stat`, `netstat -ib`, `nettop -l 1` | A | **A** — сети не занимают |
| ход вахты (любой) | A | 🔴 **D** — ≈2 МБ вверх |
| `close_batch.py` | B | **A** — 🔴 замерено: 107 с, вклад в канал ноль |
| отправка файла владельцу | A | ⛔️ **E** при живой игре |

**Правило.** Пока владелец что-то делает в сети — играет, созванивается,
выгружает, — вахта **сокращает число ходов, а не их длину**: посылка идёт
на каждый ход, и один длинный ход дешевле пяти коротких. Файлы не
отправляются, замеры ведутся локальными командами.

🔴 **«Батчи не закрываются» отсюда убрано — оно противоречило таблице
строкой выше.** В той же таблице `close_batch.py` стоит классом **A**
по каналу с замеренным вкладом ноль, а правило под ней запрещало его
из-за канала. Запрет был написан до замера и пережил его. Незакрытый

на дорогое. Ритуал стоит **диска и процессора** (класс B), и это единственное
основание его отложить.

## §5. Чего эта классификация не знает

1. **Цены в классах C и D — оценка по природе операции**, а не замер. Замерены
   только строки §4. Уточнять по мере накопления журнала;
2. **прирост не складывается линейно**: две операции класса B при живой игре
   могут дать больше, чем одна класса C, потому что очередь растёт быстрее
   суммы (каждая ждёт диска);
3. **память здесь не учтена вовсе**, а на 8 ГБ она — второй потолок:
   операция может быть дешёвой по процессору и вызвать своп;
4. **диск по процессам в macOS не измеряется** (`iotop` не существует),
   поэтому «упирается в диск» — вывод по природе операции, а не показание.
6. 🔴 **экран добавлен осью в тот же день** (§4д) и **противоречит каналу**:
   по каналу выгодны длинные редкие ходы, по экрану — короткие. Разрешается
   «редко и коротко, содержание в файлы», но это правило, а не замер: сколько
   именно кадров стоит строка вывода, не мерялось;
5. 🔴 **канал добавлен отдельной осью только 05.09.2026** (§4г), и класс по нему
   у одной и той же операции может отличаться от класса по процессору на три
   ступени. Остальные строки §2 по этой оси **не размечены** — размечать
   по мере замеров, а не задним числом по догадке.
