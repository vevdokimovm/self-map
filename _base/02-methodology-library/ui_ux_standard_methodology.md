## 1. Нормативный язык: RFC 2119 в русском изложении

Требование без нормативного слова нельзя ни выполнить, ни проверить: «нужно бы сделать
контраст получше» не отличает дефект от пожелания.

| Слово | Англ. | Смысл |
|---|---|---|
| **ДОЛЖЕН / ДОЛЖНА** | SHALL / MUST | обязательное. Невыполнение = **дефект, блокирующий приёмку** |
| **СЛЕДУЕТ** | SHOULD | настоятельная рекомендация; отклонение — при явном обосновании |
| **МОЖЕТ** | MAY | опционально |
| **НЕ ДОЛЖЕН** | SHALL NOT | прямой запрет |

## 2. Формат карточки требования

Пять полей, каждое отвечает на свой вопрос:

| Поле | Вопрос |
|---|---|
| **ID** с доменным префиксом | о чём это и где искать |
| **формулировка** (шаблон EARS: *When/While/If/Where … система ДОЛЖНА …*) | что именно требуется |
| **приоритет** (MoSCoW) | обязательно или желательно |
| **критерий приёмки** | **как проверить, что выполнено** |
| **стандарт** (внешний источник) | почему требование не выдумано |

🔴 **Без критерия приёмки карточка бесполезна.** Требование, которое нельзя проверить,
не спорит ни с чьим мнением, а значит не работает: приёмка сведётся к «мне кажется,
нормально».

**Префиксы доменов** — чтобы ID не конфликтовали между реестрами:
`TOK-` токены · `IA-` архитектура и навигация · `ST-` состояния · `CMP-` компоненты ·
`A11Y-` доступность · `FRM-` формы · `FB-` обратная связь.

## 3. Шесть доменов — каркас, а не список пунктов

| Домен | Вопрос, на который отвечает | Опора |
|---|---|---|
| **IA** — архитектура | *где я, что здесь главное, что делать дальше* | ISO 9241-110, эвристики Нильсена №1, №6 |
| **ST** — состояния | что видит пользователь, когда **данных нет, идёт загрузка, случилась ошибка** | ISO 9241-112 |
| **CMP** — компоненты | одинаковое ли выглядит одинаково | WAI-ARIA APG |
| **A11Y** — доступность | работает ли без мыши, без цвета, при увеличении | WCAG 2.2 AA |
| **FRM** — формы | понятно ли, что вводить и что пошло не так | ISO 9241-143 |
| **FB** — обратная связь | понял ли пользователь, что действие произошло | ISO 9241-110 |

> **Домены не тематические разделы, а перечень мест, где интерфейс ломается.**
> Их шесть потому, что столько независимых способов не сработать у него есть.

## 4. Дизайн-токены — контракт оформления

**Токен** — именованная переменная (цвет, отступ, кегль, тень), на которую ссылаются
все компоненты. Без токенов консистентность и контроль контраста недостижимы:
каждый экран считает пиксели заново, и значения расходятся.

| ID | Требование | Приоритет |
|---|---|---|
| **TOK-01** | цвет — только **семантическим** токеном (`--color-text-primary`), не сырым `#0a0a0a` | Must |
| **TOK-02** | полный парный набор токенов для светлой и тёмной темы; **бренд-цвет = акцент, не заливка** | Must |
| **TOK-03** | типографика из **модульной шкалы**, тело текста **≥ 16px** | Must |
| **TOK-04** | отступы кратны базовому шагу (4/8px) | Should |
| **TOK-05** | радиусы, тени, границы — токенами, консистентно по смыслу | Should |
| **TOK-06** | токены движения + уважение `prefers-reduced-motion` | Should |
| **TOK-07** | единый видимый **фокус-ринг**, контраст ≥ 3:1; `outline: none` без замены запрещён | Must |
| **TOK-08** | согласованные breakpoints, проектирование **mobile-first** | Should |

**Почему семантика, а не «синий»:** роль (`--color-danger`) переживает смену палитры
и темы, название цвета — нет. Тема переключается атрибутом на корне, каскад делает
остальное, JS не нужен.

### Антипаттерны фундамента

1. Цвета, отступы и кегли «по месту» в каждом шаблоне — гарантированный рассинхрон.
2. **`outline: none` без альтернативного фокуса** — ломает клавиатурную навигацию.
   Частая ошибка «убрать некрасивую обводку».
3. Яркий бренд-цвет как заливка рабочих экранов — визуальный шум и провал по контрасту.
4. Базовый шрифт < 16px на мобильном.

## 5. Нормативные источники, на которые опирается стандарт

| Источник | Роль |
|---|---|
| **WCAG 2.2, Level AA** | нормативный: контраст, фокус, формы, масштабирование |
| **ISO 9241-110:2020** — принципы взаимодействия | каркас доменов IA / ST / FRM / FB |
| ISO 9241-112 — представление информации | состояния, иерархия |
| ISO 9241-143 — формы | домен FRM |
| ISO/IEC 25010 — interaction capability | recognizability, learnability, error protection |
| **ГОСТ Р ИСО 9241-210** — человеко-ориентированное проектирование | обоснование процесса (годится для ВКР) |
| **WAI-ARIA APG** | нормативный для паттернов компонентов |
| 10 эвристик Якоба Нильсена | справочный, обоснование принципов |

🔴 **Ссылка на стандарт в карточке — не украшение.** Она отвечает на возражение
«почему именно так»: требование опирается на внешнюю норму, а не на вкус автора.

## 6. Прогрессивное улучшение — для server-rendered интерфейсов

Если приложение отдаёт HTML с сервера, а интерактивность добавляется скриптом:

1. **Базовый сценарий работает на серверном HTML и нативных элементах.** JS — слой
   улучшения, а не условие работоспособности: форма отправляется и при выключенном JS.
2. **Состояния — это разметка, а не только JS-стейт.** `empty` и `error` серверных
   страниц рендерит сервер, `loading` для фрагментов — клиент. **Нормируются оба пути.**
3. **Никаких тяжёлых зависимостей ради мелочей.** Консистентность достигается
   переменными и переиспользуемыми партиалами, а не подключением UI-библиотеки.
