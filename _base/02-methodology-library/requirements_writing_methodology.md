# Методология требований: типы, EARS, критерий приёмки

## 1. Сначала тип требования, потом текст

От типа зависит, **что в нём проверять**.

### Функциональные (FR) — ЧТО система делает

Наблюдаемое поведение. Большинство требований. Пишутся по EARS (§2).

> When пользователь нажимает «Удалить», система ДОЛЖНА запросить подтверждение.

### Нефункциональные (NFR) — НАСКОЛЬКО ХОРОШО она это делает

🔴 **Главное правило: NFR обязан быть измеримым.** «Быстро», «надёжно», «безопасно» —
не требования, а пожелания: их нельзя ни выполнить, ни провалить.

| Категория | Пример измеримой формулировки |
|---|---|
| **PERF** производительность | «p99 latency эндпоинта ДОЛЖЕН быть < 200 мс при N параллельных запросах» |
| **REL** надёжность | «При недоступности внешнего источника система ДОЛЖНА деградировать graceful, а не падать» |
| **SEC** безопасность | «Админ-эндпоинты ДОЛЖНЫ требовать ключ» |
| **LEGAL** юридические | «Система ДОЛЖНА предоставлять механизм удаления персональных данных» |
| масштабируемость, совместимость, доступность | см. `ui_ux_standard_methodology.md`, домен A11Y |

## 2. Шаблон EARS — пять форм, выбираешь по ситуации

**EARS** (Easy Approach to Requirements Syntax) не даёт написать требование, которое
непонятно когда применяется.

| Форма | Шаблон | Пример |
|---|---|---|
| **Ubiquitous** — всегда | *Система ДОЛЖНА `<реакция>`* | Система ДОЛЖНА хранить суммы с точностью до копейки |
| **Event-driven** — на событие | *When `<триггер>`, система ДОЛЖНА …* | When пользователь нажимает «Удалить», система ДОЛЖНА запросить подтверждение |
| **State-driven** — в состоянии | *While `<состояние>`, система ДОЛЖНА …* | While пользователь не авторизован, система ДОЛЖНА показывать только демо-данные |
| **Unwanted behaviour** — нежелательное | *If `<условие>`, система ДОЛЖНА …* | If внешний источник недоступен, система ДОЛЖНА сохранить последние известные данные |
| **Optional feature** — для опции | *Where `<функция включена>`, система ДОЛЖНА …* | Where задан ключ, система ДОЛЖНА требовать его на админ-эндпоинтах |

> **Форма «If — нежелательное» — та, которую забывают.** Требования пишут про успешный
> путь, а ломается система на отказах, и нормировать их нужно так же явно.

## 3. Нормативный язык — RFC 2119

**ДОЛЖЕН** (MUST) — невыполнение = дефект, блокирующий приёмку · **СЛЕДУЕТ** (SHOULD) —
отклонение при явном обосновании · **МОЖЕТ** (MAY) — опционально ·
**НЕ ДОЛЖЕН** (MUST NOT) — прямой запрет.

## 4. Доменные префиксы ID — единая схема

Каждое требование получает `<ПРЕФИКС>-NN`. Префикс = домен, и он же говорит, где искать.

`AUTH-` аутентификация · `SEC-` безопасность · `PERF-` производительность ·
`REL-` надёжность · `DATA-` данные и миграции · `LEGAL-` юридические ·
`UX-` поведение и опыт · `UI-` интерфейс.

**Новый домен — добавить префикс в схему**, а не заводить вторую нумерацию.

## 5. 🔴 Пять признаков плохого требования

1. **Не проверяемо** — «сделать удобно», «быстро работать» без метрики.
2. **Содержит решение вместо потребности** — «использовать Redis» вместо
   «кэшировать с TTL». Решение принимает исполнитель, требование задаёт нужду.
3. **Несколько требований в одном предложении** — разбить: иначе половина выполнена,
   а карточка не закрыта.
4. **Нет критерия приёмки** — как ревьюер примет работу?
5. **Описан только успешный путь** — не сказано, что происходит при отказе
   (`00-infrastructure/07-writing-methodology.md`: требование неполно, пока
   не описаны не-успешные состояния).

> **Требование без критерия приёмки не спорит ни с чьим мнением.** Приёмка тогда
> сводится к «мне кажется, нормально», а спор о готовности решается по старшинству,
> а не по факту.
