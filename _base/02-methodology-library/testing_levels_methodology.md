# Уровни тестов: восемь слоёв и что ловит каждый

> **Поднято 24.08.2026** из `finpilot/docs/testing_infrastructure.md` (183 строки).
> Продуктовые примеры заменены. Дополняет `04-product-dev-kit/STANDARD.md` §2, где
> описаны **тиры прогона** (когда запускать), но не **уровни** (что именно проверяется).

---

## 1. Восемь уровней — каждый ловит свой класс дефектов

| Уровень | Что проверяет | Что ловит, чего не ловят соседи |
|---|---|---|
| **Unit** | функции ядра в изоляции | логику ветвлений; быстрый, детерминированный, основная масса тестов |
| **Integration** | связки через реальный клиент и **реальную схему БД** | 🔴 заодно проверяется **применимость миграций**: схема строится теми же миграциями через старт приложения |
| **Property-based** | математические инварианты на **тысячах случайных входов** | регрессию, которую точечные кейсы пропускают |
| **E2E** | реальный браузер по реальному UI | **разрыв между UI и API** |
| **Visual regression** | скриншоты страниц против эталона | «уехавшую» вёрстку и слетевшую тему — селекторные тесты их не видят |
| **Live-a11y** | движок доступности **в рендере** | нарушения WCAG, которые не видит парсер HTML |
| **Load** | нагрузочный сценарий | бутылочное горло под конкурентной нагрузкой |
| **Security** | статанализ + аудит зависимостей | уязвимые паттерны и CVE |
| **Mutation** | вносит мутации в ядро и смотрит, ловят ли тесты | 🔴 меряет **не покрытие, а силу тестов** |

## 2. 🔴 Property-based — не «несколько кейсов», а свойство для всех входов

Формулировка требования меняется: не «на этих данных результат такой», а
**«свойство обязано держаться для ЛЮБЫХ входов»**.

Примеры формы: величина неотрицательна · доля не превышает порога · сумма долей = 1 ·
размер множества ≤ N · значение в диапазоне [0,1] · выбор = argmax по критерию ·
веса в сумме = 1.

> **Это самый дешёвый способ поймать математическую регрессию.** Точечный кейс проверяет
> одну точку пространства входов; свойство — всё пространство, и находит ту точку,
> о которой автор не подумал.

Инварианты сверяются **строго по документу модели**, а не по коду: иначе тест
подтверждает то, что код делает, а не то, что он должен.

## 3. 🔴 Базовый CRUD обязан иметь E2E — правило, купленное дефектом

Живой случай: **удаление сущности было сломано версиями при зелёных юнит-тестах**.
Юнит проверял функцию удаления, она работала; ломался путь от кнопки до функции.

> **Зелёный юнит-тест говорит «функция работает», а не «пользователь может ею
> воспользоваться».** Между ними лежит весь слой интеграции UI и API, и он не покрыт
> ни одним юнит-тестом по построению.

Это тот же вывод, что в `04-product-dev-kit/STANDARD.md` §2а про моки, с другой стороны:
там мок скрывал непонятое, здесь юнит скрывал непройденный путь.

## 3а. 🔴 Обещание воспроизводимости проверяется между платформами, а не внутри одной

Поднято 25.08.2026 из разбора снимка 13.08 (`finpilot`, волна 0, п. 0.5).

**Ситуация.** Документация модели обещала воспроизводимость по seed — дословно
«совпадение доказано сверкой до копейки». Проверка при этом гонялась **только внутри
одной платформы**, между версиями генератора.

**Чего это не покрывает.** Арифметика с плавающей точкой теоретически расходится
между платформами: разные реализации `libm`/BLAS, `x86_64` против `arm64`. Обещание
«одинаковый seed → одинаковый результат» на этом молчит.

> **Проверка внутри одной платформы доказывает стабильность генератора,
> а не воспроизводимость результата.** Это разные утверждения, и первое читается
> как второе, пока не назвать вслух, между чем именно шла сверка.

**Как закрывается:** прогон на локальной машине (`x86_64`) и в Linux-контейнере
с той же версией языка, что в CI, затем сверка выходов до последнего знака.
Ждать docker-готовности циклом, а не паузой:

```bash
until docker info >/dev/null 2>&1; do sleep 3; done; echo "docker ready"
```

### Смежное правило из того же разбора: снимок читает константы из кода

Снимок состояния модели (эталон для сравнения прогонов) **не переписывается руками** —
он читает константы **прямо из кода**. Иначе повторяется `PIT-140`: число живёт
в двух местах и расходится.

> **Эталон, набранный вручную, стареет молча.** Он выглядит как измерение,
> а является копией измерения, сделанного когда-то.

## 4. Три категории прогона — по скорости и частоте

Разработка не должна тормозить из-за тяжёлых проверок. Отбор — маркерами.

| Тир | Состав | Когда |
|---|---|---|
| **fast** | unit + integration + property + **e2e-smoke**, гейт покрытия, матрица СУБД | каждый push/PR, блокирует мёрж |
| **full** | мультибраузерные E2E + визуальная регрессия + live-a11y + security + нагрузочный smoke | на тегах релиза и вручную |
| **deep** | стресс-property (тысячи примеров) + мутационное | по расписанию и вручную |

🔴 **Маркер быстрого тира навешивается автоматически** на любой тест, не помеченный
как `full`/`deep`/`e2e` — через хук сбора тестов. Иначе сотни тестов пришлось бы
размечать руками, и часть выпала бы из прогона молча.

> **Тест, забытый при разметке, не падает — он просто не запускается.** Поэтому
> умолчание должно быть «included», а исключение — явным.

## 5. Матрица СУБД — обязательна, не опциональна

Быстрый тир гоняется на **двух** СУБД. Причина: код, написанный под одну, молча
опирается на её частности (типы, регистр имён, поведение транзакций), и расхождение
всплывает на проде.

**Мультибраузерные E2E — только в CI:** эталоны визуальной регрессии привязаны
к платформе рендера, локальные скриншоты не совпадут с эталоном ни при какой правке.
