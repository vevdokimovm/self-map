### `test_base_sync.sh` — 6 кейсов / 21 проверка (заведён 03.09.2026)

**Почему этот скрипт покрыт раньше остальных:** `sync_base_local.py` —
единственный в системе, кто делает `rmtree` по чужой репе. Около **28 тысяч
удалений за проход**; ошибка в границе того, что считать `_base/`, стоила бы
содержимого репы.

| Кейс | Что проверяет |
|---|---|
| S1 | постусловия: штамп версии, наличие китов, **отсутствие `_base/.repo-id`** |
| S2 | 🔴 **граница `rmtree`**: собственное содержимое репы не тронуто |
| S3 | инвариант `_base/`: что чинит `--force`, а что не ловится без него |
| S4 | предохранитель приватности: публичная репа канон не получает |
| S5 | 🔴 свежая репа, которой ещё нет на GitHub, — дефект `migration` |
| S6 | `--check` и `--plan` не пишут ничего |

🔴 **Тест сузил обещание в шапке скрипта.** Там значилось: «конфликты слияния
невозможны **по построению**». Проверка показала — шире правды: при совпадении
версии и отпечатка репа пропускается («уже актуальна»), и порча **внутри**
`_base/` не обнаруживается, потому что `BASE_FINGERPRINT` лежит в копии
и описывает **канон**, а не саму копию.

Пропуск осознан и оставлен (28 тысяч удалений × 60 реп ради недоказанной
порчи — дорого), поэтому чинилась не логика, а формулировка. Тест закрепляет
**оба** поведения: пропуск по умолчанию и починку по `--force`.

**Герметичность:** `gh` подменяется стабом — иначе тест проверял бы состояние
GitHub, а не наш скрипт.

### `test_version_bump.sh` — 5 кейсов / 16 проверок (заведён 03.09.2026)

Проверяет инвариант, объявленный в шапке `bump_repo.py`:
**`VERSION` == версия в `CHANGELOG` == версия в `WATCHLOG` §0.** Расхождение
любых двух означает, что подъём оборвался посередине, и репа **выглядит
закрытой, не будучи ею**.

🔴 **Нашёл два настоящих дефекта в первый же прогон** (`PIT-170`):

1. **`bump_repo.py` превращал мусор в версию.** Шапка обещала «мусор
   в `VERSION` останавливает работу» — а `bump()` дополнял недостающие части
   нулями, и `VERSION` с содержимым `мусор` становилась `мусор.0.1`,
   записанной во все три файла. Скрипт-лекарство от полузакрытых реп сам
   приводил репу в неподнимаемое состояние.
2. **Тест был негерметичен и загадил реальный `~/Downloads`.**
   `pack_release.py` не имеет флага `--dest` (`OUT_DIR` зашит жёстко),
   и лишний аргумент разбирался молча. Починено подменой `HOME`; добавлен
   ассерт «настоящий `~/Downloads` не тронут» — проверка стоит в тесте,
   а не в памяти вахты.

### `test_repo_lifecycle.sh` — 9 кейсов / 20 проверок (заведён 03.09.2026)

**Повод, дословно от владельца:** *«постоянно ошибки в создании реп созании
архивов постоянно констурктор уже ошибается…. как тогда работать если уже
при создании объекта лажа»*.

Конструктор (`new_repo.py`), деструктор (`retire_repo.py`) и раздатчик канона
(`sync_base_local.py`) были **без тестов вовсе** — при том что именно они
создают и уничтожают объекты, с которыми работает вся остальная система.

| Кейс | Что проверяет |
|---|---|
| L1 | конструктор создаёт объект, удовлетворяющий инварианту |
| L2 | канон раздаётся конструктором, а не отдельным шагом |
| L3 | публичная репа канон НЕ получает (ADR-004) |
| L4 | **сильная гарантия**: нарушен инвариант → каталога не остаётся |
| L5 | предусловия: имя, повторное создание, целость существующей репы |
| L6 | инвариант ловит подделки на живой репе (R-06, R-08, R-09) |
| L7 | канарейка самого инварианта |
| L8 | **деструктор**: вечные классы не расформировываются |
| L9 | **деструктор**: план по умолчанию, архивы не удаляются никогда |

🔴 **Что тест нашёл в первые прогоны — три настоящих бага:** раздача канона
отказывала любой свежей репе («нет в `gh repo list`» читалось как «публичная»);
шаблон README ссылался на `TASKS.md`, которого класс `satellite` не получает;
инвариант требовал от новорождённой репы записи о выпуске. Ни один не был бы
найден чтением кода — все три проявляются только при исполнении.

Ноль зависимостей: ни сети, ни GitHub-токена, ни реальных реп. Вместо GitHub — локальные
bare-репы (`REMOTE_BASE`), вместо `gh` — стаб `tests/bin/gh` с журналом вызовов.
Код возврата `0` — зелено, `1` — есть падения. В конце печатается покрытие по зонам.

## Почему зоны, а не сквозная нумерация

Раньше кейсы шли подряд и каждый отвечал одному найденному дефекту. У такого набора два
изъяна: по нему **не видно, чего не хватает** — видно только то, что уже покрыто. И он
растёт хвостом, где новое всегда в конце и не связано с родственным.

Теперь у кейса идентификатор зоны — `C4`, `G2`. Буква говорит **что именно проверяется**,
цифра — номер внутри зоны. Пробел в покрытии виден сразу: мало проверок в зоне → там тонко.

Зоны выбраны по **последствиям отказа**, а не по устройству кода: неважно, в какой функции
ошибка, важно — что теряет человек.

## Правила поддержки

**Новое поведение покрыто только когда есть утверждение о ВТОРОМ прогоне.** Фикстура
`make_zip` + `run_deploy` воспроизводит первый запуск: архив на месте, версия новая, ассета
нет. Пользователь почти всегда в другом состоянии — уже опубликовано, архив удалён. Шесть
дефектов подряд жили именно там (разбор: `reports/incidents/unreachable_code_pattern.md`).

```bash
run_deploy "$D" >/dev/null      # переходное состояние
OUT="$(run_deploy "$D")"        # устоявшееся — здесь живёт пользователь
assert ...
```

Образцы: `A2`, `G12`, `G13`п.7.

Проверочный вопрос до выпуска: **сработает ли это на втором запуске подряд, когда входных
данных для шага уже нет, а результат его прошлой работы всё ещё лежит на диске?**

**Новый флаг не готов, пока по нему нет кейса.** Особенно если он что-то удаляет: код,
который не выполнялся ни разу ни в одном тесте, — не рабочий код, а предположение.

**Поймал баг — сначала кейс, который его воспроизводит, потом фикс.** Кейс попадает в зону
по последствиям отказа, а не по месту в коде.

**Перед выпуском — инвентаризация покрытия**, а не ощущение:

```bash
grep -oE '^\s*[A-Z_]+="\$\{[A-Z_]+:-' templates/deploy.sh | grep -oE '[A-Z_]+' | sort -u \
| while read -r f; do grep -q "$f=" tests/test_deploy.sh || echo "БЕЗ ТЕСТА: $f"; done
```

Сейчас без тестов осознанно: `BRANCH`, `RETRIES`, `GH_TIMEOUT` — низкий риск, проверяются
косвенно самим фактом работы ретраев.

## Три приёма, без которых набор проверяет не то

*Извлечено 21.08.2026 из `mission-control/scripts/tests/test-push-inbox.sh`.*

### 1. 🔴 Проверять ОТРИЦАТЕЛЬНОЕ свойство, а не правильность вывода

«Сухой прогон ничего не меняет» **нельзя проверить по выводу**: у прогона, который
втихую сходил в сеть, вывод точно такой же. Проверяется отсутствие действия:

```bash
cat > "$FAKE_BIN/gh" <<'EOF'
#!/usr/bin/env bash
echo "GH ВЫЗВАН с аргументами: $*" >> "$GH_CALL_LOG"
exit 1
EOF
# …прогон…
CALLS=$(wc -l < "$GH_CALL_LOG")     # утверждение: ровно 0
```

Заглушка **логирует вызовы**, тест утверждает, что журнал пуст. То же для «PUT
не вызывается при совпавшем хеше»: заглушка на неожиданный вызов печатает
`PUT НЕ ДОЛЖЕН БЫЛ ВЫЗВАТЬСЯ`, тест проверяет **отсутствие** этой строки в выводе.

Обобщение: **у необратимых операций доказывается не «сделало правильно», а «не сделало
вовсе»** — это разные утверждения, и второе сильнее. Ложится на `G3` и `E1` зоны G/E.

### 2. Границы вырезки проверяются с ОБЕИХ сторон

Тест на «взяли свою секцию» обязан утверждать три вещи, а не одну:

| Утверждение | Что ловит |
|---|---|
| содержит своё | секция вообще найдена |
| **не содержит следующую** | конец среза уехал вперёд |
| **не содержит предыдущую** | начало среза уехало назад |

Односторонняя проверка проходит зелёной ровно на том дефекте, ради которого писалась:
захват соседа не мешает своему содержимому присутствовать.

### 3. Отсутствие фреймворка — не причина отложить тесты

`bats` на машине нет. Это **не повод** оставить скрипт без набора: 175 строк чистого
bash дают `assert_contains` / `assert_not_contains` / `assert_exit_code`, счётчик
`PASS/FAIL`, `mktemp -d` с `trap … EXIT` и ненулевой код в конце. Ноль зависимостей —
то же свойство, что у этого набора.

Отложенный на фреймворк тест не пишется никогда: к моменту, когда фреймворк появится,
поведение уже забыто.

## Прогон на боевой машине (обязателен перед выпуском)

Стенд линуксовый и запускается в bash. Владелец работает на macOS в zsh, и **все четыре
дефекта класса PIT-B пришли именно оттуда** — стенд их не ловит по построению.

Поэтому перед выпуском версии скрипта:

```bash
zsh <путь-к-base-repo>/tests/test_deploy.sh
```

Если под zsh падает сам стенд — это тоже находка: значит различие оболочек затрагивает
и тестовый код, а не только скрипт.

## Известное ограничение

Кейсы делят песочницу и местами опираются на состояние соседей (`D6` использует репу из
`D5`, `H4` — карту из `H3`). Это удешевляет набор, но означает: **прогонять целиком**,
запуск отдельной зоны не поддерживается. Вырастет ещё — разносить фикстуры.

## Что стенд не проверяет

Права токена, реальную приватность реп, сетевые таймауты, лимиты GitHub API, рендер
markdown в вебе и **поведение BSD-утилит macOS** (стенд линуксовый). Отсюда правило:
первый запуск на новых данных — всегда `DRY=1`.
