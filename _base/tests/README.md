# `tests/` — регрессионный набор инфраструктуры

**71 кейса · 274 проверок · 9 зон ответственности**

```bash
bash tests/test_deploy.sh        # из корня base-repo
```

Ноль зависимостей: ни сети, ни GitHub-токена, ни реальных реп. Вместо GitHub — локальные
bare-репы (`REMOTE_BASE`), вместо `gh` — стаб `tests/bin/gh` с журналом вызовов.
Код возврата `0` — зелено, `1` — есть падения. В конце печатается покрытие по зонам.

---

## Почему зоны, а не сквозная нумерация

Раньше кейсы шли подряд и каждый отвечал одному найденному дефекту. У такого набора два
изъяна: по нему **не видно, чего не хватает** — видно только то, что уже покрыто. И он
растёт хвостом, где новое всегда в конце и не связано с родственным.

Теперь у кейса идентификатор зоны — `C4`, `G2`. Буква говорит **что именно проверяется**,
цифра — номер внутри зоны. Пробел в покрытии виден сразу: мало проверок в зоне → там тонко.

Зоны выбраны по **последствиям отказа**, а не по устройству кода: неважно, в какой функции
ошибка, важно — что теряет человек.

## Перед правкой — лидерборд дефектов

`reports/incidents/PITFALLS.md` — классы повторяющихся дефектов со **счётчиками повторов**,
отсортированные по частоте. Читать заголовки перед каждой правкой поведения: 30 секунд.
Поймал дефект — увеличить счётчик своего класса. Счётчик дошёл до 3 → заплатки не работают,
нужна механическая проверка.

## Правила поддержки

**Новое поведение покрыто только когда есть утверждение о ВТОРОМ прогоне.** Фикстура
`make_zip` + `run_deploy` воспроизводит первый запуск: архив на месте, версия новая, ассета
нет. Пользователь почти всегда в другом состоянии — уже опубликовано, архив удалён. Шесть
дефектов подряд жили именно там (разбор: `reports/incidents/unreachable_code_pattern.md`).

```bash
run_deploy "$D" >/dev/null      # переходное состояние
OUT="$(run_deploy "$D")"        # устоявшееся — здесь живёт пользователь
assert ...
```

Образцы: `A2`, `G12`, `G13`п.7.

Проверочный вопрос до выпуска: **сработает ли это на втором запуске подряд, когда входных
данных для шага уже нет, а результат его прошлой работы всё ещё лежит на диске?**

**Новый флаг не готов, пока по нему нет кейса.** Особенно если он что-то удаляет: код,
который не выполнялся ни разу ни в одном тесте, — не рабочий код, а предположение.

**Поймал баг — сначала кейс, который его воспроизводит, потом фикс.** Кейс попадает в зону
по последствиям отказа, а не по месту в коде.

**Перед выпуском — инвентаризация покрытия**, а не ощущение:

```bash
grep -oE '^\s*[A-Z_]+="\$\{[A-Z_]+:-' templates/deploy.sh | grep -oE '[A-Z_]+' | sort -u \
| while read -r f; do grep -q "$f=" tests/test_deploy.sh || echo "БЕЗ ТЕСТА: $f"; done
```

Сейчас без тестов осознанно: `BRANCH`, `RETRIES`, `GH_TIMEOUT` — низкий риск, проверяются
косвенно самим фактом работы ретраев.

## Прогон на боевой машине (обязателен перед выпуском)

Стенд линуксовый и запускается в bash. Владелец работает на macOS в zsh, и **все четыре
дефекта класса PIT-B пришли именно оттуда** — стенд их не ловит по построению.

Поэтому перед выпуском версии скрипта:

```bash
zsh <путь-к-base-repo>/tests/test_deploy.sh
```

Если под zsh падает сам стенд — это тоже находка: значит различие оболочек затрагивает
и тестовый код, а не только скрипт.

## Известное ограничение

Кейсы делят песочницу и местами опираются на состояние соседей (`D6` использует репу из
`D5`, `H4` — карту из `H3`). Это удешевляет набор, но означает: **прогонять целиком**,
запуск отдельной зоны не поддерживается. Вырастет ещё — разносить фикстуры.

## Что стенд не проверяет

Права токена, реальную приватность реп, сетевые таймауты, лимиты GitHub API, рендер
markdown в вебе и **поведение BSD-утилит macOS** (стенд линуксовый). Отсюда правило:
первый запуск на новых данных — всегда `DRY=1`.
