# 05 — Лаборатория синтеза инфраструктур

> **Что это.** Рабочее место для операции «собрать служебки со всех реп → синтезировать в
> `base-repo` → раздать обратно». Операция повторяется, стоит дорого и ломается одинаково,
> поэтому у неё есть свой кит: стандарт, чек-лист, реестр граблей, журналы прогонов и
> описание инструментов.
>
> **Зачем отдельно от `00-infrastructure/`.** Там живут **правила игры** — короткие,
> редко меняющиеся. Здесь — **машинерия операции**: пошаговый алгоритм, накопленные грабли,
> история прогонов с цифрами. Правило-указатель на этот кит —
> `00-infrastructure/53-infrastructure-sync-standard.md`.

## Зачем это существует

Первый же прогон (2026-08-20) дал: работу переделали с нуля, потеряли два файла молча,
разнесли публичный датасет в репу, наступили на биометрический риск, помеченный в плане
за три недели до этого, и повторили миграцию, которая была закрыта 13.08.

Ни одна из этих ошибок не была новой в момент совершения — все они уже были описаны
где-то в системе. Проблема была не в отсутствии знания, а в том, что знание лежало
в семи разных документах и не собиралось в один рабочий алгоритм.

**Этот кит и есть тот алгоритм.**

## Структура

| Путь | Что внутри |
|---|---|
| `STANDARD.md` | Алгоритм операции: фазы, порядок, правила переноса, критерии решений |
| `CHECKLIST.md` | Приёмка прогона — по нему вахта самопроверяется до и после |
| `PITFALLS.md` | Грабли, специфичные для синтеза (общесистемные — в `reports/pitfalls.md`) |
| `tools/README.md` | Какие скрипты уже написаны, что делают, чего не делают |
| `templates/run-log.md` | Шаблон журнала прогона |
| `templates/candidate-decision.md` | Шаблон решения по кандидату в базу |
| `runs/README.md` | Реестр прогонов: дата, объём, итог, ссылка |
| `runs/<дата>-<имя>/` | Журнал конкретного прогона: факты, решения, что пошло не так |

---

## Как пользоваться

1. **Перед прогоном** — прочитать `STANDARD.md` целиком и `PITFALLS.md`. Не по диагонали:
   каждая строка в `PITFALLS.md` стоила отдельной поломки.
2. **Проверить `tools/README.md`** — почти наверняка нужный инструмент уже написан.
   Первый прогон начался с написания своего аудитора при живом `collect_to_base.py`.
3. **Завести папку прогона** `runs/<дата>-<имя>/` из `templates/run-log.md` — **до** первой
   мутирующей операции, а не после.
4. **Вести журнал по ходу.** Не в конце: токены кончаются внезапно, и незаписанное теряется.
5. **По каждому кандидату** — решение по `templates/candidate-decision.md`, чтобы следующий
   прогон не предлагал то же самое заново.
6. **На закрытии** — `CHECKLIST.md`, пополнить `PITFALLS.md`, строка в `runs/README.md`.

## Главное правило кита

> **Док описывает замысел. Диск даёт факт. Утверждение о состоянии системы делается
> только после команды, показавшей это на диске.**

Первый прогон целиком построил план на чтении документации и выдал владельцу описание
архитектуры как проверенное. Реальность отличалась: механизм `_base/` оказался внедрён
наполовину, в двенадцати репах два поколения раздачи лежали друг на друге. Расхождение
нашлось за три команды — после того, как владелец усомнился.

В любой живой системе есть зазор между «так задумано» и «так есть», и он тем больше,
чем дольше идёт незавершённая миграция.
