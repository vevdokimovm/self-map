# Резервные копии для одного человека с умирающим диском

**Исследование 02.09.2026.** Контекст: SSD выработал 108 % ресурса записи,
распаян на плате, резервных копий не существует ни одной.

---

## §0. 🔴 Главная находка: копировать нужно не 81 ГБ, а 53

Из 81 ГБ первой копии примерно **28 ГБ восстанавливаются загрузкой
из интернета**:

| Что | Объём | Чем заменяется |
|---|---:|---|
| `/Applications` | 21 ГБ | переустановка |
| `/usr/local` (brew) | 7 ГБ | `brew bundle dump` — файл на килобайты |

> **Это не бэкап, это рецепт.** 28 ГБ данных заменяются несколькими
> килобайтами инструкции.

Реально невосстановимое — личные документы, фото, `~/Documents/_heavy-originals/`
(файлы, намеренно вынесенные из git из-за лимита GitHub) и два файла инструкций
Claude, которые определяют весь конфиг.

**Этот объём влезает в бесплатные облачные тарифы прямо сейчас, без денег.**

## §1. 🔴 Второй риск: иллюзия покрытия

У рабочей базы **нет локального `.git`** — репозитории уезжают на GitHub только
через `deploy.sh`.

> «63 репозитория на GitHub» — правда ровно настолько, насколько недавно
> гонялся деплой. **Окно потери = разрыв между локальным `VERSION`
> и верхним тегом.**

### ✅ Проверено 02.09.2026 — иллюзии не оказалось, но нашлась дыра

```
локально: 64 репы · на GitHub: 63
```

Пять ключевых реп сверены поимённо, версии совпадают до цифры:
`base-repo` 4.56.0, `mission-control` 2.4.3, `control-panel` 0.20.0,
`personal-finance-dss` 8.30.2, `self-map` 1.12.5. Деплой отработал.

🔴 **Но одна репа не защищена ничем:** `migration`, заведённая сегодня.
Её нет на GitHub, локального `.git` у неё тоже нет — единственный экземпляр
лежит на умирающем диске. Архив собран (`~/Downloads/migration-v0.1.0.zip`),
но `~/Downloads` — тот же диск.

> **Это иллюстрация к самому правилу:** проверка «все ли уехали» находит
> не старое расхождение, а **свежесозданное**. Новая репа не защищена
> ровно до первого деплоя, и это окно тем опаснее, чем меньше о нём помнят.

Команда проверки на будущее:

```bash
cat ~/repos/base-repo/VERSION
gh api repos/vevdokimovm/base-repo/tags --jq '.[0].name'
```

## §2. 🔴 Загрузочный клон на этой macOS сделать НЕЛЬЗЯ

Ожидание «сделаю клон диска, воткну и загружусь» — устарело на шесть лет.

С macOS 11 системный том стал **Signed System Volume**, криптографически
запечатанным. Дословно от разработчика Carbon Copy Cloner:

> *«That seal can only be applied by Apple; ordinary copies of the System volume
> are non-bootable without Apple's seal»*
> *«No, in fact we no longer recommend that you attempt to make your backup
> bootable»*

**Восстановление после отказа в 2026 году одинаково для всех инструментов:**
переустановка macOS → Migration Assistant. Это часы, а не минуты.

> Старый довод «клон загрузится, а Time Machine нет» умер в 2020 году.
> Разница между TM и клоном сегодня гораздо меньше, чем принято думать:
> оба — источник для Migration Assistant.

## §3. Правило 3-2-1 — и откуда оно взялось

Первоисточник установлен точно: документ CISA/US-CERT «Data Backup Options»,
**1 октября 2012**, со ссылкой на **Peter Krogh, *The DAM Book*, 2009, стр. 207**.

🔴 **Правило пришло не из корпоративного IT, а из фотоархивов** — то есть
изначально было про одного человека с невосполнимыми файлами. Ровно наш случай.

| | Что | Сейчас |
|---|---|---|
| копия 1 | внутренний SSD | 🔴 есть, износ 108 %, распаян |
| копия 2 | внешний диск | 🔴 нет |
| копия 3 | offsite | 🔴 нет |

**Состояние: одна копия из трёх, и она на умирающем носителе.**

🔴 **«Два носителя» — не про бренд, а про режим отказа.** Два раздела одного
SSD — одна копия. Смысл требования: чтобы **одна причина** не убила обе.

## §4. Три инструмента по задачам

| Задача | Time Machine | CCC / SuperDuper | restic / borg |
|---|---|---|---|
| файл, удалённый неделю назад | 🟢 профильная | 🟡 только со снапшотами | 🟢 любой снапшот |
| система после отказа диска | 🟢 через Migration Assistant | 🟡 то же самое | 🔴 только данные |
| **шифровальщик убил диск и бэкап** | 🔴 подключённый диск шифруется тоже | 🔴 то же | 🟢 **append-only** |

### restic — единственная документированная защита от шифровальщика

Из официальной документации: *«To prevent a compromised backup client from
deleting its backups (for example due to a ransomware infection), a repository
service/backend can serve the repository in a so-called append-only mode»*.

Две честные оговорки из той же документации: обслуживание (`prune`) требует
полного доступа и делается **отдельным ключом с другой машины**; атакующий
с append-only доступом может дописывать мусорные снапшоты.

**borg в этом режиме слабее:** `delete` и `prune` в append-only **разрешены**,
и защита не работает, если у атакующего есть прямой файловый доступ.

🔴 **Опровергнуто расхожее мнение:** официальная таблица borg показывает
для macOS **ACLs, xattr и BSD flags — все Yes**. Утверждение «borg плохо
сохраняет метаданные macOS» документацией не подтверждается.

## §5. Чего Time Machine не покрывает

1. **исключает системные файлы и приложения** из состава macOS — по документации
   Apple;
2. 🔴 **APFS local snapshots — не бэкап.** Дословно: *«Snapshots aren't backups…
   Any disk failure, including some relatively small errors, can make snapshots
   unusable»*. Живут на **том же диске**. Это уже жгло: один снапшот держал ~50 ГБ;
3. **подключённый диск шифруется вместе с рабочим** при атаке шифровальщика.

**Полагаться на неё единственной нельзя** — но не потому, что «часто ломается»
(систематической статистики отказов в открытом доступе **не найдено**,
и это честная констатация), а по двум структурным причинам:

- она **локальная** — не закрывает ни offsite, ни шифровальщика;
- 🔴 **при отсутствии диска она молчит.** Худший режим отказа: настройка
  выглядит включённой, `AutoBackup = 1`, копий ноль. **Ровно это и обнаружилось.**

## §6. Шифрование копии в облаке

| Сервис | Шифрует до отправки | Оговорка |
|---|---|---|
| **restic** | 🟢 AES-256 CTR + Poly1305 | ключ только у вас; потеря = потеря архива |
| **borg** | 🟢 аутентифицированное | алгоритм дословно не процитирован |
| Arq | 🟢 заявлено E2E | алгоритм не подтверждён, FAQ отдал 404 |
| **Backblaze Personal** | 🟡 есть приватный ключ | 🔴 **AES-128, не AES-256** — расходится с ожиданием |
| iCloud + ADP | 🟡 E2E для большинства | не покрывает совместную работу iWork и Shared Albums |
| Яндекс.Диск, Mail.ru | 🔴 клиентского шифрования нет | → только как «глупое хранилище» под restic |

> 🔴 **Практический вывод.** Российские облака клиентского шифрования не дают,
> зарубежные не оплачиваются российской картой. Выигрышная комбинация одна:
> **restic поверх любого дешёвого хранилища.** Шифрование обеспечивает клиент,
> провайдер становится взаимозаменяемым, и вопрос доверия к нему не возникает.

## §8. 🔴 Что сделать СЕГОДНЯ при бюджете ноль

### Приоритет — от невосстановимого к воспроизводимому

| # | Что | Объём | Почему здесь |
|---|---|---:|---|
| 1 | `~/Documents/Claude/Instruction files/` | **60 КБ** | определяют весь конфиг, копируются за секунду |
| 2 | `~/Documents/_heavy-originals/` | **>1 ГБ** | вынесены из git — **не покрыты ничем** |
| 3 | личные документы и фото | десятки ГБ | невосстановимо в принципе |
| 4 | проверить, что репы реально уехали | — | бесплатно, закрывает главную иллюзию |
| 5 | ~~`/Applications`~~ | 21 ГБ | **не копировать** — переустанавливается |
| 6 | ~~`/usr/local`~~ | 7 ГБ | **не копировать** — `brew bundle dump` |

### Команды

```bash
# 0. Освободить место под сборку
tmutil deletelocalsnapshots /

# 1. Воспроизводимое — записать рецептом, а не копировать
brew bundle dump --file=~/Documents/Brewfile
uv python list > ~/Documents/python-versions.txt

# 2. Проверить главную иллюзию
cat ~/repos/base-repo/VERSION
gh api repos/vevdokimovm/base-repo/tags --jq '.[0].name'

# 3. Зашифрованный архив невосстановимого
hdiutil create -srcfolder ~/Documents -volname RESCUE \
  -fs APFS -format UDZO -encryption AES-256 ~/rescue-docs.dmg

# 4. Копия с сохранением метаданных macOS — ditto, НЕ cp
ditto ~/Documents/_heavy-originals /Volumes/ФЛЕШКА/heavy-originals
```

`ditto` — штатная утилита, сохраняет xattr, ACL и resource forks, в отличие
от голого `cp`.

## §9. Найденные противоречия

1. 🔴 **База устарела по Git LFS.** `13-github-limits-and-rendering.md` (июль 2026)
   говорит «1 GB хранилища + 1 GB трафика». GitHub сегодня: **10 GiB и 10 GiB**,
   пакеты данных отменены в пользу метрового биллинга. **Требует правки**;
2. **rsync на macOS** — расхожее «Apple поставляет древний 2.6.9 от 2006» неверно:
   с **macOS 15.4** Apple заменила его на **openrsync**. Проверено эмпирически
   на этой машине: строка «2.6.9 compatible» — режим совместимости, не старый код;
3. **Backblaze** — ожидание AES-256 против фактического **AES-128**;
4. **Internxt** — обзоры пишут 10 ГБ, сайт сегодня показывает 1 ГБ.

## §10. Что осталось неизвестным

- **рублёвые цены на диски** — маркетплейсы блокируют ботов;
- **тарифы Яндекс.Диска и Mail.ru** — страницы требуют авторизации;
- **отдаётся ли приватный ключ Backblaze на сервер** при веб-восстановлении —
  help-центр вернул 403; историческое поведение за текущее не выдаётся;
- **режимы отказа Time Machine** — форумы Apple недоступны для запросов,
  **ноль подтверждённых фактов** по этому блоку;
- **случаи шифровальщика, добравшегося до диска TM** — ни подтверждения,
  ни опровержения.

**Ограничение метода:** лимит поиска был исчерпан до начала работы (400/400).
Агенты работали прямыми запросами. Это реально повлияло: рублёвые цены
не добыты вовсе.
