## 1. Как устроен стенд

Тесты гоняют **полный боевой цикл**, но без единого обращения наружу:

- **Вместо GitHub** — локальные bare-репозитории (`REMOTE_BASE` подменяет `https://github.com/<owner>`).
  Push, клон, теги — настоящие git-операции, просто remote локальный.
- **Вместо `gh`** — стаб `tests/bin/gh`, подставляемый через `PATH`. Хранит состояние реп и релизов
  в файлах и ведёт журнал вызовов, по которому проверяется поведение.
- **Изолированный `HOME`** и песочница в `mktemp -d`, удаляется по выходу.

Ноль зависимостей: ни сети, ни токена, ни реальных реп. Запуск: `bash tests/test_deploy.sh`.
Код возврата `0` — зелено, `1` — есть падения.

## 4. Что стенд НЕ проверяет

Честная граница покрытия — эти вещи проверяются только боевым прогоном на GitHub:

- права и срок жизни токена `gh`;
- реальная приватность создаваемых реп;
- сетевые таймауты и поведение ретраев под РФ-TLS;
- лимиты GitHub API;
- рендер описания релиза в вебе (markdown-нюансы);
- **поведение BSD-утилит macOS** — стенд линуксовый, и баг с `Illegal byte sequence` тесты
  не воспроизвели: GNU `cut` глотает невалидные байты, BSD — нет. Нашлось только у тебя.

**Отсюда правило приёмки:** первый запуск на новых данных — всегда `DRY=1`, затем боевой прогон
с `ONLY="одна-репа"`, проверка глазами на GitHub, и только потом вся пачка.

## 5. Правило поддержки

Поймал баг в деплойере — **сначала тест, который его воспроизводит**, потом фикс. Кейсы 2, 5, 15,
21 появились именно так. Тест, написанный после фикса, проверяет фикс; тест, написанный до, —
проверяет проблему.
