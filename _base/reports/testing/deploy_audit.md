# Ревизия `deploy.sh` — полный аудит

**Дата:** 2026-07-29 · **Объект:** `templates/deploy.sh` v2.2.0 и его служебка
**Повод:** баги находились только тогда, когда владелец тыкал пальцем. Тесты должны были
ловить их раньше — значит проблема не в отдельных багах, а в способе тестирования.

---

## 1. Что было не так с процессом

Тесты писались **реактивно**: нашёлся баг → написан тест на этот баг. Так покрываются
только те пути, по которым уже прошёл человек. Всё остальное остаётся тёмной зоной,
и обнаруживается тем же способом — человеком.

Показательный случай: `DROP_LEGACY_ASSETS` (удаление ассетов, необратимая операция).
Код написан, флаг задокументирован, в журнал внесён — а стаб `gh` не умел `delete-asset`,
то есть **путь не выполнялся ни разу**. Внутри него сидели два дефекта.

Вывод, ради которого этот документ: **покрытие надо считать, а не оценивать на глаз.**

---

## 2. Методика ревизии

Не «посмотреть код внимательно», а четыре механические процедуры:

1. **Инвентаризация поверхности.** Выгрузить из скрипта список всех переменных-режимов
   и механически сверить с тестами: какие упоминаются, какие нет.
2. **Статический анализ.** `shellcheck -S warning` на весь файл.
3. **Инвентаризация деструктивных операций.** Найти все `rm -rf`, `delete`, `--force`,
   замену дерева — и по каждой проверить: есть ли защита, есть ли тест.
4. **Эмпирическая проверка подозрений.** Любое предупреждение проверять запуском,
   а не рассуждением. Догадка о поведении bash — не доказательство.

---

## 3. Что нашла инвентаризация покрытия

Из 20 переменных-режимов **9 не упоминались в тестах ни разу**:

`ASSET`, `BRANCH`, `GH_TIMEOUT`, `MIN_FILES`, `PRIVATE`, `REPO_MAP`, `RETRIES`,
`SERVICE_RE`, `VARIANT_REPOS`, `VERIFY`.

Отсортировано по цене ошибки:

| Режим | Чем грозит | Итог |
|---|---|---|
| `VERIFY` | говорит, какие архивы **можно удалить** — ошибка стоит данных | **был сломан целиком** |
| `PRIVATE` | приватная репа могла бы создаться публичной | работал, теперь покрыт |
| `MIN_FILES`, `SERVICE_RE` | защиты от публикации мусора | работали, теперь покрыты |
| `REPO_MAP`, `VARIANT_REPOS` | архив уедет не в ту репу | работали как дефолты; покрыто переопределение |
| `ASSET` | релизы без ассетов | работал, теперь покрыт |
| `BRANCH`, `RETRIES`, `GH_TIMEOUT` | низкий риск | оставлены без тестов осознанно |

## 4. Найденные дефекты

### Д1. `VERIFY` не работал вообще — режим был мёртв

**Симптом:** для любого архива, полностью опубликованного на GitHub, режим отвечал
«ДЕРЖАТЬ». То есть никогда не сказал бы, что удалять безопасно.

**Механика.** Блок `VERIFY` стоял в файле **раньше**, чем определения функций `gh_try`
и `release_state`. В shell функция должна быть объявлена до вызова — а этот режим выходит
из скрипта до того места, где функции появляются. Каждый вызов падал с
`release_state: command not found`, ошибка глушилась, и «релиз» всегда числился отсутствующим.

**Почему не заметили раньше:** ошибка уходила в `/dev/null`, а результат «ДЕРЖАТЬ» выглядит
осторожно и правдоподобно. Ошибка в безопасную сторону, но режим бесполезен — при этом он
был отдан владельцу как инструмент принятия решения об удалении данных.

**Фикс.** Все функции подняты в отдельный блок **до первого исполняемого шага**.
Проверка встроена в ревизию: последнее объявление функции обязано идти до «ШАГ 1».

**Контроль:** тесты 52–53.

### Д2. Список к удалению ломал `xargs`

**Симптом:** пути в `~/Downloads/safe_to_delete.txt` писались с отступом в два пробела
(как в выводе на экран). Команда `xargs -d '\n' rm --`, которую владелец получил в
инструкции, на таком файле не нашла бы файлы.

**Фикс.** Отступ срезается при записи. Тест проверяет не формат, а факт: `xargs` по этому
файлу реально находит файлы.

**Урок:** одна и та же строка не может служить и человеку, и машине.

### Д3–Д4. Чистка ассетов (закрыто до начала ревизии, здесь для полноты)

Удаление шло **до** загрузки замены — при обрыве сети релиз оставался без ассета вовсе.
И сам блок был недостижим у релизов, где канонический ассет уже есть, — то есть ровно
в том сценарии, ради которого флаг вводился. Разбор — `deploy-CHANGELOG.md` v2.1.2.

### Д5. Мёртвый код и невидимая версия

`SCRIPT_VERSION` объявлена и нигде не использовалась — версия скрипта не попадала в вывод,
и по логу нельзя было понять, какая ревизия отработала. `CL_USED` и `IS_NEW` — остатки
прежних правок. Версия теперь печатается в первой строке, мёртвые переменные удалены.

## 5. Что проверено и оказалось исправным

Важная часть аудита — зафиксировать, что **не** сломано, чтобы не проверять по кругу.

- **`shellcheck -S warning`** на весь файл: ошибок нет, предупреждений нет
  (кроме двух ложных, см. ниже).
- **SC2221/SC2222** — «паттерн `case` перекрывает следующий». Выглядело опасно: если
  фолбэк недостижим, каждый отказ `gh` ретраился бы трижды с паузами. Проверено
  **запуском** на пяти входах: `release not found` и `HTTP 403` дают no-retry,
  `rc=124` и `i/o timeout` дают retry. Предупреждение ложное — shellcheck не разбирает
  перенос строки внутри списка паттернов.
- **Деструктивные операции** — полный список и статус защиты:

| Операция | Защита | Тест |
|---|---|---|
| Замена дерева репы | маркеры корня (`README.md`, `MIN_FILES`) до сноса | 7, 21, 55 |
| Удаление ассета | только по флагу, только дубль той же версии, только после подтверждения канонического | 49, 50, 51 |
| Удаление рабочей папки | `$WORK` создаётся сам скриптом, снос в конце | — |
| Перезапись описания релиза | только заглушки; осмысленное — по `FORCE` | 10, 24, 45 |
| Перезапись тега | запрещена всегда | 3 |

- **Переменные в пайпах**: два места с `| while read`. Оба только печатают/удаляют,
  ничего не возвращают наружу — потеря переменных в сабшелле безвредна.
- **`cd` без проверки**: одно место, `cd "$HOME" && rm -rf "$WORK"` — `&&` защищает.

работал корректно, но исключение делало правило непроверяемым. Перенесён в блок функций.

## 7. Правило на будущее

**Перед выпуском новой версии скрипта — прогнать инвентаризацию покрытия, а не полагаться
на ощущение.** Одной командой:

```bash
grep -oE '^\s*[A-Z_]+="\$\{[A-Z_]+:-' templates/deploy.sh | grep -oE '[A-Z_]+' | sort -u \
| while read -r f; do
    grep -q "$f=" tests/test_deploy.sh || echo "БЕЗ ТЕСТА: $f"
  done
```

И жёстко: **новый флаг не считается готовым, пока по нему нет теста.** Особенно если он
что-то удаляет. Код, который не выполнялся ни разу ни в одном тесте, — не рабочий код,
а предположение о том, что он рабочий.
