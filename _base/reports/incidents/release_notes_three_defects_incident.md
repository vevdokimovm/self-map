## Резюме

За один вечер, в трёх последовательных попытках «сделать описание релиза как в `legal-knowledge-base`»,
инструмент выпуска сломался тремя разными способами. Пострадали три выпущенных релиза
(`v1.0.0`, `v1.1.0`, `v1.2.0`) и один холостой прогон утилиты починки. Содержимое репы,
теги и ассеты не пострадали ни разу — ломался только слой описаний.

| Симптом (что видел владелец) | Дефект | Версия, где исправлено |
|---|---|---|
| `v1.0.0`: релиз не создан, деплой завершился ошибкой | `deploy_from_zip.sh` зовёт `publish.sh --auto-asset`, а в дереве лежал `publish.sh` **без** этого флага | v1.1.0 |
| `v1.1.0`: описание открывается блокквотом, строки `## [1.1.0] — дата — название` нет | парсер CHANGELOG брал секцию **со следующей строки** после заголовка | v1.2.0 (частично) |
| `v1.2.0`: заголовок «**repo** v1.2.0», описание «**Release 1.2.0**» | (а) off-by-one: поиск конца секции стартовал со строки заголовка → тело пустое → фолбэк; (б) `basename` корня git-дерева = `repo` | v1.3.0 |
| `fix_release_notes.sh --all`: «исправлено 0, пропущено 1» | в **zsh** нет word splitting: `for V in $VERSIONS` дал один элемент `"1.0.0 1.1.0 1.2.0 1.3.0"` | v1.3.1 |

## Хронология

1. **v1.0.0** — интеграция проекта архивного анализа. Дерево запушено (коммит `f91735d`, 603 файла),
   автопроверка «файлов в коммите == в дереве» пройдена. Далее `deploy_from_zip.sh` вызвал
   `publish.sh --version 1.0.0 --auto-asset` → `ОШИБКА: неизвестный аргумент: --auto-asset`.
   **Рассинхрон линии шаблонов:** `25-versioning-and-releases.md` описывает `--auto-asset`,
   `deploy_from_zip.sh` его использует, а сам `publish.sh` в дереве — версии без него.
2. **v1.1.0** — флаг добавлен, релиз вышел. Но описание начиналось сразу с блокквота: парсер
   секции стартовал с `start = i + 1`, то есть выбрасывал саму строку `## [X.Y.Z] — …`.
3. **v1.2.0** — «исправление» сделало хуже. `start = i` вернул заголовок в срез, но цикл поиска
   конца секции остался `range(start, …)`, а строка заголовка сама матчится `^\s{0,3}##\s+` →
   `end == start` → тело пустое → сработал фолбэк `Release {version}`. Параллельно заголовок
   релиза был собран как `basename $(git rev-parse --show-toplevel)`, что в контексте
   `deploy_from_zip.sh` даёт **`repo`** (клон живёт в `$WORK/repo`), а не имя репозитория.
4. **v1.3.0** — обе ошибки исправлены (`range(start + 1, …)`, `--title "$TAG"`), проверено прогоном
   извлечения по всем четырём секциям CHANGELOG. Добавлена утилита `fix_release_notes.sh` для
   правки уже выпущенных релизов.
5. **Прогон утилиты** — `zsh ./fix_release_notes.sh --all` → «исправлено 0, пропущено 1».
   Список версий собирался в строку и обходился `for V in $VERSIONS`; **zsh, в отличие от bash,
   не разбивает unquoted-переменную по словам**, поэтому в цикл ушёл один элемент
   `"1.0.0 1.1.0 1.2.0 1.3.0"`.
6. **v1.3.1** — утилита переписана на файл + `while IFS= read -r … done < "$VLIST"`
   (редирект, а не пайп: пайп создал бы subshell и потерял счётчики). Проверено прогоном: 4 итерации.

## Корневые причины

**RC-1. Документация опережала код.** `--auto-asset` был описан в протоколе версионирования и
вызывался деплой-скриптом раньше, чем появился в самом `publish.sh`. Три артефакта одной линии
(`25-versioning-and-releases.md` → `deploy_from_zip.sh` → `publish.sh`) разъехались, и разрыв
обнаружился только в проде — на последнем шаге выпуска.

**RC-2. Проверка не покрывала предмет правки.** После каждой правки прогонялся `bash -n`
(синтаксис) — и ни разу не проверялся **результат работы парсера**. Синтаксически безупречный
скрипт трижды выдавал неверный текст. Проверялось не то, что менялось.

**RC-3. Предположения об окружении.** Дважды: `basename` корня дерева считался именем репы
(неверно в контексте временного клона), и bash-семантика считалась действующей в скрипте,
который запускается командой `zsh`. Шебанг `#!/usr/bin/env bash` при запуске `zsh script.sh`
не действует.

## Что сделано

- `publish.sh`: добавлен `--auto-asset` (zip-снапшот тега через `git archive` с wrapper-папкой,
  идемпотентно); исправлен off-by-one в парсере CHANGELOG; заголовок релиза = тег.
  Обе копии — корневая и `00-infrastructure/templates/publish.sh`.
- `fix_release_notes.sh` (новый, обе копии): правит уже выпущенные релизы задним числом —
  `title = vX.Y.Z`, описание = секция CHANGELOG **вместе** со строкой заголовка. Теги и ассеты
  не трогает. Режимы: перечисление версий или `--all`.
- Грабли занесены в `pitfalls.md` (PIT-013, PIT-014) и в `WATCHLOG §4`.

## Уроки

1. **Правку инструмента проверяй его собственным выходом.** Для парсера — прогон извлечения на
   реальном файле, а не `bash -n`. Правило: *менял парсер — распечатай, что он вернул*.
2. **Линия шаблонов версионируется целиком.** Меняешь контракт (`--auto-asset`) — правь протокол,
   вызывающий скрипт и вызываемый скрипт одновременно, иначе разрыв всплывёт в момент выпуска.
3. **Скрипты системы исполняются zsh.** Пиши переносимо: списки — через файл и `while IFS= read -r`,
   редирект вместо пайпа (счётчики), никаких предположений о word splitting.
4. **Не выводи имя репы из путей рантайма.** Клон может лежать в папке с любым именем — бери имя
   из обёртки архива, `VERSION`, remote URL или просто не используй.
5. **Ошибка в слое описаний — не повод пересобирать релиз.** Содержимое, теги и ассеты остаются
   валидными; правится метаданными через `gh release edit`. Именно для этого существует
   `fix_release_notes.sh`.
