# Post-mortem: deploy.sh — четыре наложившихся дефекта тишины на медленной сети, 2026-08-27 (SEV3)

Авторы: Claude (вахта V, IX) · Статус: Final

## Summary

Прогон `deploy.sh` (публикация волны из 40 репозиториев после мега-волны MVP) на
нестабильном VPN-канале (40–150 КБ/с) выглядел зависшим несколько раз подряд —
владелец не мог отличить «работает медленно» от «сломано» ни на одном из трёх шагов
(клон, Ctrl+C, заливка ассета релиза), хотя формально всё это время скрипт либо
действительно работал, либо (один раз) действительно упирался в мёртвую точку без
выхода. Публикация в итоге успешно завершилась — все 40 репозиториев подтверждены
на GitHub с правильным тегом, ассетом и описанием — но потребовала около часа
наблюдения и нескольких перезапусков вместо ожидаемых минут.

## Impact

- Длительность: ~1 час наблюдения владельцем (23:19-20:19 по логам), несколько
  ручных перезапусков скрипта.
- Затронуто: 40/40 репозиториев в итоге опубликованы успешно, потерь данных не было
  — только время и нервы.
- Деньги/SLA: нет.
- **Второй ущерб:** доверие к собственным индикаторам прогресса скрипта. Строка
  `Receiving objects: X%` — единственный визуальный сигнал «жив/мёртв» — не
  обновлялась во время реального зависания (см. BUG-003), и владелец физически не
  мог отличить «ждать ещё» от «прерывать и перезапускать» без стороннего
  подтверждения (в данном случае — меня).

## Detection

От пользователя, в реальном времени, по мере наблюдения за прогоном (не от
мониторинга — мониторинга у самого скрипта, по сути, и не было до этой серии
фиксов). Каждый из четырёх багов был замечен владельцем визуально («висит»,
«не реагирует на Ctrl+C», «зависает почти в самом конце») и диагностирован по
запросу в реальном времени, под давлением срочности.

## Root cause (по каждому из четырёх багов)

### BUG-001 · [Major/P1] Порог зависания не ловил «еле ползёт», только «мертво»

| Поле | Значение |
|---|---|
| Окружение | macOS, zsh, git через VPN с нестабильной пропускной способностью |
| Компонент | `templates/deploy.sh`, `CLONE_LOW_SPEED_LIMIT`/`CLONE_LOW_SPEED_TIME` |
| Статус | Closed (v4.21.1) |

**Как проявлялся:** клон висел без вывода прогресса минутами на скорости
40–150 КБ/с; git не обрывал соединение, потому что технически оно ещё было живым.

**Корневая причина:** `CLONE_LOW_SPEED_LIMIT=1024` (1 КБ/с) — порог, введённый в
этой же сессии (v4.21.0) для решения точно этой проблемы, был откалиброван по
интуиции («явно мёртвое соединение»), а не по реальным цифрам деградации VPN.
Реальность — устойчивые 40–150 КБ/с, что технически **выше** старого порога и
поэтому никогда не срабатывало.

**Фикс:** порог поднят до 51200 байт/с (50 КБ/с), время срабатывания снижено
30с→15с.

**Почему не поймали раньше:** порог вводился и проверялся синтетически (тест I6
на bare-remote с фальшивыми значениями `CLONE_LOW_SPEED_LIMIT=7`), не на реальном
медленном канале. Синтетический тест подтверждает, что флаги долетают до `git` и
не ломают обычный прогон — не подтверждает, что конкретное число откалибровано
под жизнь. Нужен отдельный класс проверки: «порог соответствует наблюдаемой
деградации реальной сети», который тест на файловом транспорте физически не
может дать.

### BUG-002 · [Major/P1] Фоновый `git clone &` не реагировал на Ctrl+C

| Поле | Значение |
|---|---|
| Окружение | zsh, неинтерактивный контекст запуска фоновой задачи |
| Компонент | `templates/deploy.sh`, цикл живого прогресса клона |
| Статус | Closed (v4.21.2) |

**Как проявлялся:** владелец жал Ctrl+C по зависшему клону раз за разом — видимой
реакции ноль, пришлось закрывать всё окно терминала.

**Корневая причина:** не гонка состояний, а документированное поведение POSIX-
шеллов: асинхронные команды (`cmd &`) в неинтерактивном контексте получают
`SIGINT` **проигнорированным** по умолчанию — это защита от случайного убийства
фоновых задач нажатием Ctrl+C на переднем плане. Эмпирически подтверждено в этой
же сессии отдельным тестом (`sleep 30 &` пережил `SIGINT` родителю).

**Фикс:** `cleanup_work` (общий `trap … EXIT INT TERM`) теперь хранит PID
активного фонового процесса в `ACTIVE_CHILD_PID` и явно убивает его: `TERM` →
до 3с ожидания → `KILL`, если завис на блокирующем сетевом вызове.

**Почему не поймали раньше:** фоновый паттерн (`&` + live-прогресс через `\r`)
введён для клона в этой же сессии как решение другой проблемы («молчание
неотличимо от зависания»), и Ctrl+C-поведение фоновых задач под `trap` никогда
не тестировалось напрямую — тестовый стенд `test_deploy.sh` не эмулирует
интерактивное прерывание пользователем.

### BUG-003 · [Minor/P2] Спам «no such file or directory» при пропаже рабочей папки

| Поле | Значение |
|---|---|
| Окружение | среда с нестабильной `$WORK` (VPN/диск/ФС — точная причина не установлена) |
| Компонент | `templates/deploy.sh`, цикл опроса прогресса клона |
| Статус | Closed (v4.21.3) |

**Как проявлялся:** десятки повторов `deploy.sh:1421: no such file or directory:
.../clone_family.log` печатались в терминал раз в секунду, пока жив PID клона.

**Корневая причина:** цикл опроса читал `$_clone_log` каждую секунду без проверки
существования файла. Эмпирически подтверждено в этой же сессии: `2>/dev/null` НЕ
гасит ошибку «no such file or directory» при отсутствующем файле для input-редиректа
— это ошибка открытия самого редиректа шеллом, а не ошибка команды, чей stderr
перенаправляется, и её нельзя заглушить редиректом самой команды.

**Фикс:** `[ -f "$_clone_log" ]` перед каждым чтением — тихий пропуск итерации,
если файла нет, вместо печати ошибки.

**Почему не поймали раньше:** этот путь кода (файл исчезает посреди активного
процесса) — крайний случай нестабильности среды, который не воспроизводится
детерминированно на тестовом стенде. Обнаружен только потому, что реально
произошёл на прогоне 27.08 (см. также **Не причина** ниже).

### BUG-004 · [Critical/P0] Заливка ассета релиза — 120с таймаут + нулевой прогресс

| Поле | Значение |
|---|---|
| Окружение | `gh` CLI, релиз с прикреплённым ассетом >100 МБ на медленном канале |
| Компонент | `templates/deploy.sh`, `ensure_release()`, `gh_try()` |
| Статус | Closed (v4.22.0) |

**Как проявлялся:** шаг `→ релизы` для `self-map` (~140 МБ) висел без единого
символа вывода несколько минут подряд — неотличимо от полного зависания.

**Корневая причина:** `GH_TIMEOUT=120` (2 минуты) — общий таймаут на **любой**
вызов `gh`, включая заливку тяжёлого ассета, применялся и к лёгким API-вызовам
(список/просмотр/правка), и к заливке многомегабайтных файлов одним и тем же
числом. На 40–60 КБ/с 120 секунд дают ~7 МБ — недостаточно для 140 МБ файла,
гарантированный таймаут на каждой из 3 попыток. Дополнительно: `gh_try()`
буферизует весь вывод через `_o="$(... 2>&1)"` — command substitution, которая
ничего не печатает, пока команда не завершится, поэтому даже если бы `gh` умел
писать прогресс в перенаправленный поток (не умеет — прогресс-бар `gh` активен
только когда stderr — реальный терминал), он всё равно не дошёл бы до экрана.

**Фикс:** новая функция `gh_try_upload()` — отдельный, намного больший таймаут
(`GH_UPLOAD_TIMEOUT`, по умолчанию 1800с) только для заливки, плюс живой
heartbeat (секундный отсчёт времени через фоновый процесс + `\r`), доказывающий,
что процесс жив, пока не может дать честный побайтовый процент (`gh` его наружу
не отдаёт).

**Почему не поймали раньше:** до этой волны деплоя ни один архив, публикуемый
через этот скрипт, не приближался к размеру, при котором 120с на текущей
скорости канала становится узким местом (health-vault ~513 МБ и self-map ~140 МБ
— archives класса «личные данные» появились впервые именно в этой волне). Порог
был достаточен для всей предыдущей истории использования и никогда не
тестировался на репозитории такого размера в связке с деградированной сетью.

## Не причина

**Не было гонки состояний между `cleanup_work` и фоновым клоном** (первая
гипотеза для BUG-002) — проверено эмпирически отдельным тестом: `sleep 30 &` под
`trap ... INT` пережил `SIGINT`, посланный родителю, без всякой гонки — сигнал
просто не долетал до фонового процесса вообще, ни при каком тайминге. Причина —
не состояние гонки, а документированное поведение шелла по умолчанию.

**Не было проблемы с самим `retry()`/экспоненциальным backoff** — механизм
повтора на реальных сетевых сбоях (`fetch-pack: unexpected disconnect`,
`early EOF`) в этом же прогоне сработал штатно несколько раз (christ-walk,
history, sales, security-forces, self-map, spycraft, truth-seeking) — каждый раз
поймал реальный обрыв и повторил успешно с первой-второй попытки. Механизм
ретраев не был дефектом ни в одном из четырёх случаев — дефект был либо в
пороге распознавания зависания (BUG-001), либо в отсутствии сигнала о
происходящем (BUG-002, BUG-003, BUG-004).

## Contributing factors

- Все четыре бага делят один корень на уровне класса: **сетевые/файловые
  операции, буферизующие или подавляющие вывод, не различимы для человека от
  зависшего процесса** — цепочка фиксов v4.21.0→v4.22.0 закрывала этот класс
  постепенно, по одному проявлению за раз, а не одним проходом.
- Давление срочности (владелец активно ждал прогон, чтобы продолжить публикацию
  волны из 40 реп) означало, что каждый фикс синхронизировался в
  `~/Downloads/deploy.sh` немедленно после написания, без полного прогона
  тестового набора между фиксами — тесты запускались параллельно/после, не как
  строгий гейт перед синхронизацией копии. Риск оправдался (все 295 тестов зелёные
  после серии), но это осознанный компромисс скорость/строгость, не образец для
  обычного режима работы.
- Впервые в истории использования этого скрипта публиковались архивы личных
  данных весом сотни мегабайт (health-vault, self-map, family) — именно этот
  размерный класс и оказался тем, что довело до предела и порог скорости клона,
  и таймаут заливки ассета одновременно.

## Resolution

- Митигация: владелец вручную повторял прогон/переключал VPN между попытками,
  пока фиксы не закрыли класс проблемы целиком.
- Фикс: `deploy.sh` 4.21.0 → 4.22.0, четыре точечных изменения (см. BUG-001-004
  выше), задокументированы в `templates/deploy-CHANGELOG.md`.
- **Внешняя точка:** прямая сверка с `gh` API после прогона — не полагаясь на
  собственный вывод скрипта, для каждого из 40 репозиториев independently
  запрошены тег и список ассетов релиза напрямую через `gh release view --json`.
  Все 40 совпали с ожиданием (правильный тег, ровно канонический ассет). Это и
  есть внешняя точка проверки, не зависящая от того, правильно ли скрипт
  отчитался о своей же работе.

## Lessons learned

- **Что сработало хорошо:** `retry()` на реальных сетевых обрывах отработал
  безукоризненно все прогоны подряд — механизм повторов сам по себе не был
  проблемой ни разу. Эмпирическая проверка гипотезы (тест на `sleep 30 &` вместо
  веры в «наверное это гонка») заняла минуту и сразу дала верный диагноз для
  BUG-002, вместо того чтобы чинить несуществующую гонку.
- **Что сработало плохо:** четыре последовательных цикла «фикс → синхронизация →
  новый прогон → новый симптом» вместо одного полного прохода по всем silent-hang
  точкам скрипта разом. Три из четырёх багов (клон, Ctrl+C, заливка) — один и тот
  же класс дефекта (буферизация/подавление вывода на потенциально долгой сетевой
  операции), и системный аудит всех точек этого класса сразу — до первого реального
  прогона — нашёл бы минимум BUG-004 заранее, без необходимости ловить его вживую
  под давлением.
- **Где повезло:** `retry()` использует ту же command-substitution-буферизацию,
  что была корнем BUG-004, но для лёгких API-вызовов (список/просмотр/правка,
  <1с каждый) это никогда не проявлялось как проблема — повезло, что первый же
  реальный прогон с тяжёлыми личными архивами (family/health-vault/self-map)
  случился в контролируемых условиях с постоянным наблюдением, а не оставлен без
  присмотра на несколько часов.

## Открытое — не пофикшено в этой серии (для следующего прохода)

### 🔴 BUG-005 · [Major/P2] `pushb`/`pusht` — тот же класс дефекта, ещё не сработал

| Поле | Значение |
|---|---|
| Окружение | тот же (медленная сеть + тяжёлый репозиторий) |
| Компонент | `templates/deploy.sh`, `pushb()`/`pusht()`, вызываются через `retry()` |
| Статус | **Open — найдено при аудите, не воспроизведено вживую, не пофикшено** |

**Как проявляется (предсказание, не наблюдение):** `git push` для веток с большим
диффом (например, первая публикация тяжёлого репозитория с личными данными или
добавление крупного бинарного содержимого в уже существующий) пройдёт через
`retry()`, который буферизует весь вывод через `_out="$("$@" 2>&1)"` — тот же
паттерн, что был корнем BUG-004 для заливки ассета. На медленном канале это даст
тот же симптом: полная тишина на весь таймаут, неотличимая от зависания.

**Почему ещё не сработал:** до сих пор push-дельты (изменения поверх уже
клонированного дерева) были меньше полного клона/ассета — обычно закоммиченные
диффы малы даже для тяжёлых репозиториев. Риск теоретический, пока не
подтверждён реальным инцидентом.

**Рекомендация:** применить тот же паттерн, что `gh_try_upload()` (heartbeat +
отдельный больший таймаут), к `pushb`/`pusht`, **до** первого реального случая,
а не после — единственный из пяти найденных багов, где есть шанс закрыть класс
превентивно, а не постфактум.
