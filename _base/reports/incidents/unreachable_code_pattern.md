# Репорт: шесть раз на одни грабли — код, недостижимый в реальном состоянии

**Дата:** 2026-07-30 · **Объект:** `templates/deploy.sh`
**Суть:** один класс дефекта воспроизведён шесть раз за одну сессию. Тесты были зелёные
каждый раз. Владелец находил каждый случай сам.

---

## 1. Шесть случаев

| № | Что заявлено | Что происходило | Как обнаружено |
|---|---|---|---|
| 1 | `DROP_LEGACY_ASSETS=1` снимает дубли ассетов | Код лежал внутри ветки «канонического ассета **нет**». У обработанных релизов ассет есть → ветка не выполняется → флаг не делает ничего | вопрос владельца «это точно проверено?» |
| 2 | `VERIFY=1` говорит, что можно удалять | Блок стоял в файле **выше** объявления функций → `release_state: command not found`, ошибка глушилась → режим всегда отвечал «ДЕРЖАТЬ» | плановая ревизия по требованию владельца |
| 3 | `DELETE_AFTER=1` удаляет архив после публикации | Удаление стояло в ветке публикации. Версия, опубликованная прошлым прогоном, пропускается по тегу → до удаления не доходит | «он ничего не удалил» |
| 4 | Автоудаление есть | Спрятано за флагом. Владелец запускает без флагов в 99% случаев → функции для него не существует | «ТЫ МОЖЕШЬ СДЕЛАТЬ ЧТОБЫ ОН ТАК ДЕЛАЛ» |
| 5 | Убираются распакованные зеркала | Каталоги искались по списку архивов **этого прогона**. Зеркало версии, чей zip удалён раньше, не рассматривалось | «он её просто оставил» |
| 6 | То же | На раннем выходе «архивов нет» скрипт завершался до блока уборки — то есть ровно тогда, когда остались только зеркала | тест, написанный к случаю 5 |

Случай 6 — единственный, найденный тестом. И только потому, что тест писался прицельно
под уже понятый класс.

---

## 2. Что у них общего

Три разных механизма, один результат.

**A. Код в ветке, ложной в устоявшемся состоянии** (1, 3, 5, 6).
Условие вида «если ассета нет», «если версия публикуется сейчас», «для архивов этого
прогона» истинно только в **первый** раз. Дальше оно ложно навсегда.

**B. Код недостижим по порядку объявлений** (2). Функция вызывается раньше, чем определена.

**C. Код достижим, но за флагом, которого пользователь не ставит** (4).

Все три дают один симптом: **функция описана в журнале, покрыта тестом, и не работает
у пользователя.**

---

## 3. Настоящая причина: я писал под первый прогон, а живут в N-ном

Вот корень, и он не в невнимательности.

Каждая новая возможность писалась в контексте «вот сейчас мы публикуем версию» — потому
что именно этот сценарий я держал в голове, разрабатывая шаг. Публикация — событие
переходное: архив есть, ассета нет, версия новая.

Но пользователь почти всегда в **устоявшемся** состоянии: версия уже опубликована, ассет
на месте, архив удалён предыдущим прогоном. Из десяти запусков девять — про уже сделанное.

Переходное состояние: 1 запуск. Устоявшееся: 9 запусков. Код писался под первое.

---

## 4. Почему тесты это пропускали

Ключевое, и самое неприятное для меня как автора тестов.

Фикстура в тестах строится естественным образом так:

```bash
make_zip "$D" "repo" "1.0.0" dot     # создали архив
run_deploy "$D"                       # прогнали
assert ...                            # проверили
```

Это **буквально первый прогон**. Архив на месте, версия новая, ассета нет. То есть
фикстура воспроизводит ровно то переходное состояние, под которое код и писался.

Тест подтверждал: «в состоянии, для которого я это писал, работает». И молчал о том,
работает ли в состоянии, в котором находится пользователь.

**Зелёный тест был правдой. Просто не про тот случай.**

---

## 5. Проверочный вопрос

Одна формулировка, которая ловит все шесть случаев. Задавать до выпуска, к каждому новому
шагу:

> **Сработает ли это на втором запуске подряд, когда входных данных для шага уже нет,
> а результат его прошлой работы всё ещё лежит на диске?**

Прогон по случаям:

| Случай | Ответ на вопрос |
|---|---|
| 1 | Нет: ассет уже есть → ветка мертва |
| 2 | Нет: функция ещё не объявлена |
| 3 | Нет: тег есть → версия пропущена |
| 4 | Нет: флаг не поставлен |
| 5 | Нет: архива нет → каталог не в списке |
| 6 | Нет: выход раньше блока |

Шесть из шести. Вопрос работает.

---

## 6. Правило для тестов: обязательная проверка второго прогона

Одного вопроса недостаточно — нужна механика, которая не зависит от того, вспомнил я
задать вопрос или нет.

**Новое поведение считается покрытым, только если есть утверждение о состоянии после
ВТОРОГО прогона.** Шаблон:

```bash
# первый прогон: переходное состояние
make_zip "$D" "repo" "1.0.0" dot
run_deploy "$D" >/dev/null

# второй прогон: устоявшееся состояние — здесь живёт пользователь
OUT="$(run_deploy "$D")"
assert ...   # поведение обязано сохраниться
```

Три уже существующих кейса делают это правильно и стали образцом: `A2` (идемпотентность),
`G12` (удаление опубликованного прошлым прогоном), `G13` пункт 7 (зеркало без архива).

## 7. Отдельно: цена в сессии

Не для самобичевания, а чтобы масштаб был зафиксирован.

- **Шесть итераций** «сделал → не работает → переделал». Каждая с выпуском версии,
  записью в журнал и прогоном на боевых репах.
- **Одна потеря данных**: у части релизов `portrait-of-taste` ассет удалился, а канонический
  не встал (случай 1 в связке с ошибкой сравнения имён). Восстановлено из тегов.
- **Один переполненный диск** — как следствие другого дефекта из этой же серии.
- **Доверие**: после четвёртого раза владелец обоснованно перестал верить формулировке
  «сделано» без своей проверки. Это дороже всего остального.

## 8. Остаточное наблюдение

Уборка зеркал рассматривает **любой** каталог, чьё имя разбирается как `<имя>-vX.Y.Z`.
В боевом прогоне под рассмотрение попал `Z-Library-3.2.0/` — сторонняя программа. Спасли
две защиты (нет `VERSION`; репы `Z-Library` нет на GitHub), но множество кандидатов шире,
чем нужно.

Не дефект — но если добавится седьмая защита или изменится порядок проверок, широкое
множество кандидатов станет опасным. Сузить до реп из `repos-map.md` — открытый пункт.
