# Реестр частых ошибок (pitfalls)

Повторяющиеся ошибки в рабочем процессе: кривые команды, привычки, грабли воркфлоу. Это **третий тип**
разбора рядом с инцидентами и расследованиями, но самого лёгкого веса.

Чем отличается от соседей:

- **Инцидент** (`incidents_summary.md`) — была реальная поломка/дефект и/или влияние. Полный разбор —
  отдельным файлом в `incidents/`.
- **Расследование** (`investigations_summary.md`) — реального дефекта НЕ оказалось (внешнее / артефакт
  / недопонимание); причина была неочевидна, её искали.
- **Pitfall (этот файл)** — повторяющаяся ошибка воркфлоу. Причина известна сразу, мистики нет,
  предмет репы не затронут. Это **не** отдельный файл-разбор, а ОДНА строка-урок: симптом → корень →
  как правильно → правило.

Заполняется АВТОМАТИЧЕСКИ (`00-infrastructure/20-knowledge-capture-protocol.md`) — как только ошибка
воркфлоу повторилась, строка сюда, не дожидаясь просьбы. Каждая запись становится переиспользуемым
правильным паттерном, чтобы не выводить его заново каждую сессию.

---

## Формат записи

```markdown
### PIT-NNN — <короткое имя> (YYYY-MM-DD)

- **Симптом:** <что увидели, как проявилось>
- **Корень:** <настоящая причина, а не поверхностная>
- **Как правильно:** <что делать впредь>
- **Правило:** <какое правило это кодифицирует>
```

## Универсальные грабли (применимы к работе в любой репе через Claude)

Эти примеры перенесены как база — они срабатывают при работе с любой репой в песочнице Claude и
экономят время. Пополняется по мере появления новых.

### PIT-001 — `find … && echo ЕСТЬ` лжёт: печатает «ЕСТЬ» и без находок

- **Симптом:** проверка существования файла через `find … -name X && echo ЕСТЬ` печатает «ЕСТЬ», даже
  когда файла нет — так можно ошибочно решить, что файл уже есть (и потерять/не создать нужный), или
  наоборот.
- **Корень:** `find` завершается с кодом `0` (успех) даже при нуле совпадений — сам поиск отработал
  корректно, просто ничего не нашёл. Оператор `&&` смотрит на код выхода, а не на наличие вывода.
- **Как правильно:** существование проверять `test -f <путь>` (или `[ -f … ]`), либо по **непустому
  выводу** (`OUT=$(find …); [ -n "$OUT" ]`), а не по факту, что `find` вообще запустился.
- **Правило:** проверять существование по результату, а не по коду выхода команды поиска.

### PIT-002 — `grep` в цепочке `&&` обрывает выполнение

- **Симптом:** команда вида `… && grep -c X file && next` — `next` молча не выполняется; счётчик/итог
  «не выводится».
- **Корень:** `grep` с НУЛЁМ совпадений возвращает код `1` → оператор `&&` обрывает весь остаток
  цепочки. Усугубление: кириллический вывод в pipe может дать битый UTF-8 и оборвать команду.
- **Как правильно:** не чейнить `grep` через `&&` — использовать `;` либо `grep … || true`; итоги
  брать из ГОТОВОГО файла (`tail`), а не хрупким `grep` на ходу; кириллицу читать через `python3`/
  `tail`, не через `grep` в `&&`-цепочке.
- **Правило:** повторная ошибка кодифицируется один раз; правильная команда переиспользуется.

### PIT-003 — движок переименования срезает ведущую точку у dotfiles (YYYY-MM-DD)

- **Симптом:** массовый нормализатор имён превращает `.gitkeep`/`.gitignore`/`.env.example` в
  `gitkeep`/`gitignore`/`env.example` — dotfile перестаёт работать (git его не видит как служебный).
- **Корень:** правило kebab-case/транслита применяется к имени целиком, не делая исключения для
  ведущей точки.
- **Как правильно:** ведущая точка — священна, нормализатор обязан её сохранять; kebab-case только к
  файлам-знаниям (md/pdf/картинки), НЕ к коду (`.py`/`.cpp`/`.sql` — импорты ломаются от дефисов).
- **Правило:** dotfiles и код не переименовываются вслепую; после массового rename — чинить ссылки в `.md`.
- **Источник:** `situations/2026-07-08-upakovka-arkhivov-v-repozitorii.md`.

### PIT-004 — «чистка ≠ долив»: распаковка зипа поверх клона оставляет старые файлы (YYYY-MM-DD)

- **Симптом:** после переименований/конвертаций распаковал полную версию поверх клона репы и запушил —
  старые (переименованные/удалённые) файлы остались, в репе задвоение.
- **Корень:** overlay поверх существующего дерева не удаляет то, чего в новой версии нет; git видит
  только добавления, а не переименования/удаления.
- **Как правильно:** клон → стереть рабочее дерево **кроме `.git`** → распаковать полную версию →
  `git add -A`. Тогда git фиксирует переименования/удаления/добавления одним чистым коммитом. Команды —
  одним копипаст-блоком, абсолютные пути, `|| continue`, без комментариев в строке; `rsync --delete`
  применять только с wrapper-директорией (см. `../../00-infrastructure/10-git-reference.md`).
- **Правило:** обновление репы через полную замену дерева, не через долив поверх.
- **Источник:** `situations/2026-07-08-upakovka-arkhivov-v-repozitorii.md`.

### PIT-005 — комментарий в строке команды zsh уходит в программу как аргумент (YYYY-MM-DD)

- **Симптом:** скопировал команду с пояснением в той же строке (`python3 analyze.py   # текущая оценка`)
  → скрипт падает с «нет файла лога: #» (или подобным) — `#` и слова после него прилетели как аргументы.
- **Корень:** в zsh опция `interactive_comments` по умолчанию **выключена** для интерактивной строки,
  поэтому `#` НЕ трактуется как начало комментария — весь хвост строки передаётся программе как argv.
  (Та же боль, что в `situations/2026-07-08-*` §10.10: «комментарий в строке — шелл подавился».)
- **Как правильно:** команды копировать **по одной, без комментариев в строке**; пояснения — в
  отдельных строках прозы, не в paste-блоке. Скрипты со своей стороны — **устойчивы к мусорному
  аргументу** (позиционный арг считать путём только если это реально существующий файл/`.csv`, иначе
  игнорировать) — так `analyze.py` и сделан.
- **Правило:** в инструкциях — чистые copy-paste-блоки без inline-комментариев; в скриптах —
  defensive-разбор argv.
- **Источник:** реальный прогон `reports/experiments/token-consumption/analyze.py` у пользователя.

### PIT-006 — `git add -A` уважает `.gitignore` → при заливке готового дерева файлы теряются (YYYY-MM-DD)

- **Симптом:** залил репу целиком из архива, `git add -A` + commit + push → на GitHub репа «пустая»
  (1 файл — сам `.gitignore`), остальное не попало в коммит.
- **Корень:** `git add -A` **уважает `.gitignore`**; если в корне широкие правила, всё содержимое молча
  выкидывается из индекса.
- **Как правильно:** когда цель — залить дерево целиком (из архива/сборки), добавлять **принудительно**:
  `git add -A -f`. Флаг `-f` обходит `.gitignore`, ничего не теряется.
- **Правило:** заливка полного дерева → всегда `git add -A -f`.
- **Источник:** `situations/2026-07-09-empty-repos-recovery.md`.

### PIT-007 — вложенная папка-обёртка после `unzip` → корень репы «пустой» (YYYY-MM-DD)

- **Симптом:** распаковал `base-repo.zip`, залил — в репе одна вложенная папка `base-repo/base-repo/…`,
  корень выглядит пустым.
- **Корень:** архив содержит одну корневую папку-обёртку; распаковали и залили **папку**, а не её
  **содержимое**.
- **Как правильно:** распаковать во временную папку; если внутри **ровно одна директория и нет файлов** —
  спуститься в неё и копировать оттуда (авто-разворот обёртки). Так делают `push_base_repo.sh`/`sync-all.sh`.
- **Правило:** после `unzip` — всегда разворачивать обёртку перед заливкой.
- **Источник:** `situations/2026-07-09-empty-repos-recovery.md`.

### PIT-008 — «пустая репа» на GitHub ≠ потеря данных (YYYY-MM-DD)

- **Симптом:** открыл GitHub, увидел пустой/однофайловый репозиторий → паника «всё стёрлось».
- **Корень:** почти всегда данные целы — это баг коммита (PIT-006 `.gitignore`) или вложенность
  (PIT-007), а не потеря. Данные живут в архивах (`~/Downloads/*.zip`), истории git и готовых сборках.
- **Как правильно:** первым делом `git log` (коммиты целы?) и `git ls-tree -r HEAD | wc -l` (что реально
  в дереве?), а не паника; после каждого пуша — автопроверка числом файлов (0/1 = баг). Архивы не
  удалять несколько дней после заливки — офлайн-бэкап.
- **Правило:** «пустая репа» → диагностика `git log`/`ls-tree`, не выводы; бэкап-архивы держать.
- **Источник:** `situations/2026-07-09-empty-repos-recovery.md`.

### PIT-009 — Info-ZIP превращает кириллические имена в literal `#Uxxxx` (2026-07-09)

- **Симптом:** после распаковки zip юниксовым `unzip` файлы называются `#U041a#U041e...md` вместо
  кириллицы; такие имена закоммитили — в репе на GitHub порча имён (так уехал весь кит
  `01-claude-context/` между v1.3.0 и v1.4.0).
- **Корень:** zip упакован без UTF-8 флага (бит 0x800); Info-ZIP не декодирует имена, а пишет
  escape-последовательности `#Uxxxx` прямо в имя файла.
- **Как правильно:** распаковывать через `python3` + `zipfile` с фиксом `cp437→utf-8` при отсутствии
  флага (рецепт в WATCHLOG academic-portfolio) и нормализацией NFC; перед `git add` проверять имена:
  `ls -R | grep '#U'` — пусто. Уже испорченное чинится декодером `#U(hex)→chr` (слияние v1.5.0).
- **Правило:** после любой распаковки кириллической репы — проверка имён на `#U`/mojibake до коммита.

### PIT-010 — деструктив в multi-line paste: `&&`-цепочка падает, а `rm`/`find -delete` выполняются не там (2026-07-09)

- **Симптом:** пользователь вставил блок «`git clone … && cd …` → `find … -delete` → …»; clone упал
  (папка существует), `cd` не выполнился, а деструктивные строки выполнились в ТЕКУЩЕЙ папке —
  вычищен `~/Downloads`, следом закоммичен снос репы (авария base-repo v1.2.0, восстановлено).
- **Корень:** в многострочной вставке каждая строка выполняется независимо от исхода предыдущей;
  `&&` защищает только внутри одной строки. Плюс `#`-комментарии в интерактивном zsh — аргументы
  (PIT-005).
- **Как правильно:** paste-блоки для пользователя — без деструктива вообще; замена дерева/чистка —
  только внутри скриптов с sanity-check маркеров (`push_base_repo.sh`, `publish.sh`) и fail-loud.
  Разбор — `reports/merges/merge_manifest_v1_5_0.md`.
- **Правило:** деструктивная команда никогда не идёт в копипаст-блок; только скрипт с проверками.

### PIT-011 — обрыв канала tool-call: `court` + сырой `<invoke>` вместо вызова (2026-07-13)

- **Симптом:** вместо исполненного инструмента в сообщение попадает видимый текст (литерал
  `court`, следом сырой `<invoke>`), ход обрывается, вызов не исполняется, результата нет.
  Идёт **сериями**: за сессию 12–13.07.2026 — трижды.
- **Корень:** сбой декодирования служебных токенов в рантайме ассистента. Первопричина — не
  в репе. Но **частота управляется поведением**: (1) ход, завершающийся вызовом; (2) сложные
  bash-команды с heredoc и вложенными кавычками; (3) **заражение из истории** — сломанный
  пример в контексте начинает воспроизводиться как текст, отсюда серии; (4) короткие
  ходы-пинги между обрывами.
- **Как правильно:** вызов инструмента — **никогда не последнее** в сообщении (ход
  заканчивается текстом + `present_files`); весь батч — за один ход; команды простые
  (тяжёлое — через `create_file` + запуск, а не heredoc); сломанные `<invoke>` из истории
  игнорировать, а не копировать; после мутирующих вызовов — **эмпирически** сверять
  фактические файлы (`grep`), потому что реальный вред — тихо пропущенный `str_replace`.
- **Правило:** глюк рантайма, но триггерится поведением → лечится механикой хода, а не
  обещаниями. Полная методичка — `02-methodology-library/tool_call_channel_failures.md`,
  вход — `00-CLAUDE-STOP.md` в корне.

### PIT-012 — живые токены в закоммиченном коде (2026-07-12)

- **Симптом:** `repo_audit.py` при первом прогоне нашёл в `academic-portfolio` рабочий VK
  access token сообщества (`main.py` чат-бота + дубль в `notes.txt`) и Telegram bot token
  (`alertmanager.yml` из лабы). Лежали месяцами, уехали в историю git.
- **Корень:** правило «секреты не коммитим» держалось на внимательности. Внимательность
  кончается раньше, чем коммиты.
- **Как правильно:** секреты — только в `.env` (+ `.env.example` в репу), для не-Python
  конфигов есть `*_file`-варианты (`bot_token_file`). Механическая защита: `.githooks/pre-commit`
  (`git config core.hooksPath .githooks`) + периодический `repo_audit.py`.
- **Правило:** **из git секрет не удаляется — он отзывается.** Порядок при утечке: отозвать у
  провайдера → выпустить новый → и только потом чистить файлы и историю. Обратный порядок
  бессмыслен: пока токен жив, он жив везде, куда успел попасть.

### PIT-013 — «temporarily unavailable» на Bash = outage классификатора, не кривая команда (2026-07-18)

- **Симптом:** нетривиальные Bash-команды (`zip`, `cp && zip`, `python3 -c …`) возвращают
  «claude-sonnet-5 temporarily unavailable, auto mode cannot determine the safety of Bash», а `echo` и
  read-only тулы (Read/Glob/Grep) работают. Ассистент повторяет идентичную команду ~15 раз и на каждый
  фейл пишет пользователю — читается как метание, бесит.
- **Корень:** внешний — классификатор безопасности авто-режима временно недоступен → команды, которые без
  него нельзя признать заведомо безопасными, отклоняются; тривиальные/read-only идут мимо классификатора.
  Это НЕ синтаксис команды и НЕ поломка шелла.
- **Как правильно:** распознать по сигнатуре (outage, не кривизна) → **не долбить**: ≥2–3 фейла → сменить
  тактику, а не повторять одно и то же. (а) свести к максимально простой одиночной команде; (б) backoff,
  не машинган; (в) `send_later`/фоллбэк + продолжить полезную read-only работу; проверить канал `echo ok`.
  Пользователю — один статус + план, не репорт каждого ретрая. Ценное держать на диске (файловые тулы идут
  мимо классификатора), под шелл оставлять только упаковку — её и откладывать.
- **Правило:** повторный фейл инструмента с «temporarily unavailable» → упростить+отложить, не повторять
  идентично; не пере-нарративить. Полный разбор — `incidents/bash_classifier_channel_outage_incident.md`
  (INC-BASH-CLASSIFIER-OUTAGE).
