# Пять нерешённых мест схемы с локальным git — что из них реально проблема

**Дата:** 09.09.2026

## Как это исследовалось

Пять параллельных субагентов, по одному на пункт, **каждый с правом ставить
эксперименты в песочнице** — а не только читать документацию. Шестой ушёл
на `git maintenance` отдельно. Проверки, давшие главные находки, делались
на живых репах этой машины, а не на выдуманных образцах: именно так
обнаружилась шестая проблема (§6), которой в исходном списке не было.

🔴 **Чего метод не даёт:** субагенты не знают состояния наших реп, пока
их об этом не спросить. Два пункта из пяти оказались несуществующими
именно после проверки на машине — из документации это не следовало никак.

> **Заказ владельца:** *«сделай про это ресёрч… как эти вещи решаются.
> например ты сказал что 5 пункт просто решается настройкой одной»*.

## §1. Две руки на публикации — единственная настоящая

**Механизм.** `flock(1)` из util-linux на macOS **нет**, но есть штатный
**`/usr/bin/lockf`** — BSD-обёртка над `flock(2)`. Питон ходит туда же
через `fcntl.flock`. Обе стороны берут один лок и взаимно исключаются.

```sh
lockf -k -t 0 "/tmp/publish-${REPO}.lock" ./deploy.sh "$@" || exit 75
```
```python
fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)   # BlockingIOError = занято
```

🔴 **Почему именно `flock`, а не `mkdir` или PID-файл.** Эксперимент
субагента: `mkdir`-лок после `kill -9` **остаётся навсегда** и блокирует
все последующие публикации. `flock` снимается ядром — застрявшего лока
не бывает по построению.

**Что проверять отдельно от лока.** Субагент указал на вероятную настоящую
причину инцидента 07.09: **непроверенный код возврата**. `git ls-remote`
без `--exit-code` возвращает 0 и на пустом выводе — проверка «есть ли тег»
всегда истинна. Плюс гарантию даёт не проверка перед push, а
`--force-with-lease=refs/tags/$TAG:` на самом push: сравнение делает сервер
атомарно.

**Где не работает:** лок advisory — процесс, который его не спрашивает,
опубликует спокойно. Это защита между **согласными** сторонами, чем наш
случай и является.

## §2. Ленивая докачка — запрещать не нужно

`GIT_NO_LAZY_FETCH=1` документирован (`man git`), с git 2.45, конфиг-эквивалента
**нет**. Эксперимент субагента на чистом partial-клоне:

| работает под запретом | падает |
|---|---|
| `status`, `diff`, `commit`, `push` | `blame`, `log -p`, `log --stat` |
| `log`, `grep` по дереву, `fetch`, `gc` | `show <коммит>`, `diff <rev> <rev>` |

🔴 **Опаснее всего:** `git checkout <rev> -- <file>` под запретом **портит
рабочее дерево** — файл исчезает, индекс уезжает на недоступный блоб.
И `git backfill` (инструмент починки) сам блокируется переменной.

**Вывод: глобально не ставить.** Вместо запрета — **предзагрузка**
на нормальной сети:

```sh
git backfill --min-batch-size=5000
git rev-list --objects --all --missing=print | grep -c '^?'   # ждём 0
```

После неё докачивать нечего, и запрет становится не нужен. 🔴 `backfill`
**не возобновляется после обрыва** — на хотспоте это аргумент за маленький
batch size.

## §3. `git maintenance` — ресёрч отдельным агентом

Задача ушла шестому агенту, результат придёт отдельно. Что известно
на момент записи: в расписании по умолчанию есть **сетевая задача
`prefetch`, ежечасно**; отключается `maintenance.prefetch.enabled=false`.
Обслуживание для репы, которая почти не растёт, скорее всего избыточно.

## §4. NFD/NFC — у нас не проявляется

**Замер по нашим репам:**

| репа | NFD-путей в индексе git |
|---|---|
| `base-repo`, `it-base`, `exam-kit`, `ml-base` | **0** |

На диске нашёлся **один** файл с NFD-именем (PDF с русским названием
в `it-base`), и git показывает его правильно — ложного diff нет.

**Почему:** `core.precomposeUnicode=true` стоит по умолчанию и нормализует
имена при чтении с диска. Проблема, названная корнем ложных diff,
у нас закрыта настройкой.

🔴 **Но найдено смежное, важное для наших скриптов.** APFS —
normalization-**insensitive**: два файла с разной нормализацией одного
имени создать **нельзя**, второй молча перезапишет первый. Отсюда
классический симптом «один файл показан дважды: `M` и `??`» — это одна
физическая сущность в двух ролях.

**Дешёвое лечение сверочных скриптов, без единого коммита:** нормализовать
пути через `unicodedata.normalize('NFC', path)` **перед сравнением**.
Это снимает ложные DIFF сразу.

🔴 **Историю переписывать НЕ надо** — цена (все SHA меняются, все копии
пересоздаются) несопоставима с выгодой.

## §5. Time Machine — проблемы не существует

**Проверка на этой машине:**

```
tmutil latestbackup → Failed to mount destination
tmutil listbackups  → No machine directory found for host
mdutil -sa          → Indexing disabled
```

**Бэкапы не идут вообще** — диск не подключён, работают только локальные
APFS-снапшоты. Spotlight-индексация выключена. Пункт был написан
для ситуации, которой нет.

🔴 **И два моих утверждения оказались неверны:**

1. **«TM перепишет packfile целиком»** — неверно дважды. Packfile при
   коммите **вообще не меняется** (только при `gc`/`repack`), а TM
   на APFS делает **поблочное** копирование, не пофайловое.
2. **«Решается одной настройкой»** — неверно. Time Machine **не понимает
   шаблонов**: исключить «все каталоги `.git`» одной настройкой нельзя,
   нужен цикл по репам. Хуже: обычное исключение (`tmutil addexclusion`)
   **теряется при пересоздании `.git`** — проверено экспериментом. Путевое
   (`-p`) переживает, но требует `sudo` и Full Disk Access.

**Что теряется при исключении `.git`,** если история на GitHub:
незапушенные коммиты · локальные ветки без upstream · `git stash` ·
**reflog** · `.git/config`. Рабочее дерево при этом бэкапится.

**Приоритет:** сначала починить сам Time Machine (сейчас его нет),
исключения — вопрос третьего порядка.

## §6. 🔴 ШЕСТАЯ ПРОБЛЕМА, КОТОРОЙ НЕ БЫЛО В СПИСКЕ

Субагент по partial clone предупредил, и проверка подтвердила:
**`extensions.partialClone` не был выставлен ни в одной репе.**

Флаг ставит только `git clone`, а мы заводим репы через `git init` +
`fetch` — он и не появился.

**Чем это грозило.** Без флага git считает репу не частичной,
а **повреждённой**. На любую команду, которой нужен нескачанный объект,
он ответил бы не «сейчас докачаю», а `unable to read sha1 file` — то есть
это выглядело бы как порча репозитория, хотя всё цело.

| репа | недостающих объектов |
|---|---|
| `it-base` | **1530** |
| `ml-base` | 877 |
| `exam-kit` | 62 |
| `base-repo` | 0 (полный клон) |

**Исправлено** во всех трёх и встроено в `git_adopt.py`; канарейка
стережёт наличие строки.

> **Проблема, которой не было в списке, оказалась опаснее всех пяти,
> которые в нём были.** Список нерешённого составлялся из того, что вахта
> *заметила* — а этого она не заметила, потому что симптом ещё не наступил.

## §7. 🔴 ГЛАВНОЕ: на этой машине — ОРИГИНАЛ, а не копия

**Владелец 09.09.2026, дословно:** *«САМОЕ ГЛАВНОЕ ТО ЧТО У МЕНЯ НА МАКЕ —
ЭТО И ЕСТЬ ЭТАЛОН. не копия. не частично. ОРИГИНАЛ»*.

Это переворачивает оценку рисков. Обычный git-репозиторий — **копия**
удалённого: испортил рабочее дерево → `git checkout` вернул из истории.
Здесь наоборот: **история на GitHub отстаёт от диска**, и любая команда,
которая «восстанавливает файлы из истории», на деле **откатывает эталон
к устаревшему состоянию**.

**Насколько отстаёт — замерено прямо сейчас:**

| репа | расхождений с GitHub |
|---|---|
| `it-base` | **211** файлов |
| `exam-kit` | **214** файлов |

Это не мусор, а результат локальной раздачи канона, которая на GitHub
не уезжала. **Каждое из этих расхождений — то, что есть только на диске.**

### Команды, которые уничтожают эталон

| команда | что делает | цена ошибки |
|---|---|---|
| `git reset --hard` | 🔴 **затирает рабочее дерево** версией из истории | все локальные правки |
| `git checkout <rev> -- <путь>` | 🔴 перезаписывает файл старым | этот файл |
| `git checkout .` / `git restore .` | 🔴 то же по всему дереву | все незакоммиченные правки |
| `git clean -fd` | 🔴 **удаляет неотслеживаемые** | 102 новых файла в `exam-kit` |
| `git stash` | прячет правки в `.git` | обратимо, но неочевидно |
| `git pull` / `merge` / `rebase` | трогают дерево | зависит |

🔴 **`git clean -fd` здесь опаснее всего.** В обычном репозитории
неотслеживаемые файлы — мусор сборки. Здесь это **новые документы,
которых ещё нет в истории**: в `exam-kit` таких 102.

### Чем это отличается от обычного проекта

| | обычный репозиторий | наш случай |
|---|---|---|
| источник правды | история (GitHub) | 🔴 **рабочее дерево (диск)** |
| `reset --hard` | штатное восстановление | 🔴 **потеря данных** |
| неотслеживаемые файлы | мусор | 🔴 **новые документы** |
| «привести к origin» | норма | 🔴 **откат эталона** |

### Что защищает сейчас

- **`publish.py` не зовёт ни одну из опасных команд** — только `add`,
  `commit`, `tag`, `push`. Проверено чтением исходника.
- **`git_adopt.py` не зовёт `checkout` и `reset`** — канарейка стережёт
  это в исходнике и падает, если вызов появится.
- **Заведение git не трогает файлы:** `read-tree` + `update-ref` ставят
  индекс и HEAD, дерево остаётся как было.

### Чего защиты НЕТ

🔴 **Ничто не мешает выполнить опасную команду вручную.** Инструменты
чисты, но `git reset --hard` из терминала сработает как обычно.
Механическая защита — тема отдельной работы (кандидаты: `pre-commit`-хук
не поможет, нужен `reference-transaction` или обёртка над git).

## §8. Что осталось неизвестным

- **`git maintenance`** — ресёрч по нему шёл отдельным агентом и на момент
  записи не вернулся. Точный состав задач, расписание и способ включения
  без сетевого `prefetch` не подтверждены экспериментом.
- **Цена `git backfill` в трафике** для репы в сотню МБ — субагент честно
  отказался экстраполировать, реальных чисел нет.
- **Текст отказа GitHub при нарушении tag ruleset** — в документации
  не найден, экспериментом не проверялся (сетевых операций к github.com
  субагенты не делали).
- **Почему macOS-`shlock` не крадёт заведомо мёртвый лок**, вопреки своему
  же man — расхождение зафиксировано, причина в исходниках Apple не искалась.
- **Поведение `git stash` поверх rename-only коммита** и взаимодействие
  с `sparse-checkout` — не проверялись.
- **Механическая защита эталона от `reset --hard` / `clean -fd`** —
  вариантов не проверял ни один. Это следующая работа, и она важнее
  остальных пунктов этого списка.
