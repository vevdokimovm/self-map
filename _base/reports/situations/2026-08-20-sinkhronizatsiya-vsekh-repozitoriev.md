# Синхронизация всех 57 репозиториев в локальную копию + находка по диску

> Формат — `reports/situations/README.md`. Инфраструктурная кампания: было → сделали → что
> пошло не так → уроки → открытые шаги.

## 1. Было

Задача — синтезировать служебки по всей системе реп, для чего нужна свежая локальная копия
**актуального** содержимого всех 57 репозиториев GitHub-аккаунта `vevdokimovm`. Прямая проблема:
GitHub Releases не годятся источником — тег/релиз ставится не на каждый коммит, правка одного-двух
файлов без бампа версии осталась бы незамеченной в релизном zip (пример на практике: `base-repo`
сам недавно словил именно это — правка карты реп была только в локальной рабочей копии и не
пушилась, релиз её не видел).

## 2. Что сделали

1. **`scripts/sync_repos_zip.py`** — синк через `codeload.github.com/.../zip/refs/heads/<branch>`
   (то же самое, что кнопка «Code → Download ZIP» на GitHub — снимок текущего состояния
   default-ветки, не привязан к тегам). Список репозиториев — `gh repo list --json`, доступ к
   приватным — `gh auth token`.
2. Первый прогон: **57/57 ok, 0 ошибок**, итоговый объём **1.9 GB** в
   `Documents/система_репозиториев/`.
3. **`scripts/verify_repos_zip.py`** — независимая проверка, не доверяющая статусу самого
   sync-скрипта: тянет полное дерево файлов default-ветки через GitHub Git Trees API (путь + точный
   размер каждого blob'а) и построчно сверяет с тем, что реально лежит на диске — пропущенные
   файлы, лишние файлы, расхождения по размеру (= разное содержимое).
4. Точечная проверка на `portrait-of-taste` (самая тяжёлая репа, много медиа): локальная копия
   384 MB практически совпала с размером zip-ассета релиза (391 MB сжатый) — подтверждение до
   API-верификации, что скачивание полное, не усечённое на середине.
5. **Полный прогон верификации:** первый заход — 53/57 чисто, 4 репы с расхождением, но во всех
   четырёх `missing=0` и `size_mismatch=0` — только «лишние» локальные файлы. Разбор показал: это
   исключительно `.DS_Store` (артефакты macOS Finder, появляются при заходе в папку через Finder/
   `du`), не часть содержимого репозитория. После добавления игнор-листа в `verify_repos_zip.py` и
   чистки `.DS_Store` — повторный прогон: **57/57 полное совпадение, 0 расхождений**. Каждый файл
   каждой репы подтверждён байт-в-байт (точный размер blob'а с GitHub Git Trees API против размера
   на диске).

## 3. Что пошло не так / важная находка

**Диск ушёл с 13.4 GB до 10.8 GB свободного** — синк 57 репозиториев съел почти 2 GB на машине,
где `00-infrastructure/52-hardware-baseline.md` уже фиксировал диск как узкое место (был 5.3%
свободного до синка, стало ещё меньше). Это не поломка самой операции — синк отработал полностью
и корректно — но прямое **усиление** уже задокументированного риска, а не абстрактная угроза «на
будущее»: следующая тяжёлая операция (ещё один синк, автономный прогон по `51`, апдейт репозитория
с медиа) может реально упереться в «no space left on device».

Второй момент, не поломка, а недопонимание в процессе: пользователь увидел размер
`portrait-of-taste` на 100 MB и заподозрил недокачку — на деле это был снимок папки **в момент**,
когда скрипт её ещё распаковывал (`shutil.move` временной директории в целевую — не мгновенная
операция для 384 MB). Разница между «скрипт ещё работает» и «скрипт закончил и результат неполный»
выглядит одинаково при беглом взгляде на Finder/`du` — стоило сразу дождаться завершения фонового
процесса перед тем, как показывать промежуточный размер.

## 4. Уроки (переиспользуемые)

1. **Zip default-ветки, не Releases — для «актуальное состояние», не «последняя помеченная
   версия».** Правки без тега — обычное дело в этой системе (WATCHLOG-дисциплина не требует релиза
   на каждый коммит); синк, полагающийся на релизы, будет систематически отставать.
2. **Не доверять «0 failed» без независимой проверки.** Статус самого синк-скрипта — это его
   собственная оценка (HTTP 200 + zip распаковался), не сверка с истиной. Отдельный верификатор
   через Git Trees API — второй независимый источник правды, дешёвый (только метаданные, не сами
   файлы). На практике это оказалось не формальностью: первый прогон верификации нашёл
   расхождения в 4 репах из 57 — синк-скрипт молча считал их «ok».
3. **«DIFF» ≠ «неполная копия» — разбирать природу расхождения, не паниковать.** Все 4 расхождения
   оказались `missing=0`/`size_mismatch=0`, только «лишние» локальные `.DS_Store` — макОС-артефакт,
   не потеря данных. Разница между «не докачал» и «на диске завёлся посторонний файл» требует
   прочитать список расхождений, не остановиться на факте «DIFF».
3. **Промежуточный размер папки во время фоновой операции — не показатель.** Проверять
   завершённость по коду выхода процесса, не по текущему `du`/размеру в Finder.
4. **Тяжёлые массовые операции синка — держать в уме бюджет диска заранее**, не постфактум.
   `52-hardware-baseline.md` уже предупреждал — стоило проверить свободное место **до** запуска
   57-репозиторного синка, а не после.

## 5. Открытые шаги

- Освободить диск — было приоритетом до синка (`52` §4), теперь тем более: 10.8 GB свободного на
  машине, где `Documents/система_репозиториев/` сама весит 1.9 GB и будет расти при каждом
  повторном прогоне (если не чистить старые снимки перед новым синком — `unpack()` в скрипте уже
  удаляет старую версию папки перед распаковкой новой, так что рост не накопительный per-run, но
  сама 1.9 GB остаётся постоянным вычетом из и без того малого свободного места).
- Результат `verify_repos_zip.py` (запущен отдельно) — если найдутся расхождения, разобрать
  отдельно, не как часть этого репорта (расследование, если причина неочевидна).
- Рассмотреть: держать ли `система_репозиториев/` постоянно на диске, или синкать → анализировать →
  удалять цикл, если места критически не хватает.
