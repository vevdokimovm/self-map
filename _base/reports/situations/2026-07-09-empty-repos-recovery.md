# Ситуация-репорт: пустые репы после заливки base-repo — паника и восстановление

> **Рубрика:** «Разбор ситуации и какие уроки я вывел». Выпуск 2.
> **Дата:** 9 июля 2026. **Тяжесть:** высокая (казалось, что потеряны все данные; по факту — не потеряно ничего).

## 1. Что делали

Вставляли инфраструктурный `base-repo` в каждую из 10 реп системы как папку `00-infrastructure/`, приводили всё к единой нумерованной структуре (`00-/01-/02-`), плюс подключали 11-ю репу (christ-walk). Заливка на GitHub шла скриптом: клон → замена рабочего дерева → `git add` → commit → push.

## 2. Что пошло не так

Два бага в командах заливки, один за другим:

**Баг №1 — `.gitignore` съел файлы.** В корне некоторых реп лежал `.gitignore` с широкими правилами. Обычный `git add -A` уважает `.gitignore`, поэтому в коммит попал только сам `.gitignore`, а всё содержимое — нет. На GitHub репа выглядела пустой (legal, christ-walk: 1 файл).

**Баг №2 — вложенная папка-обёртка.** После первого фикса `unzip` распаковал архив так, что всё легло на уровень глубже: `base-repo/base-repo/...`. Корень репы снова выглядел «пустым» — там была только одна вложенная папка.

**Итог для пользователя:** он открыл GitHub, увидел пустые репозитории и решил, что я стёр все его данные. Сильная паника, злость, слёзы — по делу: это его многолетние базы знаний.

## 3. Что было на самом деле

**Данные не терялись ни на секунду.** Они всё время существовали в трёх местах:
- в архивах, которые пользователь скачал (`~/Downloads/*.zip`);
- в истории git (коммиты никуда не делись);
- в моих готовых сборках.

Диагностика (`git log`, `git ls-tree`, `ls -la`) сразу показала правду: коммиты на месте, просто в них попало не то (баг №1) или всё уехало во вложенность (баг №2).

## 4. Как починили

Финальный скрипт заливки, закрывающий оба бага разом:
- распаковка во временную папку + **авто-разворот обёртки** (если внутри одна папка — берём её содержимое) → нет вложенности;
- **`git add -A -f`** — флаг `-f` добавляет файлы принудительно, мимо `.gitignore` → ничего не теряется;
- абсолютные пути + пропуск при отсутствии архива/клона → нет слепых удалений.

Результат — проверка числа файлов по всем 11 репам: academic 1283, it-base 2296, self-map 480, health-vault 378, family 275, legal 230, edu-base 219, christ-walk 167, truth-seeking 126, misc-vault 111, base-repo 108. Ни одного нуля. Полностью восстановлено.

## 5. Уроки

**Технические (git):**
1. **`git add -A` уважает `.gitignore` — это ловушка при заливке готового дерева.** Когда цель — залить репу целиком из архива, добавлять надо принудительно: `git add -A -f`. Иначе широкий `.gitignore` молча выкидывает файлы из коммита.
2. **Всегда разворачивать обёртку при `unzip`.** Архив может содержать одну корневую папку. Заливать надо *содержимое*, а не папку. Паттерн: распаковать во временную, если внутри ровно одна директория — спуститься в неё, копировать уже оттуда.
3. **После каждого пуша — автопроверка `git ls-tree -r HEAD | wc -l`.** Число файлов ловит оба бага мгновенно: `1` = сработал .gitignore, «всё в одной папке» = вложенность. Не полагаться на глаз по вебу.
4. **«Пустая репа» на GitHub почти никогда не значит потерю.** Первым делом `git log` (коммиты целы?) и `git ls-tree` (что реально в дереве?), а не паника.

**Процессные:**
5. **Бэкап существует всегда, если есть архивы.** Данные лежали в трёх местах. Правило на будущее: **не удалять `~/Downloads/*.zip` минимум несколько дней после заливки** — это офлайн-бэкап всех реп.
6. **Тестировать деструктивную команду на одной репе, потом на всех.** Массовый цикл по 11 репам множит одну ошибку на 11. Сначала одна — проверка — потом остальные.
7. **Отдавать пользователю самопроверку вместе с решением.** Не «я всё починил», а команда-счётчик, которая покажет правду по каждой репе. Доверие строится на проверяемости.

**Человеческие:**
8. **Когда человек в панике за свои данные — первым делом снять страх фактами, а не объяснять причину.** Пользователь прямо сказал: «мне насрать на причину, просто почини». Правильно: сразу дать рабочий фикс + напомнить, что данные целы (в архивах и истории), а разбор причин — потом. Я местами лез в объяснения, когда нужно было чинить. Это раздражало по делу.
9. **Признавать факап прямо, без самоуничижения и без оправданий.** Ошибка в командах — моя. Но данные не потеряны, и путь назад всегда есть. Спокойствие и проверяемость важнее извинений.

## 6. Что сделано, чтобы не повторилось

- Написан `sync-all.sh` (лежит в `base-repo/00-infrastructure/`): обновляет `00-infrastructure` во всех репах с обеими защитами (`-f` + авто-разворот обёртки), пушит только изменённое, в конце печатает счётчик файлов. Есть `--dry-run` и `--no-push`.
- Зафиксировано правило бэкапа архивов и правило автопроверки числом файлов.
