# ТЗ: единый деплойер репозиториев (`templates/deploy.sh`)

> ⚠️ **Это исторический документ** — ТЗ на момент консолидации восьми скриптов.
> Действующий контракт поведения — `templates/deploy-SPEC.md`. Здесь оставлено то,
> ради чего документ ценен: постановка задачи и почему решения приняты именно такие.

**Статус:** реализовано · **Версия скрипта:** поставляется в `base-repo` v1.13.0
**Дата:** 2026-07-24 · **Заменяет:** 8 предыдущих скриптов (см. `reports/merges/scripts_consolidation_report.md`)

## 1. Проблема

К июлю 2026 в системе накопилось **восемь** скриптов деплоя, написанных в разное время под разные
частные случаи: `publish.sh`, `deploy_all.sh`, `deploy_from_zip.sh`, `deploy_all_versions.sh`,
`commit_to_main.sh`, `commit_all_versions.sh`, `push_archives.sh`, `push_base_repo.sh`. Каждый умел
свой кусок и по-своему ошибался. Симптомы, которые это давало:

- нельзя вспомнить, какой скрипт запускать под текущую задачу;
- релизы в разных репах оформлены по-разному (где-то заголовок без тезиса, где-то описание-заглушка
  `Release 1.0.0`, где-то нет приложенного архива);
- часть скриптов носила описания релизов **зашитыми в код** — то есть при каждом релизе скрипт надо
  было править;
- периодические сбои «архив не пушится» без внятной причины;
- случай, когда коммит прошёл, а тег/релиз — нет.

**Формулировка заказчика:** «мне НУЖЕН ОДИН РАБОЧИЙ ФУЛ ПРУФ СКРИПТ для всех репов. ОДИН. который
делает всё, учитывает лучшие практики прошлых версий, ничего старое не ломает, а просто пропускает
или фиксит то, что не по стандарту».

## 2. Требования

### 2.1. Функциональные

| # | Требование | Как реализовано |
|---|---|---|
| F1 | Один скрипт на всю систему | `templates/deploy.sh`, остальные — в `templates/_archive/` |
| F2 | Запуск одной командой, папка = где лежит скрипт | `DIR="${1:-$SELF_DIR}"`; `zsh ~/Downloads/deploy.sh` |
| F3 | Найти все версионные архивы в папке, сгруппировать по репам | шаг 1, инвентаризация в `$INDEX` |
| F4 | Публиковать версии по возрастанию SemVer | числовая сортировка `sort -t. -k1,1n -k2,2n -k3,3n` |
| F5 | Нет репы — создать (приватную по умолчанию) | `gh repo create`, флаг `PRIVATE` |
| F6 | Чистая замена дерева, а не долив поверх | снос всего кроме `.git`, затем `cp -a` |
| F7 | Коммит → тег → push → GitHub Release | шаги 2B–2D |

| F9 | Канонический ассет `<repo>-vX.Y.Z.zip` на каждом релизе | §4 стандарта 42 |
| F10 | Чинить старые релизы, сделанные не по стандарту | режим `REPAIR`, заглушки перезаписываются |

| F12 | Регистрировать новую репу в `repos-map.md` + история карты | шаг 3 |
| F13 | Принимать исторический нейминг архивов | §2.3 |
| F14 | Цветной вывод | ANSI с детектом TTY, `NO_COLOR` |
| F15 | Режим плана без изменений | `DRY=1` |

### 2.2. Нефункциональные

- **Идемпотентность.** Повторный прогон на тех же данных не делает ничего. Проверяется тестом 3.
- **Устойчивость батча.** Сбой на одной версии/репе не роняет остальные (тест 22).
- **Fail loud, not silent fix.** Проблемы, которые скрипт не вправе чинить сам (тег указывает на
  чужое дерево — переписывание истории опубликованного тега), выводятся отдельным блоком
  «ТРЕБУЕТ ТВОЕГО РЕШЕНИЯ» и остаются человеку.
- **Никакой порчи данных.** Ни при каком сценарии ошибки скрипт не должен разрушить существующую
  репу. Дерево трогается только после подтверждения маркеров корня.
- **Работа под РФ-сетью.** Ретраи с экспоненциальным backoff на сетевых операциях (TLS-таймауты
  к GitHub — регулярное явление).
- **Совместимость.** Запускается через `zsh` (macOS по умолчанию) и `bash`.

### 2.3. Нейминг архивов

Канон — **точки**: `<repo>-vX.Y.Z.zip`. Но исторические ошибки принимаются, чтобы старые архивы
не выпадали из системы:

| Принимается | Пример |
|---|---|
| канон | `dota-dossier-v2.12.0.zip` |
| подчёркивания в версии | `base-repo-v1_11_0.zip` |
| дефисы в версии | `repo-v1-2-0.zip` |
| подчёркивание как разделитель | `repo_v1.2.0.zip` |
| без префикса `v` | `repo-1.2.0.zip` |
| две части версии | `repo-v2.7.zip` → читается как `2.7.0` |
| мусорные хвосты ОС | `repo-v1_2_0__copy_.zip`, `repo-v1.2.0 (1).zip` |

Всё неканоничное **обрабатывается**, но помечается в выводе строкой `→ канон: <repo>-vX.Y.Z.zip`.
Канонический ассет в релизе **всегда** с точками, независимо от имени исходного файла.

## 3. Ключевые проектные решения

**Р1. Единственный источник описания — `CHANGELOG.md`.** Прежние скрипты держали текст релиза в
себе. Это означало правку кода на каждый релиз и рассинхрон между историей в репе и текстом на
GitHub. Теперь секция версии пишется один раз в CHANGELOG, а скрипт достаёт из неё и тело, и тезис
для заголовка.

**Р2. Парсер CHANGELOG — на python, а не на `sed`/`awk` в пайпе.** Описания на русском, с em-dash
и эмодзи. Пайп-обработка регулярно била UTF-8. Python читает файл и пишет `--notes-file`.

**Р3. Предполётная проверка архива до создания репы.** Проверка «битый/мало файлов/нет README/
VERSION≠имени» делается по списку файлов (`unzip -Z1`, без распаковки) на этапе инвентаризации.
Иначе плохой архив успевал породить на GitHub пустую репу-сироту.

**Р4. Маркеры корня до деструктива.** Дерево репы очищается только после подтверждения, что
распакованный корень — действительно репа (есть `README.md`, файлов больше порога). Историческая
причина: один из прежних скриптов на плоском архиве снёс содержимое репы.

**Р5. Заморозка опубликованного.** Тег и релиз неизменяемы (`21-revision-protocol`). Скрипт
исправляет только заглушки; осмысленный текст не перезаписывает без явного `FORCE=1`.

## 4. Критерии приёмки

1. Все 30 кейсов регрессионного набора зелёные: `bash tests/test_deploy.sh` → 89 проверок.
2. Боевой прогон на реальных архивах: дерево каждого тега соответствует своей версии, мусора ОС
   в дереве нет, папка-обёртка развёрнута, ассет назван канонически.
3. Повторный прогон не производит изменений.
4. `DRY=1` не создаёт ни репы, ни коммита, ни релиза.
5. Ни один сценарий из набора не приводит к потере данных в существующей репе.

---

## 5. Что осознанно НЕ входит

- **Автоматическая починка битой истории тегов.** Только сигнал человеку: переписывание
  опубликованного тега — решение, а не операция.
- **Генерация текста CHANGELOG.** Скрипт доставляет, а не сочиняет. Нет секции — говорит об этом.
- **Работа без `gh`.** Без GitHub CLI дерево и теги уезжают, релизы — нет; скрипт предупреждает.
- **Мультиаккаунтность.** Один `OWNER` на прогон.
