# Гипотеза: модель расхода токенов Claude (живая, v0.1)

> Текущая рабочая модель «сколько токенов/лимита стоит запрос и от чего это зависит». Ведётся по
> методологии `../../../00-infrastructure/28-empirical-experiment-methodology.md`. **Не истина —
> гипотеза**, сходящаяся с данными. Живой narrative-контекст (якоря, тариф, промо) — в
> `../../../00-infrastructure/16-limits-empirical-estimate.md`; здесь — операционная модель + факторы +
> что мерить. Автоснимок текущей оценки из данных даёт `python3 analyze.py`.

Единица: **Opus-эквивалент** расхода лимита (Opus 4.8 = 1.0×). План: **Pro**.

---

## 1. Целевые величины (TARGET)

- `T_ctx` — токены контекста, занятые ходом (окно 200K, модель-независимо).
- `C` — расход лимита за ход (что деплетит бар сессии/недели) = `M × работа`.

### 🆕 F10 — нагрузка и время суток: заведено 22.08.2026 по вопросу владельца

Фактора не было среди `F1`–`F9` вовсе — и это была дыра, а не осознанное исключение.
Вопрос владельца: «бывает час пик, много людей — и лимит кончается быстрее».

**Прежде всего разводятся три величины, которые под этим смешивают:**

| Величина | Зависит от нагрузки? | Почему |
|---|---|---|
| **Цена хода в токенах** | 🔴 **нет, по построению** | `cache_read` = размер контекста, выход = длина ответа. Это арифметика, сервер её не меняет |
| **Задержка ответа** | 🟡 **вероятно да** | очередь и доступная ёмкость — то, что задержка и отражает |
| **Скорость исчерпания лимита** | 🟢 **зависела — до 06.05.2026** | см. ниже |

**Про лимит — факт с датой, а не догадка.** 6 мая 2026 Anthropic объявил три изменения
разом: удвоение пятичасовых лимитов Claude Code для Pro/Max/Team/Enterprise ·
**снятие урезания лимитов в часы пик для Claude Code на Pro и Max** · существенное
повышение API-лимитов для Opus. Поводом названа сделка по вычислительным мощностям
(Colossus 1, >300 МВт).

> **Механизм существовал и был убран.** Интуиция владельца верна ретроспективно:
> до 06.05.2026 «в час пик лимит кончался быстрее» было **правдой для Claude Code Pro/Max**.
> С этой даты — нет.

🔴 **Граница утверждения:** снято **для Claude Code на Pro и Max**. Про веб-интерфейс,
про другие планы и про поведение при аварийной нагрузке официальная формулировка
ничего не говорит — **это не «нигде нет», это «не проверено»**.

**Про задержку — свой замер, и он неубедителен.** Прогон `load_probe.py` по шести
собственным логам: **767 реплик**, десять часов суток, задержка нормирована на объём
выхода, медиана (среднее перекосил бы один тяжёлый ход).

| час UTC | реплик | с/1к токенов |
|---|---|---|
| 21 | 83 | **13.8** ← минимум |
| 3 | 183 | 15.2 |
| 9 | 55 | 18.2 |
| 20 | 84 | 20.1 |
| 19 | 59 | 21.4 |
| 8 | 14 | **22.1** ← максимум |

Размах **×1.6** — и **атрибутировать его нагрузке нельзя**:

- часы различаются **составом работы**, а не только загрузкой (в 2–4 UTC шло сплошное
  чтение чужих реп, в 19–22 — правка базы); нормировка на выход снимает объём,
  но не глубину рассуждения;
- максимум стоит на часе с **14 репликами** — это шум;
- картина **не ложится ни на одно окно пика**: минимум и максимум оба попадают
  в американский день.

**Статус F10: 🔴 приор.** Разделяющий опыт: один и тот же короткий эталонный запрос,
прогоняемый в фиксированные часы несколько дней подряд, — тогда состав работы постоянен
и остаётся только время. Инструмент для замера есть:
`reports/experiments/token-consumption/load_probe.py`.

## 3. Текущая модель (DECOMPOSE)

### 🔴 Замер 02.09.2026 — самая длинная сессия в реестре, и она опровергла ожидание

| Величина | Значение | Прежний рекорд |
|---|---:|---:|
| ходов главного треда | **3202** | 2090 |
| прочитано из кэша | 1 827 919 766 | — |
| hit rate | **98.9 %** | 99.3 % |
| макс. контекст | 999 761 | — |
| прирост на ход | **62 токена** | — |
| падений контекста | 6 | — |

**Что подтвердилось:** прирост контекста на ход остаётся малым (62 токена),
кэш держит почти всё (98.9 %), и это при сессии в полтора раза длиннее прежней.
Гипотеза о линейном росте цены хода от контекста тоже держится: ×6.5
на диапазоне 50 000…975 000.

### 🔴 Замер 03.09.2026 разошёлся с этим в 22 раза — и объяснение найдено

Вахта A (`auto-watch-A-images`), 609 ходов, макс. контекст 878 377:

| Величина | 02.09 (3202 хода) | **03.09 (609 ходов)** | разница |
|---|---:|---:|---|
| hit rate | 98.9 % | **99.0 %** | — |
| **прирост на ход** | **62 токена** | 🔴 **1370 токенов** | **×22** |
| рост цены хода | ×6.5 (50K…975K) | ×4.6 (25K…875K) | сопоставимо |

**Не противоречие, а разная работа.** 62 токена — сессия, которая **читает
и правит текст**: контекст растёт на разницу между ходами. 1370 — сессия,
которая **читала изображения**: за ночь разобрано 5361 кадр очереди,
из них около сорока открыто в кадрах.

🔴 **Изображение стоит контекста как страница текста, но не кэшируется
повторно так же охотно** — каждый новый кадр это новый префикс. Отсюда
и прирост: не «сессия хуже держит контекст», а «в неё вложено принципиально
другое содержимое».

**Практический вывод, которого не было в §3:** планируя вахту с разбором
изображений, считать бюджет по **1000–1500 токенов на ход**, а не по 62.
На 609 ходах это 878K контекста против 38K, которые дала бы текстовая работа
той же длины — **разница в двадцать раз при одинаковом числе ходов**.

**Чего замер не показывает:** сколько именно стоил один кадр. `session_metrics.py`
не различает источники прироста, а `isSidechain` пуст (субагентов не было).
Отделить цену изображения от цены обычного хода можно только специальным
замером — вынесено в §5.

### 🆕 Замер 05.09.2026 — третья точка, вдвое выше рекомендованной границы

Сессия `dota-diagnostics-with-images`, 92 хода, макс. контекст 288 177.
Работа: диагностика машины по **скриншотам владельца**, присланным пачками
по 4–9 кадров.

| Величина | 02.09 текст | 03.09 кадры очереди | **05.09 скриншоты** |
|---|---:|---:|---:|
| ходов | 3202 | 609 | **92** |
| hit rate | 98.9 % | 99.0 % | **96.9 %** |
| **прирост на ход** | 62 | 1370 | 🔴 **2867** |
| записей с attachment | — | — | **440** |
| плотность вложений | — | ~0.07 кадра/ход | **4.8 записи/ход** |

🔴 **Рекомендация «1000–1500 токенов на ход» занижена вдвое** для сессии,
куда картинки приходят **от владельца пачками**, а не открываются вахтой
по одной. Прежняя строка не отменяется — она верна для своего случая
(разбор очереди, кадр за ходом); здесь другой режим подачи.

**Что отличает этот случай от 03.09 — плотность, а не природа вложения.**
Вахта, читающая очередь, открывает кадр на ход. Владелец, снимающий HUD
игры, присылает девять за одно сообщение, и каждый — нативный Retina-скрин
2000×1250, то есть по формуле патчей ⌈2000/28⌉×⌈1250/28⌉ ≈ **3200 токенов
за кадр**.

🔴 **И hit rate впервые просел ниже 98 %** — 96.9 % против 98.9–99.0 %
в обеих прежних точках. Согласуется с объяснением из блока выше: каждый
новый кадр — новый префикс, а залповая подача бьёт по кэшу сильнее
равномерной.

**Практический вывод:** пачка из девяти скриншотов стоит около **29 000
токенов контекста** — примерно как 12 страниц плотного текста. Это стоит
называть владельцу до того, как он пришлёт вторую.

**Чего замер по-прежнему не показывает:** «440 записей с attachment» —
это записи журнала, а не обязательно 440 изображений; счётчик включает
и другие вложения. Точная цена одного кадра так и не отделена — пункт §5
остаётся открытым.

### 🔴 Что опровергнуто: субагенты не защищают от лимита

**Ожидание было:** делегирование субагентам разгружает главную сессию —
её контекст не растёт, значит окно живёт дольше.

**Замер показал обратное.** За сессию запущено около **тридцати** субагентов,
из них **порядка восемнадцати упали по превышению лимита**, некоторые
по три-четыре раза подряд с перезапуском.

Причина в том, что уже записано в `/auto` §4.5, но недооценено: **каждый
субагент несёт свой полный контекст в ту же квоту**. Пять параллельных —
пять контекстов сразу. При этом их расход **не виден в логе родителя**
(`isSidechain` пуст), то есть измеряется только косвенно — по отказам.

> **Практический вывод, стоивший половины дня:** субагент экономит контекст
> ГЛАВНОЙ сессии и тратит квоту ОБЩУЮ. Это разные ресурсы, и подмена одного
> другим приводит к тому, что окно кончается быстрее, а не медленнее.
>
> Верхняя граница на практике — **два субагента за раз**, и это записано
> в промптах: заходы с четырьмя-пятью падали стабильно.

### Панели на момент замера

`session (5h): 54 % · week (7d): 29 %` — при 3202 ходах и почти двух
миллиардах прочитанных токенов. Недельная квота израсходована на треть,
то есть узкое место — **пятичасовое окно**, а не недельное.



```
C_ход ≈ M × ( a·вход + b·выход + Σ(tool) + Σ(вложение) + thinking ) + кэш-оверхед
```

Известные оценки (уточняются `analyze.py` по мере данных):

| Параметр | Оценка v0.1 | Доверие | Источник |
|---|---|---|---|
| 🔴 **Цена хода растёт с контекстом линейно** | `C_ход ≈ 0.1 × контекст + 5 × выход` | 🟢 | **Опровергает вывод `context-growth-analysis.md` «цена хода почти не росла».** Замер 21.08.2026 по двум полным логам. Opus 5, диапазон 25K→710K: средняя цена хода **14 537 → 75 921** усл. ед., рост **×5,2**. Сверка по сырому `cache_read`: ходы с контекстом <100K дают в среднем **59 851** прочитанных из кэша токенов, ходы >500K — **615 727**, то есть **×10,3** (Sonnet 5 на своём логе: ×12,4). Механика очевидна задним числом: цена хода доминируется `cache_read`, а `cache_read` **равен размеру контекста** — значит зависимость линейна **по построению**, а не эмпирически. **Уточнено 21.08.2026 (вахта VII, 608 реплик, контекст до 998 655).** Формула разложена на два слагаемых и проверена по бакетам: ошибка предсказания **−2.0%** на 700–1000K, **−2.9%** на 500–700K, **−6.4%** на 150–300K и растёт вниз по контексту (остаток — запись в кэш по ×1.25, её доля тем выше, чем моложе сессия). То есть **на большом контексте модель точна до 2%**, и именно там она нужна. Второе слагаемое объясняет, почему на малом контексте цена хода «не падает до нуля»: там доминирует выход, а не история. Рост по бакетам ×4.5 на 25K→975K (прежние ×5.2 и ×5.7 считались по завышенным данным, PIT-H). Прежний вывод был верен **внутри диапазона замера** (до 325K рост с 20K до 35K выглядит плоским на глаз) и стал ложным при расширении диапазона вдвое |
| 🔴 **Потолок контекста — НАБЛЮДЁН, а не оценён снизу** | **окно ≈1M; auto-compact срабатывает у самой границы** | 🟢 | **21.08.2026, вахта VII — первое ПРЯМОЕ наблюдение.** Все прежние записи (`>200K`, `>325K`, `>710K`) были **границами измеренного**: замер кончался раньше, чем кончалось окно, и каждая следующая вахта поднимала планку. Здесь окно кончилось само: на ходу **597 контекст 998 655 → 46 603**, то есть **auto-compact сработал вплотную к 1M и срезал до 4.7% окна**. Это меняет статус величины: раньше знали, что «не меньше чем», теперь знаем, **где именно граница и что происходит на ней**. Сходится с объявленным окном 1M (`49` §1). Прежний текст записи: сессия Opus 5, 648 ходов (**исправлено: 484 реплики, PIT-H**), контекст дошёл до **710 599** токенов, падений контекста **ноль** — auto-compact не сработал ни разу. Предыдущая запись (>325K) была верхней границей **измеренного**, а не потолка. Параллельная сессия Sonnet 5 в тот же день: **567 332** и три падения контекста до нуля (ходы 18, 53, 402 — при 84K, 157K и 454K), что на компакт не похоже (компакт не обнуляет) и требует отдельного разбора |
| Прежняя запись потолка | ~~>325K, не 200K~~ | 🟢 | **Опровергнуто и исправлено 2026-08-20**: та же сессия продолжена до 315 ходов, контекст дошёл до 325 120 токенов **без единого auto-compact** (маркеры отсутствуют в логе) — предыдущая запись «≈200K» была преждевременным выводом по одной точке (184K), принятым за потолок. Согласуется с тем, что Sonnet 5 объявлен с окном до 1M (`49` §1). Полный разбор роста — `context-growth-analysis.md` |
| 🔴 **Кэш сбрасывается сменой ПРЕФИКСА, а не только по TTL** | промах стоит ×11–12 обычного хода; выживает 16 900 ток. | 🟢 | **Измерено 21.08.2026, вахта VII — и это не то, что искали.** Бэклог §5.7 планировал мерить промах как «пауза > TTL». Пауз >60 мин в сессии **не было ни одной**, TTL часовой не истекал — а промахи случились, три штуки. Причина: **команда, меняющая системный префикс**. `/reload-plugins` в 14:39 (сразу после упора в `five_hour` лимит) и `/login` в 17:28. В обоих случаях после команды выжило **ровно 16 900 токенов** кэша (системный промпт + описания инструментов — то, что стоит до точки изменения), а **весь остальной контекст переписан заново**: 293 670 и **657 998** токенов записи. Цена: ход на контексте 675K стоил **×12.1** того, во что обошёлся бы при попадании, — это **12.7 обычных ходов за одну реплику**. Три хода = **0.5% ходов и 37.7% всей записи в кэш**, переплата 2.8% цены сессии. **Практическое следствие:** релогин и перезагрузку плагинов делать на **маленьком** контексте; при четырёх аккаунтах (`84`) переключение вахты в конце длинной сессии — самая дорогая кнопка в интерфейсе |
| 🔴 **Компакт: порог, состав, цена** | порог **1 000 215** (Opus 5) / **934 095** (Sonnet 5); сводка **13 452** = 1.3% замененного | 🟢 | **Наблюдён живьём 21.08.2026** (`context-growth-analysis.md` §11). ### 🔴 Замер 22.08.2026, вечер — три вещи, которых не знали утром

**1. Расход субагентов ИЗМЕРИМ — просто не из родительского лога.**

Прежняя формулировка звучала так: «ноль записей `isSidechain` не значит, что субагентов
не было; мерить по этому файлу делегирование нельзя». Верно — и **неполно**. На диске
под каталогом сессии лежит `subagents/`, и там **отдельный лог на каждого**:

```
projects/<session-id>/subagents/agent-<id>/    ← свой лог, свой usage, своя meta.json
```

За эту сессию их четыре, опознаны поимённо: три `repo-inventory` (по репам кампании)
и один `token-probe`. **`isSidechain` в родителе = 0 — четвёртое подтверждение изоляции**,
но теперь известно и где искать саму цифру.

> **Разница между «не измеряется» и «не измеряется отсюда» — это разница между закрытым
> вопросом и ненайденным файлом.** Первую формулировку записали, вторую не искали.

**Что это открывает:** полный расход прогона = родитель + сумма субагентов, и его наконец
можно посчитать. До сих пор все суммы сессий с делегированием были **занижены**
на неизвестную величину — тем же способом, каким занижен расход сессии с компактом
(цена самой компакции в лог не пишется).

**2. Бакет цены хода — историческая точка, а не текущее состояние.**

Аномальный бакет 650K (**157 935** при соседних ~70 000) за полдня работы **не изменился
ни на единицу**. Причина проста и её стоит записать: сессия ушла вперёд по контексту,
**в это 25K-окно больше не попал ни один ход**, бакет закрыт навсегда.

> Бакеты пройденного диапазона **заморожены по построению**. «Аномалия сгладится
> со временем» — невозможно: усреднять больше нечем. Либо она объяснена, либо остаётся
> в ряду как есть.

**3. Компакт не сработал за 12 ч 52 мин работы.** Контекст дошёл до **868 072** — ниже
наблюдённого порога Opus 5 (**1 000 215**) на 132K и **ниже даже спорной community-цифры
83.5 %** (~830K для окна 1M) — до неё тоже не дотянули 38K, так что **точка
не различающая**, и записана как таковая.

📍 Отдельно стоит зафиксировать, **как** это проверено: грубый поиск по тексту дал
**11 совпадений** со словом `compact_boundary` — все они оказались упоминаниями
**в содержимом сообщений** (обсуждение методики). Системных маркеров — **ноль**, проверено
построчным разбором JSON. Ровно та ловушка, что описана в `23` §5в: совпадение по слову
проверяется контекстом, прежде чем стать наблюдением.

всему текущему контексту, `cache_read` падает до **16 900** (голый системный префикс,

### 🔬 ПРЕДРЕГИСТРАЦИЯ 23.08.2026 — вопрос владельца о `/clear` после компакта

> **Владелец, дословно:** *«Есть смысл вообще в нашей работе жать `clear`, если, как
> я понимаю, когда чат компактится, то весь контекст также очищается? Или нет?
> В чём разница между компактом и `clear` конкретно ПОСЛЕ того, как он выполнился?»*

Записано **до** события: контекст 903K+, компакт близко (порог 999 944). Предсказания
фиксируются заранее, иначе после факта любое объяснение выглядит верным (`28` §10б).

#### Что предсказывает модель — и что из этого проверяемо

| Величина | После компакта | После `/clear` | Проверяемо? |
|---|---|---|---|
| `cache_read` первого хода | ~16 900 (голый префикс) | ~16 900 | 🟢 да, из лога |
| контекст первого хода | **сводка + системный префикс** | **только префикс** | 🟢 да |
| цена самого сброса | читает весь диалог ради сводки | не читает ничего | 🔴 **в лог не пишется** (П7) |
| что доступно дальше | пересказ прошлого разговора | ничего из разговора | 🟢 да, по поведению |

🔴 **Ключевое различие — не в цене сброса, а в том, ЧТО остаётся.** Оба обнуляют кэш
одинаково. Но компакт оставляет **сводку**: она занимает место в новом контексте
и продолжает оплачиваться в каждом последующем ходе. `/clear` не оставляет ничего.

**Отсюда прямой ответ на вопрос владельца:** давить `/clear` **после** компакта смысл
имеет ровно один — убрать сводку, если она не нужна. Если работа продолжается по тем же
файлам, сводка полезна и `/clear` вреден; если начинается другая задача — сводка
это балласт, который платится каждый ход.

#### Три предсказания, которые можно опровергнуть

1. **Контекст первого хода после компакта будет ЗАМЕТНО больше 16 900** — на размер
   сводки. Если он окажется равен голому префиксу, значит сводка в контекст не входит,
   и вся модель неверна.
2. **`cache_read` первого хода после компакта ≈ 16 900**, как у `/clear` и `/login`.
   Все три сброса приводят в одну точку по кэшу.
3. **Цена компакта в лог не попадёт** — ни отдельной записью, ни в `usage` соседних
   ходов. Замерить её можно только по времени (130 с в прошлый раз).

#### Чего этот замер по-прежнему НЕ даст

Числа для `/clear` на большом контексте: он в этой сессии не нажимался. Оговорка
из таблицы выше остаётся в силе — `[ДН]` не закрыт, и закрыть его может только
намеренный `/clear` на контексте ≥300K с первым ходом после него.

**Между батчами `/clear` предпочтительнее ожидания компакта:**

1. компакт срабатывает **сам** и на **максимальном** контексте — то есть в самой дорогой точке;
2. `/clear` делается **осознанно** и в самой дешёвой — сразу после закрытия батча;
3. сводка компакта сохраняет 7 сообщений хвоста, а точка входа в файлах сохраняет **всё,
   что нужно** — при условии, что она работает (до 22.08 не работала, `PIT-116`).

🔴 **Условие одно и жёсткое: чистить между батчами, а не внутри.** Батч — единица, которая
переживает обрыв; незакрытый теряется целиком, потому что решения существуют только
записанными.

### Второй урок того же дня: измерительный код врёт тише всего

Все агрегаты лаборатории за 20–21.08 оказались завышены в **1.6–2.2 раза**: скрипт считал
**строки лога**, а одна реплика пишется несколькими строками, и каждая несёт одинаковый
`usage` (`PIT-H` в `reports/incidents/PITFALLS.md`).

> **Почему не заметили три вахты подряд.** Ошибка сохраняла всё, на что смотрели:
> порядок величины, форму зависимости, направление сравнений. «648 ходов» так же
> правдоподобно, как «300». А главное — **эталона нет по построению**: лабораторию
> и завели потому, что настоящих чисел никто не знает, поэтому сверять результат
> не с чем, и остаётся верить инструменту.

**Правило:** у измерительного кода проверяется не результат, а **единица подсчёта**.
Вопрос дешёвый и задаётся один раз: *строка источника — это сущность или её часть?*
Если у сущности есть идентификатор (`message.id`), агрегат считается по нему.

**Механическая защита вместо памяти:** `python3 session_metrics.py --selftest` — канарейка
на заведомо задвоенном логе (три строки одной реплики + одна другой должны дать два хода).
Проверена снятием фикса: без дедупликации падает с четырьмя расхождениями (`71` §7в).

**Что уцелело в старых замерах:** максимумы (`max` не суммирует) и доли/проценты
(числитель и знаменатель завышены одинаково). **Что не уцелело:** число ходов, все суммы
расхода и всё, что делится на число ходов, — прирост контекста, средняя цена хода.

### 🔴 Правило сбора: с кадра снимаются ВСЕ служебные данные, а не только токены

**Заказ владельца 25.08.2026, дословно:** *«про лабу токенов учти скриншоты, что в папке
скриншоты, и при анализе считывай все данные, что Клод-код даёт там: `/status`, `/stats`,
`/usage`, разные советы, которые он пишет — что жрёт, и т. д. ВСЕ данные собирай,
что возможно, а не только токены»*.

**Повод.** Разбор кадров 14.08 дал четыре замера, и три из них — **не про токены**:
общий счётчик лимитов веба и CLI, стоимость в долларах, календарное время против API-времени.
Ни один не появился бы, если снимать только `cache_read`.

> **Лаборатория называется «расход токенов», и это имя сужает сбор.** Кадр служебной
> команды содержит десяток величин, из которых токены — одна; остальные отвечают
> на вопросы, которые ещё не заданы, и потому кажутся ненужными в момент чтения.

### Что снимать с каждого кадра — полный перечень

| Команда | Что забирать |
|---|---|
| **`/status`** | версия CLI · **Session ID** · cwd · метод входа · Organization · **Email** · модель по умолчанию · MCP: сколько подключено / ждут авторизации / упало |
| **`/context`** | 🔴 **разбивка по потребителям**: system prompt, system tools, **каждый MCP-инструмент отдельно**, файлы памяти, скиллы, агенты · свободное окно · **блок Suggestions — что именно жрёт и сколько сэкономит** |
| **`/usage`** | total cost · **API duration против wall duration** · строки кода добавлено/удалено · по каждой модели: input, output, cache read, cache write · процент израсходованного лимита · **время сброса** |
| **`/stats`** | total tokens за всё время · число сессий · **самая длинная сессия** · активные дни и streak · суммарные input/output/cache |
| **панель веба** | предупреждения о лимите · **«limits shared with Claude Code»** · промо и акции с датами |
| **`/usage` → «What's contributing to your limits usage?»** | 🆕 **три эвристики за 24ч, дословно, с процентом каждой**: доля хода при контексте >150k · доля из subagent-heavy сессий · доля из сессий активных 8+ часов · доля из `/auto` — и текст совета под каждой строкой |
| **вкладка Config (`/config`)** | 🆕 булевы переключатели, которые молча решают поведение сессии — минимум: `Auto-compact`, `Continue automatically at usage limit`, `Switch models when a message is flagged`, `Use auto mode during plan`, `Default permission mode` |
| **вкладка Stats → Models** | 🆕 график «Tokens per Day» по моделям (даты по оси) + таблица all-time: доля %, In/Out, cache read/write **на модель** — тот же срез, что даёт `session_metrics.py`, но по ВСЕМ сессиям сразу, не по одной |
| **любой экран** | 🔴 **советы и предупреждения самого инструмента** — «This tool is consuming a significant portion of context», «Consider starting a new chat», «84 of 100 images» |

### Почему советы инструмента важнее собственных догадок

Строка `take_screenshot using 243.7k tokens (25%) → save ~48.7k` содержит и диагноз,
и оценку выигрыша. Такое не выводится из логов: `session_metrics.py` видит суммы по ходам,
но **не видит разбивку по инструментам** — её показывает только `/context`.

> **Часть замеров существует только на экране и нигде больше.** Лог знает, сколько
> потрачено; `/context` знает, **на что** — и второе нельзя восстановить из первого.

**Практически:** каждый кадр служебной команды из свалки скриншотов разбирается
**целиком**, все числа переносятся сюда, даже те, для которых пока нет гипотезы.
Незаписанное число не участвует ни в одном будущем рассуждении, а кадр после разбора
удаляется — второго шанса прочитать его не будет.
