## [4.22.0] — 2026-08-27 — Заливка ассета: живой heartbeat + отдельный больший таймаут (MINOR)

Тот же прогон, четвёртый и последний баг того же класса в этой серии: владелец
сообщил «на релизы просто висит, ничего не показывает» — `self-map` (~140 МБ ассет)
на шаге `→ релизы` был тих несколько минут подряд.

### Fixed
- **`GH_TIMEOUT=120` (2 минуты) — общий для лёгких API-вызовов и заливки
  многомегабайтных ассетов.** На 40-60 КБ/с 120с дают ~7 МБ — недостаточно для
  140 МБ, гарантированный таймаут на каждой из 3 попыток `gh_try()`, полностью
  тихий (весь вывод буферизуется через `_o="$(...)"`, ничего не печатается до
  завершения попытки). Новая переменная `GH_UPLOAD_TIMEOUT` (по умолчанию 1800с,
  30 минут) — только для заливки, лёгкие вызовы не затронуты.
- **Новая функция `gh_try_upload()`** — тот же ретрай-паттерн, что `gh_try()`, но
  запускает `gh` в фоне и печатает живой отсчёт времени (`\r заливаю... Nс`) вместо
  полной тишины. Побайтовый процент недоступен (`gh` пишет прогресс-бар только в
  реальный терминал, не в перенаправленный поток) — heartbeat подтверждает, что
  процесс жив, а не завис.
- Оба места заливки ассета (`ensure_release()` — создание релиза с ассетом и
  дозаливка канонического ассета к существующему релизу) переведены на
  `gh_try_upload()`, с явным сообщением размера файла перед стартом.

### Added
- Косметика: строка `[N/40] repo` (обновляется через `\r` во время сканирования
  архивов) теперь завершается явным переводом строки — раньше первая репа сводки
  версий печаталась впритык к хвосту этой строки на одной визуальной строке,
  а не с новой, как остальные репы списка.

## [4.21.3] — 2026-08-27 — Дочищена симптоматика 4.21.2: спам ошибок + повторная защита в retry() (PATCH)

Тот же прогон продолжился: несмотря на 4.21.2, владелец увидел ту же картину на `family` —
десятки повторов `no such file or directory: .../clone_family.log`, затем `retry()` всё
равно вошёл в 5 бессмысленных попыток («Unable to read current working directory») прежде
чем сдаться. Два отдельных недочёта в самой защите 4.21.2, не новый класс дефекта.

### Fixed
- **Цикл опроса прогресса спамил нечитаемой ошибкой.** Раз в секунду читал
  `$_clone_log` без проверки существования; если файл (или вся `$WORK`) пропадал
  посреди клона, `< "$_clone_log"` на отсутствующий файл кричит "no such file or
  directory" **прямо в терминал** — эмпирически подтверждено: `2>/dev/null` эту
  ошибку не гасит ни в bash, ни в zsh, потому что это ошибка открытия редиректа
  самим шеллом, а не ошибка команды, чей stderr перенаправляется. Добавлена
  проверка `[ -f "$_clone_log" ]` перед каждым чтением.
- **`retry()` не проверял `$WORK` на своей точке входа.** Guard из 4.21.2 стоял
  только ДО первой попытки клона — если `$WORK` пропадала уже ПОСРЕДИ этой первой
  попытки (ровно случай `family`: 74% готовности, 475 КБ/с — сеть была жива),
  скрипт всё равно уходил в `retry()` и повторял идентичный провал 5 раз (~2 минуты
  чистого ожидания на одну репу). Тот же fail-loud guard добавлен второй раз — прямо
  перед входом в `retry()`, а не только перед первым клоном.

Точная причина, почему `$WORK` пропадает посреди активного клона без Ctrl+C, **всё ещё
не установлена** (VPN-клиент/диск/файловая система — кандидаты, не подтверждено
экспериментом) — 4.21.3 не устраняет первопричину, только её самые болезненные
симптомы (спам в терминал, бессмысленные ретраи).

## [4.21.2] — 2026-08-27 — Гонка Ctrl+C с фоновым клоном + fail-loud на исчезнувшей рабочей папке (PATCH)

Тот же прогон, что нашёл 4.21.1: владелец, дожидаясь исправления порога, продолжал
наблюдать `fatal: Unable to read current working directory: No such file or directory`
и `fatal: remote helper 'https' aborted session` — не разово, а **на каждой следующей
репе подряд** в одном и том же прогоне (health-vault → history → linguistics →
mathematics, все с идентичной ошибкой). Разбор вскрыл два отдельных дефекта.

### Fixed
- **Гонка cleanup_work / фоновый `git clone &`.** Клон запускается в фоне (для живого
  прогресс-бара), PID нигде не отслеживался за пределами локальной переменной. При
  Ctrl+C трап `cleanup_work` (`EXIT INT TERM`) удалял `$WORK` немедленно, а фоновый
  git-процесс мог пережить это на секунду-две и продолжал писать в уже стёртую папку —
  ровно та ошибка, что видел владелец. Теперь PID активного клона хранится в
  `ACTIVE_CHILD_PID`, и `cleanup_work` сначала убивает и дожидается его смерти, потом
  чистит `$WORK` — гонка исключена по конструкции, не по таймингу.
- **Fail-loud, если `$WORK` пропала БЕЗ Ctrl+C.** Второй, более тревожный случай:
  рабочая папка исчезла посреди активного клона (health-vault, 85% готовности,
  686 КБ/с — сеть была живой) без единого нажатия Ctrl+C. Без проверки скрипт слепо
  уходил в `retry()` — 5 попыток клонирования в несуществующую папку, гарантированно
  проваливающихся одинаково, — **на каждой следующей репе**, пока владелец не прервал
  прогон вручную. Добавлена проверка `[ -d "$WORK" ]` перед каждым клоном: если папка
  пропала, скрипт останавливается сразу с понятным объяснением («среда нестабильна,
  перезапусти»), вместо того чтобы жечь ретраи там, где чинить нечего. Точная причина
  исчезновения `$WORK` в этом случае не установлена (VPN-клиент/диск/ФС — кандидаты,
  не подтверждено экспериментом) — это защита от последствий, не устранение первопричины.

## [4.21.1] — 2026-08-27 — Порог зависания перекалиброван: 1024 → 51200 байт/с (PATCH)

В тот же день, первый реальный прогон 4.21.0 на живой VPN-нестабильности (волна деплоя
40 реп): владелец наблюдал зависшие строки прогресса `git clone` и был вынужден вручную
прерывать (`Ctrl+C`) раз за разом — ровно то, что 4.21.0 должна была предотвращать.

**Причина.** `CLONE_LOW_SPEED_LIMIT=1024` (1 КБ/с) — порог «соединение почти мертво».
Реальный симптом на нестабильной VPN — не смерть соединения, а устойчивое ползание:
лог показал минуты передачи на 46–150 КБ/с, что технически **выше** старого порога.
Механизм ни разу не сработал за весь наблюдаемый прогон — не потому что не нужен, а
потому что порог не совпадал с реальностью канала, которую он должен был ловить.

### Changed
- `CLONE_LOW_SPEED_LIMIT` по умолчанию: `1024` → `51200` (50 КБ/с) — теперь ловит
  «мучительно медленно», не только «мертво».
- `CLONE_LOW_SPEED_TIME` по умолчанию: `30` → `15` — быстрее реакция, меньше времени
  теряется перед тем, как механизм вообще заметит проблему.

## [4.21.0] — 2026-08-27 — Зависшая на TCP-уровне передача обрывается сама (MINOR)

Владелец: на нестабильном канале (в т.ч. при переключении VPN на лету) скорость `git
clone`/`git push` может упасть с ~10 МБ/с до долей кбит/с, но соединение при этом не
рвётся — git ждёт молча, без кода ошибки, который мог бы увидеть `retry()`. Прежде
единственным выходом было прервать процесс вручную (`Ctrl+C`, иногда `kill -9`, что
могло оставить недочищенную папку клона и сломать следующий заход) и перезапускать
скрипт заново, теряя прогресс текущей репы.

### Added
- `CLONE_LOW_SPEED_LIMIT` (по умолчанию 1024 байт/с) и `CLONE_LOW_SPEED_TIME`
  (по умолчанию 30 с) — новые переменные окружения, как `RETRIES`/`RETRY_SLEEP`.
  Передаются в `git clone`/`git push` через `-c http.lowSpeedLimit=… -c
  http.lowSpeedTime=…` (скоуп только на вызов, глобальный `git config` не трогается).
  Если средняя скорость держится ниже порога дольше указанного времени, git сам
  обрывает передачу штатным кодом ошибки — с корректной подчисткой частичного клона —
  и она уходит в уже существующий `retry()` с экспоненциальной паузой. Применено к
  обеим точкам клонирования (первая попытка и повтор после сетевого сбоя) и к
  `pushb`/`pusht`.
- `retry()` — при паузе между попытками печатает подсказку, что сейчас безопасно
  переключить VPN: следующая попытка откроет соединение заново на новом интерфейсе.

## [4.20.1] — 2026-08-25 — Сообщение MISSING repos-map не звучит как блокер, которым не является (PATCH)

Владелец на живом прогоне: сообщение «ТРЕБУЕТ РЕШЕНИЯ: repos-map: нет в карте вовсе —
research-engine» напечаталось, а следующим шагом скрипт **сам** добавил строку в карту
(шаг 3) — противоречие того же класса, что чинил `v4.17.1` для итогового блока, но
здесь про **inline**-сообщение по ходу прогона, не про сводку в конце.

**Причина.** Текст сообщения (`loud "repos-map: нет в карте вовсе — ..."`) не различал
«репа не зарегистрирована в карте вообще» (это чинится автоматически шагом 3) и «зона
ответственности не описана» (это остаётся за человеком). Оба смысла жили в одной фразе
«нет в карте вовсе», и она читалась как полный блокер.

**Правило.** Текст `loud`-сообщения обязан называть именно ту часть, которую скрипт
**не** почини́т сам — если часть проблемы устраняется следующим шагом того же прогона,
сообщение обязано это сказать, а не выглядеть цельным блокером.

## [4.19.0] — 2026-08-23 — Шаг 1 перестал молча читать все архивы целиком (MINOR)

🔴 **Найдено владельцем:** *«что-то странное происходит со скриптом деплоя, я его
запускаю и он стоит на месте долго»*. Скрипт печатал «Шаг 1. Ищу версионные архивы»
и замолкал; владелец прерывал прогон дважды.

**Зависания не было — было молчание.** Замер 23.08.2026: **47 секунд** на 47 архивах
(1.2 ГБ суммарно), из них 3.8 с на один архив в 268 МБ.

**Причина — `unzip -t` в предполётной проверке.** Комментарий рядом с ним утверждал
«дёшево — по списку файлов, без распаковки». Утверждение неверно: `-t` проверяет CRC
**каждого файла**, то есть распаковывает архив целиком.

> **Проверка делала не то, что от неё требовалось.** Нужно было отличить оборванный
> архив от целого; вместо этого пересчитывался CRC всего содержимого. Центральная
> директория дописывается **последней** (`PIT-130`) — её наличия достаточно.

**Заменено на `zipinfo -1`:** 47 с → **1.2 с**, в 40 раз быстрее, поведение то же.

**Добавлен прогресс** — `[N/47] имя-архива`. Молчание на десятки секунд неотличимо
от зависания, и это стоило двух прерванных прогонов.

## [4.17.2] — 2026-08-21 — MIRRORS дополнен четырьмя публичными репами (PATCH)

ни в одной из восьми публичных реп — проверено.

**Список остаётся** для скорости и читаемости, но единственной защитой не является.
Рядом с ним записана команда сверки списка с GitHub.

Поведение не менялось ни в одном режиме — правится значение по умолчанию и комментарий.

Поведение публикации не изменилось ни в одном режиме — правится только печать
итогового блока. Новых ключей нет, `deploy-MODES.md` не трогается.

## [4.17.0] — 2026-08-21 — Тег без релиза больше не тупик; настоящая ошибка вместо догадки (MINOR)

**Боевой случай.** Публикация 20 версий `base-repo`: релизы 1.64–1.72 создались,
на 1.73–1.74 пришло «GitHub недоступен», 1.75 прошла, прогон прерван. Повторные запуски

уборки честно значилось «не хватает: релиз» у **десяти** версий.

### Fixed

- **Диагноз без команды починки — половина работы.** По умолчанию релизы делаются только
  для версий **текущего** прогона (`ALLTAGS="$PUBLISHED"`), и тег, уехавший без релиза,
  обычным прогоном не чинится **никогда**. Механизм починки существовал (`REPAIR=1`),
  но владелец видел проблему и не видел выхода. Теперь блок уборки, обнаружив нехватку
  релиза, печатает **точную команду**.
- **`release_state` возвращала вердикт и глотала причину.** На экран уходила зашитая
  фраза «GitHub недоступен» — догадка вместо факта; настоящий текст `gh` терялся.
  Причин у кода 2 минимум шесть (502/503/504 · таймаут · сброс соединения · DNS),
  и лечатся они по-разному. Теперь текст кладётся в `RELEASE_STATE_ERR` и **печатается**,
  а сообщение переформулировано в наблюдение: «не смог узнать состояние релиза».
  Разбор класса — `00-infrastructure/71-fail-loud-and-sourcing.md` §7г.

### Changed

- В список признаков «ответить невозможно» добавлены **`429`, `rate limit`,
  `secondary rate`**. Двадцать релизов с загрузкой ассетов подряд упираются во вторичный
  лимит GitHub, и прежде такой ответ трактовался как «релиза нет» — то есть скрипт

## [4.16.2] — 2026-08-20 — Переменная вплотную к «кавычке» убивала прогон под `set -u` (PATCH)

Первый релиз деплойера из базы после возврата канона. Дефект найден набором тестов, который
три недели не видел рабочего кода: копия в базе стояла на 4.3.2, а разработка шла в другой репе.

### Fixed
- **`«$_ridrepo»` и `«$_aid»`: шелл приклеивал первый байт закрывающей кавычки к имени
  переменной.** У «» это 0xC2 0xBB; при разборе имени байт 0xC2 попадал внутрь идентификатора,
  получалось несуществующее имя, и под `set -u` прогон **умирал** — причём ровно в той строке,
  которая должна была назвать проблему. Наружу вместо диагноза выходило
  `line 992: _ridrepo?: unbound variable`.
- **Последствие было тяжелее самой опечатки.** Обе строки — диагностические:
  «`.repo-id` указывает на другую репу, пропускаю» (предполёт) и «публикуем не туда — СТОП»
  (последний рубеж перед заливкой). Вместо пропуска одного архива падал **весь батч**, нарушая
  инвариант И8 («сбой на одной версии не роняет остальные»). Триггер — любое имя репы
  с не-ASCII в `.repo-id`.
- Лечение — фигурные скобки: `${_ridrepo}`, `${name}`, `${_aid}`, `${REPO}`.

### Added
- **Тест I5 закрывает класс, а не два случая.** Статическая проверка: в скрипте не должно быть
  `$var` вплотную к `«»„“”‘’`. Плюс живой прогон — архив с `.repo-id` на кириллице обязан дать
  диагноз, а не `unbound variable`, и репу не создать.

### Fixed (в самом наборе тестов)
- **`xargs -d '\n'` — GNU-расширение, которого нет в BSD-xargs на macOS.** Проверка G4 падала
  не из-за деплойера, а из-за себя самой. Переписана на NUL-разделитель (`tr '\n' '\0' | xargs -0`),

### Verified
- **278 проверок, всё зелено** (было 271 из 274 — два провала в зоне C от дефекта выше,
  один в G от бага теста). Зон девять, кейсов 73.

Разбор боевого прогона вскрыл потерю данных: у `portrait-of-taste` часть релизов осталась
вообще без zip-ассета. Причина — точка в имени файла трактовалась как метасимвол регулярки.
Плюс закрыты ещё три дефекта того же прогона.

### Fixed
- **Точка в имени ассета матчила что угодно.** Проверка «канонический ассет уже есть» шла
  через `grep -qx "$_aname"`, а `portrait-of-taste-v1.0.1.zip` как шаблон совпадает
  с `portrait-of-taste-v1_0_1.zip` — точка матчит подчёркивание. Итог: канон считался
  присутствующим, загрузка пропускалась, а легаси-ассет удалялся как дубль. Релиз
  оставался с двумя авто-архивами GitHub и без своего. Заменено на `grep -Fxq`
  (буквальное сравнение).
- **Команда удаления не работала на macOS.** Печатали `xargs -d '\n'`, но BSD-версия
  ключа `-d` не знает — у владельца команда падала с `invalid option`. Теперь переносимый
  вариант: `tr '\n' '\0' | xargs -0 rm --`.
- **Существующая репа считалась отсутствующей при сбое связи.** Скрипт лез создавать
  `family` и получал `GraphQL: Name already exists`. Введено три состояния (есть / нет /
  связь не отвечает), как уже сделано для релизов.
- **Сообщение коммита было техническим** (`release: v1.2.3 — tree sync`).

### Changed
- **Коммит версии несёт `<repo> vX.Y.Z — <тезис>`** — то же, что заголовок релиза, из той же
  секции CHANGELOG. `git log --oneline` теперь читается как оглавление проекта.

### Added
- **Тест G7** — канона нет, есть только легаси с подчёркиваниями: канон обязан появиться,
  релиз не остаётся без ассета.
- **Тест A8** — в сообщении коммита есть репа, версия и тезис; нет «tree sync».
- **Тест G8** — печатаемая команда удаления не содержит `-d` и использует `-0`.

### Verified
- 215 проверок зелёные, 61 кейс.

### Notes
- Урок: имя файла — не регулярное выражение. Любое сравнение имён должно быть буквальным
  (`grep -F`, `[ "$a" = "$b" ]`), иначе точка в версии тихо превращает проверку в ложное «да».

## [2.1.2] — 2026-07-29 — Чистка ассетов приведена в безопасный вид и покрыта тестами (PATCH)

вопросу владельца вскрыла в этом коде два содержательных дефекта — оба закрыты, путь

## [2.0.0] — 2026-07-28 — Режимы, ретраи, проверка перед удалением архивов (MAJOR)

Первый полный боевой прогон по всем репам занял около двух часов, потому что скрипт
на каждом запуске проходил ревизию всех релизов подряд. Теперь по умолчанию он делает
только то, ради чего запускается: публикует новые версии из папки. Ревизия истории
вынесена в отдельный режим. Заодно закрыты три дефекта, которые вскрыл прогон на
нестабильной сети, и добавлена проверка «что уже безопасно удалить локально».

### Changed
- **MAJOR: дефолт изменён.** `zsh deploy.sh` = коммит + тег + релиз только для новых
  версий из папки. Проверка старых релизов больше не запускается автоматически.
- **`AUDIT=1`** — полная ревизия всех релизов всех реп (прежнее поведение по умолчанию).
  `REPAIR=1` и `FORCE=1` включают её автоматически.

### Added
- **`SCRIPT_VERSION`** в шапке + этот журнал.
- **`VERIFY=1`** — проверка перед удалением локальных архивов: для каждого архива
  сверяет наличие тега, релиза и канонического ассета на GitHub. Безопасные пишет
  в `~/Downloads/safe_to_delete.txt`, остальные показывает с причиной.
- **`GH_TIMEOUT`** (по умолчанию 120 с) — предел на один вызов `gh`.
- **`gh_try`** — ретраи с нарастающей паузой, но **только** на признаки сбоя связи
  (таймаут, обрыв, 502/503/504, rate limit). «Не найдено» и отказы прав не ретраятся.
- **`release_state`** — отличает «релиза нет» от «запрос не прошёл». При сбое связи
  версия помечается и пропускается, а не считается отсутствующей.

### Fixed
- **`FORCE=1` валил версии без секции в CHANGELOG.** Пустой notes-файл уходил в
  `gh release edit --notes-file`, и версия падала с «не удалось обновить». Теперь тело
  правится только когда есть чем; при отсутствии секции описание и заголовок остаются
  как были, а версия называется в выводе.
- **Утечка `TITLE` между итерациями.** Если notes-файл уже был создан на этапе публикации,
  `build_notes` не вызывался — и версия получала заголовок предыдущей. Так тег `v1.17.0`
  base-repo получил заголовок v1.18.0. Теперь заголовок считается заново для каждой версии.
- **Разнобой шапок в теле релиза.** Секции вида `## vX.Y.Z — …` (без скобок) уезжали
  в релиз как есть, и такие релизы выглядели иначе. Шапка нормализуется к канону
  `## [X.Y.Z] — дата — тезис (BUMP)`; содержимое секции не трогается.
- **Зависание на нестабильной сети.** Вызовы `gh` шли без таймаута — прогон мог стоять
  десятками минут на одной версии.

### Verified
- 158 проверок зелёные, 47 кейсов. Новые: 45 (FORCE без секции), 46 (нормализация шапки),
