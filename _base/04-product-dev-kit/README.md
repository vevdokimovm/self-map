# PRODUCT-DEV-KIT — лаборатория запуска IT-продукта

Стартовый комплект для нового кодового проекта (не knowledge-репы — **code-репы**: есть код, тесты,
пользователи). Извлечён из реальной, действующей практики **FINPILOT** (продакшен-СППР личных
финансов) и обобщён так, чтобы новый проект наследовал правильную дисциплину с первого коммита,
а не набивал те же шишки заново.

**Отличие от соседей:**
- `02-methodology-library/` — библиотека **теории для чтения** (порт «all in», ничего не выбрасывать
  до ревизии). Здесь — не теория, а **дерево файлов, которое копируется** в новый репозиторий.
- `03-role-kit/` — **фабрика производства** ролей (генераторы с нуля/из источников). Здесь —
  **готовые заготовки** трёх ролей под IT-продукт (`roles/`), не инструмент их сборки.

## Состав кита

| Путь | Зачем |
|---|---|
| `STANDARD.md` | Сама методология: TDD-протокол, трёхуровневые CI-гейты, версии/ADR-дисциплина, hook в `reports/` |
| `CHECKLIST.md` | Приёмка: по каким признакам проект считается унаследовавшим кит |
| `configs/` | Копируемые стартовые конфиги: flake8, mypy, coverage, pre-commit, pytest, Makefile |
| `ci/ci.yml.template` | Стартовый GitHub Actions workflow — preflight + fast/full/deep гейты |
| `docs-skeleton/` | `ARCHITECTURE.md`, `SECURITY.md`, `LEGAL.md`, `adr/` — стартовый набор проектной документации |
| `roles/` | Три готовые заготовки роли под IT-продукт: архитектор, юрист, security — `00_ROLE.md` + инструкция по дозаполнению |

## Как применить к новому проекту (6 шагов)

1. **Скопируй `configs/*`** в корень нового репозитория, убрав суффикс `.template`
   (`configs/flake8.template` → `.flake8` и т.д.). Проверь актуальность версий пакетов в
   `pre-commit-config.yaml` перед первым коммитом.
2. **Скопируй `ci/ci.yml.template`** в `.github/workflows/ci.yml`, поправь под стек проекта
   (если не Python — команды тестов/линтеров, сама трёхуровневая структура остаётся).
3. **Скопируй `docs-skeleton/*`** в `docs/` нового проекта, заполни `ARCHITECTURE.md`/`SECURITY.md`/
   `LEGAL.md` под реальный стек и юрисдикцию (шаблоны дают структуру, не готовый текст).
4. **Заведи `docs/reports/`** по диспетчеру `../00-infrastructure/19-reporting-system.md` — не
   изобретай свою систему отчётов, используй существующую (она уже рассчитана на code-репы, см.
   §1 «Применимость по типу репы» в файле `19`). `docs/WATCHLOG.md` — по `../00-infrastructure/03-watchlog-template.md`.
5. **Возьми нужные роли из `roles/`** (архитектор/юрист/security — по потребности проекта; для
   публичного продукта с персональными данными — юрист обязателен), дозаполни
   `01_CONTEXT.md`/`02_WORKLOG.md`/`03_PRINCIPLES.md` под конкретный проект по
   `../03-role-kit/STANDARD.md` (роли здесь дают только самодостаточное ядро `00_ROLE.md`).
6. **Прогони `CHECKLIST.md`** перед первым релизом — убедись, что TDD-гейт, версии и ADR реально
   работают, а не просто скопированы.

## Откуда это взято

Прямая порт-линия: `finpilot/CLAUDE.md`, `finpilot/.github/workflows/ci.yml`,
`finpilot/docs/engineering_practices.md`, `finpilot/docs/versioning_and_releases.md`,
`finpilot/docs/reports/adr/`, `finpilot/SECURITY.md`, `finpilot/LEGAL.md`,
`finpilot/knowledge/roles/{architect,lawyer,security}-finpilot/`. Обезличено до переиспользуемого
шаблона — проектные детали (домен, юрисдикция, конкретные ADR) остаются в исходном проекте, сюда
идёт только форма и метод.

---

> **Что это НЕ есть:** не готовый код, не готовая архитектура конкретного продукта. Это дисциплина —
> как вести разработку, чтобы через полгода не было мучительно стыдно за отсутствие тестов и
> непонятные решения без контекста.
