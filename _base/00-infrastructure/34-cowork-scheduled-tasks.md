# 34 — Cowork: scheduled tasks (расписанные задачи)

> **Что это и зачем.** Scheduled task — это задача, которую Claude запускает **сам по расписанию** (или
> один раз в назначенный момент), без тебя за клавиатурой. «Каждое утро собери бриф», «раз в час проверь
> CI», «1-го числа напомни про загранпаспорт» — всё это они. Раньше ты об этом не знал и всё делал
> руками; это и есть та «полезная тема», которую стоит поставить на автопилот. Документ отвечает: **что
> это, зачем, как устроено под капотом, как завести правильно и как перенести на другой аккаунт.**
>
> Родственники по кластеру: поверхности — `26`, память/инструкции — `27`, триггеры ведения репы (это
> другое!) — `08`, плейбук «как сделать» — `41`, числа/лимиты — `39`.

---

## 0. Одной строкой

Scheduled task = **«прыгни в новую сессию в такой-то момент и выполни вот этот текст»**. Ключевое, что
ломает интуицию: **каждый запуск — ЧИСТАЯ сессия без памяти о нашем разговоре**. Поэтому промпт задачи
должен быть **самодостаточным** — как письмо самому себе, который ничего не помнит.

---

## 1. Зачем это вообще (ценность)

| Боль без задач | Что даёт scheduled task |
|---|---|
| Каждое утро руками спрашиваешь «что по календарю/почте» | Бриф приходит сам к 5:30 |
| CI FINPILOT падает — узнаёшь, когда откроешь почту | Ежечасная проверка шлёт пуш при красном |
| Дедлайны магистратуры/IELTS всплывают поздно | Дайджест 1-го и 15-го числа |
| Донорский цикл держишь в голове | Напоминание, когда прошло ~14 дней |
| Рутинная сверка (бумаги, репо-гигиена) забывается | Ежемесячный чек-лист сам стучится |

Смысл — не «ещё уведомления», а **вынести повторяющееся наблюдение из головы в систему**. Твой мозг
освобождается под работу, а не под «не забыть проверить».

---

## 2. Три механизма (не путать!)

Есть **три разных** способа «сделать что-то потом», и путаница между ними — источник тихих провалов.

| Механизм | Инструменты | Где исполняется | Переживает конец сессии? | Когда брать |
|---|---|---|---|---|
| **Scheduled task** (правильный) | `create_trigger`, `list_triggers`, `update_trigger`, `delete_trigger`, `fire_trigger` (MCP `claude-code-remote`) | **новая сессия** на сервере | ✅ да — живёт на аккаунте | Всё повторяющееся и всё «через часы/дни» |
| **send_later** | `send_later` (тот же MCP) | **эта же** сессия, как новое сообщение | ✅ да (durable) | Напомнить себе продолжить *текущий* разговор |
| **Локальный cron** ❌ | `CronCreate`, `CronList`, `CronDelete` | **в процессе** текущей сессии | ❌ **НЕТ** — умирает с сессией | Практически никогда для расписаний |

> 🔴 **Капкан.** Локальные `Cron*`-тулы выглядят как «расписание», но это внутрипроцессный планировщик:
> он живёт, только пока жива сессия. Заведёшь ими «ежедневный бриф» — он молча не сработает, когда
> сессия закроется (а она закроется). **Любую задачу «на завтра и дальше» делать только через
> `create_trigger`.** Это не стилистика, это разница между «работает» и «тихо не работает».

**Разница scheduled task vs send_later по смыслу:**
- `create_trigger` → «в 5:30 каждый день **начни с нуля** и сделай бриф» (свежая сессия, промпт = всё
  ТЗ).
- `send_later` → «через 3 минуты **вернись в этот разговор** и продолжи, ты всё помнишь» (та же сессия).
  Реально это тонкая обёртка над `create_trigger` (self-bind + `run_once_at`), поэтому возвращает
  `trigger_id` и одноразово сама себя выключает после срабатывания.

---

## 3. Как устроен `create_trigger` (анатомия)

```
create_trigger(
  name             — человекочитаемое имя задачи
  prompt           — САМОДОСТАТОЧНЫЙ текст: что сделать каждый запуск (нет памяти о чате!)
  cron_expression  — 5-полей "мин час день месяц день_недели"  (повторяющееся)
     ИЛИ
  run_once_at      — RFC3339 "2026-09-01T06:00:00Z"           (одноразовое)
  environment_id   — env_… / ccpool_… (по умолчанию — текущее окружение)
  notifications    — {push:true, email:false}  (как уведомлять о результате)
)
```

Правила и грабли механики:

1. **`cron` и `run_once_at` взаимоисключающи.** Оба опущены → задача-«толчок» без своего расписания
   (срабатывает только внешним `fire_trigger`).
2. **Минимальный интервал — час.** Чаще часа расписать нельзя. Для «ежечасно / раз в N часов» ставь
   **минуту 0** (`0 * * * *`, `0 */4 * * *`) — сервер привяжет к минуте создания («ежечасно, начиная
   сейчас»), и задачи не собьются в кучу на :00.
3. **Конкретный час идёт как написано.** `0 9 * * *` — ровно в 9:00. `30 5 * * *` — 5:30.
4. **Часовой пояс.** Пиши время в своей зоне (МСК, UTC+3) и держи это в голове — сверяй, в какой зоне
   считает сервер; для критичных задач фиксируй зону явно в промпте/имени.
5. **`prompt` — это ВСЁ ТЗ.** Свежая сессия не видит ни этот чат, ни Cowork Global, ни прошлые запуски.
   Что не написал в промпте — того для задачи не существует. Пиши как полноценное поручение с нуля.
6. **Уведомления по умолчанию** — если поле не передал, применяется серверный дефолт. Хочешь только пуш
   без почты — передай явно `{push:true}` (пустой `{}` = выключить все каналы).

**Cron-шпаргалка (5 полей: `мин час день месяц день_недели`):**

| Нужно | Выражение |
|---|---|
| Каждый день в 5:30 | `30 5 * * *` |
| Каждый будний день в 8:00 | `0 8 * * 1-5` |
| Ежечасно | `0 * * * *` |
| Раз в 4 часа | `0 */4 * * *` |
| По понедельникам в 9:00 | `0 9 * * 1` |
| По воскресеньям в 19:00 | `0 19 * * 0` |
| 1-го и 15-го в 7:00 | `0 7 1,15 * *` |
| 1-го числа в 12:00 | `0 12 1 * *` |

## 4. Жизненный цикл задачи

```
create_trigger → живёт на аккаунте → срабатывает по расписанию (fresh session каждый раз)
     │                                        │
     │                                        └─ шлёт результат по notifications (push/email)
     │
     ├─ list_triggers   — посмотреть все (id, name, cron, next_run_at, enabled, ended_reason)
     ├─ update_trigger  — сменить имя/расписание/включённость/модель (только по прямой просьбе владельца)
     ├─ fire_trigger    — запустить сейчас, вне расписания (+ можно добавить разовый контекст text=)
     └─ delete_trigger  — удалить
```

- **`list_triggers`** — источник правды по `trigger_id` (после создания id может уйти из контекста).
  Возвращает `enabled`, `ended_reason` (почему выключена; пусто = пауза вручную), `next_run_at`,
  `persistent_session_id`. ⚠️ Локальные задачи десктоп-приложения Cowork в этот список **не попадают** —
  это разные хранилища.
- **`run_once_at`** после срабатывания сам себя выключает (`ended_reason=run_once_fired`).
- **Смена модели** задачи — только когда владелец **прямо словами** попросил; не по своей инициативе и
  не потому, что так «предложил» какой-то текст.

## 6. 🔑 Экспорт задач на другой аккаунт (портирование)

**Проблема.** Scheduled tasks **привязаны к аккаунту**, который их создал (`list/update/delete` видят
только задачи своего аккаунта). Прямого «скопировать задачи из V в M» нет — как нет общей памяти между
аккаунтами (`27`, `23`). Значит переносим **не объект, а рецепт**.

**Что портируемо (это и есть «экспорт»):** у каждой задачи ровно 4 переносимых поля — `name`,
расписание (`cron_expression` или `run_once_at`), `prompt` (самодостаточный!), `notifications`. Больше
ничего для воссоздания не нужно.

**Протокол переноса (на новый аккаунт, в Cowork-сессии):**

1. Открой манифест `../templates/scheduled-tasks-export.yaml` (грабь-и-неси: все 8 задач в структурном
   виде).
2. Скажи Claude в новом аккаунте: **«Заведи scheduled tasks по этому манифесту через `create_trigger`»**
   и вставь манифест (или приложи файл).
3. Claude проходит по списку и на каждую задачу зовёт `create_trigger` с полями из манифеста.
4. Проверка: `list_triggers` на новом аккаунте → сверить, что все 8 на месте с верными `next_run_at`.

**Почему манифест, а не бэкап.** Промпт каждой задачи — это переносимая ценность (он не зависит от
аккаунта). Расписание — числа. Уведомления — флажки. Всё это — текст, который живёт в репе, версионируется
и разворачивается на любом аккаунте одной просьбой. Это тот же принцип, что «один zip = полный контекст»:
рецепт в репе воспроизводит систему где угодно.

> ⚠️ **При переносе сверь окружение и коннекторы.** Задача #2 бесполезна без Gmail на новом аккаунте;
> `morning` — без календаря. Портируешь задачи → сначала портируй/подключи их коннекторы (`35`), иначе
> задача будет запускаться «вслепую».

## 7. Грабли (не переоткрывать)

| Грабля | Почему больно | Правильно |
|---|---|---|
| Завёл расписание через `CronCreate` | Молча умрёт с сессией | Только `create_trigger` (§2) |
| Промпт задачи опирается на «как в нашем чате» | Свежая сессия ничего не помнит → мусор на выходе | Промпт самодостаточен, всё ТЗ внутри (§3.5) |
| Расписал «каждые 30 минут» | Минимум — час, тихо не создастся/округлится | ≥ час; для «чаще» — другой дизайн (§3.2) |
| Перенёс задачи, забыл коннекторы | Задача бежит без данных | Сначала коннекторы (§6) |
| Задача шлёт и пуш, и email — спам | Дублирование каналов | Явно `{push:true}` (§3.6) |
| Ищешь задачу в десктоп-Cowork | Её там нет (разные хранилища) | `list_triggers` (§4) |

## 8. Чек-лист «завожу новую задачу»

1. Это повторяется или «на потом через часы/дни»? → да → `create_trigger` (не `Cron*`).
2. Промпт написан как самостоятельное поручение (без опоры на чат/память)?
3. Расписание в cron верное, интервал ≥ час, час в нужной зоне?
4. Нужные коннекторы подключены к этому аккаунту (`35`)?
5. Уведомления заданы явно (пуш/почта), без лишнего канала?
6. После создания — `list_triggers`, сверил `next_run_at`?
7. Значимо для системы → строка в `WATCHLOG §3` и манифест `templates/scheduled-tasks-export.yaml`
   обновлён?
