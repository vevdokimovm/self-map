## §2. Как проверено (повторяемо)

```bash
# Охват GitHub: сравнить список локальных реп с удалёнными
gh repo list --limit 100 --json name -q '.[].name' | sort > /tmp/gh.txt
for d in ~/repos/*/; do [ -f "$d/VERSION" ] && basename "$d"; done | sort > /tmp/loc.txt
comm -23 /tmp/loc.txt /tmp/gh.txt        # пусто = все репы на GitHub

# Отставание удалённой копии от диска
cat ~/repos/base-repo/VERSION
gh api repos/vevdokimovm/base-repo/tags --jq '.[0].name'

# Time Machine
tmutil destinationinfo        # куда настроен
tmutil latestbackup           # когда был последний
tmutil listlocalsnapshots /   # локальные снимки APFS
```

**Что показал `tmutil` 29.08.2026:**

```
Name : NO NAME · Kind : Local
tmutil latestbackup → Failed to mount destination (Code=18)
tmutil listlocalsnapshots / → только com.apple.os.update-*, снимков TM нет
AutoBackup = 1
```

Читается так: **резервное копирование включено, назначение задано, диска нет.**
Автобэкап при отсутствующем диске не ругается и не напоминает — он просто
ничего не делает. Это худший вид отказа: настройка выглядит включённой.

## §3. Почему удаление локальных архивов — не потеря

Правило `06-autonomous-mode-kit/STANDARD.md` §2 говорит: **архивы не удалять,
пока у репы нет git**. Оговорка «пока нет git» существенна и часто теряется.

29.08.2026 в `~/Downloads` осталcя **один** zip из десяти созданных за ночь.
Проверка `deploy_last_run.log` показала последовательность:

```
base-repo|v3.110.0|дерево|закоммичено+тег
base-repo|v3.110.0|релиз|создан
base-repo|v3.110.0|архив|удалён локально      ← только ПОСЛЕ двух строк выше
```

То есть архив удаляется **после** того, как содержимое доехало до git и до
релиза. К этому моменту zip — третья копия, а не единственная, и держать его
в `~/Downloads` незачем.

🔴 **Опасен обратный порядок.** Архив, удалённый до успешного пуша, — потеря.
Порядок в `deploy.sh` правильный; проверять его при любой правке деплойера.

## §4. 🔴 Единственная реальная дыра: связка ключей

`94-secret-storage.md` выбрал связку ключей macOS хранилищем секретов, и выбор
остаётся верным (доводы там). Но у него есть цена, которую надо назвать вслух:

> **Связка привязана к одной машине и одному логину macOS.** Она не в git — и
> не должна быть. Значит при смерти диска секреты уходят вместе с ним, а
> Time Machine, который мог бы её прикрыть, **сейчас не работает**.

### Что это стоит на самом деле — меньше, чем кажется

Секрет — не документ. Утрата секрета не уничтожает работу: **все 13 ключей
системы перевыпускаемы**. VK, Todoist, OpenDota, SMTP, Telegram — у каждого
есть кабинет провайдера, где выдаётся новый.

| | Утрата репы | Утрата секрета |
|---|---|---|
| Что теряется | труд, невосстановимо | доступ, восстановим |
| Цена | месяцы | полчаса на перевыпуск |
| Прикрыто | GitHub ×63 | ничем — и это терпимо |

Поэтому решение не «срочно копировать связку куда-то», а **знать, что чинить,
и уметь это за полчаса**. Именно для этого §5.

### Чего делать НЕ надо

| | Почему нет |
|---|---|
| **Экспорт связки в файл и в репу** | ровно то, что `94` §2 запрещает: секрет попадёт в архивы и в 54 копии базы |
| **Копия связки в iCloud** | iCloud Keychain синхронизирует свою связку, а не эту; и это снова одна учётка как узел отказа |
| **Записать секреты в заметку** | заметки уходят в экспорты и выгрузки — уже случалось (`vk-graph.zip`) |

## §5. Порядок восстановления — от лёгкого к тяжёлому

### 5.1. Потерян один секрет

```bash
python3 ~/repos/base-repo/scripts/secret.py list      # что вообще нужно системе
python3 ~/repos/base-repo/scripts/secret.py set ИМЯ   # завести заново, ввод вслепую
```

Значение берётся **в кабинете провайдера перевыпуском**, а не поиском старого:
засветившийся или потерянный секрет отзывается, а не восстанавливается
(`32-git-hooks-and-secret-scanning.md`).

### 5.2. Потеряна одна репа (снёс, испортил, перезаписал)

```bash
gh repo clone vevdokimovm/ИМЯ ~/repos/ИМЯ
```

История, теги и релизы на месте. Затем раздать базу:

```bash
python3 ~/repos/base-repo/scripts/sync_base_local.py ИМЯ
```

### 5.3. Потеряна машина целиком

Порядок, и он же — проверка, что кит полон:

1. **Клонировать всё** — 63 репы приватные, нужен вход в GitHub под
   `vevdokimovm`:
   ```bash
   mkdir -p ~/repos && cd ~/repos
   gh repo list --limit 100 --json name -q '.[].name' | xargs -I{} gh repo clone vevdokimovm/{}
   ```
2. **Завести секреты заново** — `secret.py list` покажет все 13 нужных,
   каждый перевыпускается у своего провайдера (§5.1).
3. **Проверить целость** — `revision_check.py` по каждой репе; `gate_monitor.py`
   для базы.
4. **Вернуть Time Machine** — §6.

🔴 **Единственное, что нельзя восстановить из GitHub, — вход в сам GitHub.**
Это узел отказа выше всех остальных: пароль и второй фактор учётной записи
`vevdokimovm`. Он **не** в компетенции этой системы и хранится там, где владелец
хранит доступы к банку. Кит на него только указывает.

## §6. Что надо сделать руками — и почему это не может сделать вахта

| Действие | Почему только владелец |
|---|---|
| **Подключить диск Time Machine** («NO NAME») | физическое действие |
| **Проверить, что бэкап пошёл** — `tmutil latestbackup` перестанет ругаться | требует подключённого диска |
| **Завести 13 секретов** — `secret.py set` | ввод вслепую с терминала владельца, значения у провайдеров |
| **Убедиться, что доступ к GitHub восстановим** — пароль и 2FA лежат вне этой машины | доступ вне системы |

Эти четыре строки заведены в `mission-control/TASKS.md`. Первая — самая
дешёвая и самая важная: **воткнуть диск.**

## §7. Чем это проверяется дальше

Кит без проверки протухает так же, как всё остальное. Замер §2 повторяется
командой и потому годится в механизм:

- **`gh repo list` против `~/repos`** — новая репа, не заведённая на GitHub,
  видна сразу. Проверяется гейтом базы (`check_repos_map_sync`).
- **отставание версии** — `VERSION` на диске против верхнего тега; расхождение
  больше чем на батч означает, что деплой давно не запускали.
- **Time Machine** — `tmutil latestbackup` возвращает ошибку, пока диска нет.

> 🔴 Ни одна из этих проверок не встроена в гейт **намеренно**: гейт проверяет
> репу, а это состояние **машины**. Смешивать их значит получить репу, которая
> «сломана», потому что владелец вынул диск. Место таким проверкам — в ките
> восстановления и в глазах владельца, а не в `revision_check.py`.
