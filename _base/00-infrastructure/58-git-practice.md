## 1. Модель: четыре места, где живёт файл

Вся путаница в git уходит, если держать в голове четыре зоны:

```
Рабочая копия  →  Индекс (stage)  →  Коммит (локально)  →  Удалёнка (GitHub)
   правишь          отобрал что        зафиксировал         поделился
   файлы            попадёт в снимок    снимок              снимком
```

| Зона | Что это | Команда «положить сюда» | Как посмотреть |
|---|---|---|---|
| Рабочая копия | Файлы на диске | (просто редактируешь) | `git status` |
| Индекс | Черновик следующего коммита | `git add` | `git diff --staged` |
| Коммит | Неизменяемый снимок + сообщение | `git commit` | `git log` |
| Удалёнка | Копия на GitHub | `git push` | `git log origin/main` |

**Главная идея:** коммит — это **снимок всего состояния**, а не «список правок». Поэтому git
умеет вернуть тебя в любую точку целиком. Отсюда правило: коммить **осмысленными кусками**, а не
по файлу — снимок должен быть рабочим состоянием, а не серединой мысли.

## 2. Ежедневный цикл

```bash
git status                  # что изменилось (смотри ВСЕГДА перед add)
git diff                    # что именно изменилось построчно
git add .                   # отобрать всё в индекс
git add path/to/file        # ...или точечно
git commit -m "feat: краткое описание"
git push                    # отправить на GitHub
```

**Сообщение коммита** — это письмо будущему себе. Формат: `тип: что сделано`.
Типы: `feat` (новое), `fix` (починка), `docs` (документация), `refactor`, `chore` (служебное).
Плохо: «правки», «апдейт», «asdf». Хорошо: `fix: publish.sh терял --auto-asset`.

## 3. Push: HTTPS, токены, ключи

**HTTPS против SSH.** Наше правило — **remote только HTTPS**: работает везде, не ломается при
смене машины, не требует возни с агентом ключей.

```bash
git remote -v                                          # какой сейчас remote
git remote set-url origin https://github.com/USER/REPO.git
```

**Пароль от GitHub в терминале не работает** — вместо него **Personal Access Token (PAT)**.
Это как пароль, но: с ограниченными правами, с сроком жизни, отзываемый по одному, не открывающий
доступ к аккаунту целиком. Создаётся в GitHub → Settings → Developer settings → Personal access
tokens. Для приватных реп нужен scope `repo`.

Чтобы не вводить каждый раз (macOS):
```bash
git config --global credential.helper osxkeychain
```

**SSH-ключи** — альтернатива: приватный ключ лежит у тебя, публичный на GitHub; сервер проверяет,
что ты владеешь приватным, пароль не передаётся вообще. Нужны, если HTTPS+PAT неудобен или
требуется автоматизация без интерактива.

## 3а. `! [rejected] … (fetch first)` — гонка, а не ошибка

Отказ push с `fetch first` означает одно: **между твоим клоном и попыткой записи
кто-то успел запушить в ту же ветку.** В системе, где несколько скриптов и несколько
вахт трогают одни репы, это не редкость, а норма.

**Живой случай.** Массовый прогон перенёс 60 файлов и упал на push: пока он работал,
другой скрипт правил карту в той же репе. Локальный клон устарел, GitHub отказал —
и 60 перенесённых файлов остались никуда не записанными.

**Лечится не «повторить руками», а паттерном в самом скрипте:**

```bash
# при отказе push — обновиться и попробовать снова, до трёх раз
git fetch origin && git rebase origin/"$BRANCH" && git push origin "$BRANCH"
```

### 🔴 `--force` в массовом скрипте — никогда

`--force` затирает чужой коммит, о существовании которого скрипт не знает.
Именно этот сценарий и вызвал отказ: посторонний коммит был **законным**.

Если форс действительно нужен — **только `--force-with-lease`**: он перезаписывает
лишь тогда, когда remote **не менялся** с момента твоего последнего `fetch`.
То есть отказывается ровно в том случае, ради которого `--force` и опасен.

| Команда | Что делает при чужом коммите |
|---|---|
| `git push --force` | **затирает молча** |
| `git push --force-with-lease` | отказывается, сообщает о расхождении |
| `fetch` + `rebase` + `push` | вплетает свою работу поверх чужой |

Проверено на стенде: после фикса перенос доезжает, **посторонний коммит остаётся цел**.

Тот же класс, что коллизия номеров версий между вахтами (`72-source-of-truth.md` §4а):
параллельные исполнители не видят друг друга, и единственная общая точка — remote.
Извлечено из `mission-control/00-infrastructure/17-gh-automation.md` §4.

## 4. Теги и релизы — зачем

**Тег** — это закладка на конкретном коммите с человеческим именем: `v1.2.0` вместо `a3f9c21`.
Коммитов сотни, значимых точек — десятки; теги отмечают именно их.

```bash
git tag -a v1.2.0 -m "Описание релиза"   # annotated — с автором, датой, сообщением
git push origin v1.2.0                    # теги не уезжают сами!
git tag                                   # список
```

**Annotated (`-a`) против lightweight.** Lightweight — просто указатель. Annotated — полноценный
объект с метаданными. **Для релизов всегда annotated**: через полгода важно, кто и зачем.

**SemVer — `MAJOR.MINOR.PATCH`:**
- `PATCH` (1.2.**0**→1.2.**1**) — починка, документация, без нового поведения;
- `MINOR` (1.**2**→1.**3**) — новая функциональность, обратно совместимо;
- `MAJOR` (**1**→**2**) — ломающее изменение.

**Release** — это тег + описание + прикреплённые файлы на GitHub. Тег = техническая метка,
релиз = витрина с changelog и артефактами.

## 5. Частые ситуации

| Ситуация | Команда | Что делает |
|---|---|---|
| Забыл файл в последнем коммите | `git add f && git commit --amend --no-edit` | Дописывает в тот же коммит |
| Опечатка в сообщении | `git commit --amend -m "новое"` | Переписывает сообщение |
| Откатить правку в файле | `git checkout -- file` | Возврат к последнему коммиту |
| Убрать из индекса, правки оставить | `git reset file` | Убирает из индекса, правки в файле остаются |
| Отменить коммит **безопасно** | `git revert <sha>` | Новый коммит-антипод, история цела |
| Посмотреть, что было | `git log --oneline --graph -20` | Компактная история |
| Кто и когда правил строку | `git blame file` | Авторство построчно |

⚠️ **`--amend` и `reset --hard` переписывают историю.** Если коммит уже уехал в push — не трогай,
используй `revert`. Иначе разъедешься с удалёнкой.

## 5а. Атрибуция: убрать ассистента из соавторов коммитов

По умолчанию Claude Code дописывает в конец сообщения коммита строку
`🤖 Generated with [Claude Code]` и трейлер `Co-Authored-By: … <noreply@anthropic.com>`.
GitHub читает трейлер как стандартную конвенцию и показывает соавтора на карточке
коммита и в Insights → Contributors.

> ### 🔴 Адрес `noreply@anthropic.com` не принадлежит Anthropic
>
> Его зарегистрировал на себя **посторонний пользователь GitHub**, и коммиты
> привязываются к нему. То есть в контрибьюторах приватной репы оказывается
> не «Claude», а **незнакомый человек**.

### 🟢 ИСПОЛНЕНО 04.09.2026 — и в два слоя, а не в один

Владелец, дословно: *«не надо чтобы Клод был как-то упомянут — это основное
правило: ни в контрибьюторах гита, ни в коммитах, ни в релизах, нигде»*.

| Слой | Где | Что стоит |
|---|---|---|
| основной | `~/.claude/settings.json` | `"attribution": {"commit": "", "pr": "", "sessionUrl": false}` — было `null`, то есть трейлер писался |
| 🔴 страховка | `~/.claude/CLAUDE.md` | явный запрет словами, с причиной и цитатой владельца |

**Второй слой не перестраховка.** Инструкция про co-author частично зашита
в системный промпт Claude Code (issue #53259: *«This instruction cannot be
reliably overridden by any user-facing mechanism»*), и в отдельных версиях
перебивала пользовательские настройки. Один `settings.json` — механизм,
который может молча перестать работать при обновлении CLI.

🔴 **Прошлое не чистится.** `git filter-repo` перепишет хеши всех коммитов
и порвёт привязку тегов и релизов к деревьям — цена выше, чем строка
в контрибьюторах приватной репы. Разбор с командами, если владелец
всё же решит: `reports/investigations/kak-ubrat-claude-iz-soavtorov-git-kommitov-i-ochistit-istori.md`.

### Отключить на будущее — пять минут

Актуальный ключ — `attribution` (с Claude Code v2.0.62). Старый `includeCoAuthoredBy`
объявлен устаревшим и в ряде версий просто игнорировался. В `~/.claude/settings.json`:

```json
{
  "attribution": { "commit": "", "pr": "", "sessionUrl": false }
}
```

`commit: ""` убирает трейлер и строку Generated · `pr: ""` — футер в описаниях PR ·
`sessionUrl: false` — трейлер `Claude-Session:`.

Приоритет областей, от высшего: managed → аргументы CLI → `.claude/settings.local.json`
→ `.claude/settings.json` проекта → `~/.claude/settings.json`. Для одной машины и всех
своих реп правильное место — **последнее, пользовательский уровень**.

Проверка: `/status`, затем тестовый коммит и `git log -1` — ни трейлера, ни строки
Generated быть не должно.

### 🔴 Чистка прошлого опасна именно в этой системе

Перезапись истории (`git filter-repo --message-callback …`) меняет **все хеши**.
У нас на каждой версии висит **тег и релиз с ассетом**, и по канону
«один zip = полный контекст» **ассет релиза и есть поставка**.

После перезаписи релиз может указывать на несуществующий коммит, **а ассеты
не пересобираются сами.**

Порядок, если чистить всё-таки надо:

1. зафиксировать список тегов и релизов **до** перезаписи;
2. переписать историю;
3. проверить **каждый** релиз и при необходимости пересоздать.

Для одного-двух последних коммитов дешевле `git rebase -i <sha>^` с `reword`
и `git push --force-with-lease` (§3а — почему именно `--force-with-lease`).

**Ещё два подводных камня.** Список контрибьюторов кешируется отдельно от истории
и пересчитывается за 24–48 часов, на малоактивных репах — неделями; ручной кнопки нет.
И у смерженных PR остаются ref'ы `refs/pull/*/head`, которые контролирует GitHub
и которые **нельзя перезаписать** force-push'ем: если трейлер был там, индексатор
может продолжать его учитывать при полностью чистой основной истории.

Автором коммита ассистент ставит владельца (`user.name`/`user.email` из git config),
себя добавляет только соавтором — проверить: `git log --format=full`.

Извлечено из `mission-control/00-infrastructure/19-claude-code.md`.

## 6. Что НЕ коммитим — никогда

- **Секреты**: пароли, токены, ключи, `.env`, данные карт. Попавший в историю секрет **считается
  скомпрометированным** даже после удаления файла — история хранит всё. Действие: **отозвать
  токен**, потом чистить.
- Тяжёлые бинарники без нужды, кэши, `node_modules`, `.DS_Store`.

Защита — `.gitignore` + хук `pre-commit`, который блокирует коммит с подозрительным содержимым
(см. `32-git-hooks-and-secret-scanning.md`).

## 7. Минимальная настройка новой машины

```bash
git config --global user.name  "Имя"
git config --global user.email "почта@example.com"
git config --global init.defaultBranch main
git config --global core.editor "vim"
git config --global credential.helper osxkeychain
```
