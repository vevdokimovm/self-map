# 🗂️ Карта репозиториев

> GitHub: [vevdokimovm](https://github.com/vevdokimovm) — личная система хранения. Одна репа = одна зона жизни, зоны не пересекаются.

> **Все репы — приватные и сугубо личные.** Это персональная система для удобного анализа и поддержания актуальности информации, а не витрина для чужих глаз. Поэтому сюда грузится **всё**, включая любые персональные данные: риски осознаны и приняты, данные мои. **Единственное железное исключение — секреты:** пароли, приватные ключи, API-токены, данные банковских карт и всё, что при утечке открывает доступ к деньгам или аккаунтам. Их — никогда, даже в приватную репу.

> 📍 Эта карта живёт в **`base-repo`** — родительской репе всей системы.

Тема научная и исследовательская, не «для прикола» и не чисто educational. Ядро — методология (как думать) + отдельная папка о том, как ломается, ошибается и продаётся сама наука.

# 📐 Стандарт репозитория

> Единый шаблон для всех реп. Эталон — `academic-portfolio`. Цель: одинаковая структура и нейминг везде, чтобы не разгребать хаос.

## 1. Нейминг папок

1. **Цифровой префикс** для порядка сортировки: `01-`, `02-`, `03-` … Гитхаб сортирует по алфавиту — префикс держит нужный порядок.
2. **kebab-case** — слова через дефис, нижний регистр: `01-bachelor-thesis`, `03-bochvar-competition`.
3. **Английский** для имён папок верхнего уровня — короткий и универсальный.
4. **Вложенность где логично**: `06-internships/vk-education-summer-2025`. Не плодить уровни без нужды.
5. Русский — только внутри контента (сами документы), не в структуре.

## 2. Логические блоки

1. Бить содержимое на **тематические папки верхнего уровня** — каждая папка это один смысловой блок.
2. Внутри блока — подпапки по типу материала (`text/`, `presentation/`, `data/`, `source-code/`), если материала много.
3. Одна папка = одна логическая единица. Не сваливать разное в кучу.
4. **Что грузим — всё.** Репы приватные и сугубо личные, поэтому заливаем любые данные, включая персональные (риски приняты, данные свои). **Не грузим только секреты:** пароли, приватные ключи, API-токены, данные банковских карт — то, что при утечке даёт доступ к деньгам или аккаунтам. Это единственное железное исключение.
5. **Файлы не из зоны репы** при разборке в неё не заливать. Складывать в один общий архив `for-other-repos.zip`, а **внутри него — вложенные архивы по имени целевой репы**: `for-other-repos.zip → health-vault.zip, academic-portfolio.zip, …`. Каждый вложенный содержит файлы, которым место в этой репе. Потом распаковал внешний — и каждый внутренний одним движением заливается в свой дом. Файлы без дома ни в одной репе — во вложенный `misc-vault.zip`.

## 3. Скелет README

Порядок секций сверху вниз:

1. **Заголовок** — `# Название — Vasilii Evdokimov`
2. **Короткое описание** — 1–2 предложения: что это за репа и зачем. С контекстом (годы, вуз, стек — что уместно).
3. **Заметка о языке** через blockquote — `> Most documents are in Russian…` (если контент на русском).
4. **`## Highlights`** — самое важное/сильное в репе, буллетами, со ссылками на папки. Это витрина.
5. **`## Repository map`** — таблица `| Folder | Contents |` со ссылками на каждую папку. Обязательна.
6. **Доп. секции по необходимости** — детали ключевых блоков (`## Thesis in brief`, `## Semester index` и т.п.).
7. **`## Data & privacy note`** — если есть чувствительные/анонимизированные данные.
8. **Дубль на русском** — `## О репозитории (RU)` — краткая версия описания.
9. **Контакты** в футере — `**Contact:** email · GitHub: @vevdokimovm`.

## 4. Технический минимум

1. `.gitignore` — всегда, под стек репы.
2. Первый коммит осмысленный: `feat: initial archive (…)`, не `initial commit`.
3. Ссылки на папки прямо в README — кликаешь и проваливаешься.
4. Ветка `main`.
5. **Размер репы — база знаний, а не свалка архивов.** Три порога:
   - 🔴 **Жёсткий потолок — 500 МБ.** Выше нельзя: Claude физически не принимает архив целиком, работа с репой в Claude ломается. Это техническая стена, не рекомендация.
   - 🟡 **Мягкий потолок — 100 МБ.** Выше — уже неудобно: медленный пуш, тяжёлый клон.
   - 🟢 **Цель — ≤50 МБ.** Репа = обобщённая, полезная база знаний. Тяжёлые бинарники (docx, pptx, сканы, TIFF) конспектируются в `.md` (подробно, со всеми таблицами/цифрами/кодом) и/или жмутся (PDF — рендер сканов, TIFF → PNG). Полные оригиналы живут локально; в репе — смысл. `.md` рендерится на GitHub и читается в Claude, docx/pptx — нет, поэтому дефолт — конспект, а не файл.
   - Правило конспекта: переносится ВСЁ содержательное (тезисы, таблицы как md-таблицы, код в fenced-блоки, формулы, числа, выводы), опускается только вода — титульники, колонтитулы, форматирование. Ничего по смыслу не теряется.

## 5. Публикация на GitHub

> Remote — **только HTTPS**. SSH (`git@github.com:`, порт 22) на моей сети режется: `Connection closed by … port 22`. HTTPS идёт по 443 и проходит. Проверено на it-base и edu-base.

Перед пушем репа на GitHub должна уже существовать — **пустая приватная**, без README и .gitignore.

**Архив без `.git` внутри (обычный случай):**

```bash
unzip <repo>.zip && cd <repo>
git init -b main
git add .
git commit -m "feat: initial archive (…)"
git remote add origin https://github.com/vevdokimovm/<repo>.git
git push -u origin main
```

**Архив пришёл уже с `.git` и коммитом внутри (как it-base):**

```bash
unzip <repo>.zip && cd <repo>
git commit --amend --reset-author --no-edit   # переписать автора коммита на свой git-конфиг
git remote add origin https://github.com/vevdokimovm/<repo>.git
git push -u origin main
```

**Дальнейшие коммиты — проще первого.** Первый пуш это разовая настройка (создать репу на GitHub, `init`, прописать `remote`, `push -u`). Дальше remote уже привязан, ветка задана — и на каждое изменение рабочий цикл всего три команды:

```bash
git add .
git commit -m "тип: что сделал"
git push
```

Ни `init`, ни `remote add`, ни `-u` больше не нужны — только add/commit/push. Состояние — `git status`, история — `git log --oneline`. Сообщения в том же духе, что и первый: `feat:` новое, `fix:` починка, `docs:` документация, `refactor:` рефакторинг. Правило про осмысленный коммит остаётся — не `update`, а что конкретно сделал.

**Разбор ошибок:**

1. `Connection closed by … port 22` / `Could not read from remote repository` → remote прописан по SSH. Лечится сменой URL: `git remote set-url origin https://github.com/vevdokimovm/<repo>.git` — и пуш заново.
2. `error: remote origin already exists` → не `remote add`, а `remote set-url` (см. пункт 1).
3. `Repository not found` при HTTPS → репа на GitHub не создана или опечатка в имени.
4. Репа на GitHub создана не пустой (с README) → `git push -u origin main --force` — допустимо только для самого первого пуша.
5. Коммит локально уже есть → `init/add/commit` не повторять. Чинишь только remote и пушишь.
