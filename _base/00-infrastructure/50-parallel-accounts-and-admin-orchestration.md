# 50 — Параллельные аккаунты и admin-оркестрация вахты

> Отвечает на два практических вопроса: можно ли параллельно вести 4 вахты (V/J/M/S) в
> разных вкладках терминала вместо последовательной передачи, и можно ли через admin key
> объединить их в одну систему мониторинга. Смежное: `04-watchlog-protocol.md`
> (текущая, последовательная модель вахты), `23-session-continuity.md`.
>
> **Перед тем как параллелить — прочитай `52-hardware-baseline.md`.** На этой машине
> (8 GB RAM, уже в свопе в состоянии покоя) техническая доступность параллельности
> (ниже) не означает, что она даст выигрыш — своп на почти заполненном SSD медленнее
> последовательной работы.

## 1. Параллельные вкладки iTerm с разными аккаунтами — работает

**Факт (документация Anthropic).** Claude Code хранит авторизацию:
- macOS — в **Keychain**, запись `Claude Code-credentials`;
- Linux — `~/.claude/.credentials.json` (права 0600);
- Windows — `%USERPROFILE%\.claude\.credentials.json`.

Официально задокументированный механизм изоляции — переменная **`CLAUDE_CONFIG_DIR`**.
По умолчанию конфиг — `~/.claude`; если задать `CLAUDE_CONFIG_DIR`, туда переносятся
настройки, история, MCP-конфиг, approvals и (на Linux/Windows дословно в доках)
credentials. Каждый процесс `claude` читает эту переменную при старте — два процесса
с разными значениями работают как два независимых инстанса.

**На macOS отдельно:** независимые источники сообщества (не дословно в официальных
доках) утверждают, что запись в Keychain ключуется хешем от `CLAUDE_CONFIG_DIR`, то
есть разные значения переменной дают разные Keychain-записи и полную изоляцию даже там,
где официальный текст явно это не проговаривает. Работает на практике, но не
гарантировано документацией — проверить на своей версии перед тем, как полагаться в
критичном сценарии.

**ToS.** Официальная позиция (Legal and compliance): OAuth-логин предназначен для
владельцев подписок Free/Pro/Max/Team/Enterprise, для «ordinary use». Запрещено явно
только: сторонним разработчикам предлагать логин через Claude.ai от лица чужих
пользователей, и нестандартные схемы обхода. Никакого пункта «одно устройство — один
аккаунт» нет. 4 личные подписки одного человека на одной машине не подпадают под
описанный запрет.

**Настройка (пошагово):**

```bash
# Вкладка 1 — аккаунт V
export CLAUDE_CONFIG_DIR=~/.claude-v
claude              # /login — сохранится изолированно в этот профиль

# Вкладка 2 — аккаунт J
export CLAUDE_CONFIG_DIR=~/.claude-j
claude

# Вкладка 3 — аккаунт M / Вкладка 4 — аккаунт S — аналогично
```

Удобнее — алиасы в `.zshrc`, и в iTerm2 профилях (Preferences → Profiles → General →
«Send text at start: `export CLAUDE_CONFIG_DIR=~/.claude-v`»):

```bash
alias claude-v='CLAUDE_CONFIG_DIR=~/.claude-v claude'
alias claude-j='CLAUDE_CONFIG_DIR=~/.claude-j claude'
alias claude-m='CLAUDE_CONFIG_DIR=~/.claude-m claude'
alias claude-s='CLAUDE_CONFIG_DIR=~/.claude-s claude'
```

**Оговорки:**
- Project-level `.claude/`, `.mcp.json`, `CLAUDE.md` **внутри репозитория** остаются
  общими для всех вкладок — изолируется только user-level конфиг (то, что в
  `CLAUDE_CONFIG_DIR`), не сама рабочая директория.
- Все 4 вкладки, работающие в **одной и той же локальной репе одновременно** — это
  реальный риск конфликтов при записи файлов/git (гонка на одних файлах, не только на
  разных usage-лимитах). Для параллельной работы над base-repo практический вариант —
  либо разные подзадачи в разных файлах, либо git worktree на аккаунт, не голая
  параллельная запись в одно рабочее дерево.
- Перед удалением/пересозданием профиля — `/logout`, чтобы вычистить Keychain-запись,
  не удалять файл вслепую.
- Известный баг (не про терминал, про VS Code extension): в двух параллельных окнах
  VS Code usage-счётчики двух аккаунтов иногда визуально «синхронизировались»
  (issue закрыт как not planned). Для терминального `CLAUDE_CONFIG_DIR`-сетапа это не
  описано, но проверять `/usage` в каждой вкладке отдельно, не доверять слепо.

**Вывод:** технически рабочая, не противоречащая ToS схема — но недокументированная-
как-«рекомендуемая практика» (официально описана только часть механики для Linux/
Windows). Держать её проверенной эмпирически, не как гарантию.

## 2. Admin API key — не то, что нужно для объединения 4 вахт

**Факт.** Admin API key (`sk-ant-admin...`) — инструмент управления **организацией**
в Console: участники и роли, инвайты, workspaces, service accounts, usage/cost reports,
Claude Code Analytics API, Compliance API. Дословно в документации: *«The Admin API is
unavailable for individual accounts»* — требует Console-организации.

**Чем отличается от обычного API key:** обычный — для инференса от имени одного
workspace/проекта; Admin — не для инференса, а для CRUD-управления самой организацией
и агрегированной отчётности.

**Применим ли к Claude Code на личной подписке (OAuth/Pro/Max):** нет напрямую. Личная
подписка, залогиненная через `/login`, не находится ни в какой организации — Admin API
к ней не подключается. Значит **выдать Admin key поверх существующих 4 отдельных Max-
подписок и получить единый обзор usage — нельзя**, это архитектурно два разных
билинговых мира.

**Официальный путь к «объединить 4 вахты в одну систему»:** перевести все 4 логина в
**одну организацию** — Claude for Teams/Enterprise или один Console org с ролью
`claude_code_user`. После этого Admin API (в частности Claude Code Analytics API и
Usage/Cost API) даёт единый вид usage по всем участникам. Это требует смены модели
подписки (с 4 отдельных Pro/Max на Team/Enterprise-план или API-биллинг), а не просто
получения ключа поверх текущей схемы.

**Если цель — сохранить 4 отдельные подписки** (текущая схема разделения лимитов
специально ради независимых бюджетов) **и при этом иметь единый мониторинг** —
официального моста нет. Либо жертвовать раздельностью лимитов ради единого обзора
(перейти на организацию), либо оставаться на раздельных подписках без единого admin-
дашборда и вести сводку вручную через WATCHLOG (текущая модель `04`).

## 2а. 🔴 Admin API недоступен на личных аккаунтах — проверено по документации

Ресёрч 21.08.2026, вопрос владельца «а можно ли объединить четыре аккаунта в общую
систему». §2 отвечал «Admin API — не то, что нужно»; теперь известна **причина**,
и она жёстче: на Pro его нет вовсе.

> **The Admin API is unavailable for individual accounts.**
> To collaborate with teammates and add members, set up your organization in
> **Console → Settings → Organization.**

`organizationType: claude_pro` — **личная** организация подписки. `organizationRole: admin`
в ней значит «админ самого себя» и Admin API **не открывает**. Проверяется командой:

```bash
claude auth status     # subscriptionType, orgId
python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['oauthAccount']['organizationType'])"
```

**Вместе с Admin API закрыто всё, что на нём стоит:** Claude Code Analytics ·
Usage & Cost · Rate Limits API · Compliance API.

### Что остаётся полезного от org ID на личном плане

| Можно | Нельзя |
|---|---|
| опознать, какой аккаунт ведёт сессию (`claude auth status`) | объединить вахты в общую рабочую область |
| сверить записанный ID с фактом, а не с памятью | увидеть чужие сессии или их лимиты |
| держать ключ на случай перехода на Team | передать живую сессию другому аккаунту |

`claude agents --json` показывает сессии **только текущего пользователя ОС** (§4).

### Что откроет Team — если решать переход

**Claude Code Analytics API** отдаёт **по каждому участнику за день**: число сессий ·
строки кода добавлено/удалено · коммиты и PR · принятия и отказы по каждому
инструменту · **разбивку по моделям с `cache_read`/`cache_creation` и стоимостью
в центах** · тип терминала. Задержка до часа, хранение без срока,
**сам API бесплатен** при наличии доступа к Admin API.

> **Половина собственного инструмента `claude-usage` на Team приходит готовой** —
> и сразу по всем аккаунтам, а не по одной машине. Своё остаётся ценным там, где
> официального нет: рост контекста по ходам, цена хода по бакетам, TTL записи
> в кэш, машинное время сброса лимита.

**Чего Team не отменяет:** сессия принадлежит аккаунту CLI — это ограничение
продукта, а не плана (`06-autonomous-mode-kit/SWITCHES.md` §4).

Идентификаторы аккаунтов и полный разбор — **`84-claude-accounts.md`**.
Хранятся в базе: она приватная, а раздача проверяет `isPrivate` **по факту**,
а не по списку (`sync-base.sh`, исполнение PIT-097).

## 3. Практический вывод для системы вахт

- **Параллельность вкладок** — да, технически доступна (`CLAUDE_CONFIG_DIR`), и может
  ускорить независимые подзадачи. Но она меняет саму модель вахты: сейчас `04` описывает
  **последовательную** передачу («по очереди», WATCHLOG как эстафетная палочка). Если
  переходить на параллельную работу нескольких аккаунтов **одновременно над одной
  репой**, WATCHLOG перестаёт быть единственной точкой синхронизации — нужен явный
  протокол «кто какой файл/раздел трогает», иначе одновременные правки в один файл
  дают конфликт, который сейчас в `04`/`22` не описан (там про слияние **разошедшихся**,
  а не **одновременных**, линий).
- **Admin key не решает объединение 4 вахт** без слома текущей архитектуры («4 личные
  подписки = 4 независимых бюджета лимита»). Единственный официальный путь объединения
  требует отказа от этой независимости.
- Практическая рекомендация: параллельность — да, для независимых подзадач в разных
  файлах/областях репы (например, один аккаунт пишет `02-methodology-library/`, другой
  ведёт `reports/`); единый admin-обзор — не заводить, пока цена (потеря раздельности
  лимитов) не оправдана; WATCHLOG остаётся источником правды при параллельной работе,
  но с явным правилом «зафиксировал, что беру в работу, до начала», не только «что
  сделал» постфактум.

## 4. 🔴 Сессии, окна и «арки»: инвентарь снимается командой

Снято с `2.1.238` 21.08.2026. Закрывает `ROADMAP.md` §P1.6c («работа в нескольких окнах
и в разных арках — как не получить две вахты с одним номером версии»).

### Живые сессии перечисляются машинно

```bash
claude agents --json
```

Отдаёт массив: `pid` · `cwd` · `kind` (`interactive`/фоновый) · `startedAt` ·
`sessionId` · `name` · `status` (`idle`/`busy`). Плюс `--all` добавляет завершённые,
`--cwd <путь>` фильтрует по каталогу.

**Замер на этой машине:** шесть живых сессий, по одной на репу
(`portrait-of-taste`, `character-a-analysis`, `dota-dossier`, `mission-control`,
`finpilot`, `base-repo`), **пять из них `idle` с 19–20.08** — то есть висят сутками,
удерживая контекст. Дублей по одному каталогу нет.

> **Правило против коллизии версий, исполняемое за секунду:**
> ```bash
> claude agents --json | python3 -c "import json,sys;print([s['cwd'] for s in json.load(sys.stdin)])"
> ```
> Перед тем как начать вахту по репе — посмотреть, не идёт ли по ней другая.
> `72-source-of-truth.md` §4а описывает **последствие** коллизии (два номера версии,
> потерянная работа); здесь — дешёвый способ её не допустить.
> До этого замера утверждение «параллельных вахт не видно» было **непроверяемым**.

### Имя сессии — не украшение

`-n, --name <имя>` показывается **в поле ввода, в пикере `/resume` и в заголовке
терминала**. Автогенерённые имена вида `base-repo-0d` уже различают сессии, но своё имя
(`base-repo-синтез-репа7`) отвечает на вопрос «что здесь идёт», а не только «где».
Для `--remote-control` есть свой префикс: `--remote-control-session-name-prefix`
(по умолчанию — hostname).

### Три способа развести работу физически

| Способ | Ключ | Когда |
|---|---|---|
| **Git worktree** | `-w, --worktree [имя]` | параллельные ветки одной репы без конфликтов рабочего дерева |
| **tmux / панели iTerm2** | `--tmux` (требует `--worktree`); `--tmux=classic` — обычный tmux | несколько окон под одну задачу; **по умолчанию берёт нативные панели iTerm2**, если он есть |
| **Облачная сессия** | `--cloud [описание\|id\|url]`, `--environment ccpool_…` | работа, не зависящая от этой машины; сюда же `--teleport [сессия]` |

### Наблюдение и вмешательство с телефона

`--remote-control [имя]` запускает интерактивную сессию с Remote Control.
**Граница уже зафиксирована** в `06-autonomous-mode-kit/SWITCHES.md` §4: сессия
принадлежит аккаунту CLI, **передать живую сессию другому аккаунту нельзя**.
Remote Control этого не меняет — он даёт **канал управления** своей сессией,
а не смену её владельца. Для недельного автономного прогона это единственный
способ вмешаться, не подходя к ноутбуку.

### Что из этого следует для четырёх аккаунтов

Объединения по-прежнему нет (§2), и `claude agents --json` показывает сессии
**только текущего пользователя ОС**, а не всех аккаунтов Claude. Значит:

- **Инвентарь параллельных вахт возможен в пределах одной машины**, и этого достаточно
  для главной опасности — двух вахт по одной репе.
- **Между аккаунтами инвентаря нет**, и заменяет его только внешний реестр
  (`mission-control`) плюс дисциплина именования.
- `claude setup-token` (долгоживущий токен по подписке) — то, чем аккаунт может
  запускать неинтерактивную работу; к **объединению** вахт отношения не имеет.
