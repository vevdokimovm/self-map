# Стандарт описания релизов (единый для всех реп)

> **Место в системе.** Этот документ — про **как выглядит релиз** (заголовок, тело, ассеты).
> Механику доставки (бамп → коммит → тег → пуш → релиз) задаёт `00-infrastructure/25-versioning-and-releases.md`,
> формат истории — `24-changelog-protocol.md`. Здесь — контракт формы, который парсит деплой-скрипт.
> Эталон, из которого выведен стандарт: `portrait-of-taste`.

---

## 1. Инвариант: CHANGELOG — единственный источник

Ты пишешь секцию версии в `CHANGELOG.md` **один раз**. Из неё скрипт достаёт всё:
заголовок релиза, тело, тезис для заголовка. Руками в GitHub ничего не набиваешь.

**Одна версия → один тег `vX.Y.Z` → один Release, чьё тело = секция этой версии из CHANGELOG.**

---

## 2. Заголовок CHANGELOG-секции (парсится машиной — формат жёсткий)

```
## [X.Y.Z] — YYYY-MM-DD — <тезис> (BUMP)
```

- `[X.Y.Z]` — версия в квадратных скобках.
- `YYYY-MM-DD` — дата, тире (`—`, em-dash) как разделитель.
- `<тезис>` — **суть батча одной строкой**, ёмко, ≤ ~60 символов. Это то, чего не хватало dota-dossier:
  «что за релиз» видно из заголовка, не открывая тело. Примеры:
  `Разведка источников по Counter-Strike`, `Откат неудачного deploy_all + починка README`.
- `(BUMP)` — `(MAJOR)` / `(MINOR)` / `(PATCH)`. Feature → MINOR, fix/docs → PATCH, слом → MAJOR.
  **Обязателен.** Без него характер изменения приходится угадывать по номерам, а
  `3.3.6 → 3.3.7` не говорит, была это фича или фикс. Деплойер отсутствие маркера
  не блокирует — публикует и предупреждает, — но релиз считается неполным по стандарту.

Из этого заголовка скрипт строит **заголовок релиза**:

```
<repo> vX.Y.Z — <тезис>
```

Пример: `dota-dossier v2.13.0 — Локальная история тиров и пул-эдвайса`.

---

## 3. Тело релиза: опорный абзац, потом блоки

Тело секции = **опорный абзац** + **стандартные блоки**. Именно опорного абзаца не хватало доссье.

### 3.1. Опорный абзац (обязателен, идёт ПЕРВЫМ, до любого `###`)

2–4 предложения своими словами: что сделано и зачем, обобщённо, без списка. Человек читает
его первым и сразу понимает суть, не вгрызаясь в пункты. Пишется сразу под заголовком секции.

> Пример:
> `## [1.0.1] — 2026-07-22 — Репортинг-инфраструктура (MINOR)`
> `Завёл каталог reports/ и честно разобрал сагу с deploy — что сломалось, почему и какие`
> `уроки вшиты в скрипт. Теперь каждый нетривиальный инцидент оседает документом, а не в памяти.`

### 3.2. Стандартные блоки (только те, что применимы; порядок фиксирован)

```
### Added        — что добавлено
### Changed      — что изменено (поведение/структура)
### Fixed        — что починено
### Removed       — что удалено/выпилено
### Notes         — контекст, оговорки, «отличие итерации», сравнения
### Verified      — что проверено / гейты зелёные (для code-реп)
```

Пустые блоки не пишем. Порядок не меняем — глаз привыкает к одному месту.

## 3.3. Сообщение коммита

Коммит версии несёт **то же, что заголовок релиза**:

```
<repo> vX.Y.Z — <тезис>
```

Не `release: v1.2.3`, не `tree sync`, не `update`. Причина простая: `git log --oneline`
должен читаться как оглавление проекта. Техническое сообщение превращает историю в список
номеров, по которому невозможно найти, где что появилось, — а именно за этим в историю
и лезут.

Тезис берётся из той же секции CHANGELOG, что и заголовок релиза, поэтому расхождения
между коммитом и релизом быть не может по построению.

---

## 4. Правило трёх ассетов

**На каждом релизе ровно 3 ассета:**

1. `<repo>-vX.Y.Z.zip` — **канонический снапшот**, заливает скрипт. Имя нормализуется
   независимо от того, как файл назван в папке, чтобы скачанные архивы разных реп/версий
   не смешивались в `~/Downloads`.
2. `Source code (zip)` — генерит GitHub автоматически из тега.
3. `Source code (tar.gz)` — генерит GitHub автоматически из тега.

То есть достаточно, чтобы скрипт **всегда прикладывал канонический zip** (не запускать боевой
релиз с `ASSET=0`) — тройка складывается сама. Проверка на релизе: имя первого ассета =
строго `<repo>-vX.Y.Z.zip`.

---

## 5. Заморозка

Тег и релиз — **неизменяемые** (`21-revision-protocol.md`). Ошибся в описании — выпускаешь
следующий PATCH, а не переписываешь старый тег. Скрипт это уважает: существующий осмысленный
релиз повторный прогон не трогает.

---

## 6. Чек-лист перед выпуском

1. Секция версии в `CHANGELOG.md` есть, заголовок по §2 (тезис + BUMP на месте)?
2. Опорный абзац написан и стоит первым (§3.1)?
3. Блоки в порядке `Added → Changed → Fixed → Removed → Notes → Verified`, пустых нет (§3.2)?
4. Запущен деплой-скрипт → тег, релиз, тело = CHANGELOG-секция?
5. На релизе 3 ассета, первый — `<repo>-vX.Y.Z.zip` (§4)?

---

> **Одной строкой:** заголовок `## [X.Y.Z] — дата — <тезис> (BUMP)` → релиз
> `<repo> vX.Y.Z — <тезис>`; тело = опорный абзац + блоки `Added/Changed/Fixed/Removed/Notes/Verified`;
> ровно 3 ассета, первый — канонический `<repo>-vX.Y.Z.zip`; всё из CHANGELOG, руками не набиваем.
