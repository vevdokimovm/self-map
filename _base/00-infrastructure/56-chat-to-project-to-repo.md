## Стадия 0 → 1. Когда чат перестаёт быть чатом

**Триггеры (хватает одного):**
- работа не влезает в одну сессию;
- появилось **состояние**, которое надо передать дальше (что прочитано, где остановились);
- появились артефакты, которые жалко потерять;
- ты второй раз объясняешь новому чату «а мы тут вот что делаем».

**Действие:** заводится **пет-проект** — переносимый пакет. Не «папка с файлами», а
самодостаточная единица (см. `57`).

### Обязательная служебка пет-проекта (все 6, без исключений)

| Файл | Зачем | Провал без него |
|---|---|---|
| `_chto-eto.md` | Манифест: что это, откуда, workflow, что внутри/исключено | Получатель не понимает, что ему дали |
| `README.md` | Структура + навигация + правила | Слепое блуждание по папкам |
| `VERSION` | Одна строка, SemVer | Непонятно, какая копия свежее |
| `CHANGELOG.md` | Что менялось, новое сверху | История теряется |
| `WATCHLOG.md` | **Где стоим сейчас**, следующий шаг, открытые вопросы | Дубли работы, потерянная точка |
| `00-infrastructure/` | Правила, шаблоны, отчёты, скрипты | Каждая сессия изобретает процесс заново |

**Правило точки возобновления:** `WATCHLOG.md` §0 — единственный ответ на вопрос «где мы».
Приняв работу, **сверь его эмпирически по файлам**, не верь на слово (PIT-«стальной указатель»).

## Стадия 1 → 2. Пет-проект становится репой

**Триггеры:** нужна история версий · работа с нескольких машин/аккаунтов · нужны релизы и теги ·
объём вырос так, что «последний zip» уже не отследить.

### Что добавляется поверх служебки

- `.gitignore` — мусор, тяжёлое, временное;
- `.githooks/pre-commit` — **защита от секретов и тяжёлых файлов** (см. `32-git-hooks…`);
- `templates/publish.sh` + `deploy_from_zip.sh` — публикация версии и деплой из архива;
- теги `vX.Y.Z` + GitHub Release на каждый значимый шаг.

### Чеклист превращения

1. `git init`, remote **только HTTPS**;
2. приватность репы **до** первого пуша (не после);
3. прогон pre-commit по всей истории — секретов нет;
4. `VERSION` = текущая, `CHANGELOG` содержит genesis-запись;
5. первый тег + релиз;
6. запись в `repos-map` (карта всех реп).

## Стадия 2 → 3. Репа как часть основной репы (мерж)

Пет-проект живёт отдельно, пока идёт активная работа. Когда работа закрыта — вливается в
основную репу как блок.

### 🔴 Контракт мержа (пишется **в момент форка**, не в момент мержа)

1. Мерж = **только add/update**. Никакого `rsync --delete`, никакого зеркалирования.
   Отсутствие папки в форке ≠ команда её удалить в основной репе.
2. Сырьё и тяжёлые блоки основной репы **не трогаются** — их в лёгком форке и не было.
3. Версия основной репы прыгает **один раз** (напр. 1.10.1 → 1.11.0), поглощая всю линию форка
   как единый мерж; в CHANGELOG — ссылка на ситуация-репорт и на линию форка.
4. Сверить **реестры и чеклисты обеих сторон**: что закрыто, паспорта качества, версии.
5. Записать манифест интеграции: что откуда пришло, что осталось за бортом и почему.

## Версионирование при форке (важное)

**Форк получает СВОЮ линию с `v1.0.0` (genesis), а не продолжает родительскую.**

- Почему: две линии не должны сталкиваться. Родитель паркуется (напр. на 1.10.1) и не трогается,
  форк идёт 1.0.0 → 1.1.0 → … При мерже коллизии номеров не возникает.
- История родителя **переносится, а не переписывается**: в CHANGELOG форка отдельным разделом
  «Наследованная история» (заморожена, справочно).
- Genesis-запись обязана перечислить: **из какого состояния родителя** взят baseline, **что
  унаследовано**, **что намеренно исключено и где оно лежит**.

## Почему временный форк безопасен

Расхождение возникает не от факта форка, а от **параллельных правок**. Условия безопасности:

1. работаем **только** в форке;
2. родитель **запаркован** и не трогается;
3. **контракт мержа записан заранее**.

При соблюдении всех трёх «расхождения» не существует — линия правок одна.

- [ ] `_chto-eto.md` объясняет пакет человеку, который видит его впервые

- [ ] Контракт обратного мержа записан
- [ ] Секретов нет
- [ ] Пакет открывается и читается **без внешних зависимостей** (см. `57`)
