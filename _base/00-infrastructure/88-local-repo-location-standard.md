# 88. Стандарт расположения рабочих репозиториев на диске

> **Решение владельца, 26.08.2026, дословно:** «все репы актуальные поддерживаемые с
> которыми мы работаем через Claude Code живут вот в папке dev/системы... туда будут
> подтягиваться новые созданные репы и тоже там жить. все копии старые дубликаты клоны
> ВНЕ этой папки моих репозиториев ДОЛЖНЫ БЫТЬ УДАЛЕНЫ или если там есть уникальный
> контент — занесён в их эталон-оригинал в папку реп на устройстве и затем удалены.
> в процессе работы каждый батч будут создаваться архивы и класться в загрузки, и оттуда
> через деплой заноситься в сам гит».

## 0. Почему это вообще стало вопросом — PIT-149

26.08.2026 обнаружено и разобрано (`reports/pitfalls.md` PIT-149): iCloud-аккаунт
владельца в состоянии `Quota exceeded`, локальный диск был почти полон (15 ГБ
свободно из 251). macOS «Optimize Mac Storage» агрессивно выселяла файлы репозиториев,
лежавших под `~/Documents/`, в облачные заглушки (`dataless`, `blocks=0` при ненулевом
размере) — до **72%** файлов в одной репе, **44%** в выборке по `base-repo`. Любая
операция, читающая содержимое (`git status`, `revision_check.py`, `zip`), зависала
на неопределённое время, потому что материализация заглушки сама стояла в очереди
за тем же исчерпанным аккаунтом. `brctl download` не форсирует это в обход.

**Вывод:** пока репозиторий лежит где-либо под активной iCloud-синхронизацией
(по умолчанию — весь `~/Documents/` и `~/Desktop/`, если включён «Desktop &
Documents Folders»), он не защищён от этого класса отказа никакими локальными
средствами — только выводом из-под синка физически.

## 1. Канон расположения

**Все репозитории, с которыми ведётся активная работа через Claude Code, живут по
одному фиксированному локальному пути, не отслеживаемому iCloud.**

Промежуточно (в разгар инцидента 26.08.2026, при живых параллельных сессиях в трёх
репах) канонической папкой временно была `~/dev/система_репозиториев/` — выбрана
быстро, единственный критерий на тот момент: подтверждённо вне `com.apple.CloudDocs`
(`brctl status` → `Client zone not found`).

**Финальное расположение — `~/repos/`** (корень аккаунта `vasyaevdokimov`, не
`~/Documents/`, не вложено в `~/dev/`). Причины:
- владелец явно предпочёл корень аккаунта вложенности в `~/dev/` — без технической
  необходимости выбирать иначе: `~/dev/` не под iCloud ровно так же, как и корень
  `~`, единственное требование — «вне Documents/Desktop»;
- английское имя (`repos`, не `система_репозиториев`) — по прямой просьбе владельца,
  «на английском будет красивее»; кириллица в пути также исторически создавала свои
  неприятности (PIT-007/009 — порча имён при архивации/распаковке).

Перенос `~/dev/система_репозиториев/` → `~/repos/` выполняется **финальным шагом**,
после того как текущий перенос из iCloud (ещё не все репы вне очереди — три репы были
заняты живыми сессиями на момент старта) полностью завершится. Причина отдельного шага,
а не сразу: оба перемещения одновременно на одном и том же дереве повышают риск гонки
без выгоды — iCloud → `~/dev/` уже безопасно от квоты, `~/dev/` → `~/repos/` — быстрый
локальный `mv` без особых мер (оба конца вне iCloud).

## 2. Четыре правила (дословно от владельца, номера сохранены)

1. Все актуальные поддерживаемые репы, с которыми ведётся работа через Claude Code,
   живут в `~/repos/`.
2. Новые создаваемые репы **сразу** заводятся там же — не в `~/Documents/`, не где-то
   ещё, с последующим переносом.
3. Любые старые копии/дубликаты/клоны **вне** `~/repos/` — под удаление. Если в такой
   копии обнаруживается контент, которого нет в эталоне внутри `~/repos/` — сначала
   перенести уникальное в эталон, только потом удалить копию. Проверка «уникальности»
   — сравнение содержимого (не имени/версии на глаз): дифф файлов, сверка git-истории
   / GitHub-релизов, а не предположение.
4. **Синхронизация с GitHub идёт НЕ через постоянное git-отслеживание рабочего дерева**,
   а через существующий батч-ритуал: `VERSION` поднята → `CHANGELOG.md` → архив
   `pack_release.py` в `~/Downloads/<repo>-vX.Y.Z.zip` → `deploy.sh` публикует тег +
   релиз с этим архивом на GitHub. GitHub-релиз — это и есть подстраховка/бэкап,
   не гранулярная история коммитов рабочего дерева. **Ошибка сессии 26.08.2026,
   для памяти:** увидев в `control-panel`/`mission-control` актуальные файлы без
   `.git`-истории, был сделан неверный вывод «работа не сохранена, под угрозой» —
   на деле `gh release list` подтвердил: релизы `v0.4.1` и `v1.13.5` уже опубликованы
   штатно этим самым механизмом. Перед тем как чинить «пропавшую» git-историю —
   **сначала проверить `gh release list --repo vevdokimovm/<repo>`**, а не чужой
   git-клон на диске.

## 4. Как проверить, что репа снова не попала под iCloud

```bash
brctl status <path-к-репе>   # "Client zone not found" = вне iCloud, это нужный ответ
```

Если путь **найден** iCloud-контейнером — это сигнал вернуть репу под `~/repos/`,
а не чинить на месте.
