## 1. Перечисление и клонирование

**Список реп.** `gh repo list` по умолчанию отдаёт **30** записей — лимит поднимается явно,
иначе операция молча накроет треть системы:

```bash
gh repo list <owner> --limit 1000 --no-archived \
  --json name,description,visibility,isPrivate,pushedAt
```

`--limit 1000` включает автопагинацию. Для сложных выборок — `gh api --paginate`
или `gh api graphql --paginate` с курсором `$endCursor`.

**Три механизма клона ортогональны** — их путают чаще всего:
`--depth` режет **историю**, `--filter` откладывает **блобы**, `sparse-checkout`
ограничивает **рабочее дерево**.

| Способ | Когда | Подвох |
|---|---|---|
| полный | нужна история, теги, `git archive` по старым точкам | долго и тяжело |
| `--depth 1` | разовая операция без истории | ломает rebase/merge, старые теги недоступны |
| **`--filter=blob:none`** | **дефолт для инфраструктурных обходов** | история цела, блобы подтягиваются по запросу |
| `--sparse` | нужен только один подкаталог | трафик сам по себе **не** снижает |

**Обновление клонов.** `git pull` в скрипте опасен: при конфликте он оставляет репу
посреди rebase, и следующая итерация цикла работает в сломанном дереве. Для **производных**
копий надёжнее детерминированное:

```bash
git fetch origin && git reset --hard "origin/$branch"
```

`reset --hard` уничтожает незапушенное — применять **только** там, где локальная копия
одноразовая. Это условие проверяется, а не подразумевается.

**Параллелизм.** Clone и fetch безопасно параллелятся (`xargs -P 8`). Push в **разные**
репы — тоже. Push нескольких процессов в **одну** репу даёт гонки и каскадные отказы;
ориентир GitHub — не более **6 push/мин на репу**.

## 2. Лимиты: читать заголовки, не зашивать числа

| Что | Значение |
|---|---|
| REST, авторизован | 5000 запросов/час |
| REST, аноним | 60 запросов/час на IP |
| GraphQL | 5000 points/час |
| `GITHUB_TOKEN` в Actions | 1000 запросов/час на репу |
| одновременных запросов | 100 (общий для REST и GraphQL) |
| вторичный, REST | 900 points/мин |
| вторичный, GraphQL | 2000 points/мин |
| размер push | 2 ГБ |

Стоимость в points: `GET`/`HEAD`/`OPTIONS` = 1, `POST`/`PATCH`/`PUT`/`DELETE` = 5.

**Обнаружение в скрипте — по заголовкам ответа**, а не по таблице выше:

- `x-ratelimit-remaining` — сколько осталось;
- `x-ratelimit-reset` — UTC epoch, когда обнулится;
- `retry-after` — если пришёл, ждать **ровно столько секунд**.

`remaining: 0` — ждать до `reset`. Продолжать долбить при активном лимите нельзя:
GitHub предупреждает о возможной блокировке интеграции.

> 🔴 **Числа из таблицы не хардкодить.** Вторичные лимиты меняются без уведомления,
> стоимость части эндпоинтов публично не раскрыта. Таблица нужна для **проектирования**
> («влезаем ли мы в порядок величин»), решение в рантайме принимается по заголовкам.
> Это тот же класс, что PIT-091: **константа в коде — снимок, сделанный однажды.**

**Транзиентные сетевые отказы — не лимит, но лечатся так же.** TLS-таймауты к
`api.github.com` роняли скрипты системы, пока обёртка вызова не получила ретраи
с экспоненциальной паузой. Обёртка ставится **один раз на весь скрипт**, а не по месту.

## 2а. Клиент к чужому API: коды, петля пагинации, форма ключа

Обобщено с `gh` на любой внешний API — образец `todoist_export.py`.

**Коды разделяются на три класса, и смешивать их нельзя:**

| Код | Реакция | Почему |
|---|---|---|
| `401`, `403` | **останов** с объяснением | ретраить нечего: ключ не тот или прав нет |
| `410` | **останов**, и в сообщении — **гипотеза о причине** | «endpoint is gone — не legacy ли это URL версии v2?» |
| `408`, `409`, `429`, `5xx` | ретрай с backoff | транзиентное; на `429` ждать `Retry-After` |
| прочие `4xx` | останов | ошибка запроса, повтор её не исправит |

Класс, который забывают, — **третий столбец у `410`**. Отказ, не поддающийся ретраю,
обязан нести **догадку о причине рядом с симптомом**: человек в момент отказа видит
строку на экране и причины не знает (`tests/README.md`, раздел про раннбук).

**🔴 Петля пагинации — отдельный отказ, который иначе виснет молча:**

```python
if cursor in seen:
    raise TodoistError(f"pagination loop detected on {path}")
seen.add(cursor)
```

Курсор, повторившийся дважды, означает, что API отдаёт ту же страницу. Без этой
проверки скрипт **не падает** — он бесконечно скачивает одно и то же, и выглядит как
«долго работает». Три строки против зависания, которое отлаживают часами.

**Форма ключа проверяется до первого запроса.** Самая частая ошибка — не «ключ
протух», а **на его месте текст-заполнитель**:

```python
if not token.isascii() or not token.strip():
    raise TodoistError("токен содержит не-ASCII или пуст — похоже, подставлен "
                       "текст-заполнитель. Настоящий выглядит как 40 hex-символов.")
```

Диагноз «это вообще не ключ» стоит одной строки; тот же случай через `401` даёт
«token rejected» и посылает перевыпускать рабочий ключ.

## 2б. 🔴 Облачный каталог: цена операции — в том, читает ли она содержимое

Замер 23.08.2026, две операции в одной среде с противоположным исходом:

| Операция | Файлов | Заглушек iCloud | Итог |
|---|---|---|---|
| дедуп `misc-vault` по sha256 | 1 490 | 451 (30 %) | **час, ноль результата** |
| раскладка `it-base` через `rename` | 7 360 | 2 780 (**38 %**) | **секунды, все 7 360** |

Заглушек во втором случае вдвое больше по доле — и они не помешали вовсе.

> **`os.rename` в пределах одной ФС меняет только метаданные.** Заглушка остаётся
> заглушкой, сеть не трогается. Хеширование, копирование, упаковка, поиск по тексту
> содержимое **читают** — и каждая заглушка становится сетевым запросом с ожиданием.

**Изнутри кода разница невидима:** обе операции выглядят как «работа с файлом»,
обе не падают, обе не сообщают о причине. Залипший процесс показывает **0.0 % CPU** —
он не считает, он ждёт.

| Не читают содержимое | Читают |
|---|---|
| `rename`, переименование, обход имён, `stat` | `sha256`, `copy`, `zip`, `grep`, чтение текста |
| заглушки безразличны | каждая заглушка — докачка из сети |

**Порядок в облачном каталоге:**

1. Спросить, читает ли операция содержимое.
2. Не читает — работать сразу.
3. Читает — сначала `brctl download <путь>`, дождаться, проверить `st_blocks > 0`.
4. Долю заглушек мерить **до** работы: `stat().st_blocks == 0` (`st_size` врёт —
   у заглушки он полный).

Разбор — `PIT-135`, смежное — `PIT-120` (перенос внутри iCloud идёт через облако).

## 3. Аутентификация и секреты

**Scopes.** Минимум для `gh`: `repo`, `read:org`, `gist` — удалить нельзя.
Дополнительно по необходимости: `workflow` (правка `.github/workflows/`),
`delete_repo`, `admin:org`.

```bash
gh auth refresh --scopes workflow,delete_repo
gh auth refresh --remove-scopes delete_repo
```

Права выдаются **на операцию и снимаются после неё** — `delete_repo`, висящий
постоянно, однажды сработает не там.

**PAT classic против fine-grained.**

| | Classic | Fine-grained |
|---|---|---|
| охват | все видимые репы одним scope `repo` | точечно по репам и правам |
| цена утечки | полный доступ | ограниченный |
| ограничение | — | **50 токенов на аккаунт**, покрывает не все сценарии |

Права fine-grained иногда требуют неочевидных permissions (например `Administration`
там, где ожидался целевой scope) — **проверять эмпирически**, а не по названию.

**Безопасность.** Токен не передавать аргументом командной строки: `argv` виден всей
машине через `ps` и попадает в историю оболочки — подробно в
`32-git-hooks-and-secret-scanning.md`. Только stdin или переменная окружения.
Ставить срок жизни; на macOS хранить в Keychain.

**CVE-2024-53858** (GHSA-jwcm-9g39-pmcw, CVSS 6.5): `gh` до **2.63.0** мог утекать токен
при рекурсивном клонировании реп с сабмодулями вне github.com. Держать `gh` ≥ 2.63.0.

## 4. Стандарт массового скрипта

**Заголовок.** `set -Eeuo pipefail` плюс `trap` для очистки. `-E` даёт наследование
`trap ERR` функциями и подоболочками — без него ошибка внутри функции не поймается.

**🔴 Подвохи `set -e`, из-за которых на него нельзя опираться в цикле по 57 репам.**
Он **не срабатывает** внутри условий (`if`, `while`, `&&`, `||`) и в функциях, вызванных
в условии. То есть ровно в тех местах, где обычно и стоит вызов `gh`. Проверять код
возврата явно, накапливать ошибки, в конце — сводка и ненулевой код.

**Тихий выход с кодом 0 при провале — антипаттерн.** Каждая репа логируется отдельно,
в конце печатается «N успешно, M провалов», при `M > 0` код возврата ненулевой
(`71-fail-loud-and-sourcing.md`).

**Идемпотентность и `--dry-run`.** Повторный запуск при том же состоянии ничего не ломает
и не дублирует. Сухой прогон **обязателен** для операции, меняющей десятки реп разом.

> **Ловушка подачи, а не кода:** разбор и `--apply`, показанные двумя строками подряд,
> вставляются одной пачкой и становятся **одним шагом**. Смысл двух шагов — в паузе
> между ними. Раннбук обязан предупредить об этом явно.

**Тестирование без сети.** `shellcheck` статически; `bats-core` — юнит-тесты с подменой
`gh`/`git` заглушками в `PATH`. Мелкие функции с одной ответственностью проще мокать.
Приёмы — `tests/README.md` («три приёма, без которых набор проверяет не то»).

### 🔴 4а. Оболочка запуска важнее шебанга — и `zsh` рвёт скрипт там, где `bash` работает

Владелец запускает **`zsh script.sh`**, а не `./script.sh`. Явно названная оболочка
**перекрывает шебанг**, то есть `#!/usr/bin/env bash` в первой строке не даёт никаких
гарантий. Скрипт, проверенный только в bash, проверен не в той среде.

**Случай, стоивший 49 реп из 49.** Разбор списка топиков шёл через `IFS=,`:

```bash
IFS=, ; for t in $topics; do … ; done      # bash разобьёт, zsh — НЕТ
```

**В zsh подстановка параметра по `IFS` не разбивается на слова** (это поведение bash/sh,
zsh его не наследует без `SH_WORD_SPLIT`). В `gh` уезжал один топик
`"python,fastapi,backend"` целиком; запятая в имени топика недопустима — упали **все
49 реп подряд**, с одинаковой ошибкой.

**Переносимое решение — позиционные параметры вместо массива и `IFS`:**

```bash
set --                                    # переносимый «массив»
rest="$topics"
while [ -n "$rest" ]; do
  x="${rest%%,*}"
  if [ "$x" = "$rest" ]; then rest=""; else rest="${rest#*,}"; fi
  [ -n "$x" ] && set -- "$@" --add-topic "$x"
done
gh repo edit "$O/$r" --description "$d" "$@"
```

Работает одинаково в `sh`, `bash` и `zsh`.

**Что из этого следует шире:** прогон набора тестов **на боевой оболочке обязателен
перед выпуском** — стенд под bash не ловит этот класс по построению. Родственные
расхождения, на которых уже спотыкались: BSD-утилиты macOS против GNU (`sed -i`, `base64`,
`date`), многобайтная пунктуация вплотную к переменной под `set -u`. Подробнее и
с кейсами — `tests/README.md`, зона `I` и раздел «Прогон на боевой машине».

**Диагноз обязан быть виден с первого прогона.** В том же случае ошибка `gh` глушилась,
и отчёт выглядел как «49 раз не удалось» без единой причины. Это не отчёт, а молчание
(`71-fail-loud-and-sourcing.md`): при массовой операции печатается **первая строка
реальной ошибки** по каждой репе, иначе один общий сбой неотличим от 49 разных.

**Совместимость.** Новые возможности — за флагами с безопасными дефолтами; поведение
по умолчанию не меняется. Ломающее изменение — новая мажорная версия
(`25-versioning-and-releases.md`).

## 5. 🔴 Три способа, которыми массовый скрипт теряет работу молча

Каждый — из живого прогона этой системы. Общее у них одно: **скрипт отчитался успехом.**

1. **Признак «затронутости» смотрит на одну сторону операции.** Скрипт считал репу
   нетронутой **по числу новых файлов**. При выносе каталога новых ноль, а удалений
   тридцать — коммита не было, изменения умерли вместе с временным клоном. Правило:
   затронутость определяется по `git status` целиком, а не по одной из его частей.
2. **Ключ сравнения без пути склеивает разные объекты.** Два разных `overview.md` из
   разных реп схлопывались в одного кандидата и объявлялись «конфликтом содержимого».
   Ключ — **относительный путь**, не имя. Родственный случай: имя, являющееся
   **подстрокой** другого (PIT-089).
3. **Область сканирования, заданная списком, не покрывает корень.** Обход шёл по
   подкаталогам, и `START-HERE.md` в 25 репах был невидим — при том что подходил под
   критерий отбора. Класс PIT-074: **список пишется головой, голова не знает структуры.**
   Лечение — вычитание вместо выбора и **измеритель покрытия**, а не уверенность
   (`scripts/audit_coverage.py`, `05-infra-synthesis-lab/runs/*/PROCEDURE.md` §0).
4. 🆕 **У генератора нет канонического выхода: три несовместимых формы за 16 дней.**

   🔴 **ПОПРАВКА К СОБСТВЕННОМУ ВЫВОДУ, 22.08.2026.** Сначала здесь было записано
   «генератор усох: 17 файлов → 6». Направление угадано, **механизм назван неверно**.
   Замер по всем 26 малым репам показал не усыхание, а **колебание**:

   | Заведены | Реп | Файлов | `START-HERE` | `TASKS` | `.repo-meta` | `00-infrastructure` | `ROADMAP` | `WATCHLOG` |
   |---|---:|---:|:---:|:---:|:---:|:---:|:---:|:---:|
   | **04–08.08** (форма α) | 18 | 15–17 | ✅ | ✅ | ✅ | ❌ | ✅ | ✅ |
   | **15.08** (форма β) | 8 | 13–17 | ❌ | ❌ | ❌ | **✅** | ✅ | ✅ |
   | **20.08** (форма γ) | 2 | **6** | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |

   **β не беднее α — она другая.** Она **добавила** `00-infrastructure/` и одновременно
   **выбросила** `START-HERE`, `TASKS` и `.repo-meta`. Монотонной деградации нет;
   есть три набора, ни один из которых не является подмножеством другого.

   > **Это хуже усыхания.** Усыхание чинится восстановлением утраченного. Здесь чинить
   > нечего: **канонического выхода не существовало ни в один момент времени**, и любая
   > «починка» будет выбором между тремя равноправными историческими вариантами.

   Общее у всех трёх — только `README`, `CHANGELOG`, `VERSION`, `.repo-id`, `.repo-class`.
   **Пять файлов из семнадцати.** Всё остальное — предмет случая, а не стандарта.

   📍 Отдельно скверно, что стандарт `83-project-maturity-levels.md` §1, записанный
   **21.08**, требует `ROADMAP` и `TASKS` в обязательном минимуме. Он совпал с формой α
   и разошёлся с β и γ — то есть **описал одно из трёх поколений и выглядел как общее
   правило**.

   **Лечение — приёмка выхода, а не приёмка запуска.** У генератора обязан быть
   **список ожидаемых артефактов**, проверяемый после прогона. Проверка одной командой:
   сравнить состав корня у самой новой и самой старой репы одного класса.

   📍 **Урок о том, как ошибка нашлась.** Первый вывод («усох 17→6») строился на **двух**
   точках — старой и новой. Две точки всегда ложатся на прямую и всегда дают
   «монотонное изменение». Третья точка сломала картину. **Тренд не объявляется
   по двум наблюдениям** (`28` §6н, `71` §7д-бис).

   **Лечение — приёмка выхода, а не приёмка запуска.** У генератора обязан быть
   **список ожидаемых артефактов**, и он проверяется после прогона, а не подразумевается.
   Проверка одной командой: сравнить состав корня у самой новой и самой старой репы
   одного класса — расхождение и есть регрессия.

## 5а. Необратимая массовая операция: четыре условия, без которых её не запускают

`00-CLAUDE-STOP.md` §3 закрывает массовые операции **с файлами на диске**. Здесь —
операции **на удалённой стороне**, где отката нет вовсе: удаление гистов, реп, релизов,
тегов. Образец, из которого извлечено, — `delete_all_gists.sh`.

**1. Бэкап — предусловие, а не сопровождение.** Сначала всё выкачивается локально,
и **неполный бэкап останавливает операцию целиком**:

```
сохранено: 37 из 40
НЕ сохранены: abc123 def456 ghi789
бэкап неполный — удаление не начинаю
```

Разница с «сделал бэкап и удаляю» принципиальная: там три несохранённых объекта
удалятся молча. Обход (`NO_BACKUP=1`) допустим, но обязан быть **явным флагом
с предупреждением**, а не поведением по умолчанию.

**2. 🔴 Пост-условие проверяется у источника, а не по кодам возврата.** Скрипт,
досчитавший до конца без ошибок, **не доказал, что работа сделана**. Последним шагом
идёт **новый запрос к системе**:

```bash
REMAIN=$(gh api --paginate /gists --jq '.[].id' | wc -l)
[ "$REMAIN" -eq "$EXPECTED" ] || { echo "осталось $REMAIN, ожидалось $EXPECTED"; exit 1; }
```

Формулировка правила: **утверждение не «скрипт отработал», а «на той стороне
получилось то, что задумано»**. Скрипты этой системы врали ровно здесь — выходили
с кодом 0, не сделав работу (см. §5 п. 1: коммита не было, изменения умерли
с временным клоном).

**3. Preflight на права — до первого изменения.** Права на подсистемы живут в отдельных
скоупах, и их нехватка **маскируется под отсутствие объекта**:

> Без скоупа `gist` список отдаётся нормально, а `delete` возвращает **404** — и это
> читается как «гиста нет», хотя он есть и остаётся на месте.

**`404` не означает «объекта нет». Он означает «я его не вижу»** — а причин две:
объекта действительно нет, либо не хватает прав. Различаются они **до** операции,
проверкой скоупа, а не по факту странного результата. То же у приватных реп: без
`repo` они неотличимы от несуществующих.

**4. Полный перебор, а не первая страница.** `gh api /gists` без `--paginate` отдаёт
**30** записей, `gh repo list` — тоже 30. «Все удалены» становится неправдой на 31-м,
и это обнаруживается через месяцы. Пагинация обязательна везде, где операция
заявляет «все».

> ### 🔴 Но и пагинации мало: курсор против фильтра
>
> Из `dota-dossier/src/history_lab/collectors.py`:
>
> > Обход всей истории по монотонному курсору — **единственный способ,
> > гарантирующий отсутствие пропусков, потому что это курсор, а не фильтрованный
> > запрос**.
>
> **Механика потери.** Постраничный обход по фильтру («всё за период», «всё с таким
> статусом») читает страницы **в разные моменты времени**. Между запросами данные
> добавляются, удаляются и меняют признак — и запись, съехавшая с третьей страницы
> на вторую, **не будет прочитана никогда**. Ошибки нет, счётчик выглядит правдоподобно.
>
> | | Фильтрованный запрос | **Монотонный курсор** |
> |---|---|---|
> | Основа | признак, который может измениться | **ключ, который только растёт** |
> | Пропуски при изменении данных | **да, молча** | нет |
> | Возобновляемость | с начала или «примерно» | **с точной позиции** |
>
> **Правило:** операция, заявляющая полноту, идёт по монотонному ключу — порядковому
> номеру, времени создания, версии. Фильтр годится для выборки, **не для описи**.
> Родня — `PROCEDURE.md` §0 (вычитание вместо выбора) на уровне доступа к API.

> **Сухой прогон по умолчанию** здесь не отдельный пункт, а следствие §4: операция без
> отката не может иметь режим по умолчанию, который что-то меняет. Реальное действие —
> только по явному `CONFIRM=1` **и** флагу.

## 5б. 🔴 «Не получилось» ≠ «невозможно»: третье состояние вместо двух

Прямая родня правила про `404` из §3, но про **время**, а не про права:
двоичное «получилось / не получилось» превращает **временный** отказ в **вечный**.

**Живой случай** (`dota-dossier/docs/DATA_ECOSYSTEM.md` §2.2). Сборщик помечал объект
«недоступным», если ответ не приходил за ~3 минуты. По хронологии сбоев провайдера
очередь обработки держалась **часами**. Объект, попавший в неё во время инцидента,
получал вечную метку «мёртв» и **больше никогда не переспрашивался** — хотя был жив
и восстановим. Потеря тихая: счётчик показывает «обработано», а часть данных выпала.

### Три состояния вместо двух

| Состояние | Значит | Что делает сборщик |
|---|---|---|
| `ok` | получено | сохраняет, больше не трогает |
| **`pending`** | не успело — вероятно, очередь на той стороне | **повторит в следующих проходах** |
| `dead` | источник действительно недоступен | помечает и перестаёт дёргать |

**`pending` — то самое третье, которого обычно нет.** Без него любая задержка
на чужой стороне читается как окончательный отказ.

### В `dead` переводит только СОВПАДЕНИЕ двух признаков

> Исчерпаны попытки **И** объект старше окна, в котором он вообще может существовать.

Одного признака мало, и каждый по отдельности врёт:

- **только попытки** → свежий объект объявляется мёртвым из-за одного инцидента;
- **только возраст** → живой, но старый объект перестают запрашивать, хотя он ещё есть.

Окно берётся из **свойства предметной области** (сколько живёт запись у источника),
а не из удобного числа. Не знаешь окна — не имеешь права ставить `dead` вовсе.

### Частота повторов задаётся временем восстановления источника, а не привычкой

«Раз в сутки» и «каждые 3 часа» — не вопрос вкуса. Если сбои и очереди у провайдера
измеряются **часами**, суточный проход означает: попал в окно инцидента — потерял день.
**Шаг опроса выбирается меньше характерного времени сбоя**, а не по круглому числу.

## 5в. 🔴 Внешний сервис — транспорт, а не хранилище

Из той же хронологии, и это вывод более общий, чем инструмент.

За полгода у провайдеров данных зафиксировано: трёхсуточный простой из-за сгоревшего
железа · сломанный API целой подсистемы без починки неделями · **инвесторы
перенаправили ресурсы, развитие приторможено** · DDoS дважды в сутки · деградация
публичного трекинга до неработоспособности.

**Ни один из этих отказов не чинится с твоей стороны.** Провайдер падает, меняет
политику, теряет финансирование, ломает совместимость — и всё это законные события,
а не аварии, к которым можно подготовиться выбором «более надёжного» сервиса.

> **Единственное, что полностью под контролем, — твоя папка на диске.
> Внешние сервисы это транспорт, а не архив.**

Практические следствия, каждое проверяемо:

1. **Сырьё сохраняется до обработки**, а не вместо. Красивый отчёт по чужому API
   не переживёт отключения API; сохранённое сырьё переживёт.
2. **Не снятое сегодня не снимается задним числом.** В том случае из ~3000 записей
   **2919 уже потеряны** для глубокого анализа — реплеи истекли, пока проект
   «собирался начать».
3. **Резервная копия архива — отдельно от рабочей.** Полный архив сырья
   невосстановим: пропадёт — вернутся только сводки, а разобранный слой нет.
4. **Хронология сбоев ведётся датами, а не впечатлением.** «Бывают перебои» —
   не аргумент; таблица «дата → что случилось» позволяет выбрать шаг опроса
   и назвать окно риска числом.

> **Признак применимости:** данные, которые источник хранит **ограниченное время**.
> Есть срок жизни — есть эта задача, и цена промедления **невозвратна**,
> в отличие от почти всего остального в инфраструктуре.

### 🆕 🔴 Копия переживает источник, а маршруты внутри копии — нет

§5в спасает **содержимое**. Есть второй слой распада, который копированием не лечится.

Из `legal-knowledge-base`, отчёт по сквозному разбору 30 организаций за один прогон:
несколько источников за это время **прекратили существовать**. И вот что стало с материалом:

> Проект осиротел: **материалы на месте, но маршруты помощи внутри них ведут к людям
> организации, которой больше нет.**

Текст сохранился дословно, форматирование целое, ссылки внутри документа работают.
Мёртво то, ради чего документ писался: «обратитесь туда-то», «напишите тому-то»,
«подробности на сайте».

> **Копия сохраняет текст, но не сохраняет его исполнимость.** Инструкция без живого
> адресата — не инструкция, а свидетельство о том, что помощь когда-то была.

**Практическое следствие для любой офлайн-копии внешнего корпуса:**

1. **Разделять при сборе слой знания и слой маршрута.** «Как устроено» стареет медленно;
   «куда обращаться» — быстро (`21` §4а-бис: контакты — 6 месяцев).
2. **Маршруты держать в одном месте**, а не россыпью по документам. Умерла организация —
   правится один файл, а не тридцать.
3. **При проверке источника проверять обе вещи:** жив ли источник **и** живы ли адресаты,
   которых он называет. Второе умирает раньше и незаметнее.

📍 Отдельно оттуда: у копии обнаружилось и **обратное** свойство — часть материала считалась
несобранной, а на деле лежала собранной **в другом аккаунте**, россыпью. Трекер разошёлся
с реальностью не из-за потери, а из-за **рассинхрона между аккаунтами** (`SYN-017`).
Перед выводом «этого нет» — сверка по диску, а не по трекеру.

## 6. Кросс-репозиторная синхронизация: почему явный скрипт

| Подход | Плюсы | Минусы для «копия базы в N реп» |
|---|---|---|
| **явный скрипт** | полный контроль, файлы обычные | идемпотентность обеспечиваешь сам |
| `git submodule` | точное версионирование, малый вес | gitlink и detached HEAD; даёт **указатель**, а нужна прозрачная копия |
| `git subtree` | файлы реально в дереве | раздувает историю **каждой** из N реп |
| template repository | хорош для создания новой репы | существующие не синхронизирует |
| `repo-file-sync-action` | декларативно, открывает PR | требует Actions и токена |

Выбор системы — **явный идемпотентный скрипт**; при переезде в CI — `repo-file-sync-action`
с PR. Обоснование границы `_base/` — `78-base-embedding.md`.

### 🔴 6а. Атрибут, обновляемый побочным эффектом, застывает у тех, кого операция обходит

Описание и топики репы проставлялись деплойером из `.repo-meta` **в архиве** — то есть
репа получала их **только в момент публикации**. Следствие: репы, которые давно
не выкладывались, годами стоят с описанием, равным собственному имени, и **никакой
сигнал об этом не приходит** — с точки зрения деплойера всё отработало.

**Класс шире метаданных:** любое свойство, которое обновляется как **побочный эффект**
другой операции, дрейфует ровно у тех объектов, с кем эта операция давно не происходила.
Чем реже трогают репу, тем сильнее у неё отстают такие атрибуты — то есть **хуже всего
там, где никто не смотрит**.

**Лечение — отдельный проход по всем сразу, со своим источником правды.** Не «починить
деплойер», а завести операцию, для которой этот атрибут — **основной результат**,
и прогонять её по всей системе (`77-system-wide-audit.md`). Дополнительно: если API
умеет только **добавлять** (`--add-topic`), скрипт обязан назвать это ограничение вслух
и напечатать команду ручного снятия — иначе накопленный мусор невидим.

**Обратный сбор** (найти в дочерних репах то, что достойно подъёма) конфликты разрешает
**детерминированным правилом**: поднимать только совпадающее во всех копиях, расхождения —
в отчёт. Результат — **не автокоммит, а решение владельца**.

> **Следствие, о котором забывают:** раздача базы намеренно **не делает релиз** в каждой
> репе — иначе это N релизов инфраструктурного шума (исторический случай: двадцать семь
> патчей подряд вида «обновление слоя до base-repo v1.xx»). Отсюда свойство: **ассет
> последнего релиза содержит базу на момент того релиза, а не текущую.** Тот, кто берёт
> базу из ассета, берёт снимок.

## 7. Когда переезжать в Actions

Стандартный `GITHUB_TOKEN` ограничен своим репозиторием и **не триггерит workflow
в других** — защита от рекурсии. Для кросс-репозиторной работы:

- **PAT в secret** — простейший путь, через `repository_dispatch` / `workflow_dispatch`;
- **GitHub App** — правильнее для долгой жизни: installation-токены живут около часа,
  права точечные, лимит растёт с числом реп (+50 запросов/час за репу свыше 20,
  потолок 12 500/час).

Для одного владельца с ручным запуском раз в месяц Actions — избыточность. Оправданы
при переходе на расписание, работе с нескольких машин или требовании короткоживущих
токенов.
