## Периодическая ревизия (раз в период)

Прогони репу по чек-листу правил чистоты (`05`):
1. Актуальность — есть устаревшее? Обнови/удали.
2. Дубли — есть повторы? Слей.
3. Обобщённость — есть сырой копипаст вместо тезисов? Сожми.
4. Лёгкость — есть тяжёлое/генерируемое? Вынеси/удали.
5. Чистота зоны — есть чужое? Перенеси.

Удобно делать в Cowork: даёшь репу + правила `05`/`06`, просишь пройтись и предложить
правки. Claude находит дубли/тяжёлое, ты подтверждаешь — и коммитишь частями.

## Конвейер: порядок и есть содержание

Когда шагов становится больше трёх, появляется соблазн написать «главный скрипт».
Его ценность **не в том, что он выполняет**, а в том, **в каком порядке** — исполняют
по-прежнему отдельные инструменты.

> **Оркестратор ничего не делает сам. Он вызывает в единственно верном порядке,
> и каждое ограничение порядка имеет названную причину.**

Пример реального конвейера обслуживания системы реп — причина стоит у каждого шага:

| # | Шаг | Почему именно здесь |
|---|---|---|
| 1 | опубликовать накопленное | иначе ревизия будет смотреть на состояние недельной давности |
| 2 | раздать базу и получить свежие клоны | клоны нужны шагу 3; раздать **после** ревизии — значит ревизовать не то |
| 3 | снять состояние (аудит) | по свежим клонам, не по памяти |
| 4 | собрать кандидатов в базу | **до** следующей публикации, иначе они ждут месяц |
| 5 | сверить карту | после того, как состав реп на GitHub уже актуален |

**Проверка, что порядок продуман:** к каждому шагу можно назвать, **что сломается,
если поставить его раньше или позже**. Не называется — порядок случайный, и его
переставят при первой правке.

### Три режима, без которых конвейер не переживёт первого сбоя

| Режим | Зачем |
|---|---|
| `FROM=N` | продолжить с шага N после сбоя, не переделывая пройденное |
| `ONLY_STEP=N` | выполнить ровно один шаг — для отладки и точечной починки |
| `DRY=1` | показать план и не делать ничего |

**Сбой обязан печатать команду продолжения**, а не только факт падения:

```
✗ шаг 3 упал — продолжить можно так: FROM=3 zsh cycle.sh
```

Это тот же принцип, что в `71-fail-loud-and-sourcing.md` §7в–§7г: **диагноз без команды
выхода — половина работы**. Владелец видит проблему и не видит, что делать; на длинном
конвейере это означает перезапуск с нуля.

### Предусловия проверяются до первого шага

Конвейер начинается с проверки, что все вызываемые инструменты на месте, — и падает
сразу, если чего-то нет. Иначе он отработает три шага, упадёт на четвёртом из-за
отсутствующего файла и оставит систему в **промежуточном** состоянии, которое надо
разбирать руками.

Извлечено из `mission-control/scripts/cycle.sh`.

## Раннбук: человеческая половина конвейера

Конвейер отвечает «в каком порядке машина». Раннбук — «что делает человек и что делать,
когда сломалось». Без него набор скриптов знает только тот, кто их написал.

**Четыре части, и третью с четвёртой обычно забывают:**

| Часть | Что в ней |
|---|---|
| 1. Порядок шагов | команда целиком, копипастой, с однострочным «зачем» |
| 2. Предусловия | что должно быть на месте до запуска (токен, права, файлы рядом) |
| 3. **Таблица «если падает»** | **симптом → конкретное действие**, строка на симптом |
| 4. **«Это не сбой»** | пугающие сообщения, которые являются нормой |

### Часть 3: симптом, а не причина

Строка таблицы начинается с того, что человек **видит**, а не с того, что произошло:

| Симптом | Что делать |
|---|---|
| `нет прав` при удалении репы | `gh auth refresh -h github.com -s delete_repo` |
| `HTTP 410` | эндпоинт мёртв — проверить версию API в URL |
| ноль записей при непустом аккаунте | тариф отдаёт ограниченную историю; расхождение пишется в манифест |
| покрытие ниже порога | **не поломка** — остались каталоги вне списка подсказок |

Человек в момент отказа не знает причину — у него есть **строка на экране**. Таблица,
отсортированная по причинам, в этот момент бесполезна.

### Часть 4: «это не сбой» — отдельным разделом

Скрипт печатает `⊘ публичные зеркала пропущены` — и это **защита**, а не ошибка.
Если раннбук об этом молчит, читающий либо испугается, либо (хуже) обойдёт защиту,
решив, что чинит поломку.

> **Правило:** любое сообщение, которое выглядит тревожно и при этом является нормой,
> **обязано быть названо в раннбуке как норма**. Иначе его начнут «чинить».

### Ловушка двухшаговых команд

Разбор и применение показываются двумя командами подряд:

```bash
python3 migrate.py <папка> --group A            # разбор, ничего не меняет
python3 migrate.py <папка> --group A --apply    # применение
```

> **Не вставляй обе одной пачкой:** вторая выполнится сразу, и посмотреть разбор
> **не успеешь**. Смысл двух шагов — в паузе между ними; вставленные вместе,
> они превращаются в один шаг с лишней строкой.

Раннбук обязан это писать прямо, иначе двухшаговая защита сводится на нет самим способом
подачи.

Извлечено из `mission-control/scripts/RUNBOOK.md`.

## 🔴 Автоматизация отваливается молча — у неё должен быть признак живости

Из `dota-dossier/docs/SETUP_AUTOMATION.md` §3. Самая недооценённая часть любого
расписания: **поставить задачу легко, заметить, что она перестала работать, — нет.**

Отказ фоновой задачи не выглядит как отказ. Ошибки нет, сообщения нет, расписание
на месте, скрипт исправен — просто результата больше не появляется. Причины
буднично-разные: сменился путь, кончились права после обновления ОС, машина спала
(`34` §6а), у источника поменялся ответ.

### Признак живости — величина, которая ОБЯЗАНА расти

Не «запускалось ли», а **«появился ли результат»**:

> Если число обработанных стоит на месте, **а работа шла** — автоматизация отвалилась.
> Лучше заметить через две недели, чем через год.

Формулировка важна двумя половинами. «Число не растёт» само по себе ничего не значит —
может, и работы не было. Признак — **расхождение между тем, что происходило,
и тем, что зафиксировано.**

| Плохой признак | Хороший признак |
|---|---|
| «задача есть в `crontab -l`» | число обработанных выросло с прошлой проверки |
| «лог не пустой» | в логе есть записи **после** последней активности |
| «ошибок нет» | ошибок нет **и** результат появился |

**Одна команда статуса важнее любого мониторинга.** Инструмент, работающий
по расписанию, обязан уметь ответить на три вопроса: сколько сделано · сколько
ждёт · когда был последний запуск. Без этого проверка живости требует раскопок,
а значит не делается.

### Почему это не лечится дисциплиной

> Если запускать руками — забудешь. **Не потому что раздолбай, а потому что это
> скучная фоновая задача без обратной связи.**

Расписание и есть способ не полагаться на память (`69` §4в про ту же механику
на уровне гейтов). Но у самого расписания обратной связи тоже нет — поэтому
к нему нужен **признак живости**, иначе цепочка обрывается на шаг позже.

## Частота задаётся ценой потери, а не удобством

Тот же документ, §2. Как выбирается интервал резервного копирования — и любой
периодической задачи, где пропуск означает потерю:

> При копировании раз в два месяца **максимальная потеря — два месяца работы**.

То есть интервал не «раз в месяц, потому что круглое», а **столько, сколько
не жалко потерять**. Вопрос ставится наоборот: сколько данных ты готов лишиться,
если диск умрёт сегодня — вот и интервал.

Смежное правило оттуда же, короткое и точное:

> **Копия считается существующей, когда их две в разных местах.**

Одна копия рядом с оригиналом — это не копия, а иллюзия: оба экземпляра гибнут
от одного события. Разбор шага опроса для сбора данных — `80` §5б; там же про
невозвратность пропущенного окна.

## Совет по ритму

Не «однажды наведу порядок», а **маленькими шагами по триггеру**. Каждый заход
оставляет репу чуть чище, чем была. Журнал (`04`) держит преемственность между заходами.
