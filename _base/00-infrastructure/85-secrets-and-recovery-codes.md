# 85 — Секреты и коды восстановления: где живут и почему не в репе

> **Заказ владельца 22.08.2026, дословно:** *«все пароли, секреты тоже полезно где-то
> держать в одном месте. А то многие приложения делают какие-то коды в случае потери
> пароля, и я не знаю, что с ними делать, я их теряю. Поэтому их тоже надо куда-то класть»*.
>
> Боль настоящая и решается — но **не так**, как решается всё остальное в этой системе.
> Ниже разобрано, почему репа здесь не подходит, и что вместо неё.

---

## 1. Почему это единственный класс, которому репа не подходит

22.08.2026 правило про личные данные было переформулировано (`05-infra-synthesis-lab/STANDARD.md`
§5): паспорта, медкарты, дневники **кладутся в приватные репы штатно** — граница проходит
по публикации, а не по прикосновению. Секреты из этого правила выпадают, и причина
механическая, а не осторожность:

| | Личный документ | Секрет |
|---|---|---|
| попал в репу | лежит, ничего не происходит | **уже скомпрометирован** |
| удалить из истории | не требуется | **невозможно** — остаётся в объектах git |
| как «отменить» | убрать файл | **отозвать у провайдера** и выпустить новый |
| приватность репы защищает? | да | **нет**: репу можно случайно открыть, форкнуть, склонировать на чужую машину |

> **Секрет опасен самим фактом попадания в файл, который версионируется.**
> Из git он не удаляется — он **отзывается**. Файл убирают уже потом, для порядка.

Это не теория: 12.07.2026 в `academic-portfolio` нашлись **живые** VK- и Telegram-токены
в закоммиченном коде (`00-CLAUDE-STOP.md` §2, `PIT-012`). 22.08.2026 при кампании переноса
`.env` с живым токеном `vk1.a…` уехал внутрь `it-base` — от коммита спасло **только**
отсутствие у неё локального `.git` (`PIT-123`).

### Отдельная репа под секреты — рассмотрено и отклонено

| Вариант | Почему нет |
|---|---|
| приватная репа `secrets` | приватность — **настройка**, а не свойство содержимого. Одно неверное нажатие, один форк, один клон на рабочей машине — и отозвать надо всё |
| зашифрованный файл **в** репе | ключ шифрования живёт там же или рядом; при утечке репы остаётся перебор офлайн, без ограничения попыток |
| git-crypt / SOPS | решает для команды с ротацией ключей; здесь один человек и один диск — сложность выше выигрыша |
| секреты в приватной репе «аккуратно» | ровно так уже было дважды (`PIT-012`, `PIT-123`) |

**Вывод: версионирование и секреты несовместимы по построению.** Не «опасно», а
несовместимо: git создан **не терять** историю, а секрет требует **гарантированного
исчезновения**.

## 2. Схема: значения вне git, индекс в git

Тот же приём, что для фотоархива (`31-media-and-photo-storage.md`): **файлы на диске,
каталог в репе**. Здесь он попадает точно:

```
~/Documents/recovery-kits/          ← ЗНАЧЕНИЯ. Вне git, вне репы, никогда не коммитятся
    github/                           коды восстановления GitHub
    proton/                           recovery kit Proton (2 аккаунта)
    vk/                               резервные коды VK ID
    _quarantine/                      найденное при переносах, до разбора

misc-vault/00-secrets-index/        ← ИНДЕКС. В приватной репе, БЕЗ значений
    README.md                         у каких сервисов есть коды, где лежат, когда обновлены
```

**Индекс лечит названную боль.** «Я их теряю» — это отсутствие **описи**, а не хранилища:
владелец не помнит, у каких сервисов коды вообще выпускались и куда положены. Индекс
отвечает на это, не показывая ни одного значения.

### Что можно писать в индекс, а что нельзя

| Можно | Нельзя |
|---|---|
| название сервиса и аккаунт | сам код, пароль, токен |
| **где** лежит файл (путь) | содержимое файла |
| дата выпуска / обновления | подсказки, из которых код восстанавливается |
| сколько кодов осталось неиспользованных | «первые четыре символа» — это уже часть секрета |

## 3. Что считать секретом — и что им НЕ является

Ошибка в обе стороны стоит одинаково: пропустить секрет опасно, а объявить секретом
всё подряд — значит перестать различать.

**Секрет:**

- токен API (`vk1.a…`, `ghp_…`, `sk-ant-…`, `xoxb-…`), ключ доступа, refresh-token;
- пароль в любом виде, включая внутри строки подключения;
- приватный ключ (`id_rsa`, `.pem`, `.p12`), файл `.keystore`;
- коды восстановления, seed-фразы, TOTP-секреты.

**НЕ секрет, хотя выглядит похоже:**

| Пример | Почему |
|---|---|
| `DATABASE_URL=sqlite:///./finpilot.db` | путь к локальному файлу, пароля нет |
| `.env.example`, `.env.template` | шаблон с плейсхолдерами — он **для того и создан** |
| `cacert.pem` из `certifi` | публичный CA-бандл, часть библиотеки |
| Org ID аккаунта | сам по себе доступа не даёт (`84-claude-accounts.md`) |
| `DEBUG=true`, `PROJECT_NAME=…` | конфигурация, не доступ |

🔴 **Проверять содержимое, а не имя.** Замер 22.08.2026: из пяти файлов `.env`, снятых
кампанией переноса в карантин, **секрет был в трёх** (один и тот же VK-токен в трёх
копиях), а два оказались dev-конфигами без единого секрета. Фильтр по имени `.env`
ошибся бы в обе стороны.

## 4. Регламент

| Когда | Что |
|---|---|
| сервис выпустил коды восстановления | положить в `recovery-kits/<сервис>/`, **дописать строку в индекс** |
| нашёлся секрет в репе или переносе | в `recovery-kits/_quarantine/`, отозвать у провайдера, записать `PIT` |
| раз в полгода | сверить индекс с диском: файлы на месте, коды не израсходованы |
| при смене устройства | `recovery-kits` переносится **вручную**, не синхронизацией |

### Проверки, которые уже работают

- `.githooks/pre-commit` — блокирует коммит с секретом (включается
  `git config core.hooksPath .githooks`);
- `scripts/migrate_to_repos.py` → `is_secret()` — уводит секрет в карантин при переносе,
  шаблоны (`*.example`) исключены;
- `sync-base.sh` и `deploy.sh` — предохранитель по `isPrivate`: публичная репа не получает
  ни базы, ни служебного слоя.

### 🆕 Указатель обязан пережить переименование каталога — `EXTERNAL-STORES.tsv`

**Повод замерен 04.09.2026, и дефект был именно здесь.** Каталог переименован
кампанией единого нейминга 03.09 (`recovery_kits` → `recovery-kits`, snake → kebab).
Переименование верное — и **не доехало до четырёх документов**, включая сам индекс
в `misc-vault`. Опись кодов восстановления полгода вела бы в несуществующий каталог.

> **Опись, ведущая по несуществующему пути, хуже отсутствия описи:** отсутствие
> заставляет искать, ложный путь убеждает, что искать негде. Это тот же класс,
> что «отмена правила, дошедшая не всюду» (`/auto` §7) — только предмет не правило,
> а **имя каталога**.

**Механизм — декларация, а не список из головы проверяющего.** Репа, указывающая
на хранилище вне git, объявляет его строкой в `EXTERNAL-STORES.tsv` в своём корне:

```
путь<TAB>что там лежит<TAB>какой документ указывает
~/Documents/recovery-kits	коды восстановления	00-secrets-index/README.md
```

`scripts/home_paths_check.py` проверяет три вещи: каталог существует · указатель
существует · **указатель называет этот же путь**. Третья и есть исходный дефект.

🔴 **Почему не «проверять все пути `~/…` в документах» — измерено и отвергнуто.**
Первая редакция скрипта делала так и дала **66 находок в базе, дефектов — ноль**.
Все законны по трём причинам: команда, которую надо ВЫПОЛНИТЬ (`brew bundle dump
--file=~/Documents/Brewfile` — файл появится после) · констатация отсутствия
(«`~/.cursor` — Cursor на машине нет») · план («убрать `~/Downloads/vk-graph.env.backup`»
верно ровно тогда, когда файла уже нет).

> **Разница между «указатель протух» и «так и задумано» лежит в намерении автора,
> и машине оно не видно.** Настраивать фильтры, пока не станет зелено, значило бы
> подгонять проверку под ответ. Декларация — способ автору назвать намерение сам;
> тот же приём, что `.runtime-writes` (`scripts/runtime_writes.py`).

**Граница:** проверка не знает, полна ли опись **содержимым**. Файл, лежащий
в хранилище и не попавший в документ, ею не ловится — сверка 04.09 нашла такой
(`proton-recovery-phrase`, заведён 23.08 мимо описи) чтением, а не гейтом.

🔴 **Чего проверки не дают:** ни одна из них не знает, **все ли** коды выпущены и собраны.
Это вопрос к владельцу, и индекс существует ровно для того, чтобы на него можно было
ответить взглядом, а не поиском по диску.
