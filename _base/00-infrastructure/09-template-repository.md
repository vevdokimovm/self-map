# 09 — `base-repo` как template repository

> Как использовать встроенный механизм GitHub «Template repository», чтобы заводить
> новые тематические репы с готовым скелетом инфраструктуры в один клик. Плюс честный
> разбор что этот механизм умеет, а что нет.

## Что это даёт

`base-repo` помечена как **template repository** (Settings → General → галка «Template
repository»). Это включает на её странице кнопку **«Use this template»**, которая создаёт
новую репу со всем содержимым `base-repo` — `00-infrastructure/`, `templates/`,
`.gitignore` — но с **чистой историей** (один коммит, без хлама прошлого).

Смысл для нашей системы: новая knowledge-репа (`health-vault`, `it-base`, …) рождается
сразу по стандарту, не надо вручную копировать инфраструктуру и потом чистить.

## Template vs Fork vs Clone (факты из GitHub Docs)

| | Что делает | История | Связь с оригиналом |
|---|---|---|---|
| **Use this template** | Новая репа из скелета | **Чистая** — один коммит | **Нет связи.** Отрезана навсегда |
| **Fork** | Серверная копия чужой репы | Тащит **всю** историю родителя | Есть upstream, можно синкать («Sync fork») |
| **Clone** | Локальная копия на диск | Полная история локально | Остаётся привязан к origin |

Ключевое:
- Template даёт **чистый старт нового проекта**; fork — для контрибьюта в чужой проект.
- Коммиты в репу-из-шаблона **идут в твой contribution graph**; коммиты в форк — нет.
- По умолчанию копируется **только дефолтная ветка** (`main`), остальные — нет.

## Подводный камень (важно)

**Синхронизации с template НЕТ.** Форк можно обновить из upstream кнопкой «Sync
fork». Репа, созданная из шаблона, **отрезана от `base-repo` в момент создания** —
обновил правило в `base-repo`, в уже созданных репах оно само не появится.

Вывод: **template решает «старт», а не «распространение обновлений».** Это фабрика
скелетов, а не живое наследование.

## Как это укладывается в ООП-метафору (честно)

- Template repo — это **не** «наследование, где потомок видит изменения родителя».
  Это **конструктор/фабрика**: `NewRepo = BaseRepo.snapshot_at_creation()`. Слепок на
  момент клика.
- Живой связи «родитель → потомки» между репами git не умеет в принципе.
- Но тебе она и не нужна, потому что **`base-repo` — единый источник правды**: правило
  живёт здесь, тематические репы на него **ссылаются** (в README: «правила — в
  `base-repo`»), а не копируют себе. Меняешь правило один раз здесь — оно актуально для
  всех, потому что все смотрят сюда.

## Рабочая схема (оба механизма, каждый под свою задачу)

1. **Завести новую репу** → «Use this template» на `base-repo`. Получаешь готовый
   скелет с инфраструктурой. Дальше наполняешь контентом по теме.
2. **Держать правила едиными** → `base-repo` как единый источник. В новой репе не
   дублируешь правила целиком, а ссылаешься на `base-repo` и переопределяешь только
   своё (как `academic-portfolio-slimming.md` наследует общий протокол сжатия).
3. **Обновил общее правило** → правишь в `base-repo`. Существующие репы перечитывают
   отсюда; если где-то была локальная копия правила — синхронизируешь вручную (потому
   и не копируем целиком, а ссылаемся).

## Как создать репу из шаблона (шаги)

1. На странице `base-repo` → кнопка **«Use this template»** → **Create a new repository**.
2. Owner: `vevdokimovm`. Имя новой репы — по неймингу (`01-repo-standard.md`).
3. Visibility: **Private** (все репы приватные).
4. Ветки: по умолчанию только `main` — этого достаточно.
5. Create repository → клонируй локально → наполняй контентом.

> Приватный template виден и доступен для «Use this template» только тебе — ровно то,
> что нужно для личной системы реп.
