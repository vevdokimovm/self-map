# 46 — Где лежит CHANGELOG

> **Зачем понадобилось.** Журнал base-repo лежал в `00-infrastructure/CHANGELOG.md`. Деплойер
> искал его только в корне, не нашёл — и выпустил **шесть релизов без описания, без тезиса,
> с техническим заголовком**. Файл всё это время существовал. Отсюда два правила: одно для
> человека (клади в корень), одно для инструмента (ищи везде).

---

## 1. Канон: корень репозитория

```
<repo>/CHANGELOG.md
```

Не `docs/`, не `00-infrastructure/`, не `meta/history/`. Корень.

Причины ровно две, обе практические:
- **Видно сразу.** Открыл репу — журнал в списке файлов, рядом с README. Не надо знать структуру.
- **Находится без догадок.** Любой инструмент — свой скрипт, чужой парсер, GitHub — смотрит
  в корень первым делом. Файл в подпапке существует, но для инструмента его как будто нет.

Один репозиторий — **один** `CHANGELOG.md`. Не заводим по журналу на подсистему: история,
разрезанная на части, перестаёт отвечать на вопрос «что менялось в проекте».

---

## 2. Исключение: журнал отдельного документа

У документа со своим ритмом жизни бывает своя история — `repos-map-CHANGELOG.md` рядом с
`repos-map.md` (см. `44`). Это **не** нарушение: имя другое (`<имя>-CHANGELOG.md`), назначение
другое, с главным журналом не конкурирует. Инструменты такие файлы из поиска исключают по имени.

---

## 3. Инструмент обязан искать везде

Стандарт не должен ломать то, что уже сделано иначе. Порядок поиска в `templates/deploy.sh`
и `templates/fix_releases.sh`:

1. `CHANGELOG.md` в корне
2. `docs/CHANGELOG.md`, `00-infrastructure/CHANGELOG.md`
3. рекурсивный поиск `CHANGELOG*.md` до 4 уровней вглубь

На каждом шаге проверяется **наличие секции нужной версии** — это единственный надёжный признак,
что найден именно тот журнал, а не шаблон и не чужая история. Из поиска исключаются
`*TEMPLATE*`, `*repos-map*`, `_archive/`, `node_modules/`, `.git/`.

Нашёл не в корне — работает, но печатает путь в выводе. Это подсказка перенести файл, а не ошибка.

---

## 4. Нет секции — нет релиза

Жёсткое правило, введённое после инцидента: **релиз без описания не создаётся вообще.**

Раньше при ненайденной секции подставлялась заглушка «Синхронизация дерева» — и релиз уезжал
на GitHub пустым. Теперь такая версия пропускается: дерево и тег публикуются, релиз — нет,
а имя версии попадает в блок «ТРЕБУЕТ ТВОЕГО РЕШЕНИЯ».

Почему так, а не «выпустим с заглушкой»: пустой релиз выглядит как сделанная работа и потому
не чинится годами. Отсутствующий релиз виден сразу и чинится за минуту — дописал секцию
в `CHANGELOG.md`, прогнал `fix_releases.sh`.

---

## 5. Проверка при заведении репы

1. `CHANGELOG.md` в корне?
2. Секция текущей версии есть, заголовок по `42` (`## [X.Y.Z] — дата — тезис (BUMP)`)?
3. Если журнал исторически в подпапке — перенести в корень, на старом месте оставить
   файл-указатель, чтобы ссылки не ломались.

---

> **Одной строкой:** `CHANGELOG.md` лежит в корне — так видно человеку и находится инструментом;
> инструмент всё равно ищет по всему дереву и выбирает тот журнал, где есть секция версии;
> секции нет — релиз не создаётся, а версия уходит в громкий флаг.
