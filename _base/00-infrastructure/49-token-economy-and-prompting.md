## 1. Из чего складывается расход

**Стейтлес-механика — корень всего.** Messages API не хранит состояние: на **каждый**
ход клиент отправляет весь предыдущий диалог заново. System prompt, определения тулов
и вся история — это input, пересчитываемый целиком каждый раз. Отсюда прямое следствие:
**стоимость хода растёт с накопленной историей, даже если новое сообщение — одно слово.**
Официально прямым текстом: «a one-line question in a session that has been open all day
still draws usage for the whole conversation».

**Prompt caching — единственный механизм, который это компенсирует.** Порядок рендера
запроса фиксирован: `tools → system → messages`. Кэш — префиксный: любое изменение байта
в начале (порядок тулов, текст system prompt, порядок сообщений) ломает кэш от этой точки
и дальше.

| Операция | Множитель к цене обычного input |
|---|---|
| Cache write, TTL 5 мин (дефолт на API-ключе/облаке) | ×1.25 |
| Cache write, TTL 1 час (дефолт на подписке Claude Code, если не сорвался в credits) | ×2.0 |
| Cache read (хит) | **×0.1** |

Промах кэша (пауза дольше TTL) откатывает следующий запрос с дешёвого read (×0.1) на
дорогой write (×1.25–2.0) — **разница в 12.5–20 раз** на объём кэшированного префикса.
Минимальная кэшируемая длина префикса — от 512 до 4096 токенов в зависимости от модели;
короче — кэш молча не срабатывает (0 в обоих счётчиках, без ошибки).

🟢 **ЗАМЕРЕНО 22.08.2026 — `/login` сбрасывает кэш целиком.** Три настоящие команды
за сессию (найдены **структурным** поиском по полю команды; текстовый поиск давал 25
ложных срабатываний — `SYN-032`). Два хода сразу после `/login`:

| Ход | Пересоздано префикса | `cache_read` | Пауза перед ходом |
|---|---|---|---|
| 11:39:32 | 49 071 | **16 900** | 8 минут |
| 11:54:49 | 83 264 | **16 900** | 3 минуты |

`cache_read` = 16 900 — это **голый системный префикс**. Паузы 8 и 3 минуты, то есть
глубоко внутри часового TTL: простоем это не объясняется.

> **Цена `/login` равна всему текущему контексту.** Здесь вышло дёшево (49K и 83K), потому
> что оба пришлись на низкий контекст сразу после компакта. На 997K тот же `/login` стоил бы
> **почти миллион токенов за один ход**.

🔴 **Отдельно: недельный лимит `/login`-ом не «пережидается», а обходится сменой аккаунта.**
В той же сессии `seven_day` rate-limit с ресетом на 25.08 прилетел в 11:44:59, а в 11:54:09
владелец сделал `/login` — и следующий ход прошёл. Наблюдение «лимит снялся сам за 9 минут»
**неверно** и опасно: по нему следовало бы ждать девять минут вместо часа.

**Что ломает кэш:** смена system prompt, смена набора tools (ломает уровень
tools+system+messages целиком), включение/выключение web search или citations, смена
`speed`/`tool_choice`/thinking-параметров, добавление/удаление изображений.

**Длина промпта пользователя** влияет напрямую (больше input) и косвенно: расплывчатый
запрос провоцирует более широкое сканирование (больше файлов читается → больше tool
calls) и более длинный ответ — эффекты мультипликативны, не складываются.

**Количество tool calls.** Каждый вызов инструмента и его результат необратимо входит
в `messages` — то есть входит в **каждый** последующий запрос сессии, пока не будет
`/clear`. 10 вызовов Bash с длинным stdout — это не 10 отдельных трат, а постоянная
надбавка ко всем оставшимся ходам. Это прямое подтверждение фактора **F5** и **F7** из
`hypothesis.md`.

**Extended thinking / effort.** Thinking-токены билятся как output. На адаптивных
моделях `effort` (`low…max`)
управляет тем, сколько модель «думает» на каждом шаге — это прямой рычаг фактора **F2**.

🔴 **Поправка 28.08.2026 (внешний ресёрч,** `reports/research/claude-official-
practice-vs-internal-2026-08-28.md` **):** упоминание «`ultracode`-режима
оркестрации поверх» удалено — уже опровергнуто внутренне (`51` §5а: в CLI
2.1.238 такого ключа нет), внешний источник закрывает вопрос со второй
стороны: словесный бюджет размышления (`think`/`ultrathink`) как официальный
интерфейс исчез из актуальной документации Claude Code, остался только
`effort`. На Claude 4.7+ `budget_tokens` **возвращает ошибку 400** —
использовать `effort`, не бюджет токенов.

**Auto-compact.** Срабатывает при приближении к лимиту контекста модели (не жёсткий
буфер «13K», это устаревшая цифра). Экономит **не в моменте**: сам вызов `/compact`
читает всю историю целиком, чтобы её суммировать — это разовый дорогой запрос.
Экономия — в будущих ходах (меньше input на каждый следующий). `/clear`, наоборот,
обнуляет историю бесплатно, без пересжатия.

**Цены моделей (лист Anthropic, если не оговорено иначе в контракте):**

| Модель | Input $/M | Output $/M | Контекст |
|---|---|---|---|
| Haiku 4.5 | $1.00 | $5.00 | 200K |
| Sonnet 5 | $3.00 | $15.00 | 1M |
| Opus 5/4.8/4.7/4.6 | $5.00 | $25.00 | 1M |
| Fable 5 / Mythos 5 | $10.00 | $50.00 | 1M |

Это **ценовая**, не расходная-по-лимиту шкала — не путать с множителями `hypothesis.md`
§3 (те про то, сколько % сессии/недели съедает ход, а не сколько это стоит в $). Но
соотношение цен даёт лучший на сегодня источник для приора F1: Sonnet:Opus ≈ 0.6 по input
и output одинаково (не 0.4, как было записано в v0.1 из старой памяти цен) — **эту цифру
стоит перепроверить эмпирически**, приоритет в backlog `hypothesis.md §5.2`.

## 1а. Кириллица дороже латиницы примерно вдвое

Токенизаторы обучены на англо-доминантных данных, поэтому кириллица дробится на **больше
токенов на символ**:

| Язык | Символов на токен (грубо) |
|---|---|
| английский, код | ≈ 4 |
| **русский** | **≈ 1,5–2** |

**Следствие, которое ломает планирование:** русский текст на 3000 символов — это примерно
1500–2000 токенов, а не 750, как получилось бы по английской прикидке. Ошибка **вдвое**,
и она систематическая, а не случайная.

Практически это значит: **дамп русского текста в контекст дороже, чем кажется по числу
символов.** При оценке «влезет ли источник» считать по русскому коэффициенту, а не по общему.

*Извлечено из `character-a-analysis/10-life-history/00-protocol/05-context-mechanics.md`
(20.08.2026, синтез инфраструктур). Оценка эмпирическая, не измерение — уточняется по
`61-token-analytics.md` §5.*

## 1б. 🔴 Effort покупает обдумывание, а не скорость; инструменты стоят на КАЖДОМ ходу

§4 (правила 9 и 10) говорит «понижай effort для рутины» и «отключай неиспользуемые
MCP-серверы» — верно, но без чисел это советы. Числа меняют решения, и они собраны
в `personal-finance-dss/docs/claude_operating_table.md` — сводке семи заходов исследования.

### Effort: растёт время до первого токена, не скорость генерации

| Уровень | Время до первого токена | Скорость генерации |
|---|---|---|
| low | ~3 с | ~52 т/с |
| medium | ~6,5 с | ~52 т/с |
| high | ~13 с | ~53 т/с |
| xhigh | ~25 с | ~53 т/с |
| **max** | **~92 с** | ~54 т/с |

**Скорость генерации почти не зависит от усилия.** Растёт только объём размышлений —
а с ним время до первого токена. Разница `low → max` по этому времени — **тридцатикратная**.

> **Поднимая effort, вы покупаете обдумывание, а не скорость.** Это самая дорогая ручка
> в контуре, и она не ускоряет ничего.

Практический вывод той же таблицы: рабочий дефолт — **high**; `max` держится на эскалацию
(сложная многофайловая отладка, архитектурные развилки) и почти всегда избыточен
для рутинного кода и рефакторинга.

### Определения инструментов оплачиваются каждым запросом

Самая недооценённая статья расхода: **инструмент стоит не при вызове, а при наличии.**

| Статья | Токены |
|---|---|
| определение одного инструмента MCP | **200–800 на каждый запрос** |
| три сервера MCP по 50 инструментов | **≈60 000 на ход** |
| то же после Tool Search | ~~~600 вместо ~12 000 (−95 %)~~ · 🔴 **уточнено 02.09.2026**: официальная цифра Anthropic — **72 000 → 8 700, −85 %** |
| коннектор репозитория в веб-версии | **≈26 000 на каждом ходу** |
| системный промпт свежей сессии | ~4 200 |
| файл проектных инструкций до первого промпта | ~1 800 |

**Шестьдесят тысяч токенов на ход, не сделав ничего** — это цена подключённых и
не используемых серверов. В сочетании с `C ≈ 0,1 × контекст + 5 × выход` (§2а) она
умножается на каждый последующий ход сессии.

> **Отключить неиспользуемый сервер — самая дешёвая оптимизация из существующих:**
> одно действие, эффект на каждом ходу до конца сессии. Механизм отложенной загрузки
> определений (Tool Search) даёт тот же порядок выигрыша, когда отключить нельзя.

🔴 **Уточнение 02.09.2026 — Tool Search включён ПО УМОЛЧАНИЮ.** `ENABLE_TOOL_SEARCH`
имеет значение `true` начиная с версии **2.1.232**; проверено на машине владельца
(2.1.258, флаг нигде не переопределён). Значит расхожая посылка «каждый
подключённый MCP-сервер грузит свои описания в каждую сессию целиком» **для нашей
установки неверна** — они лежат в индексе поиска.

Прежняя внутренняя цифра «−95 %, ~600 вместо ~12 000» пришла из сводки
`personal-finance-dss/docs/claude_operating_table.md`, происхождение неизвестно.
Официальная — **72 000 → 8 700 (−85 %)**, замер Anthropic 24.11.2025. Порядок
выигрыша совпадает, конкретные числа разные; строка помечена, а не переписана
молча (`71` §5д: опровержение записывается **поверх**, а не вместо).

Второй рычаг, о котором стоит знать: `MCP_DISCOVERY_CACHE` — список инструментов
удалённого сервера читается из кэша, сам сервер подключается при первом вызове.
🔴 **По умолчанию `false` начиная с v2.1.238**, включается как
`MCP_DISCOVERY_CACHE=1 claude`.

Разбор целиком — `13-ai-tools-lab/research/mcp-protocol-2026-09-02.md`.

### Метка «публично не существует» — четвёртая степень уверенности

Та же таблица размечает каждое число одной из четырёх меток: **официальная документация ·
независимо измерено (с указанием кем) · оценка · публично не существует**.

Четвёртая — добавка к схеме `28` §6а («измерено или выведено»), и она рабочая: строка
«разбивка по усилиям для такой-то модели — **[ДН]**» сообщает, что искать бесполезно,
и **закрывает вопрос**, вместо того чтобы оставлять пустую клетку, которую следующая
вахта пойдёт заполнять заново.

> **Срок годности такой таблицы низкий, и это пишется в ней самой.** Правило оттуда:
> устаревшую строку **не переписывать молча** — помечать дату и что изменилось.
> Иначе таблица чисел превращается в таблицу утверждений без возраста
> (`SYN-023`: число без версии источника не воспроизводится).

**Родня:** §2а (компакция: цена хода растёт с контекстом) · §4 правила 9–10 ·
`28` §6а (пометка происхождения числа) · `16-limits-empirical-estimate.md`.

## 2. Специфика Claude Code — как смотреть расход у себя

- **`/usage`** — актуальная команда (заменила `/cost`). Даёт точную разбивку по сессии:
  input, output, cache read, cache write, по каждой использованной модели + расчётную
  цену по листовым ставкам. На платных планах — ещё атрибуция по skills/subagents/
  plugins/MCP-серверам.
- **`/context`** — живая разбивка контекста по категориям (system prompt ~4200 базово,
  auto memory, CLAUDE.md, прочитанные файлы, MCP tool listing, вывод хуков) — используй,
  когда непонятно, что именно раздуло контекст.
- **Статусбар** — можно включить постоянный показ usage (`/config` → статуслайн).
- **Точность:** `/usage` считает по листовым ставкам локально, реальный контрактный
  биллинг может отличаться — авторитетный источник для денег, не для % лимита, это
  Console/Enterprise Analytics API.
- **Сторонний инструмент — `ccusage`** (ccusage.com): читает локальные JSONL-логи
  сессий, даёт отчёты по дате/сессии/проекту/модели, hit-rate кэша, тренды. Дополняющие:
  `ccwhy` (находит конкретных «съедателей» токенов), Claude-Code-Usage-Monitor
  (реалтайм-график + прогноз времени до лимита).

**Это прямой ответ на пункт 3 исходного запроса** (тот же анализ средствами самого
Claude Code): `/usage` — теперь основной инструмент калибровки `measurements.csv` вместо
процента в статусбаре; протокол замера обновлён в
`reports/experiments/token-consumption/README.md`.

## 2а. 🔴 Компакция: порог, рычаги, и почему она ВЫГОДНА по расходу

Наблюдена живьём 21.08.2026, сверена с документацией
(`code.claude.com/docs/en/model-config`). Разбор с числами —
`reports/experiments/token-consumption/context-growth-analysis.md` §11.

### Порог по умолчанию — не процент, а предел окна

> *«If you don't set an auto-compact window, Claude Code compacts when the conversation
> reaches **the model's context limit**»*

| Конфигурация | Когда компактит |
|---|---|
| Opus с 1M-окном | **на пределе окна** — замерено **1 000 215** |
| Sonnet 5 | **заранее, ~967K** по документации (было ~934K до 2.1.247, 26.08.2026) — замерено **934 095** до этой версии |
| Sonnet 4.6 / Opus 4.6 без extended context | граница **200K** |
| Opus 4.8 / Opus 5 на Bedrock, GCP, Foundry | граница **200K** |
| `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` | **200K** для всех, включая нативные 1M |
| Облачные сессии | «по мере приближения» к пределу |

🔴 **Ходовая community-цифра «83.5% с буфером 33K» — неверна** для локальной сессии;
оба наших замера ей противоречат.

🟡 **Пересмотрено 28.08.2026 (внешний ресёрч):** утверждение «переменной
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` в официальной документации нет» —
**вероятно опровергнуто**. Она найдена среди официальных переменных
управления компакцией на `code.claude.com/docs/en/model-config` (процент
1–100 от auto-compact-окна), но без отдельной дословной цитаты — статус
«вероятно опровергнуто, нужна одна прямая перепроверка», не «точно
неверна». Два сценария: переменную добавили в доки после 21.08.2026
(тогда прежняя запись была верна на свою дату), либо первая проверка её
просто не нашла.

**Opus поднимается до 1M автоматически** на планах Max/Team/Enterprise — без `[1m]`
и без настройки.

### Рычаги, приоритет сверху вниз

1. `CLAUDE_CODE_AUTO_COMPACT_WINDOW` — скрипты и облако, **перебивает всё остальное**,
   принимает только голое число.
2. `--autocompact` при запуске — на один запуск; в отличие от команды **не перебивается**
   managed settings.
3. `/autocompact 500k` — сохраняется в user settings как `autoCompactWindow`;
   `/autocompact auto` возвращает настроенный под модель порог.

Диапазон **100K…1M** (`200000`, `500k`, `1M`, либо 100–1000 как тысячи). Выше окна
модели не поднять — обрезается. Смежные: `DISABLE_COMPACT` (выключить совсем),
`CLAUDE_CODE_MAX_CONTEXT_TOKENS` (объявить окно для шлюза), 
`CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1`.

### Что компакт делает с диалогом

Из маркера `{"type":"system","subtype":"compact_boundary"}` в логе сессии:

- **сводка = 1.3% замененного** (13 452 против 1 000 215);
- 🔴 **хвост диалога переносится ДОСЛОВНО** — поле `preservedMessages`, у нас
  **27 сообщений**. Значит «после компакта модель ничего не помнит» неверно:
  теряется **середина**, ближний контекст остаётся буквальным;
- `preCompactDiscoveredTools` помечает инструменты, подгруженные по ходу, к восстановлению;
- **время**: 175 секунд у Opus, **715 секунд** у Sonnet на сопоставимом объёме. В ночном
  автономном контуре 12 минут тишины легко принять за зависание (`06-autonomous-mode-kit`).

### 🔴 Поведенческое следствие: доверие саммари РАСТЁТ с заполнением окна

**Поднято 05.09.2026** из `character-a-analysis/LESSONS.md` У-3 — там это
измерено на 19 сессиях подряд.

Потеря середины (выше) — свойство механизма. У неё есть следствие, которое
касается не расхода, а **надёжности работы**:

> **Чем полнее контекст, тем чаще исполнитель подменяет проверку
> воспоминанием.** К этому добавляется дрейф формата и нумерации:
> ближе к концу длинной сессии таблицы и счётчики начинают расходиться
> с теми, что в начале.

**Чем это оборачивалось на практике** (там же, У-1): дубликат уже написанного
батча · «~30 страниц прочитано» при непрочитанном источнике · батч, числившийся
готовым в сводке и отсутствовавший в файлах.

🔴 **Опасность в том, что признак незаметен изнутри.** Ошибка выглядит как
уверенное знание: исполнитель не чувствует разницы между «помню» и «проверил»,
и заполненность окна эту разницу как раз и стирает.

**Противоядия, по убыванию надёжности:**

1. **перечитывать реестр командой, а не памятью** — каждый раз, даже если
   «только что смотрел»;
2. **свежая сессия обнуляет проблему** — это довод в пользу хендоффа
   раньше, чем окно упрётся;
3. **сверять состояние эмпирически в начале сессии**, а не принимать сводку
   предыдущей на веру (`73-chat-handoff.md`: «не верь саммари, проверь файлы»).

**Связка с компактом:** после него ближний контекст буквален, а середина —
сводка на 1.3 % объёма. То есть сразу после компакта риск максимален именно
для того, что обсуждалось в середине сессии, и именно там надо перечитывать
файлы, а не вспоминать.

### 🔴 По расходу компакт — не издержка, а самая выгодная операция

Ход на пределе окна стоит ~107 000 усл. ед., ход сразу после компакта — ~13 000.
Экономия ~94 000 на ход при оценочной цене компакции ~167 000: **окупается меньше
чем за два хода**, дальше держит цену втрое ниже.

> **Бояться компакта по деньгам не нужно — он их возвращает.** Его цена в другом:
> потерянная середина истории и минуты ожидания. Решать по ним.

🔴 **Цена самой компакции в лог не пишется** — между последним ходом до и первым после
нет записей с `usage`. Значит суммарный расход любой сессии с компактом **занижен**;
это дефект метода замера, а не данных.

**Ловушка:** после компакта контекст растёт **быстрее** (2 206 против 1 628 ток/реплику) —
сводка плотная, файлы подтягиваются заново. Второй компакт придёт раньше первого.

### Цены: излома на 200K нет

> *«The 1M context window uses standard model pricing with no premium for tokens
> beyond 200K»*

Подтверждено независимо замером: кривая цены хода проходит через 200K без ступеньки.
Значит планировать расход можно одной формулой на всём окне — `0.1×контекст + 5×выход`.

### Продуктовый слой меняет расход молча

Официальный постмортем (`anthropic.com/engineering/april-23-postmortem`): с **4 марта
по 7 апреля 2026** дефолтный `effort` в Claude Code был снижен с `high` до `medium`,
а с 26 марта баг чистил старое «мышление» каждый ход. Закрыто к 20 апреля; сырое API
не затрагивалось.

> **Правило для любого замера расхода: фиксировать не только модель, но и версию CLI
> и дату.** Продуктовый слой меняется независимо от модели и меняет расход, не сообщая
> об этом. Замеры по разные стороны такой правки несравнимы.

## 3. Subagents — экономия и её цена

Каждый субагент — **отдельное контекстное окно**, отдельный (короче) system prompt.
Официальный пример: субагент прочитал 6100 токенов файлов у себя, в контекст родителя
вернулось только 420 токенов финального текста + метаданные.

**Собственный замер (2026-08-20, реальный лог, `token-consumption/measurements.csv`,
baseline `subagent-fanout-4x`):** 4 параллельных research-субагента потратили сами
342 164 токена (97979+87702+93570+62913), но рост контекста родителя в момент их спавна
остался в пределах обычного приращения хода — почти весь этот расход прошёл мимо
контекста родителя. Подтверждает механику не только по документации, но и на реальной
сессии этой репы.

- **Экономия** — родительский контекст не пухнет историей чтения субагента, все
  следующие ходы родителя дешевле.
- **Не бесплатно** — субагент реально тратит собственные input/output токены, это
  дополнительный, параллельный биллинг, не трюк с нулевой ценой. Плюс стартовый оверхед
  на спавн (CLAUDE.md, MCP, skills подгружаются заново).
- Модель субагента настраивается отдельно (дешевле для рутины — `model: haiku`).
- **Agent teams** (параллельные полноценные инстансы) — расходуют ориентировочно
  **в ~7 раз больше**, чем одна сессия, в plan mode — каждый тиммейт держит своё полное
  окно. Не включать по умолчанию. 🔴 **Число не подтверждено внешним источником
  (28.08.2026)** — целевой поиск по трём независимым субагентам не нашёл ни
  подтверждения, ни опровержения; происхождение внутри системы неизвестно.
  Официальные цифры **другие и про другое**: агенты в целом ≈ **4×** расхода
  относительно обычного чата, полноценные многоагентные системы ≈ **15×**
  (`anthropic.com/engineering/multi-agent-research-system`, 13.06.2025). Не
  заменено — при использовании в решениях помнить, что 7× не официальная
  цифра, а 4×/15× — да, но про другой сценарий (не про `agent teams`
  конкретно).

## 4. Playbook — 12 правил с механикой, а не советы вообще

1. **Формулируй промпт конкретно (файл/функция/строка), не «улучши код».** Расплывчатый
   запрос запускает широкое сканирование → больше tool calls → каждый необратимо входит
   в контекст (§1) → дороже все следующие ходы.
2. **`/clear` при смене темы, не тяни старую сессию.** Стухший контекст пересчитывается
   как input на каждом ходе даже для однострочного вопроса; `/clear` — бесплатно,
   `/compact` — нет (сам читает всё, чтобы сжать).
3. **Не трогай начало system prompt/порядок tools между запросами без нужды.** Любое
   изменение здесь роняет кэш по всей цепочке `tools→system→messages` — следующий
   запрос откатывается с ×0.1 на ×1.25–2.0.
4. **Держи паузы между сообщениями короче TTL кэша** (5 мин на API-ключе/облаке, 1 час
   на подписке Claude Code) — иначе первый запрос после паузы полностью промахивается
   мимо кэша.

   🔴 **Замерено 22.08.2026, лог `2de60c0b`, 529 ходов.** Правило верно и **стоит больше,
   чем кажется по формулировке**. Два простоя — 3 ч 55 м и 4 ч 33 м — дали пересоздание
   префикса на **157 566** и **641 538** токенов. Это **40 % всего `cache_creation`
   за сессию** на двух ходах из 529, при среднем hit rate **99.3 %**.

   > **Простой ≥ 1 часа стоит одного полного контекста.** `cache_read` падает
   > до 16 900 — голого системного префикса, — и весь набранный контекст
   > оплачивается заново. На 650 000 это дороже, чем весь предшествующий час работы.

   **Практическое следствие для автономных прогонов:** интервал сторожевого будильника —
   не вопрос удобства. Он обязан удерживать прогон **внутри часового окна**; выбранный
   «по длине батча» интервал 1800 с оставлял простои, выходившие за TTL (`SYN-031`).

   📍 **Правило существовало здесь всё время и не доехало до решения.** Интервал сторожа
   выбирали в `/auto`, не заглянув в `49` §4.4 — классическая цена того, что правило
   лежит в документе, а решение принимается в другом. Разбор — `21` §4г-трис.
5. **Делегируй «шумные» операции (тесты, логи, доки) субагентам.** Субагент читает
   много, в родителя возвращает только summary — не экономит абсолютный бюджет
   организации, но экономит контекст родителя (а значит все его следующие ходы).
6. **Ставь субагентам дешёвую модель, если не нужен сложный ризонинг.** Haiku в 5–25 раз
   дешевле Opus по input/output — для «сходи прочитай/просуммируй» обычно достаточно.
   🔴 **Ловушка, найдена 28.08.2026 (внешний ресёрч):** минимум кэшируемого префикса
   **не монотонен по поколениям** — 512 токенов у Opus 5/Fable 5/Mythos 5, 1024 у
   Sonnet 5/Opus 4.8, 2048 у Opus 4.7/Haiku 3.5, но **4096 у Haiku 4.5 и Opus 4.6/4.5**.
   На короткой задаче (system prompt субагента + краткое задание короче 4096 токенов)
   Haiku 4.5 **молча не кэшируется вовсе** — без ошибки, с нулями в обоих счётчиках
   кэша. «Дешёвая модель» на коротких задачах может выйти дороже ожидаемого — сверять
   длину префикса, не только цену токена.
7. **Не включай agent teams по умолчанию.** Параллельные полноценные инстансы — это
   ~7× расход, оправдан только когда параллелизм реально нужен, а не «для скорости».
8. **Специфичные workflow — в skills, не в CLAUDE.md.** CLAUDE.md грузится целиком при
   старте КАЖДОЙ сессии; skills — только когда реально вызваны.
9. **Отключай неиспользуемые MCP-серверы, предпочитай CLI-эквиваленты** (`gh`, `aws`
   вместо MCP-обёрток). Каждый MCP-сервер добавляет имя+метаданные в базовый контекст
   на старте, CLI-тул — нет.
10. **Понижай `effort` для рутины, поднимай только для архитектурных решений.** Effort —
    главный рычаг адаптивного thinking (биллится как output) и глубины/числа tool calls.
11. **Клади критерий проверки прямо в промпт** (тесты, ожидаемый вывод, скриншот).
    Модель сама верифицирует до ответа — меньше циклов «сделал не так → правь» = меньше
    повторных полных пересчётов контекста.
12. **Мониторь `/usage` и `/context` регулярно**, для трендов — `ccusage`. Ловит
    деградацию кэша (много cache write при ожидаемых read) раньше, чем она станет
    дорогой привычкой.
