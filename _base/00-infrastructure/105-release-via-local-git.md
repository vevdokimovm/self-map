## §2. Порядок работы — три команды

```bash
python3 scripts/close_batch.py <репа> --minor --title "…" --body-file <файл>
python3 scripts/publish.py <репа>
```

`close_batch.py` поднимает версию, пишет журналы, собирает архив и **сам
печатает следующий шаг**. `publish.py` делает шесть шагов, каждый проверяется:

| шаг | чем | зачем |
|---|---|---|
| 1. атрибуция | `attribution_check.py` | в истории только владелец |
| 2. описание | `release_notes.py` → парсер **деплойера** | формат как у остальных 530 релизов |
| 3. ассет | `<репа>-v<версия>.zip` | как делает деплойер |
| 4. коммит и тег | локальная подпись + хуки | подпись не зависит от глобального конфига |
| 5. push | ветка и тег | — |
| 6. релиз | `gh release create` с телом и ассетом | — |

Заведение `.git` в новой репе — `python3 scripts/git_adopt.py <репа>`.

## §2а. Два режима `github_sync.py` — деплой архива и синхронизация

Заведён 13.09.2026 по заказу владельца: *«сделай так чтобы ты пушил комитил
релизил описания делал во всех репах также как делал это скрипт деплоя»*.

| режим | что делает | когда |
|---|---|---|
| `--archive <zip>` | версия из архива: коммит → тег → push → релиз с описанием из `CHANGELOG` архива и архивом во вложении | архив собран `pack_release.py`, но не выпущен |
| `--sync <репа>` | GitHub приводится к рабочей копии 1 в 1 (по правилам `.gitignore`) | диск ушёл вперёд GitHub |

🔴 **Режим архива не трогает рабочее дерево.** Архив распаковывается
во временный каталог, коммит собирается через **временный индекс**
(`GIT_INDEX_FILE`) и `commit-tree`. Ни `checkout`, ни `reset`, ни `clean`
не зовутся нигде: рабочая копия — оригинал, а не копия истории.

🔴 **Несколько версий одной репы — ОДИН push.** Раздельный push гонит общие
объекты дважды: у `legal-knowledge-base` это 975 МБ за одну версию и 1388 МБ
за вторую при том, что большая часть файлов у них общая.

### Две проверки до любой отправки, их нельзя отключить флагом

1. **Секреты** — функцией `scan_secrets` **из самого хука** `.githooks/pre-commit`,
   а не её копией: правило живёт в одном месте (`PIT-G`).
2. **Атрибуция** — `attribution_check.py` по сообщению и подписи.

**Правила веса и форматов хука здесь не применяются**, и это осознанно:
`deploy.sh` их тоже не применял (он работал в своём клоне без хуков),
а эталон на диске прошёл их при сборке архива.

## §3. 🔴 Настройки, без которых это не работает

Ставятся **локально** при заведении. Каждая — из замера, а не из вкуса.

| настройка | значение | что будет без неё |
|---|---|---|
| `user.name` / `user.email` | владелец | подпись возьмётся из глобального конфига или окружения — непредсказуемо |
| **`core.autocrlf`** | **`false`** | 🔴 `git status` уходит в сеть **по запросу на файл** |
| `core.hooksPath` | `.githooks` или `_base/.githooks` | защита атрибуции не сработает |
| `feature.manyFiles` | `true` | `status` в разы медленнее на больших репах |
| `core.fsmonitor` | `true` | то же самое |

### Почему `core.autocrlf=false` — главная строка

Хеш локального файла — это **не** `sha1(файл)`, а `sha1(convert_to_git(файл))`.
При `autocrlf=input` конвертация зовёт `has_crlf_in_index()`, а та **читает
старый блоб из базы объектов** — безусловно, даже если в файле нет ни одного
`CR`. Блоба при частичном клоне нет → докачка по сети, по одному
HTTP-запросу на файл.

**Замер на двух репах, отличается одна строка конфига:**

| | `exam-kit` (`input`) | `ml-base` (`false`) |
|---|---|---|
| `.git` после `status` | 4884 КБ | **264 КБ** |
| сетевых докачек | **29** | **1** |
| время `status` | минуты | **1 с** |

**Побочная выгода:** документация `core.safecrlf` предупреждает, что
конвертация **портит бинарные файлы**, ошибочно принятые за текст. В этих
репах лежат PDF, PNG и ZIP.

## §4. Цена — замерена, а не оценена

### Диск

**`.git` зависит от ЧИСЛА файлов, а не от их веса.**

| репа | рабочая копия | файлов | `.git` | доля |
|---|---|---|---|---|
| `it-base` | **754 МБ** | 12 263 | 9.3 МБ | 1.2 % |
| `exam-kit` | 136 МБ | 913 | 4.9 МБ | 3.6 % |
| `ml-base` | — | ~5 000 | **264 КБ** | — |

**Прогноз на 67 реп: 200–400 МБ** при 57 ГБ свободных — меньше процента.

### Скорость

`it-base`, 12 263 файла, git 2.50.1:

| | время |
|---|---|
| первый `status` после включения ускорения | 479 мс |
| повторный | **98 мс** |

### Память

Индекс — около **100 байт на файл**. Для самой большой репы пара мегабайт.
На 8 ГБ незаметно.

## §6. Чего эта схема НЕ решает

1. **Правило одной руки держится на дисциплине, а не на механизме.** Ничто
   не мешает запустить деплойер параллельно; 07.09 это стоило пропущенного
   тега и релиза (`PIT-208`).
2. **Ленивая докачка отключена, но не запрещена.** Документированный запрет —
   `GIT_NO_LAZY_FETCH=1`; он не включён, потому что не проверен здесь.
3. **`git maintenance start` не включался намеренно:** в его расписании
   `prefetch` стоит ежечасно, а он **сетевой**. На мобильном канале владельца
   это лишний трафик.
4. **NFD/NFC.** Пути, закоммиченные в NFD, остаются в NFD навсегда;
   `core.precomposeUnicode` влияет только на чтение из ФС. Это, судя по
   ресёрчу, и есть корень известной проблемы с ложными DIFF.
5. **Time Machine и Spotlight** будут переписывать `.git` при каждом коммите.
   Исключения не настроены.

## §7. История ошибок этого решения

Оно принималось **через три отозванных вывода подряд**, и каждый был
подтверждён замером:

| вывод | почему оказался ложным |
|---|---|
| «4 ГБ истории, канал не вытянет» | мерился полный клон, который здесь не нужен |
| «448 КБ, задача решена» | это только `fetch`; докачка переехала на `status` |
| «`read-tree` вместо `reset` решает» | ни та, ни другая команда ни при чём — дело в `autocrlf` |

🔴 **Нашла причину не вахта, а независимый ресёрч** с контролируемым
экспериментом. Урок общий: **замер может быть точным, метод правильным,
а вывод ложным — если мерялась не та стадия** (`PIT-210`).
