# 07 — Как писать методички, справочники, правила

> Единый стандарт письма для всех `.md` в репе, чтобы документы читались одинаково
> и плотно. Форма должна помогать быстрому входу — и тебе, и Claude.

## Общий принцип

Плотно, тезисно, применимо. Документ отвечает на **конкретный вопрос** и позволяет
по нему **действовать**, а не просто «рассказывает тему». Меньше воды — больше
структуры (таблицы, списки, короткие абзацы).

## Структура документа

1. **Заголовок** — о чём документ, одной строкой.
2. **Blockquote «что это и зачем»** — 1–3 строки: на какой вопрос отвечает, кому/когда
   нужен. Это то, что читают первым.
3. **Разделы** — по одному смысловому блоку, с внятными заголовками.
4. **Таблицы и списки** там, где это плотнее прозы (сравнения, «если → то», шаги).
5. **Чек-лист** в конце, если по документу нужно действовать по пунктам.
6. **Первоисточники / ссылки** в конце, если факты на что-то опираются.

## Тон

- Прямой, без канцелярита и воды. Русский для текста, английский для терминов/путей/кода.
- Термины при первом упоминании — коротко расшифровать (или вынести в глоссарий).
- Пиши так, будто объясняешь коллеге, который умён, но контекста этой темы не имеет.

## Типы документов — что когда

| Тип | Когда | Форма |
|---|---|---|
| **Методичка** | Как что-то делать (процесс, подход) | Шаги + правила + чек-лист |
| **Справочник** | Свести факты/данные для быстрого поиска | Таблицы, определения, индекс |
| **Правила** | Зафиксировать договорённости «как у нас принято» | Нумерованный список правил |
| **Разбор** | Исследовать вопрос, прийти к выводу (напр. `truth-seeking`) | Тезис источника → проверка → вывод |
| **Шаблон** | Заготовка для повторяющегося документа | Структура с плейсхолдерами `<...>` |

## 🔴 Требование: нормативный язык и полный набор состояний

Из `personal-finance-dss/docs/ui_requirements_guide.md`. Правило записано про интерфейс,
но ничего интерфейсного в нём нет — оно про **любой документ, который что-то предписывает**.

### Нормативный язык вместо оценочного

**ДОЛЖЕН** — обязательно · **СЛЕДУЕТ** — настоятельно, отклонение обосновывается ·
**МОЖЕТ** — допустимо.

> Без «удобно», «красиво», «современно», «качественно» — **это не требования, а вкус**.

Проверка одна: можно ли по формулировке **однозначно сказать, выполнено или нет**.
«Интерфейс должен быть понятным» непроверяемо; «каждое поле ввода ДОЛЖНО иметь видимый
фокус» — проверяемо. Оценочное слово в требовании означает, что решение отложено
на исполнителя и будет принято по-разному каждый раз.

### Описан только успешный путь — значит, не описано

Самая частая дыра, и она одинакова во всех жанрах:

> Для любой области данных нужен **полный набор состояний**: обычное · загрузка ·
> **пусто** · **ошибка**. Описан только «успешный» вид — остальные забыты.

Это ровно тот класс, который в системе всплывает снова и снова с разных сторон:
пустой ответ инструмента, записанный как содержимое (`71-fail-loud-and-sourcing.md` §7з) ·
пустой срез, принятый за сбой (§7е-бис) · проверка, прошедшая пропуском вместо выполнения
(§7в) · гейт, отказавший по таймауту и не вернувший ничего (`69` §2). **Во всех случаях
не-успешное состояние существовало, а описано не было** — и потому обрабатывалось наугад.

**Практика:** у любого предписывающего документа — раздела процедуры, спецификации, контракта
инструмента — проверяется наличие ответа на четыре вопроса:

1. что происходит **в норме**;
2. что происходит, пока **результат не готов**;
3. что происходит, когда результата **законно нет** (пусто ≠ ошибка);
4. что происходит при **отказе** — и **как отказ отличить от пустоты**.

Четвёртый вопрос — самый дорогой из пропущенных: именно на нём строятся молчаливые сбои.

**Родня:** `71` §7з (пустой ответ не записывается как содержание) · `71` §7в («зелёный»
≠ «проверено») · `19-reporting-system.md` §3а (лог пробелов с причиной) ·
`21-revision-protocol.md` §4е (снятие ограничения взводит спрятанное).

## Правила единообразия

- Одна тема — один документ (не размазывать, не дублировать — `05-…` правило 2).
- Заголовки по неймингу файлов (`01-repo-standard.md`).
- Если документ вырос и стал про несколько тем — разбить.
- Ссылки между документами — относительные, по имени файла, чтобы кликалось.
