# 10 — Git: как устроен и как с ним работать

> Парный документ к `02-claude-workflow.md`. Инфраструктура = Git + Claude: Claude
> генерит и сжимает знания, Git их хранит и версионирует. Здесь — модель Git (чтобы
> проблемы стали механикой, а не магией), лимиты GitHub, рабочие команды и разбор
> типовых ошибок. Факты — из git-scm (Pro Git) и GitHub Docs.

---

## 1. Как Git хранит данные (модель, без которой всё — магия)

Git — не «система бэкапов диффов», а **content-addressable база ключ-значение** внутри
папки `.git`. Всё, что ты коммитишь, становится одним из четырёх типов объектов, и
каждый адресуется SHA-1-хешем своего содержимого:

| Объект | Что это |
|---|---|
| **blob** | Содержимое одного файла (без имени и пути — только байты) |
| **tree** | Каталог: список записей «имя + режим + хеш» на blob'ы и другие tree |
| **commit** | Снимок: указатель на корневой tree + метаданные (автор, дата, сообщение) + ссылка на родительский коммит |
| **tag** | Именованный указатель на объект (обычно на commit) |

Три следствия, которые надо понимать:

1. **Коммит хранит не диффы, а снимок целиком** — ссылку на корневой tree, который
   рекурсивно ссылается на всё дерево файлов на тот момент. Диффы Git вычисляет на
   лету, сравнивая два дерева.
2. **Дедупликация по содержимому.** Имя объекта = SHA-1 его содержимого → одинаковый
   контент хранится **один раз**. Не изменился файл между коммитами — Git переиспользует
   тот же blob. Поэтому история из тысяч коммитов не раздувается: «полное дерево» на деле
   «общее дерево».
3. **Ветка — это просто файл** в `.git/refs/heads/` с одним хешем коммита внутри.
   Поэтому ветки дёшевы: создать ветку = записать 40 байт. `HEAD` — указатель на текущую
   ветку.

Как это происходит физически: `git add` хеширует изменённые файлы, пишет их blob'ы в
`.git/objects/` и обновляет **индекс** (staging area). `git commit` берёт индекс,
собирает из него tree, создаёт commit-объект на этот tree и двигает файл ветки на новый
коммит. Новые объекты сперва лежат «россыпью» (loose, zlib-сжатые), потом `git gc`
пакует их в packfiles с дельта-сжатием.

Посмотреть своими глазами: `git cat-file -p HEAD` (содержимое коммита),
`git ls-tree HEAD` (дерево), `git cat-file -t <hash>` (тип объекта).

> Практический смысл: понимая модель, ты чинишь «страшные» проблемы механически —
> восстанавливаешь потерянный коммит через reflog, читаешь merge руками, понимаешь
> почему `--force` опасен (переписывает ref, старые коммиты висят до `gc`).

## 2. Ключевое ограничение: история хранит всё навсегда

Раз коммит ссылается на blob'ы, а объекты дедуплицируются и **остаются в истории**,
получается важное для наших knowledge-реп следствие:

> **Удалил тяжёлый файл в новом коммите — он всё ещё в истории.** `git clone` тянет
> **всю** историю, включая каждую версию каждого файла. Один раз закоммитил 100 МБ
> бинарник — каждый клон каждого форка навсегда качает эти 100 МБ, даже если файл
> давно удалён.

Отсюда правила лёгкости (`06-volume-compression.md`) — не только про текущий размер, а
про то, чтобы **тяжёлое вообще не попадало в историю**. Дельта-сжатие packfile **не
помогает** на уже сжатых форматах (JPEG, MP4, ZIP, docx) — ещё одна причина не коммитить
их, а конспектировать.

Если тяжёлое уже попало в историю и `.git` распух:
- `git verify-pack -v .git/objects/pack/*.idx | sort -k3 -n | tail` — найти самые
  большие объекты.
- `git rev-list --objects --all | grep <hash>` — узнать имя файла по хешу.
- Вычистить из истории — переписать историю (`git filter-repo`, современная замена
  `filter-branch`; или BFG). **Это ломает уже запушенное** и требует force-push —
  делать только осознанно. Для личных приватных реп, где ты один, допустимо; но проще
  **не допускать** попадания тяжёлого в историю.
- Радикально и чисто для нашего кейса: пересоздать историю одним коммитом через
  `git checkout --orphan` (см. §6).

## 3. Лимиты GitHub (факты из GitHub Docs)

### Размер файла
- **> 50 МиБ** — git выдаёт **warning**, пуш проходит, но страдает производительность.
- **> 100 МиБ** — GitHub **блокирует пуш**. Нужен Git LFS. Для knowledge-репы это сигнал
  «файл не туда» — конспектируй, а не тащи в LFS.
- **Загрузка через браузер** — максимум **25 МиБ** на файл.

### Рендер и отображение
- **Markdown / Mermaid** рендерятся если файл **< 2 МБ**; сложнее — падает в plain text
  или не отображается. → крупный `.md` дроби на части.
- **Рендеримых файлов в одном diff** (картинки, PDF) — максимум **25**.
- Raw-версии всегда доступны через `raw.githubusercontent.com`.

### Размер репозитория
- Жёсткого числового лимита нет, но GitHub **рекомендует < 1 ГБ**.
- **~5 ГБ** — мягкий предел: GitHub может написать с просьбой уменьшить репу.
- Наш внутренний стандарт жёстче и завязан ещё и на Claude: 🟢 ≤50 МБ / 🟡 100 МБ /
  🔴 500 МБ (`01-repo-standard.md` §4).

### Восстановление
- Удалённую репу можно восстановить в течение **90 дней** (если не была частью активной
  fork-сети). Появляется в списке восстановления в течение ~часа после удаления.

## 4. Рабочий цикл (наш стандарт)

Разовая настройка репы и первый пуш — в `01-repo-standard.md` §5 (только HTTPS, SSH на
этой сети режется). Здесь — повседневность.

**Каждое изменение — три команды:**
```bash
git add .
git commit -m "тип: что сделал"
git push
```

**Префиксы сообщений** (Conventional Commits): `feat:` новое, `fix:` починка,
`docs:` документация, `refactor:` перестройка, `chore:` рутина (чистка, зависимости).
Сообщение — осмысленное: не `update`, а что конкретно.

**Состояние и навигация:**
```bash
git status            # что изменено/застейджено
git log --oneline     # история коротко
git diff              # что изменено но не застейджено
git diff --staged     # что застейджено но не закоммичено
```

## 5. Полезные команды под наши задачи

**Отменить/починить:**
```bash
git restore <файл>              # откатить незастейдженные изменения файла
git restore --staged <файл>     # убрать из stage (изменения останутся)
git commit --amend              # переписать последний коммит (до пуша!)
git reset --soft HEAD~1         # отменить последний коммит, изменения оставить
git reset --hard <хеш>          # ВЕРНУТЬ всё к состоянию коммита (изменения теряются)
git reflog                      # журнал всех перемещений HEAD — спасение потерянного
```

**Восстановить потерянное:**
```bash
git reflog                      # найти хеш «потерянного» коммита
git checkout -b recover <хеш>   # воскресить его в новой ветке
```
Reflog — почему потерянную работу почти всегда можно вернуть: пока `gc` не убрал
недостижимые объекты (по умолчанию — месяцы), они лежат в `.git`.

**Диагностика размера:**
```bash
du -sh .git                                             # сколько весит история
git count-objects -vH                                   # сводка по объектам
git verify-pack -v .git/objects/pack/*.idx | sort -k3 -n | tail   # топ тяжёлых
```

**Игнор задним числом** (файл уже трекается, добавил в `.gitignore` — не помогает):
```bash
git rm --cached <файл>          # убрать из трекинга, оставить на диске
git commit -m "chore: stop tracking <файл>"
```

## 6. Обнуление истории (когда `.git` распух после ревизии)

Типовой кейс: провёл slimming, удалил кучу тяжёлого — но `.git` всё ещё хранит старые
версии, клон тяжёлый. Для **личной приватной** репы, где ты один, чистое решение —
пересоздать историю одним коммитом:

```bash
git checkout --orphan clean-main    # новая ветка без истории
git add -A
git commit -m "feat: clean snapshot after slimming"
git branch -D main                  # удалить старую ветку с тяжёлой историей
git branch -m main                  # переименовать clean-main → main
git push -f origin main             # перезаписать удалённую (force!)
git gc --aggressive --prune=now     # локально выкинуть старые объекты
```

> `-f` (force) допустим здесь потому, что репа личная и никто от неё не форкается.
> На общих/командных репах так **нельзя** — сломаешь всем историю. Перед операцией —
> убедись, что рабочая копия содержит всё нужное (это единственный оставшийся снимок).

## 7. `.gitignore` — что не пускать в репу

Базовый шаблон — `templates/gitignore.template`. Логика для knowledge-реп:
- **Секреты** — `.env`, ключи, токены (железное правило, `05-knowledge-base-rules.md`).
- **Артефакты сборки** — `bin/`, `obj/`, `*.exe`, `*.o`, `__pycache__/`, `.venv/`,
  `node_modules/`, `*.pyc`. Пересобираются из исходников, в истории им не место.
- **Системный мусор** — `.DS_Store`, `._*`, `~$*`.
- **Тяжёлое генерируемое** — собранные отчёты, экспорты (храним источник, не результат).

Проверить, что реально попадёт в коммит: `git status` и `git add -n .` (dry-run).

## 8. Чеклист перед пушем

- [ ] `git status` — коммичу то, что хотел (нет случайного мусора/секретов).
- [ ] Нет файлов > 50 МиБ (иначе warning; > 100 МиБ — блок).
- [ ] Крупные `.md` разбиты (< 2 МБ, чтобы рендерились).
- [ ] Сообщение коммита осмысленное, с префиксом (`feat/fix/docs/...`).
- [ ] Remote по HTTPS (`git remote -v` → `https://...`).
- [ ] Секретов в коммите нет (`.env` в `.gitignore`).

## 9. Git + Claude = инфраструктура (как связка работает)

- **Claude** (`02-claude-workflow.md`) — генерит контент, конспектирует тяжёлое в `.md`,
  проводит ревизии. Пока репа лёгкая, Claude видит её целиком; переросла — RAG.
- **Git** (этот документ) — версионирует результат, хранит историю, даёт откат.
- **Стык:** Claude готовит изменения → ты коммитишь тремя командами → история чистая,
  репа лёгкая, всё рендерится на GitHub. Правило лёгкости обслуживает обоих: и Git
  (история не пухнет, клон быстрый), и Claude (репа влезает в контекст).
