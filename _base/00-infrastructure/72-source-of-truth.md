# 72 — Источник правды: GitHub

> **Одной строкой:** репа живёт на GitHub. Архив — снимок, снятый оттуда, и ничего больше.
>
> **Зачем.** Копий у системы много, и они расходятся **молча**. Локальная папка отстала
> на три версии, в переписке лежит zip недельной давности, в загрузках — распакованное дерево,
> которое кто-то правил руками. Пока источник правды не назначен, каждая копия выглядит
> одинаково убедительно, и вопрос «какая версия настоящая» решается памятью. **Память врёт.**
>
> **Происхождение.** Извлечено из `mission-control/00-infrastructure/12-source-of-truth.md`
> (20.08.2026, синтез инфраструктур). В базе правило упоминалось в нескольких документах,
> но собственного дома не имело.

---

## 1. Правило

**Источник правды для любой репы — её ветка `main` на GitHub.** Архив, локальная папка,
zip в переписке, распакованное дерево — всё это **производные копии**. Расходится копия
с GitHub — прав всегда GitHub.

Отсюда порядок, который не обсуждается:

- **Нужен актуальный архив — снимается с GitHub**, а не ищется по папкам:
  `gh release download`, `git clone` либо выгрузка ветки.
- **Работа закончена — результат уезжает на GitHub** через деплойер.
  **Пока не уехал, работы как будто не было.**
- **Скрипт, которому нужны репы, клонирует их сам.** Он не полагается ни на локальные
  каталоги, ни на то, что владелец что-то заранее скачал.

## 2. Почему именно GitHub

Три причины, и все три обязательные:

1. **Он единственный** — у остальных копий нет свойства единственности по построению.
2. **У него есть история и теги** — можно ответить не только «что сейчас», но и «что было».
3. **Он доступен всем вахтам одновременно.** Локальная папка живёт на одной машине;
   вахта с другого аккаунта её не видит и проверить не может.

Третий пункт решает: в системе, где работают несколько аккаунтов по очереди, источником
правды может быть **только то, что видно всем**.

## 3. Как это уточняет канон «один zip = полный контекст»

Канон остаётся, но читается точнее: **zip нужен, чтобы модель прочитала репу целиком
за одну сессию.** Это про контекстное окно, а не про хранение.

> **Zip — вагон, а не склад.**

Практическое следствие: архив, приложенный к передаче вахты, обязан быть снят с GitHub
**на момент передачи**. Архив «из папки, где он лежал с прошлого раза» — источник
рассогласования: работа идёт по устаревшему дереву, а потом результат затирает чужие коммиты.

## 4. Проверка перед работой и перед выпуском

```bash
cat <репа>/VERSION                                  # версия в архиве
gh release list -R <owner>/<репа> --limit 1         # старший тег на GitHub
```

Сходится — работаем. Не сходится — **берём с GitHub**, архив из переписки откладываем.

> ### 🔴 Проверка обязательна и тогда, когда «и так всё знают»
>
> **Живой случай.** Журнал §0 от 16-го числа говорил «репы ещё нет на GitHub». Через три дня,
> починив в ней баг, вахта поверила этой строке и собрала фикс как **v0.1.0** — не проверив
> `gh release list`. Релиз v0.1.0 уже существовал: его выложили между двумя датами, а §0
> не обновили. Архив пришлось пересобирать.
>
> Правило существовало и раньше. Нарушено не из-за его отсутствия, а потому что репа,
> о которой не было свежих новостей, показалась **не требующей проверки**.
>
> **§0 журнала — ориентир для человека, а не источник правды для решения о номере версии.**
> Сверка делается перед выпуском **любой** репы, включая те, что «недавно смотрели».

Это тот же класс, что PIT-086 («верь файлам, не саммари») и PIT-072 (состояние работ
восстановлено по своему полю зрения): **запись о состоянии — гипотеза о состоянии.**

## 4а. Коллизия номеров между параллельными вахтами

Случай §4 — журнал отстал, и вахта одна. Здесь другой: **вахт несколько, и они идут
одновременно.**

Четыре аккаунта работают параллельно и **не видят чужих чатов**. Две вахты берут одинаковый
«следующий» номер — каждая честно, от того состояния, которое видит, — обе выпускают архив.
На GitHub остаётся тот, кто запушил **последним**.

**Последствие здесь тяжелее, чем в §4.** Там пересобирают архив; тут **работа второй вахты
исчезает с GitHub целиком** — не «частично», не «придётся вспомнить». И исчезает молча:
номер занят законно, релиз выглядит нормально, отсутствует лишь чужое содержимое.

> ### 🔴 Коллизия бьёт по ЛЮБОМУ сквозному реестру, а не только по версиям
>
> Дополнено 21.08.2026 из `exam-kit/docs/RELEASING.md` §1: там задвоились **и версия
> `v1.9.0`, и урок `L-016`** — обе линии нумерации, и обе пришлось разводить задним числом.
>
> Механика одна: **сквозной номер, который назначается «следующим от того, что видно»,
> сталкивается при параллельной записи** — неважно, версия это, `PIT-NNN`, `SYN-NNN`,
> `ADR-NNN` или `L-NNN`. Для версий спасает GitHub (единственное общее место, `gh release list`),
> **для остальных реестров общего места нет** — они живут внутри репы, и вторая вахта
> увидит коллизию только после слияния.
>
> **Что делать:** перед выпуском прогонять проверку на дубли **по всем** сквозным реестрам
> репы, а не только по версии:
>
> ```bash
> grep -oE '^#{2,3} (PIT|SYN|ADR|L)-[0-9]+' reports/pitfalls.md … | sort | uniq -d
> ```
>
> Пусто — чисто. Непусто — разводить **до** слияния, пока известно, какая запись чья.

Живой случай (`mission-control`, 09.08.2026): две вахты выпустили `0.16.0`. Дожила версия
про ремонтные режимы; отчёт по сверке старых реп и переписанные маршруты пропали
и восстанавливались заново **четыре дня спустя**.

**Правило.** Номер берётся не «следующий за тем, что в архиве», а следующий за тем,
что **на GitHub**:

```bash
gh release list -R vevdokimovm/<репа> -L 3      # перед КАЖДЫМ выпуском
```

Номер занят — версия **сдвигается**, а не перезаписывается. Принял вахту по архиву,
который старше GitHub, — сначала сверься, потом работай.

> **Почему это не решается «договориться, кто какой номер берёт».** Договорённость требует
> общего канала, а его нет по построению: аккаунты изолированы. Единственное общее место —
> GitHub, поэтому и очередь номеров ведётся там, а не в головах.

Разошедшиеся линии, если коллизия всё же случилась, сводит `22-merge-protocol.md`.
Извлечено из `mission-control/00-infrastructure/13-watch-discipline.md` §3б.

## 4б. Производное чинится в источнике, а не в себе

Правка сгенерированного файла — **тупик по построению**: следующая пересборка её перетрёт,
и труд исчезнет без следа. Хуже — исчезнет молча, потому что правка выглядела применённой.

**Живой случай — цепочка карты репозиториев.** Она замкнута:

```
.repo-meta в архиве  →  деплойер  →  описание репы на GitHub  →  сборщик карты  →  repos-map.md
```

Пометка «НЕ ОПИСАНА» в карте лечится **не правкой карты**, а добавлением `description=`
в `.repo-meta` нужной репы и обычным прогоном деплоя. Дописать строку в карту руками —
значит потерять её на следующей пересборке.

**Как отличить производное от источника.** Три признака, любого достаточно:

| Признак | Пример |
|---|---|
| файл собирается инструментом | `repos-map.md`, `BOARD.md` планировщика |
| в шапке сказано «не редактировать» / «перегенерировать» | `INBOX-FROM-*`, `_base/DO-NOT-EDIT.md` |
| та же информация есть где-то ещё **раньше по цепочке** | описание репы: `.repo-meta` → GitHub → карта |

**Правило:** нашёл ошибку в производном — **найди источник и почини там**, затем
перегенерируй. Если источник не находится, значит файл на самом деле не производный,
и это отдельная находка.

Тот же принцип действует для файла доставки моста (`74-planner-bridge.md` §3: правки в нём
теряются при следующем прогоне) и для `_base/` (`78-base-embedding.md`: каталог сносится
целиком при раздаче).

Извлечено из `mission-control/00-infrastructure/17-gh-automation.md` §5.

## 4б-бис. 🆕 🔴 Копия, честно указывающая на источник, всё равно читается вместо него

§4б требует чинить производное в источнике. Вот случай, где производное сделано **правильно
и добросовестно** — и оттого опаснее небрежного.

Из `academic-portfolio`: в корне листовой репы лежит `repos-map.md` — копия карты всей
системы. Копия **сама признаётся, что она копия**, прямо в шапке:

> «📍 Эта карта живёт в **`base-repo`** — родительской репе всей системы.»

И всё равно она разошлась: 147 строк против актуальной карты на 57 реп, перечень
десятилетней давности по составу системы. Хеши не совпадают.

### Почему честность копии работает против читателя

> **Строка «источник вон там» читается как знак качества, а не как указание уйти.**
> Читатель видит, что документ знает своё место в системе, ставит ему доверие — и читает
> **его**, потому что он уже открыт. Небрежная копия хотя бы вызывает подозрение;
> аккуратная не вызывает ничего.

Ссылка на источник **не заменяет** актуальности и не отменяет распада. Она лишь делает
распад вежливым.

### Что вместо

| Плохо | Лучше | Лучше всего |
|---|---|---|
| копия без пометки | копия с пометкой «источник там» | **ссылка вместо копии** |
| | | копия **с датой снятия** и строкой «сверить с источником, если старше N» |

**Правило:** если производное нельзя заменить ссылкой (нужно офлайн, нужно в архив),
оно несёт **дату снятия** — без неё «источник вон там» становится единственной защитой,
а она не работает. Дата превращает вопрос «актуально ли» из невидимого в арифметический.

📍 Живой контрпример из этой же кампании: `_base/` в каждой репе — тоже копия базы, и она
**не** порождает этой проблемы, потому что раздаётся скриптом и помечена как зеркало,
которое не редактируют. **Копия безопасна, когда у неё есть механизм обновления;
без механизма любая пометка — просто вежливость.**

**Родня:** §4б (производное чинится в источнике) · §4е (повторённое утверждение) ·
`21` §4а-бис (дата проверки) · `78-base-embedding.md`.

## 4в. Канон обязан помещаться в канал доставки

Вопрос «сделать каноном внешний инструмент» (доска задач, вики, канвас) возникает регулярно
и отклоняется по одной причине, которая формулируется общо:

> **Канон должен доезжать туда, куда доезжает работа.**

В этой системе работа доезжает архивом («один zip = полный контекст»). Внешний сервис
в архив не попадает — значит его содержимое существует **только пока есть доступ к сервису**,
и всякая сессия, работающая с архивом, канона не видит.

Отсюда три следствия, каждое проверялось на практике:

| Соблазн | Что ломается |
|---|---|
| держать задачи во внешнем трекере | второй источник правды; при работе с нескольких аккаунтов расхождение неизбежно |
| держать схему/карту в канвасе | не едет в архив, не читается сессией, не версионируется |
| `git submodule` для общей части | **не попадает в zip** при обычной выгрузке — то есть не решает исходную задачу |

**Проверка перед тем, как что-то объявить каноном:** окажется ли оно в архиве целиком.
Нет — это **вид или вспомогательный инструмент**, но не источник правды.
Внешним сервисом пользоваться можно; каноном он быть не может.

Извлечено из `mission-control/reports/2026-07-31-consolidation-brainstorm.md` §5.

## 4в-бис. Прежде чем строить хранилище — проверить, не нужен ли вид

Запрос «нужен трекер / канбан / вики / mind map» почти всегда формулируется как
**новое хранилище**. Проверка перед постройкой одна:

> **Существуют ли эти данные уже? Если да — строится не хранилище, а вид.**

В разобранном случае формулировка «интегрировать Miro / Notion / Confluence» после
проверки свелась к «отрендерить то, что уже есть»: трекер — это таблица, канбан —
разделы существующего файла, вики — сами репы, mind map — рендер поверх маркдауна.
Ни одна сущность не потребовала нового места хранения.

**Почему это важнее, чем экономия работы.** Новое хранилище — это **второй источник
правды** по определению: данные попадают туда копией и с этого момента расходятся
молча (§1). Вид расходиться не может — он производен и перестраивается из источника.
Отсюда и признак: **если «интеграция» требует что-то туда переложить, а не отобразить —
это не интеграция, а вторая копия.**

### Третий довод, который обычно не называют: инструмент смертен, данные — нет

Из `control-panel/docs/adr_001_markdown_is_the_database.md` — решения, принятого
по этому же случаю. Два довода выше про **правду** и про **доставку**; третий про **время**:

> «Панель — личный инструмент одного человека. Она может **надоесть, сломаться, остаться
> без времени на поддержку**. Содержимое обязано это пережить.»

**Личный инструмент имеет срок жизни, и он короче, чем у данных.** Это не пессимизм,
а обычная арифметика: заметки живут годами, а самодельная панель — ровно столько, сколько
у автора есть время её чинить. Данные, лежащие внутри приложения, наследуют **его**
срок жизни, а не свой.

Отсюда проверка, которую стоит задавать при любом «давай сделаем инструмент»:

> **Если завтра этот инструмент удалить — что останется?** Останется всё, и работа
> продолжается как раньше — инструмент построен верно. Останется дамп, который надо
> куда-то конвертировать, — построено хранилище, и оно уже второй источник правды.

Тот же ADR называет и цену правильного выбора: **«Выключи панель — система работает
как работала»**. Это формулировка приёмки для любого инструмента поверх данных,
и она проверяется одной командой — выключить.

**Смежное следствие для этой системы:** плоский текст — не эстетика, а **условие
работоспособности передачи вахты**. Канон «один zip = полный контекст» работает ровно
потому, что всё лежит текстом; хранилище в приложении обрывает его молча (§4в).

## 4в-тер. 🔴 Плоский индекс поверх вложенных данных — чтобы работали обычные инструменты

Частный случай §4в-бис, встречающийся чаще всего. Из
`dota-dossier/src/build_match_index.py`:

> Детали лежат в тысячах отдельных JSON. Узнать, кто участвовал, значит **открыть
> огромный файл**. Скрипт проходит папку один раз и пишет плоский `match_index.csv`:
> строка на запись, ключевые поля рядом — **чтобы сама папка стала просматриваемой
> `grep`-ом, таблицей, чем угодно, не трогая ни одного JSON**.

**Что здесь сделано.** Не заменено хранилище и не заведено второе — **добавлен вид**,
производный и пересоздаваемый. Исходные данные остались единственным источником правды.

| | Вложенные данные | Плоский индекс |
|---|---|---|
| Полнота | всё | только ключевые поля |
| Кто читает | код | **человек и любой текстовый инструмент** |
| При расхождении | **источник правды** | пересобрать из источника |

**Три условия, без которых индекс становится вторым источником правды:**

1. **Пересобирается одной командой** из исходных данных.
2. **Безопасен к повторному запуску** — добавились записи, прогнал снова.
3. **Никто в него не пишет руками.** Правка в индексе исчезнет при пересборке —
   и это `72` §4б (производное чинится в источнике).

## 4г. Один файл — два владельца: машина строит каркас, человек пишет прозу

Случай, не покрытый §4б. Там артефакт **целиком** производный и чинится в источнике.
Здесь файл **один**, и у него **две зоны с разными владельцами**: скрипт отвечает
за структуру (какие секции, в каком порядке, по каким группам), человек — за содержание
внутри секции.

**Цена ошибки известна: пересборка карты реп однострочниками из GitHub затёрла
15 авторских описаний** средней длины ~290 символов. Машинная затравка формально
«актуальнее», а фактически беднее в десять раз, и восстановить её неоткуда.

**Правило: при пересборке скрипт обязан вычитать существующее авторское и перенести
дословно.** Не «сгенерировать заново правильнее», а **разобрать → сохранить → собрать
вокруг**. Порядок именно такой, и он обязателен:

```python
header, bodies = parse_existing(path.read_text())   # 1. вычитать авторское
...                                                  # 2. собрать структуру заново
out += ["", bodies[name], ""] if name in bodies else [затравка]   # 3. вернуть на место
```

Три детали, каждая из практики:

1. **Собственную заглушку сохранять нельзя.** Если скрипт когда-то вписал
   «⚠️ НЕ ОПИСАНА», при следующем разборе она выглядит как авторский текст и **залипает
   навсегда**. Заглушка узнаётся по маркеру и отбрасывается на шаге 1.
2. **Затравка обязана называть себя затравкой** — и говорить, что с ней делать:
   *«Допиши зону ответственности прямо здесь — скрипт этот текст сохранит»*. Артефакт,
   не сообщающий читателю своих правил, редактируют вслепую либо не редактируют вовсе.
3. **Необъяснимое не проглатывается молча.** Объект, не попавший ни в одну группу,
   выносится в раздел «Без класса» с явным призывом — а не раскладывается по умолчанию
   в самую многочисленную группу (`71-fail-loud-and-sourcing.md`).

> **Как отличить этот случай от §4б:** спроси, **можно ли выбросить файл и собрать
> заново**. Можно — он производный, правило §4б. Нельзя, потому что часть текста
> существует только здесь, — это §4г, и скрипт обязан уметь читать, а не только писать.

## 4д. 🔴 Второй корпус об одном предмете: дубль ловится счётом, а не памятью

**Живой случай, `dota-dossier`.** Две независимые генерации одного и того же:

| Когда | Что построено | Чем |
|---|---|---|
| 14.08.2026, v2.34.0 | `knowledge/heroes/` **128** файлов, `knowledge/items/` **417** | `src/corpus/` (три модуля) |
| 20.08.2026, v2.40.0 | `docs/heroes/<slug>/overview.md` **130**, `docs/items/<slug>/overview.md` **409** | `src/hero_data_sheet.py`, `src/item_data_sheet.py` |

Один автор, шесть дней, один и тот же источник данных (`dotaconstants` + `patchnotes.json`),
один и тот же жанр документа: характеристики · способности · таланты · полная история патчей.
**545 файлов, пересечение по `sha256` — ноль.** Ни один генератор не упоминает другой
(`grep -c corpus src/hero_data_sheet.py` → 0; `grep -c "docs/heroes" src/corpus/*.py` → 0).
Ни `README.md`, ни `ROADMAP.md` репы **не упоминают `knowledge/heroes` и `knowledge/items`
вовсе** — при том что `ROADMAP` подробно описывает второй корпус как новую работу.

**Это не «забыли про чужой инструмент» (PIT-072). Это забыли про свой, шестидневный.**
Правило «сначала искать готовое» держится на памяти о собственной работе — а память
о собственной работе и есть первое, что уходит между сессиями. У кого несколько аккаунтов
и чатов, она уходит гарантированно.

### Почему обычные признаки не срабатывают

- **По именам** — не совпадают: `knowledge/heroes/enigma.md` против
  `docs/heroes/enigma/overview.md`.
- **По хешам** — пересечение **ноль**, и это выглядит как доказательство, что деревья
  **разные**. Ровно наоборот: разный рендер одних и тех же фактов даёт ноль общих байт
  по построению (`PROCEDURE.md` §3: прежде чем опереться на хеш, назови, что сравниваешь).
- **По размеру** — оба «большие», сравнивать не с чем.

### Признак, который работает: одинаковая мощность множества

Предметная область имеет **естественную мощность** — героев ровно 127, предметов ровно 409.
Два каталога, каждый со счётом около этого числа, описывают **одно и то же множество**,
как бы ни назывались файлы.

```bash
# по каждому каталогу с однотипными документами — счёт
find . -type d -not -path "*/.git/*" | while read d; do
  n=$(find "$d" -maxdepth 1 -type f -name '*.md' | wc -l | tr -d ' ')
  [ "$n" -gt 50 ] && printf "%5s  %s\n" "$n" "$d"
done | sort -rn
```

Две строки с близкими числами — **повод открыть по файлу из каждой**, а не вывод.
Числа `128 / 130` и `417 / 409` в разных ветках дерева были видны в обычной переписи
каталогов (`PROCEDURE.md` §1.2) и **читались как две разные задачи**, пока не сравнили
предмет.

> **Что делать, обнаружив.** Не удалять и не сливать по ходу другой работы. Записать
> обе редакции, назвать, **какая новее и чем каждая богаче**, и вынести сведе́ние
> отдельной задачей: у двух корпусов почти всегда есть непересекающееся содержание
> (здесь — `INDEX.md` с приоритетом по пулу есть только в старом, живые срезы меты
> только в новом). Сведение вслепую теряет ровно эту разницу.

**Родня:** §4в-бис (прежде чем строить хранилище — проверить, не нужен ли вид),
`21-revision-protocol.md` §4б (механизм добавления есть у всего, механизма удаления нет),
PIT-072.

## 4е. 🆕 🔴 Утверждение, повторённое по системе, становится опорой без единого замера

Из `truth-seeking`, где это названо **иллюзией истины**: повторённое много раз начинает
казаться правдой **от самого повторения**. В корпусе документов эффект сильнее, чем
в разговоре: у повторов появляется вид независимого подтверждения.

> **Одно утверждение, процитированное в пяти документах, читается как пять источников.**
> Источник по-прежнему один, и он может быть непроверенным.

### Живой случай базы — тот, на котором строились выводы

Утверждение **«база раздаётся в 57 реп»** стояло в нескольких документах и служило
основанием: «каждый дубль в базе едет во все 57», оценка стоимости правки базы,
приоритет задач по чистке дублей.

**Замер 22.08.2026** (`scripts/base_coverage.py`): покрыто **47 из 57**. Из десяти
непокрытых шесть — публичные витрины, которые базу не получают **осознанно**.
То есть исходное утверждение было неверным **дважды**: и по числу, и по смыслу
(«пробел» оказался наполовину решением). Разбор — `SYN-030`.

**Как оно продержалось.** Никто его не выдумывал: оно было верным приближением
на момент записи и **устарело молча** — репы заводились, раздача за ними не шла.
Повтор в документах законсервировал состояние, а вид у него остался утвердительный.

### Признак: у утверждения нет команды, которая его проверяет

Это единственный надёжный различитель, и он механический.

| | |
|---|---|
| **измерение** | есть команда, число воспроизводится, у числа стоит дата |
| **опора** | утверждение цитируется, число круглое или равно числу объектов в системе |

🔴 **Круглое число и число «всех объектов» — два маркера повышенного риска.** «Все 57»,
«каждая репа», «всегда» — формулировки, которые никто не считал, а вывел из определения.

**Правило.** Утверждение о **состоянии системы**, на котором строится решение, обязано
нести **дату замера и команду**. Нет их — оно помечается как оценка (`71`), а не факт,
и первым же делом измеряется, если решение того стоит.

### 📍 Побочный эффект: считают дошедших, а не всех

Оттуда же **ошибка выжившего**. Свод по системе строится по тому, что нашлось, —
а не найденное невидимо и в знаменатель не попадает. Живой случай той же недели:
покрытие базой считалось по репам, **у которых есть каталог инфраструктуры**;
репы без него не попадали в счёт вовсе и потому «не портили» картину.

**Лечение — знаменатель берётся из независимого списка** (`repos-map.md`, перечисление
каталога), а не из тех объектов, что прошли фильтр измерения.

**Родня:** `67` §3а (свод наследует качество худшего входа) · `71` §7д-бис (верный вывод
по неверному основанию) · `28` §6л (согласованность независимых срезов — работает,
только если срезы действительно независимы) · `SYN-030`.

## 5. Единственное исключение

Репа, которой на GitHub ещё нет: новый скелет, собранный, но не прошедший деплой.
**До первого деплоя источник правды — архив.**

Ровно поэтому первый деплой не откладывается: пока он не прошёл, **у репы нет дома** —
есть только копия в загрузках, и она смертна.
