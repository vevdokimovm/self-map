# 17 — Методичка: создание контекстных файлов через интервью

> Стандартизированный процесс: провести структурированное интервью через `AskUserQuestion` и на выходе получить готовый `.md` файл. Проверено на `psychology.md`, `tone-of-voice.md`, и наборе стандартов (frontend, backend, architecture, code-review, interview-prep).

---

## 1. Когда использовать

Этот процесс подходит, когда нужно превратить размытое "хочу файл про X" в конкретный, рабочий документ:

- Контекстные файлы для Claude Cowork / Projects (правила, стандарты, профили)
- Методички, инструкции, чеклисты
- Профили (личность, tone of voice, стиль кода)
- Любой документ, где важны **личные предпочтения пользователя**, а не общие best practices

**Не использовать**, когда:
- Ответ очевиден и не зависит от предпочтений (просто напиши файл)
- Пользователь уже дал детальное ТЗ (не переспрашивай — делай)

---

## 2. Стартовый промпт

Пользователь запускает процесс примерно так:

> Помоги мне создать [тип файла]. Задавай вопросы по одному через AskUserQuestion, чтобы понять [что именно]. Задай 40–50 вопросов всего. По одному. Дави если ответ размытый — проси конкретный пример. В конце собери всё в .md файл.

Ключевые параметры которые пользователь задаёт:
- **Тип файла** — что делаем
- **Количество вопросов** — обычно 40–50 для глубокого профиля, 15–25 для узкой задачи
- **Формат вопросов** — по одному (не пачкой)
- **Строгость** — давить на размытые ответы или нет

---

## 3. Правила проведения интервью

### 3.1. Один вопрос за раз

Всегда один `AskUserQuestion` за ход. Не вываливай пачку — это перегружает и снижает качество ответов. Нумеруй: **"Вопрос 5 из ~45"** — пользователь видит прогресс.

### 3.2. Формат вопроса

Используй `AskUserQuestion` с 2–4 вариантами ответа. Варианты должны быть:
- **Взаимоисключающими** — не пересекаться по смыслу
- **Короткими** — метка в пару слов, не абзац
- **Реалистичными** — покрывать настоящий спектр ответов, включая "не знаю" / "не думал об этом"

Типы вопросов:
- `single_select` — выбор одного (по умолчанию)
- `multi_select` — выбор нескольких (когда несколько ответов валидны одновременно)
- `rank_priorities` — ранжирование (когда важен порядок приоритетов)

### 3.3. Дави на размытые ответы

Если ответ размытый ("не определился", "зависит", "всё из списка") — **не иди дальше молча**. Останови поток и попроси конкретику текстом:

> Окей, но "не определился" — это слабая позиция для файла правил. Что ты пробовал хотя бы раз? Что видел и думал "это разумно"?

Один уточняющий вопрос текстом, потом обратно к структуре.

### 3.4. Пуш-бэк на слабые решения

Это ключевое отличие от простого опроса. Если ответ технически рабочий, но стратегически плохой для цели пользователя — **скажи прямо**, объясни почему, предложи альтернативу:

> Подожди. Если цель — найти работу, русский README сильно сужает аудиторию. Рекрутеры ожидают английский на GitHub. Ты целенаправленно ищешь только в русскоязычных компаниях, или просто не думал об этом?

Пользователь либо соглашается, либо объясняет свой резон. В обоих случаях файл становится лучше.

### 3.5. Фиксируй пробелы вслух

Когда всплывает слабое место ("не знаю что такое миграции") — сразу говори, что это пойдёт в файл как приоритет:

> Зафиксировал — это критический пробел. Войдёт в файл как приоритет №1.

Так пользователь видит, что интервью не просто собирает данные, а строит карту.

---

## 4. Логика ведения

### 4.1. Группируй по темам

Разбей вопросы на смысловые блоки под каждый будущий файл/раздел. Проходи блок за блоком, обозначая переходы:

> Переходим к code-review.md. Это твой личный чеклист перед каждым git push.

### 4.2. Развилка при интересном ответе

Если ответ открывает важную деталь — задай доп-вопрос текстом вне структуры:

> Хорошо. Тогда уточню. Что конкретно спрашивали на собеседовании? Один-два примера которые тебя завалили.

Развёрнутый текстовый ответ часто ценнее десяти кнопочных.

### 4.3. Держи темп

Не растягивай. Если тема исчерпана — переходи. Пользователь устаёт от 45 вопросов, последние не должны быть водой.

---

## 5. Что на выходе

### 5.1. Формат

Готовый `.md` файл (или несколько), созданный через `create_file`, сохранённый в outputs, показанный через `present_files`.

### 5.2. Структура файла

Хороший контекстный файл содержит:

1. **Заголовок + одна строка назначения** (`> Что это и зачем`)
2. **Разделы по темам** — таблицы для правил, прозой для объяснений
3. **Конкретные примеры** — код, шаблоны, готовые формулировки
4. **Секция "Что Claude никогда не должен делать"** — явные запреты (мощнее чем список "делай так")
5. **Приоритеты / план** — если это про развитие или обучение

### 5.3. Принципы содержания

- **Prescriptive, когда пользователь не знает** — если "не определился со стеком", файл сам задаёт дефолты, а не пишет абстракции
- **Конкретика вместо общих слов** — не "пиши чистый код", а "функции не длиннее 50 строк"
- **Запреты сильнее рекомендаций** — "никогда не хардкодь секреты" работает лучше чем "используй .env"
- **Отражай реальные пробелы** — то что всплыло как слабое место в интервью, идёт в файл как явный фокус
