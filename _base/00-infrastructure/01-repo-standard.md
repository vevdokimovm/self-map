# 01 — Стандарт репозитория

> Единый шаблон структуры для всех knowledge-реп. Цель: одинаковый нейминг и
> организация везде, чтобы не разгребать хаос и чтобы Claude мгновенно
> ориентировался в любой репе. Эталон — самая обжитая репа (например `academic-portfolio`).

## 1. Нейминг папок

1. **Цифровой префикс** для порядка: `00-`, `01-`, `02-` … GitHub сортирует по
   алфавиту — префикс держит нужный порядок. `00-` резервируется под
   инфраструктуру (эту папку), тематика идёт с `01-`.
2. **kebab-case** — слова через дефис, нижний регистр: `01-civil-law`, `03-case-studies`.
3. **Английский** для имён папок верхнего уровня — короткий, универсальный.
4. **Вложенность где логично**: `04-contracts/lease-agreements`. Не плодить уровни без нужды.
5. **Русский — только внутри контента** (сами документы), не в структуре.

## 2. Логические блоки

1. Содержимое бьётся на **тематические папки верхнего уровня** — одна папка =
   один смысловой блок.
2. Внутри блока — подпапки по типу материала (`text/`, `sources/`, `data/`,
   `notes/`), если материала много.
3. Одна папка = одна логическая единица. Не сваливать разное в кучу.
4. **Грузим всё** (репа приватная и личная), **кроме секретов**: пароли, приватные
   ключи, API-токены, данные карт — то, что при утечке даёт доступ к деньгам или
   аккаунтам. Это единственное железное исключение.
5. **Файлы не из зоны репы** при разборке не заливать сюда. Складывать в общий
   архив `for-other-repos.zip`, а внутри — вложенные архивы по имени целевой репы
   (`health-vault.zip`, `it-base.zip`, …). Файлы без дома нигде — во вложенный
   `misc-vault.zip`.

   🔴 **У этого контейнера обязан быть срок и адресат — иначе он становится могилой.**
   Замерено 22.08.2026: `for-other-repos.zip` пролежал в `~/Downloads` **три дня**,
   спрятанный **внутри двух вложенных zip** (`files 2.zip → for-other-repos.zip`).
   Внутри — **34 файла магистерской ВКР**, 7 МБ: два `.docx` текста, 16 диаграмм,
   отчёты трёх экспериментов, ТЗ-записка, чертёж.

   **Ни один из 34 не доехал до целевой репы.** Проверено по хешам: совпадений
   с `academic-portfolio` — **ноль**. При этом внутри лежал грамотный `README-перенос.md`
   с причиной, границей зон и прямым указанием «разобрать при следующей вахте по той репе».
   **Вахта по той репе была** — и файлов не увидела, потому что они лежали не в репе,
   а в `Downloads`.

   > **Контейнер «на потом» виден только тому, кто про него помнит.** Вахта работает
   > по репе, а не по загрузкам; аккуратная записка внутри контейнера не помогает,
   > если контейнер не попадается на глаза.

   **Правило:** заведя `for-other-repos.zip`, в тот же заход завести **строку в `TASKS.md`
   целевой репы** — «принять входящее из `for-other-repos.zip` от ДД.ММ». Тогда контейнер
   ищет не память, а `TASKS`, который читается при каждом входе в репу.

   **Проверка при ревизии:** `find ~/Downloads -name "for-other-repos*"` — нашлось,
   значит есть неразобранное входящее, и это дефект вне зависимости от того, насколько
   хорошо оно упаковано.

## 2а. 🆕 Порядок каталогов задаётся читателем, а строятся они в обратном порядке

§1 требует цифровой префикс «для порядка» и **не говорит, чем этот порядок задан**.
На практике номера расставляют по тому, как материал накапливался, — и получают структуру,
где вход в репу лежит в середине.

Из `family` (генеалогический архив), где обе оси названы явно и **не совпадают**:

| № | Каталог | Что это |
|---|---|---|
| `01-dossier` | сводные досье | **синтез** — «точка входа, если нужно быстро понять всю картину» |
| `02-tree-visuals` | схемы, карта, интерактив | производное от данных |
| `03-primary-sources` | рукописные мемуары: **скан + расшифровка** | первоисточник |
| `05-data-tables` | таблицы, выгрузки ДНК | данные |
| `06-research` | незакрытые вопросы и план архивных запросов | **фронт работы** |

README при этом говорит: «структура — **от первоисточников к синтезу**». Это не
противоречие, а две разные оси:

> **Порядок построения** идёт от источника к выводу: сначала мемуары, потом таблицы,
> потом досье. **Порядок нумерации** идёт наоборот — **синтез первым**, потому что
> открывший репу хочет сначала понять картину, а к рукописям спускается только если
> картины не хватило.

### Правило

**Номер обслуживает того, кто открыл репу впервые, а не хронологию накопления.**
Первым номером идёт то, что отвечает на вопрос «что здесь вообще» за один файл;
сырьё и первоисточники — глубже, они нужны не всем и не сразу.

**Обязательное следствие:** README называет **и точку входа, и направление построения**.
Без первого читатель начинает с `01-` и попадает куда попало; без второго не понимает,
что чем обосновано, и принимает синтез за источник.

🔴 **Признак, что номера расставлены по накоплению:** первый каталог — самый старый,
а не самый объясняющий; «главное» лежит под номером 4–6. Проверка одной фразой:
*какой каталог ты назовёшь человеку, у которого есть пять минут?* Если это не `01-`,
нумерация обслуживает историю, а не читателя.

📍 **Отдельная позиция, которую стоит держать своим номером, — «фронт работы»**
(здесь `06-research`: незакрытые вопросы, гипотезы, план запросов). Она не про материал,
а про то, **что в репе ещё не сделано**, и потому не сворачивается в `ROADMAP`:
роадмап хранит приоритеты, а этот каталог — само содержание разысканий.

**Родня:** §1 (нейминг) · `75` §5б (README каталога: «Здесь» и «Растить») ·
`83` §1 (критерий выхода) · `72` (источник правды: производное чинится в источнике).

## 3. Скелет README (корневой)

Готовый шаблон — `templates/REPO_README_TEMPLATE.md`. Порядок секций сверху вниз:

1. **Заголовок** — `# Название — Vasilii Evdokimov`
2. **Короткое описание** — 1–2 предложения: что за репа и зачем, с контекстом.
3. **Заметка о языке** через blockquote — `> Most documents are in Russian…`
4. **`## Highlights`** — самое важное/сильное, буллетами, со ссылками на папки. Витрина.
5. **`## Repository map`** — таблица `| Folder | Contents |` со ссылками. Обязательна.
6. **Доп. секции по необходимости** — детали ключевых блоков.
7. **`## Data & privacy note`** — если есть чувствительные/анонимизированные данные.
8. **Дубль на русском** — `## О репозитории (RU)` — краткая версия описания.
9. **Контакты** в футере — `**Contact:** email · GitHub: @vevdokimovm`.

## 4. Технический минимум

1. `.gitignore` — всегда, под стек репы (шаблон — `templates/gitignore.template`).
2. Первый коммит осмысленный: `feat: initial archive (…)`, не `initial commit`.
3. Ссылки на папки прямо в README — кликаешь и проваливаешься.
4. Ветка `main`.
5. **Размер репы — знания, а не свалка файлов.** Репа = хранилище информации (конспекты, суть, логика, тезисы), а не архив. Три порога:
   - 🟢 **≤50 МБ — норма и цель.** В среднем все репы должны быть такими.
   - 🟡 **100 МБ — мягкий потолок.** Выше неудобно (медленный клон/пуш), допустимо в исключениях.
   - 🔴 **500 МБ — жёсткий потолок.** Выше Claude физически не принимает архив целиком — работа с репой в Claude ломается.

   Числа 500/100/50 — рабочий ориентир, не догма: исключения разбираем по кейсу и обновляем правила в процессе. Как удержаться в норме (что в репу можно, что нет, лимиты GitHub, сжатие) — `06-volume-compression.md`. Коротко: `.md` преимущественно, немного картинок (≤0.5 МБ, только по делу), немного PDF (≤5 МБ, первоисточники/результаты), скрипты и результаты анализа. **Никаких `.zip`/`.docx`/`.pptx`** — распаковать и законспектировать.

## 5. Публикация на GitHub

> Remote — **только HTTPS**. SSH (`git@github.com:`, порт 22) на этой сети режется
> (`Connection closed by … port 22`). HTTPS идёт по 443 и проходит.

Перед пушем репа на GitHub должна уже существовать — **пустая приватная**, без
README и `.gitignore`.

**Первый пуш (архив без `.git` внутри):**
```bash
unzip <repo>.zip && cd <repo>
git init -b main
git add .
git commit -m "feat: initial archive (…)"
git remote add origin https://github.com/vevdokimovm/<repo>.git
git push -u origin main
```

**Дальнейшие коммиты — три команды**, разовая настройка уже позади:
```bash
git add .
git commit -m "тип: что сделал"
git push
```
Ни `init`, ни `remote add`, ни `-u` больше не нужны. Состояние — `git status`,
история — `git log --oneline`. Префиксы сообщений: `feat:` новое, `fix:` починка,
`docs:` документация, `refactor:` перестройка. Всегда осмысленно — не `update`, а
что конкретно.

**Разбор ошибок git:**
1. `Connection closed by … port 22` / `Could not read from remote repository` →
   remote прописан по SSH. `git remote set-url origin https://github.com/vevdokimovm/<repo>.git` → пуш заново.
2. `error: remote origin already exists` → не `remote add`, а `remote set-url`.
3. `Repository not found` при HTTPS → репа на GitHub не создана или опечатка в имени.
4. Репа создана не пустой (с README) → `git push -u origin main --force` — допустимо
   ТОЛЬКО для самого первого пуша.
5. Коммит локально уже есть → `init/add/commit` не повторять, чинишь только remote.
