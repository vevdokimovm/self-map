# 25 — Версии, теги и релизы (и автопуш одной командой)

> **Зачем.** Ручной релиз — это цепочка из пяти шагов (бамп версии → коммит → тег → пуш → GitHub
> Release с описанием), где легко забыть звено: закоммитил, но не поставил тег; поставил тег, но не
> сделал релиз; сделал релиз, но описание набил руками с опечатками. Этот документ задаёт **единый
> механизм версионирования** и **скрипт автопуша** (`templates/publish.sh`), который делает всю
> цепочку одной командой из консоли — включая тег, GitHub Release и описание, вытянутое из
> `CHANGELOG.md`. Максимум автоматизации, минимум ручных звеньев. История версий — `24-changelog-protocol.md`;
> Git-механика и лимиты — `10-git-reference.md`; сетевые грабли РФ — `15-gotchas-claude-git.md`.

---

## 1. SemVer — как нумеруем

`MAJOR.MINOR.PATCH` (например `1.4.2`):

- **MAJOR** — несовместимое изменение (сломали обратную совместимость правил/структуры/API).
- **MINOR** — добавили новое, старое не сломали.
- **PATCH** — починили/уточнили без нового функционала.

Правило батча: фича = **MINOR**, фикс/доки = **PATCH**, слом = **MAJOR**. Для knowledge-реп без
кода версии можно вести по датам (`2026-07-06`) — но теги/релизы одинаково полезны как точки-снимки.

---

## 2. Три сущности и как они связаны

| Сущность | Что это | Где живёт |
|---|---|---|
| **Версия** | номер `MAJOR.MINOR.PATCH` | файл `VERSION` (или `app/config.py` в code-репе) |
| **Тег** | неизменяемая метка коммита `vX.Y.Z` | git (`git tag`) |
| **Release** | страница на GitHub с описанием и (опц.) ассетами | GitHub, привязан к тегу |
| **Запись CHANGELOG** | человекочитаемое «что изменилось» | `CHANGELOG.md` (`24`) |

Связь: **одна версия → один тег `vX.Y.Z` → один GitHub Release, чьё описание = секция этой версии из
`CHANGELOG.md`**. `CHANGELOG` — единственный источник текста релиза: пишешь изменения там один раз,
скрипт вытягивает их в описание релиза. Не дублируешь руками.

**Тег и Release — замороженные** (`21-revision-protocol.md`): выпущенную версию не переписываем.
Ошиблись — выпускаем следующую (PATCH), а не правим старый тег.

## 3. Что автоматизирует `publish.sh` (вся цепочка одной командой)

Скрипт `templates/publish.sh` (копируется в корень репы) делает по шагам:

1. **Определяет версию** — из аргумента (`--version 1.4.2`), из бампа (`--patch` / `--minor` /
   `--major` от текущей в `VERSION`), либо берёт то, что уже в `VERSION`.
2. **Идемпотентность + режим доделки** — если тег `vX.Y.Z` уже существует (локально или на
   remote), скрипт НЕ падает и НЕ переписывает выпущенное, а **достраивает недостающее**: пушит
   незапушенный тег; создаёт релиз, если его нет; заполняет описание-заглушку («Release X.Y.Z»)
   из CHANGELOG и ставит человеческий заголовок; докидывает недостающие ассеты. Осмысленное
   описание релиза никогда не перезаписывается — тег и релиз заморожены (`21-revision-protocol.md`).
   Всё уже на месте → сообщает и выходит с кодом 0. Перезапуск всегда безопасен.
3. **Записывает версию** в `VERSION` (бейдж/константу в README при желании обновляешь отдельно —
   скрипт трогает только `VERSION`, чтобы оставаться репо-агностичным).
4. **Вытягивает описание релиза** — секцию `## [X.Y.Z]` из changelog **питоном** в отдельный
   временный файл (`--notes-file`), а не через shell-пайп — чтобы UTF-8/тире/кириллица не билась.
   Changelog ищется по кандидатам (первый существующий): `$CHANGELOG_FILE → CHANGELOG.md →
   00-infrastructure/CHANGELOG.md → docs/CHANGELOG.md`, сначала от текущей папки, потом от корня
   git-репы. Секция не найдена → **громкое предупреждение**, а не молчаливая заглушка (именно
   молчаливая заглушка выпустила v1.5.0 base-repo пустой — разбор:
   `reports/incidents/publish_stub_release_notes_incident.md`). Заголовок релиза строится из
   заголовка секции: `## [1.5.0] — дата — Суть (MINOR)` → `<repo> v1.5.0 — Суть`.
5. **Коммитит** изменения (Conventional Commit: `release: vX.Y.Z`).
6. **Ставит аннотированный тег** `vX.Y.Z` с тем же описанием.
7. **Пушит** коммит и тег на remote — **с ретраями** (TLS-таймауты к GitHub из РФ — известная
   инфраструктурная беда, не баг; подробнее — `15-gotchas-claude-git.md` и `10-git-reference.md`).
8. **Создаёт GitHub Release** через `gh release create vX.Y.Z --notes-file <tmp>` — тоже с ретраями.
   Если версия — предрелиз (`X.Y.Z-rc1`), помечает `--prerelease`.
9. **(Опц.) Прикладывает ассеты** — для code-реп с архивной доставкой: собранный `.zip` (упакованный
   с wrapper-директорией — `10-git-reference.md`) добавляется в Release как asset (у GitHub Releases
   нет лимита размера/трафика, в отличие от LFS).
10. **Фолбэк без `gh`** — если GitHub CLI не установлен/не залогинен, скрипт всё равно пушит тег и
    печатает готовую команду/ссылку для ручного создания релиза. Ничего не теряется.

Итог: `zsh ~/Downloads/publish.sh --minor` — и версия поднята, закоммичена, отегана, запушена, релиз
создан с описанием из CHANGELOG. Ноль ручных звеньев.

**Внешняя обвязка — `templates/deploy_from_zip.sh` (пара к publish.sh).** publish.sh работает
*внутри* клона; деплойер закрывает путь *снаружи*: получил от Claude архив `<repo>-vX_Y_Z.zip` →
одна команда `zsh deploy_from_zip.sh <zip>` → sha256-сверка (`SHA=`), разворот обёртки, маркеры
корня, клон, чистая замена дерева, push, автопроверка «файлов в коммите == в дереве», затем сам
вызывает publish.sh из дерева (`--version <из обёртки/VERSION> --auto-asset`). Универсален для
любой репы системы (имя репы и версия выводятся из обёртки и файла `VERSION`, при обоих —
обязаны совпадать). `ALSO_PUBLISH="X.Y.Z ..."` — доделать старые релизы (заглушки описаний,
недостающие ассеты) тем же прогоном. Аналог FINPILOT-публикатора, защиты те же.

## 4. Грабли, которые скрипт уже обходит (закодированы внутри)

Эти уроки вшиты в `publish.sh`, не наступай на них заново:

- **CHANGELOG парсится питоном в `--notes-file`, не пайпом.** Shell-пайп с кириллицей/тире портит
  UTF-8 и рвёт команду. Питон читает секцию версии и пишет чистый временный файл.
- **Все `gh`/`git push` — с ретраями.** TLS-хендшейк к GitHub из РФ периодически таймаутит; одна
  попытка ненадёжна. Скрипт повторяет с бэк-оффом.
- **`gh release view` (проверка существования) — вывод в temp-файл**, потом читаем; прямой пайп в
  питон конфликтует по stdin.
- **Существование тега/релиза проверяется по РЕЗУЛЬТАТУ, а не по коду выхода** (`find`/`grep`
  возвращают 0/1 обманчиво — `reports/pitfalls.md` PIT-001/002).
- **Абсолютные пути** к системным утилитам, где критично (копипаст в zsh ломает PATH — привычка из
  FINPILOT-инструкций).
- **Архив пакуется с wrapper-директорией** (`repo_vX_Y_Z/`), а не «плоско» — плоская упаковка +
  `rsync --delete` однажды снесла репу (критический инцидент; `10-git-reference.md`).

## 5. Порядок выпуска версии (ручные шаги ДО скрипта)

Скрипт автоматизирует доставку, но контент готовишь ты:

1. Сделал изменения батча (для code-репы — с TDD, гейты зелёные).
2. **Записал в `CHANGELOG.md`** секцию новой версии (`24-changelog-protocol.md`) — это станет
   описанием релиза.
3. Обновил `WATCHLOG §3` (окно 10) и §0 (resume point).
4. Запустил `publish.sh` с нужным бампом → он делает шаги 3–10 из §3.
5. Проверил на GitHub, что тег, релиз и описание на месте.

Правило: **сначала CHANGELOG, потом publish** — иначе описание релиза будет пустым.

---

## 6. Knowledge-репа vs code-репа

- **code-репа** (FINPILOT): полный SemVer, версия в `app/config.py`, ассет-`.zip` в релизе, гейты
  перед публикацией. У FINPILOT свой специализированный `finpilot_publish.sh` — `publish.sh` здесь
  это его обобщённый, переиспользуемый предок для любой репы.
- **knowledge-репа**: версии по SemVer или по датам; ассет обычно не нужен (репа сама и есть
  контент); теги/релизы = точки-снимки «состояние базы на дату». Скрипт работает и так, и так.

---

## 7. Чек-лист выпуска

1. Изменения готовы (гейты зелёные, если code-репа)?
2. Секция версии записана в `CHANGELOG.md`?
3. `WATCHLOG §0/§3` обновлён?
4. Запущен `publish.sh` с верным бампом (`--patch`/`--minor`/`--major` или `--version`)?
5. На GitHub: тег `vX.Y.Z` есть, Release создан, описание = CHANGELOG-секция?
6. (code) Ассет-`.zip` приложен и распаковывается с wrapper-директорией?

---

> **Одной строкой:** одна версия → один тег `vX.Y.Z` → один GitHub Release с описанием из
> `CHANGELOG.md`; всю цепочку (бамп → коммит → тег → пуш → релиз + описание, опц. ассет) делает
> `templates/publish.sh` **одной командой** из консоли, идемпотентно, с ретраями под РФ-таймауты и
> `--auto-asset` (zip-снапшот дерева тега через `git archive` — прикладывается к релизу) и
> питон-парсингом CHANGELOG в `--notes-file` (чтобы кириллица не билась); сначала пишешь CHANGELOG —
> потом запускаешь скрипт.
