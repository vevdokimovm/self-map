## §0. Ответ одной фразой

**Хранение сессий привязано к рабочему каталогу. Живая связь между сессиями — нет.**

Это два разных механизма, и всё непонимание растёт из того, что их считают одним:

| | Привязано к каталогу? | Чем смотреть |
|---|---|---|
| **История** — прошлые чаты, `/resume` | 🔴 **да**, по умолчанию | `claude --resume`, `Ctrl+A` снимает фильтр |
| **Живая связь** — сообщения между сессиями | 🟢 **нет**, видит все | `ListAgents`, `SendMessage` |

Поэтому владелец «не видит чаты» из другой папки — но при этом сессия из `repos/base-repo`
**свободно пишет** сессии из `Documents/portrait-of-taste`. Проверено опытом, §5.

## §1. Где сессии лежат физически

```
~/.claude/projects/<слаг рабочего каталога>/<uuid>.jsonl
```

**Слаг** — путь рабочего каталога, где **каждый не-алфанумерный символ заменён на `-`**.
Не только `/`, как считалось раньше, — любой. Отсюда наблюдаемое на диске:

```
-Users-vasyaevdokimov-repos-base-repo                       ← ~/repos/base-repo
-Users-vasyaevdokimov-Documents----------------------portrait-of-taste
```

🔴 Двадцать два дефиса во втором — это **кириллица**: папка называлась
`Documents/система репозиториев/portrait-of-taste`, и каждая русская буква стала дефисом.
**Следствие:** два разных кириллических пути одинаковой длины дают **один и тот же слаг**
и их сессии смешиваются в одном каталоге. Латиница в путях — не вкусовщина, а условие
различимости истории.

При длине слага свыше **200 символов** он обрезается, и к нему добавляется хеш полного
пути — тогда столкновения не происходит.

### 🔴 Переезд репы дробит её историю

У одной репы `portrait-of-taste` на диске **три** каталога сессий:

```
-Users-vasyaevdokimov-Documents----------------------portrait-of-taste   ← кириллический путь
-Users-vasyaevdokimov-Documents-portrait-of-taste                        ← после ухода от кириллицы
-Users-vasyaevdokimov-repos-portrait-of-taste                            ← нынешний
```

Слаг считается от **пути**, а не от репы. Переехала папка — прежние чаты остались
за старым слагом: они целы, но `/resume` из нового места их не покажет, пока не нажать
`Ctrl+A`. У `character-a-analysis` — то же самое, тоже три каталога.

> Это прямой ответ на «почему я вижу разные чаты»: **менялся не Claude Code,
> менялся путь**. Два переезда системы — три несвязанные пачки истории.

### 🆕 🔴 Рабочий каталог сессии закреплён при старте — сменить его изнутри нельзя

**Живой случай 08.08.2026**, `personal-finance-dss`: репа переехала
`~/Downloads/…-v8.3.1` → `~/Documents/…-v8.5.0`, вахта работала из старой папки,
и владелец **не мог этого исправить словами**. Дословно, с нарастающим раздражением:
*«ты можешь поменять папку в которой мы работаем»* → *«в смысле ты работаешь оттуда.
у меня до сих пор пишет старую папку `~/Downloads/personal-finance-dss-v8.3.1`»*.

**Ответ: нет, не может.** Рабочий каталог фиксируется при **запуске** `claude`
и живёт до конца сессии. `cd` внутри команды меняет каталог **только этой команды**;
харнесс подтверждает это явной строкой после каждого такого вызова:

```
Session cwd remains /Users/vasyaevdokimov/repos/base-repo;
directory changes made by the backgrounded command do not apply to subsequent commands.
```

> **Проверено в этой же сессии 04.09.2026** — строка выше снята с живого вывода,
> а не взята из документации.

| Что хочется | Что на самом деле |
|---|---|
| «перейди в новую папку» | сессию надо **перезапустить** из неё |
| `cd` в Bash-вызове | действует на один вызов, `cwd` сессии не двигает |
| работа по абсолютным путям | 🟢 работает и есть обходной путь, но слаг истории останется старым |

🔴 **Цена — не только неудобство.** Слаг каталога сессий считается от пути (выше),
поэтому работа «из старой папки по новым путям» пишет историю **не туда, куда
владелец будет её искать**. Правильный порядок при переезде репы: закрыть сессию,
запустить `claude` из нового каталога, при необходимости достать прежние чаты
через `Ctrl+A`.

### Что ещё лежит в каталоге проекта

Проверено по диску, документацией не описано:

```
-Users-vasyaevdokimov-repos-base-repo/
├── 2b3d0213-….jsonl          транскрипт сессии
├── 2b3d0213-…/               одноимённый КАТАЛОГ той же сессии
│   ├── custom-title.json     {"customTitle": "base-05"} — имя сессии
│   └── subagents/            транскрипты субагентов, отдельными файлами
└── memory/                   🔴 авто-память: MEMORY.md и файлы фактов
```

🔴 **`memory/` лежит рядом с сессиями, но принадлежит КАТАЛОГУ, а не сессии.**
Поэтому память переживает удаление сессий и видна всем сессиям этой папки — и поэтому же
она **не переезжает** вместе с репой: сменил каталог, начал с пустой памятью.

### Что внутри `.jsonl`

Формат внутренний и меняется между версиями — на него **нельзя опираться в скриптах**
(наши `session_metrics.py` и `token-probe` читают его сознательно, с канарейкой). Типы
записей, замер по крупнейшей сессии (63 583 записи, 181 МБ):

| Доля объёма | Тип | Что это |
|---:|---|---|
| 68.8 % | `user` | 🔴 сюда попадают **результаты инструментов**, отсюда и вес |
| 14.8 % | `attachment` | служебные вставки |
| 11.8 % | `assistant` | собственно ответы |
| 3.1 % | `file-history-snapshot` | снимки файлов для `/rewind` |

Внутри `attachment` крупнейшая доля — **`hook_success`, 19.1 МБ в одной сессии**: вывод
хука `SessionStart` пишется в транскрипт **каждый ход**. Хук в одну строку стоит десятков
мегабайт за долгую вахту.

## §2. Почему `/resume` показывает разные чаты — и как снять фильтр

**По умолчанию** пикер показывает сессии текущего worktree плюс те, что добавили этот
каталог через `/add-dir`. Отсюда ощущение «чаты пропали» — они целы, просто отфильтрованы.

### 🔴 Поправка к прежней записи базы

`97-claude-code-capabilities.md` §6-кватер утверждал: *«`/resume` показывает сессии
ТОЛЬКО текущего рабочего каталога»*. **Это неверно с версии 2.1.196** — в пикере есть
клавиши, снимающие фильтр. Запись прожила в базе один день и исправлена здесь.

| Клавиша в пикере | Что показывает |
|---|---|
| `Ctrl+A` | **все проекты на машине** — вот чем смотреть «все чаты» |
| `Ctrl+W` | все worktree текущего репозитория |
| `Ctrl+B` | только текущую ветку |
| `/` + текст | поиск по названиям |
| `Ctrl+R` | переименовать сессию прямо в пикере |

**В пикер не попадают** (даже под `Ctrl+A` — кроме фоновых): сессии, начатые с `/loop`;
сессии SDK; неинтерактивные запуски с `-p`. Фоновые помечены `bg` и видны под `Ctrl+A`.

**По ID фильтра нет вовсе.** С версии 2.1.223 `claude --resume <id>` ищет сначала
в текущем проекте, затем **во всех остальных на машине**, и открывает, если ID нашёлся
ровно один раз. Сессия из чужого каталога: того же репозитория — открывается на месте;
другого — Claude Code кладёт в буфер обмена готовую команду `cd … && claude --resume …`,
но сам не выполняет.

## §3. Управление сессиями

| Команда | Что делает |
|---|---|
| `claude -c` / `--continue` | последняя сессия **этого каталога**, без пикера |
| `claude -r` / `--resume` | пикер |
| `claude --resume <имя\|id>` | конкретная, минуя пикер |
| `claude -n <имя>` | **задать имя заранее**, при запуске |
| `claude --fork-session` | при возобновлении завести **новый** ID, оставив исходную целой |
| `claude --session-id <uuid>` | назначить ID самому |
| `claude --no-session-persistence` | не писать транскрипт вовсе (только с `-p`) |
| `claude -w` / `--worktree` | своё git-worktree под сессию — изоляция файлов |

Внутри сессии: `/rename <имя>` · `/resume` (переключиться, **не восстанавливая** режим
разрешений) · `/branch <имя>` (копия транскрипта до этой точки, отдельной сессией) ·
`/rewind` (откат к контрольной точке) · `/clear` (новая пустая; **старая остаётся** на
диске и доступна через `/resume`).

Имя без `-n` генерируется само: `<имя-каталога>-<2 символа>` — эта сессия зовётся
`base-repo-2b`. При конфликте живых имён новая получает суффикс из двух слов.

## §4. 🔴 Удаление: транскрипты стираются сами через 30 дней

**Ключ `cleanupPeriodDays` в `settings.json`, по умолчанию 30.** Проверено 30.08.2026:
**в наших настройках он не задан ни в одном файле** — ни в `~/.claude/settings.json`,
ни в `base-repo/.claude/settings.json`. Значит работает дефолт, и транскрипты старше
месяца удаляются молча.

**Замер сейчас:**

| Сессий | Объём | Возраст |
|---:|---:|---|
| 0 | — | старше 30 дней |
| 0 | — | 25–30 дней |
| 53 | 351 МБ | 7–25 дней |
| 18 | 949 МБ | младше 7 дней |

Самая старая — **22 дня**, система живёт с 21.08.2026. Значит **чистка ещё ни разу
не срабатывала, и ничего пока не потеряно**. Первое срабатывание — около **20.09.2026**,
и под него уйдут транскрипты первых вахт: разборы, отменённые решения, обоснования.

> **Это тот же класс, что удаление архивов релизов (ритуал `close_batch.py`, шаг 4):
> носитель считается копией, пока не выяснится, что он единственный.** Наш `WATCHLOG`
> и `CHANGELOG` хранят **решения**, транскрипт — **как к ним пришли**. Второе нигде
> не дублируется.

**Отключить чистку штатно нельзя** — документация даёт только изменение числа. Практика:
поставить заведомо большой срок либо забирать нужное до срока.

### 🔴 Что делать нам — решено 30.08.2026, и первое решение отменено на месте

**Напрашивалось:** поднять `cleanupPeriodDays` до года и не терять историю.
**Проверка диска это запретила.**

```
диск: занято 12 ГБ, свободно 7.4 ГБ (62 %)
темп роста сессий: 70 МБ в день
```

| Срок | Сколько займут сессии |
|---:|---|
| 30 дней (дефолт) | ≈ 2.1 ГБ — умещается |
| 90 дней | ≈ 6.1 ГБ — съедает **почти всё** свободное |
| 180 дней | ≈ 12.3 ГБ — **физически не влезает** |
| 365 дней | ≈ 24.9 ГБ — исключено |

> **Дефолт в 30 дней при нашем темпе и нашем диске — не небрежность настройки,
> а единственный умещающийся вариант.** Решение «поднять срок» было принято
> до того, как спросили диск, и отменено после. Записано как есть: это тот же
> порядок, что `/auto` §1.1 — **сначала факт с диска, потом суждение**.

**Что делаем вместо этого:**

1. **Срок не трогаем** — 30 дней остаются, места на большее нет;
2. **ценное из транскрипта не хранить в транскрипте** — переносить в репу сразу
   (`20-knowledge-capture-protocol.md`: находка без файла теряется вместе с сессией).
   Транскрипт — черновик с расписанным сроком, а не архив;
3. **предупреждать заранее**: в `scripts/system_status.py` заведён порог
   «сессий на грани удаления» — сообщает, когда транскрипты подходят к сроку,
   чтобы владелец успел решить, надо ли что-то вынуть;
4. **`hook_success` — 19 МБ в одной сессии**: вывод хуков держать коротким,
   он пишется каждый ход и разгоняет темп тех самых 70 МБ в день.

### Удаление вручную

🔴 **`claude rm <id>` удаляет только ФОНОВУЮ сессию** — так написано в собственной
справке CLI (`Delete a background session`). К обычным чатам эта команда неприменима;
внешний разбор, называющий её общим средством удаления, здесь ошибается.

Обычная сессия удаляется удалением её `.jsonl`. Рядом остаются одноимённый каталог
(`subagents/`, `custom-title.json`) — их удалять тем же движением. `memory/` **не трогать**:
она принадлежит каталогу, а не сессии.

Ещё два ключа: `desktopSessionCleanupPeriodDays` — для сессий приложения;
`CLAUDE_CODE_SKIP_PROMPT_HISTORY` — переменная окружения, отключает запись истории вовсе.

## §5. Связь между сессиями — проверено опытом, а не по документации

**Опыт 30.08.2026.** Из сессии в `~/repos/base-repo` вызван `ListAgents`:

```
This session is base-repo-2b [bb4f22]
Peer sessions (2):
  pot-01 [ed6655]  ·  interactive · idle · started 2h ago
  ca-01  [98a3f7]  ·  interactive · idle · started 2h ago
```

🔴 **Обе соседние сессии — из других рабочих каталогов** (`~/repos/portrait-of-taste`
и `~/repos/character-a-analysis`), и обе видны. Сообщение ушло в `pot-01`, и **пришёл
ответ**: сосед подтвердил свой каталог и то, что видит нас у себя. Связь двусторонняя
и границ каталога не знает.

> **Вот и весь ответ на вопрос владельца: история фильтруется каталогом, живая связь — нет.**
> `/resume` спрашивает «что здесь было», `ListAgents` — «кто сейчас жив», и второе
> границ каталога не знает.

### Чем связываться

- **`ListAgents`** — кто жив: текущая сессия, субагенты, соседние локальные сессии,
  облачные (при Remote Control), сессии на других машинах.
- **`SendMessage`** — послать текст по имени. **Имя и есть адрес.** Приходит получателю
  обёрнутым в `<cross-session-message from="…">`; отвечают, копируя `from` в `to`.
- **`@имя-сессии`** в промпте (с 2.1.232) — владелец адресует прямо из строки ввода.
- **`notify_when_idle: true`** — один сигнал, когда соседняя сессия освободится.
  Дешевле, чем спрашивать «ты закончил?»; опрашивать в цикле запрещено.

**Передаётся только текст.** Ни история, ни файлы отправителя не идут — **прочитать
транскрипт соседа нельзя**. Для передачи содержания есть `/export`.

Внутри одной машины сообщения идут через Unix-сокет, **минуя серверы Anthropic**;
между машинами — через Anthropic и Remote Control.

### 🔴 Запрет, который важнее всех возможностей

**Разрешения действуют посессионно.** Нельзя просить соседнюю сессию сделать то,
что в своей запрещено или предсказуемо будет запрещено: это **обход решения владельца
чужими руками** — «отмывание разрешений» через сессию. Заблокированное возвращается
владельцу, а не переадресуется соседу.

Управление входящими — ключ **`crossSessionInbound`** в `settings.json`, три значения:
`accept` (доставлять), `hold` (показать уведомление, придержать; очередь до 100),
`refuse` (отбрасывать). По умолчанию зависит от режимов разрешений обеих сторон.
Ключ **`isolatePeerMachines: true`** требует одобрения каждого сообщения на другую машину.

### 🆕 Живой случай 04.09.2026: запрет сработал в обе стороны, и это дало пользу

**Владелец попросил дословно:** *«ты можешь зайти во вторую рабочую сессию Клода
и сделать то, что он там не может»*. Речь шла о хуке `PreToolUse`, который
второй вахте **трижды подряд** запретил ставить классификатор авто-режима:
запись в `.claude/hooks/` и `.claude/settings.json` — это правка собственной
конфигурации агента.

**Что произошло дальше, и почему это стоит записать:**

| Сторона | Что сделала |
|---|---|
| `base-06` (эта вахта) | спросила прямо: «что именно ты не можешь?» — вместо догадок |
| `finpilot-02` | 🟢 **сама отказалась просить:** *«просить обход запрета я не буду, ты прав по существу»* |
| обе | сошлись, что это `permission laundering`, и вернули задачу владельцу |

> **Запрет не пришлось применять — он сработал как общее понимание.** Обе стороны
> назвали класс одинаково, ни одна не попыталась. Это и есть рабочее состояние
> правила: оно не удерживает, а **избавляет от необходимости удерживать**.

### 🔴 А польза оказалась в другом — и её нельзя было получить иначе

В том же обмене вторая вахта получила от новой проверки `Г4` отказ и **уже
собиралась править журнал**. Вместо того чтобы принять вердикт, она спросила
точный критерий:

> *«Если проверка читает не первые N строк, а что-то другое — скажи, подгоню
> под него, а не под догадку»*.

**Её собственная гипотеза была неверна.** Но вопрос вскрыл настоящую причину:
проверка читала `WATCHLOG.md` в корне, а у репы там **указатель** на
`docs/WATCHLOG.md`. Дефект был в проверке; репа была права.

| Без обмена | С обменом |
|---|---|
| чужой батч потрачен на ненужную правку | правка остановлена сообщением |
| дефект проверки живёт дальше | найден и починен в тот же час |

> **Соседняя сессия — не только исполнитель, но и независимый наблюдатель.**
> Она смотрит на твой инструмент снаружи, не наследуя твоей рамки, — и потому
> замечает то, что изнутри выглядит нормой (`70-independent-review-blindness.md`).

**Практическое следствие:** отправляя чужой сессии вердикт своего инструмента,
имеет смысл сразу давать **точный критерий проверки**, а не только вывод.
Иначе она будет подгонять под догадку — и, возможно, испортит то, что было верно.

### Фоновые сессии

`claude --bg "задача"` · `claude agents` (обзор) · `claude attach <id>` ·
`claude logs <id>` · `claude stop <id>` · `claude respawn <id>` · `claude rm <id>`.
Изнутри сессии — `/bg`. Фоновые автоматически получают своё worktree, поэтому
за файлы не дерутся.

### Команды агентов — экспериментально

`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` включает команду независимых сессий с общим
списком задач и прямой перепиской, координация — через `~/.claude/teams/<имя>/`.
Отличие от субагентов: субагент работает **внутри** одной сессии и возвращает результат;
участник команды — самостоятельная сессия со своим окном.

🔴 **Цена в токенах — по числу участников**, у каждого своё окно контекста. Учитывая
замер, что субагенты дали **40 % расхода за день**, а на последовательных задачах
многоагентность **проигрывает** одиночной на 39–70 %, — для нашей системы это
не улучшение по умолчанию.

## §6. Сколько сессий и как они влияют друг на друга

Замер 30.08.2026:

| Величина | Значение |
|---|---:|
| каталогов проектов | 18 |
| сессий верхнего уровня | 71 |
| транскриптов субагентов | 148 |
| всего файлов `.jsonl` | 219 |
| общий объём | **1.5 ГБ** |
| крупнейшая сессия | 181 МБ, 63 583 записи |

**Предела на число одновременных сессий в документации нет.**

**По квоте сессии складываются, а не делятся.** Каждая фоновая сессия и каждый участник
команды тратят из общего лимита независимо — это ровно тот механизм, что дал разбор
инцидента с лимитом (`reports/incidents/rate_limit_after_account_switch_incident.md`):
пятичасовое окно считается от первого запроса и принадлежит **аккаунту**, а не сессии.

**Две сессии в одном каталоге не конфликтуют за хранение** — у каждой свой `.jsonl`.
🔴 Но **за рабочие файлы дерутся**: правки не изолированы ничем. Средство — `--worktree`.

## §7. Что из этого мы применяем

1. **`Ctrl+A` в пикере** — так владелец видит все чаты, а не только текущей папки.
2. **Латиница в путях репозиториев** — кириллица схлопывает слаги (§1).
3. **Срок жизни НЕ трогать** — 30 дней дефолта упираются в свободные 7.4 ГБ (§4);
   вместо этого — порог в `system_status.py` и вынос ценного в репу до срока.
4. **Ценное — в репу, а не в транскрипт**: транскрипт стирается по расписанию.
5. **`ListAgents` перед долгой работой** — соседняя сессия может делать то же самое.
6. **Разрешения не обходить через соседа** (§5) — это правило, а не совет.

## §8. Чего мы не знаем

- **Точный формат записей `.jsonl`** — объявлен внутренним и меняющимся между версиями.
  Наши инструменты его читают, поэтому у них канарейка.
- **Штатного способа отключить чистку** не нашлось — только менять число.
- **Предел одновременных сессий** нигде не указан.
- **Блокировки файлов** между сессиями одного каталога не описаны; наблюдаемо их нет.
- **Что именно остаётся на диске после `claude rm`** — справка говорит «удаляет фоновую
  сессию», подробностей нет.
