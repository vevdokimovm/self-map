# 94. Где живут секреты системы

> **Вопрос владельца, 29.08.2026, дословно:** *«что по итогу какое решение по
> секретам? мы так и не решили как в системе их хранить — репа? или что?»*
>
> **Ответ одной строкой: связка ключей macOS. Не репа, не файл, не база.**
> Реализовано, не отложено: `scripts/secret.py`, исключение в `pack_release.py`,
> проверка в `revision_check.py`. Ниже — почему именно так и как этим пользоваться.

Этот документ отвечает на вопрос **«где лежит значение»**. Вопрос **«как
код его получает»** уже закрыт в
[`32-git-hooks-and-secret-scanning.md`](32-git-hooks-and-secret-scanning.md)
(`os.getenv`, `.env` в `.gitignore`, секрет не в argv) — и эти два документа
не спорят, а стыкуются: 32 говорит «читай из окружения», 94 — «а откуда
окружение берёт значение».

---

## §1. Решение

| | |
|---|---|
| **Хранилище** | связка ключей macOS, служба `repos:<ИМЯ_КЛЮЧА>` |
| **Реестр «что нужно»** | существующие `.env.example` в репах — нового файла нет |
| **Инструмент** | `base-repo/scripts/secret.py` |
| **Файл `.env`** | собирается по требованию, живёт минимально, в архив не входит |
| **Предпочтительный способ** | `secret.py run <репа> -- команда` — файла не возникает вовсе |

```bash
secret.py list                    # что нужно системе и что из этого заведено
secret.py set VK_TOKEN            # завести (ввод вслепую, не аргументом)
secret.py env personal-finance-dss   # собрать .env из связки, режим 600
secret.py run vk-graph -- python3 export.py   # без файла вообще
```

## §2. Почему НЕ репа — довод замеренный, а не вкусовой

Соблазн понятен: у системы 63 репы, всё живёт в файлах, логично завести
`secrets-vault` и хранить там. **Три факта этой конкретной системы делают
такое решение худшим из возможных.**

**1. У рабочих реп нет `.git`, и каждый батч пакует репу в zip.**
🟡 **Уточнено 07.09.2026:** у `base-repo` локальный `.git` заведён, у остальных
66 реп — нет. Для этого раздела ничего не меняется: секрет, попавший в архив,
остаётся в архиве независимо от наличия git, а `pack_release.py` `.git`
в архив не кладёт вовсе.
`pack_release.py` кладёт архив в `~/Downloads`, и архивы **намеренно не
удаляются** — решение владельца 22.08.2026: пока нет git, архив не копия,
а оригинал. Значит секрет в репе — это секрет в архиве, по экземпляру
на каждую версию, навсегда.

**2. Это уже происходило.** В `mission-control/TASKS.md` до сих пор висит
открытым: «🔴 **Отозвать токен VK** — `.env` в `vk-graph.zip`, 220 символов».
Не гипотетический риск — сработавший механизм.

**3. База раздаётся в 54 репы.** `sync_base_local.py` копирует содержимое
`base-repo` в каждую. Секрет, положенный в базу, размножается ×54 при следующей
же раздаче, и отзывать его пришлось бы 54 раза, один раз забыв.

> Общее правило, которое из этого следует: **секрет не должен лежать там,
> где работает механизм копирования.** А в этой системе копирование работает
> везде — упаковка, раздача, синхронизация зеркала. Единственное место вне
> его досягаемости — связка ключей.

## §3. Почему не gpg / sops / age / 1Password

Проверено 29.08.2026 командой `command -v`:

| | |
|---|---|
| `security` (связка macOS) | **есть**, `/usr/bin/security` |
| `gpg` | есть, `/usr/local/bin/gpg` |
| `sops`, `age`, `op`, `pass`, `git-crypt` | **нет ни одного** |

`sops`/`age` требуют установки и, главное, **мастер-ключа**. `gpg` установлен,
но требует того же: ключ плюс парольная фраза. И вот здесь ловушка, ради
которой этот абзац написан:

> **Шифрованный файл в репе не решает задачу, а сдвигает её.** Появляется
> новый секрет — ключ расшифровки, — который надо где-то хранить. Если хранить
> его в связке, то связка и так уже хранилище, и промежуточный шифрованный
> файл ничего не добавляет. Если хранить рядом с репой — секрет снова в репе,
> только с лишним шагом.

Связка обрывает рекурсию: её ключ — **пароль входа в macOS**. Он уже
существует, уже введён, уже защищает всё остальное на машине, и его не надо
никуда класть. Тем же механизмом Claude Code хранит собственный токен.

Когда решение поменяется: появится вторая машина или потребуется передавать
секрет кому-то ещё. Тогда — `age` + шифрованный файл в репе, потому что задача
станет другой (переносимость), а не потому, что связка плоха.

## §4. Реестр — это `.env.example`, и нового файла нет

Прямое применение `PIT-097`: **список — намерение, свойство объекта — факт.**

| | Где | Что говорит | Кто пишет |
|---|---|---|---|
| **намерение** | `.env.example` в репе, коммитится | какие ключи репе НУЖНЫ | тот, кто пишет код |
| **факт** | связка ключей | у каких ключей ЕСТЬ значение | владелец, один раз |

Третий файл-реестр («список наших секретов») был бы **четвёртым местом для
расхождения** и первым же кандидатом протухнуть: его надо помнить обновлять,
а `.env.example` обновляется сам собой, потому что без него код не запускается.

`secret.py list` просто сопоставляет эти два источника и показывает разницу.
Расходиться им негде — ни один из них не дублирует другой.

### Как отличается секрет от настройки

В `.env.example` **пустое значение = сюда подставляется секрет** (конвенция
описана в шапке `personal-finance-dss/.env.example`). Но не всякий пустой
ключ секрет: `VAULT_ROOT=` пуст потому, что путь у каждого свой. Поэтому
отсекаются имена на `_ROOT`, `_DIR`, `_FILE`, `_PATH`, `_REPO`, `_URL`,
`_HOST`, `_PORT`, `_ID`, `_USERNAME` и подобные.

🔴 **Для живого `.env` это правило не работает и применять его туда нельзя** —
там значения заполнены по определению, и «пусто = секрет» даёт ровно обратный
ответ. Найдено 29.08.2026 канарейкой: проверка гигиены молчала на `.env`
с живым токеном именно по этой причине. Для живого файла источник правды —
соседний `.env.example`, а если его нет — признак по имени (`TOKEN`, `SECRET`,
`PASSWORD`, `_KEY`, `DSN`, …). Ошибка в сторону «это секрет» дешевле: лишний
разговор против незамеченного токена.

## §5. Механизмы, а не обещания

Правило в документе — совет. Ниже то, что работает само:

| Механизм | Где | Что делает |
|---|---|---|
| **исключение из архива** | `pack_release.py`, `is_secret_file()` | `.env`, `.envrc`, `.netrc`, `*.pem`, `*.key`, `id_rsa`… не входят в zip. `.env.example` — входит |
| **громкий пропуск** | там же | список исключённого печатается: тихий пропуск оставил бы непонятное «не стартует после распаковки» |
| **канарейка упаковщика** | `selftest_secret_files()` | сборка **отменяется**, если упаковщик перестал отличать `.env` от `.env.example` |
| **гейт, FAIL** | `revision_check.py`, `check_secret_hygiene()` | `.env` есть, а правила в `.gitignore` нет |
| **гейт, WARN** | там же | в `.env` лежит непустое значение секретного ключа |
| **канарейка гейта** | `selftest_secret_hygiene()` | проверяет **различение**: ловит открытую репу и молчит на закрытой |
| **отсутствие флага значения** | `secret.py`, конструкция CLI | флага `--value` нет **вовсе** — значение физически негде передать через argv |

Последняя строка — самая важная и самая дешёвая. Правило «не передавай секрет
аргументом» соблюдается ровно до первой спешки. **Отсутствующий флаг соблюдается
всегда**, потому что нарушить его нечем.

## §6. Если секрет всё же засветился

Порядок прежний и единственный (`32` §«Секрет в аргументе командной строки»):

1. **Отозвать у провайдера.** Это единственный шаг, который что-то меняет.
2. Перевыпустить, положить новый в связку: `secret.py set ИМЯ`.
3. Только потом — чистить файлы, историю, архивы.

> Чистка без отзыва не решает ничего: копия уже могла быть снята. Отзыв без
> чистки решает всё, кроме опрятности.
