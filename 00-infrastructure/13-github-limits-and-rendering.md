# 13 — GitHub: лимиты, рендеринг форматов, подводные камни

> Методичка инфраструктуры `base-repo`. Точные значения — из официальной документации GitHub (docs.github.com) на июль 2026. Проверять актуальность, лимиты иногда меняются.

---

## 1. Лимиты размеров (жёсткие и мягкие)

| Что | Значение | Тип |
|-----|----------|-----|
| Файл через `git push` | > **50 MiB** → предупреждение (но пушится) | 🟡 мягкий |
| Файл через `git push` | > **100 MiB** → **блокируется** (push отклоняется) | 🔴 жёсткий |
| Файл через загрузку в браузере | ≤ **25 MiB** | 🔴 жёсткий |
| Размер одного push | **2 GB** | 🔴 жёсткий |
| Частота пушей | рекомендуется ≤ **6 пушей/мин** на репу | 🟡 |
| Размер репозитория | рекомендуется **< 1 GB**, настоятельно **< 5 GB** | 🟡 (>5 GB — письмо от GitHub) |

**Git LFS** (для файлов > 100 MiB): максимальный размер файла — **2 GB** (Free/Pro), **4 GB** (Team), **5 GB** (Enterprise Cloud). Бесплатная квота LFS: **1 GB хранилища + 1 GB трафика/мес** — быстро кончается, докупается пакетами.

**Сверка с нашими порогами** (🟢≤50 / 🟡100 / 🔴500 МБ): наши пороги — про то, чтобы **Claude мог взять архив целиком** и репа оставалась здоровой, и они **строже** GitHub'а по репозиторию (500 МБ ≪ 5 GB). Важно не путать: у GitHub **100 MiB — это лимит на ОДИН ФАЙЛ** (жёсткий), а не на репу. Наш «мягкий 100 МБ» — про репу; это разные вещи.

## 2. Что GitHub отображает в браузере БЕЗ скачивания

Рендерится прямо на странице файла (кнопка `Raw` всегда даёт исходник):

| Формат | Как отображается | Ограничение |
|--------|------------------|-------------|
| **Markdown** (`.md`) | форматированный | превью надёжно если файл **< ~2 MB** |
| **Mermaid** (в ```` ```mermaid ```` внутри `.md`) | диаграмма | как markdown |
| **Изображения** PNG, JPG, GIF, PSD, SVG | картинка (+ diff-режимы 2-up/swipe/onion) | SVG без скриптов/анимации; в Firefox SVG иногда не рендерится |
| **PDF** | постранично в браузере | превью надёжно если небольшой |
| **CSV / TSV** | таблица с поиском | большие таблицы не отрендерятся (таймаут) |
| **JSON** | подсветка синтаксиса | (как GeoJSON → карта, см. ниже) |
| **GeoJSON / TopoJSON** (`.geojson`/`.topojson`/`.json` с нужным type) | интерактивная карта (Leaflet) | лучше конвертировать в TopoJSON (−80% размера) или бить на части |
| **Jupyter** (`.ipynb`) | статический HTML | интерактивные JS-графики не работают; рендер часто таймаутит (→ nbviewer, но **не для приватных реп**) |
| **3D** (`.stl`) | интерактивный WebGL-вьювер (вращение/зум) | **> 10 MB — не отображается**; нужен WebGL в браузере |

**Общее правило рендеринга:** GitHub рендерит превью, если файл **небольшой (обычно < 2 MB)**. Сложные/большие файлы **таймаутят** → откат в plain text или «не отображается». Рендеринг делается в браузере (nbconvert, psd.js, three.js) и **недетерминирован** — один и тот же большой файл может отрендериться сейчас и не отрендериться потом. **Не полагаться на превью GitHub для критичных больших файлов** — держать файлы маленькими (это ровно наш протокол сжатия в тезисные `.md`).

**Подсветка кода:** очень большие исходники теряют подсветку/показываются как «too large». Держать файлы читаемыми.

## 3. Лимиты diff / PR (полезно знать)

- Diff одного файла: максимум **20 000 строк** или **500 KB** сырого diff; авто-загружается **400 строк / 20 KB**.
- Максимум **300 файлов** в одном diff.
- Максимум **25 рендеримых файлов** (картинки/PDF/GeoJSON) в одном diff.
- Списки коммитов в compare/PR: до **250 коммитов**.
- Вкладка Commits: максимум **10 000**.

## 4. Подводные камни (то, что легко упустить)

1. 🔴 **Секрет в истории живёт вечно.** Закоммитил и запушил токен/пароль → удаление файла в следующем коммите **НЕ убирает** его из истории. Нужно переписывать историю (`git filter-repo`) **и ротировать секрет**. Отсюда наше железное правило «секреты не грузим никогда» — не про аккуратность, а про необратимость. GitHub Push Protection / Secret Scanning может заблокировать push с секретом.
2. 🔴 **Удаление большого файла не уменьшает репу.** Файл остаётся в истории, `.git` не худеет. Реальное уменьшение — только переписыванием истории (`git filter-repo`) + `git gc`. Инструмент диагностики — `github/git-sizer`.
3. 🟡 **Архивы (.zip) в git = быстрое раздувание.** Git не диффит бинарники — каждое изменение архива **пересохраняет его целиком** в историю. Для версионируемого контента хранить **распакованный текст**, а не архив. (Наш принцип «один zip = полный контекст» — это про **передачу/бэкап**, а не про версионируемое хранение исходников; zip — транспортный артефакт, генерируем на отдачу, а в репе живут текстовые исходники.)
4. 🟡 **`.gitignore` не убирает уже отслеживаемые файлы.** Если файл уже закоммичен, добавление в `.gitignore` не поможет — нужен `git rm --cached <file>`.
5. 🟡 **Line endings на macOS.** Кросс-платформенно нормализовать через `.gitattributes` (`* text=auto`), чтобы не было «весь файл изменён» из-за CRLF/LF.
6. 🟡 **Регистр имён.** macOS файловая система регистронечувствительна, git — чувствителен. Переименование только регистра (`file.md`→`File.md`) может глючить; делать через `git mv`.
7. 🟡 **LFS-трафик кончается.** 1 GB/мес бесплатно; при активных клонах/скачиваниях LFS-файлы станут недоступны до сброса/докупки. Лучший ответ — **не хранить большие бинарники вообще**.
8. 🟡 **Force-push переписывает общую историю** — на приватных соло-репах ок, но привычка опасная.

## 5. Как работать оптимально (наш стандарт)

1. **Только текст, маленькими файлами.** Тезисные `.md` < 2 MB → и рендерятся надёжно, и Claude берёт легко, и diff читаемый.
2. **Никаких секретов и больших бинарников** в git (см. §4.1, §4.2).
3. **Remote только HTTPS** (наш стандарт).
4. **Conventional Commits**, осмысленная история (её видит рекрутер).
5. **Диагностика здоровья репы** — `git-sizer` при подозрении на раздувание.
6. **Большие данные** — не в git: releases (для раздачи бинарников, без лимита размера/трафика на отдачу), внешнее хранилище, или пакетный менеджер для зависимостей.
7. **README как точка входа** — и для человека, и для Claude (рендерится первым).
