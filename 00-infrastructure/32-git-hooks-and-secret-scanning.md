# 29 — Git-хуки и защита от секретов

> Единственное железное правило репы (`01-repo-standard.md` §2.4) — **секреты не коммитим
> никогда**. Правило хорошее, но оно держится на внимательности, а внимательность
> заканчивается в 2 часа ночи на пятнадцатом коммите. Этот файл — про то, как перевести
> правило из режима «я помню» в режим «система не даёт».

## Почему одного правила мало — живой пример

12.07.2026 при первом же прогоне `repo_audit.py` в `academic-portfolio` нашлись **живые
токены**:

- VK access token сообщества — прямо в `main.py` чат-бота, плюс дубль в `notes.txt` рядом;
- Telegram bot token — в `alertmanager.yml` из лабы по мониторингу.

Оба лежали в репе месяцами и уехали в историю git. Репа приватная, так что катастрофы не
произошло, но урок оказался жёстче, чем кажется:

> **Из git секрет не «удаляется». Он отзывается.**

Убрать строку из файла — не помогает: она остаётся в истории. Переписать историю через
`git filter-repo` — тоже не гарантия: копии архива уже разошлись по машинам, чатам и
бэкапам. Единственная мера, которая реально закрывает дыру, — **отозвать токен у
провайдера**, после чего строка в истории превращается в безобидный мусор.

Отсюда порядок действий, если секрет всё-таки уехал:

1. **Отозвать** (VK: Управление → Настройки → Работа с API → удалить ключ. Telegram:
   `/revoke` у @BotFather. GitHub: Settings → Developer settings → Revoke).
2. Выпустить новый, положить в `.env`.
3. Только потом чистить файлы и, при желании, историю.

Обратный порядок бессмысленен: пока токен жив, он жив везде, где успел оказаться.

## Хук

`.githooks/pre-commit` — Python-скрипт, лежит **в репе** (то есть версионируется и едет
вместе с ней, в отличие от `.git/hooks/`, который локален и теряется при клоне).

Включается одной командой на репу:

```bash
git config core.hooksPath .githooks
chmod +x .githooks/pre-commit
```

Проверяет три вещи в том, что уже попало в индекс:

| Что | Почему |
|---|---|
| **Секреты** | VK / Telegram / OpenAI / GitHub / Slack / AWS-токены, приватные ключи, присвоения вида `password = "..."` |
| **Вес** | Картинка >0.5 МБ, PDF >5 МБ, любой файл >10 МБ. Git хранит **каждую версию** бинарника вечно — репа толстеет необратимо |
| **Форматы** | `.zip`, `.docx`, `.pptx`, `.rar`, бинарники сборки — по `06-volume-compression.md` им в репе не место |

Осознанно обойти: `git commit --no-verify`. Это нормально — хук страхует от невнимательности,
а не спорит с решением.

## Почему не просто `grep -E "token"`

Первая версия так и делала — и в отчёт попали все конспекты, где слово «token» встречается
в тексте. Сигнал утонул в шуме, а хук, который кричит на каждый коммит, ровно через три дня
начинают обходить по привычке.

Поэтому ищется не слово, а **присвоение значения**: `token = 'реальная_строка'`. И
отдельно — плейсхолдеры и чтение из окружения (`os.getenv`, `${VAR}`, `xxx`, `your_key`,
`.env.example`) в срабатывания не идут, потому что это как раз то, к чему мы стремимся.

Правило простое: **хук должен молчать, когда всё хорошо.** Иначе он бесполезен.

## Как правильно хранить секреты

```python
import os
from dotenv import load_dotenv

load_dotenv()

TOKEN = os.getenv("VK_TOKEN")
if not TOKEN:
    raise RuntimeError("нет VK_TOKEN — заполни .env по образцу .env.example")
```

Рядом с кодом:

- `.env` — реальные значения, **в `.gitignore`**;
- `.env.example` — те же ключи с болванками вместо значений, **коммитится**. По нему
  понятно, что вообще нужно для запуска.

Для конфигов, которые не Python (Alertmanager, Prometheus, nginx), — почти всегда есть
`*_file`-вариант: секрет лежит в отдельном файле, файл в `.gitignore`, конфиг ссылается на
путь. Например `bot_token_file: /etc/alertmanager/telegram_token`.

## Регулярная проверка

Хук ловит новое. Старое ловит аудитор — `repo_audit.py` из
[`edu-base/02-analytics/tools`](https://github.com/vevdokimovm/edu-base):

```bash
python repo_audit.py ~/repos/<репа>
```

Он же считает размер по трём порогам, находит дубли по хэшу, тяжёлые файлы и битые ссылки в
`.md`. Прогонять при ревизии (`21-revision-protocol.md`) и перед публикацией зеркала.
